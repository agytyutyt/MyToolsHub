### 实测样本长什么样（后续碰到同类文件可直接对照）

`demoData_real.xlsx` 37,768 B → 清理后 25,424 B，被删的就是那张背景图：

### 关键实现结论（踩过/验证过的）

- **不能用 openpyxl 做这件事**：实测 `load_workbook` + `save` 会**静默丢掉**背景图（这也是现状产物里
  看不到背景图的原因），但它同时会重写整个包——样式/宏/透视表全变样。背景清理必须走 **zip 级字节手术**：
  只改命中的三个部件，其余部件 `writestr` 原样搬运（保时间戳、压缩方式、包注释）。
- **`_clone_info` 千万别复制 `flag_bits`**：源包若带 data descriptor 标志位（bit 3），而写出时不写
  descriptor，沿用该标志会产出**损坏的 zip**（读取方按错长度一路读下去）。名字编码不受影响——
  `ZipInfo._encodeFilenameFlags()` 会自己给非 ASCII 名字补 UTF-8 标志。
- **删除图片本体前必须全包扫 `.rels` 反查引用**：同一张 `xl/media/imageX.png` 可能既被背景引用、
  又被 `xl/drawings/_rels/*.rels` 引用（浮动 logo）。只解除背景引用、保留本体，才不会误删用户内容。
  被删部件在 `[Content_Types].xml` 里的 `Override` 也要一起清（`Default` 按扩展名无需处理）。
- **`.xls` 不做检测是有依据的**（不是偷懒）：LibreOffice 把带背景的 xlsx 转成 xls 后，Escher 里
  **连 blip（图片数据）都没有**（`msofbtDgg` 记 0 drawing、Dg 里只有一个空 SpContainer），
  说明旧格式的背景图存储形态本身就随实现而异、无稳定判据；加上两个插件的 .xls 路径都是
  "xlrd 读成二维表 → 重新生成 xlsx"，产物天然不含背景图。如实说明比硬猜好。
- **失败姿态 = fail-open**：畸形包 / 加密 zip（`flag_bits & 0x1`）/ 解压超 256MB（防 zip 炸弹）/
  任何解析异常 → **原字节返回 + 照原样继续流程**，原因写进报告 `note`。背景清理是增值步骤，
  不该让一个畸形文件把业务链路卡死。
- **`report["bytes"]` 要按"实际删除的图片本体"统计**：最初按引用次数累加，两张表共用一张图时会翻倍。

### 出包时的环境坑（值得记住）

- 仓库里**有并发会话在写**（`demo/`、`.bench_corpus/`、根目录两份《压缩算法评估》md）→ 出包脚本的
  `dirty` 判定是 `git status --porcelain` **全仓库**计数，这些未跟踪文件会把戳记成 `dirty=true`。
  处置：`.bench_corpus/` 由 .gitignore 忽略（上一会话已加）；`demo/` 与那几份 md 用
  **`.git/info/exclude` 临时排除**（本地、不入库、出包后删掉那段）；上一会话遗留的 memory 日志与
  `.gitignore` 改动如实补了个 chore 提交。**两次出包之间要先提交 `tools/plugin-packages.json`**，
  否则第二个包的 dirty 判定会看到第一个包写的登记。
- 教训：**别对共享工作区用 `git stash -u`**。本次为拿干净戳 stash 了并发会话正在写的 `demo/` 文件，
  它随后又重建了一部分（encoder/layout/phone_sim），我只能按"缺失的补回、已重建的不覆盖"收尾。
  以后再遇到"要干净工作区"，优先用 `.git/info/exclude`/`assume-unchanged` 这类**不改动文件**的手段。
