用户需求：**在开始文档处理流程前加入"删除背景图片"环节，识别该文档是否嵌入了背景图片，是则删除**；

### 实测样本长什么样（后续碰到同类文件可直接对照）

`demoData_real.xlsx` 37,768 B → 清理后 25,424 B，被删的就是那张背景图：

- `xl/worksheets/sheet1.xml` 末尾 `<picture r:id="rId1"/>`（在 `headerFooter` 之后，属 CT_Worksheet 序列末段）
- `xl/worksheets/_rels/sheet1.xml.rels`：`rId1 → ../media/image1.png`
- `xl/media/image1.png` 7,417 B
- 包里**没有** `xl/drawings/`，所以"只有 `<picture>` 没有 drawing"就是纯背景图的特征

### 关键实现结论（踩过/验证过的）

- **不能用 openpyxl 做这件事**：实测 `load_workbook` + `save` 会**静默丢掉**背景图（这也是现状产物里
  看不到背景图的原因），但它同时会重写整个包——样式/宏/透视表全变样。背景清理必须走 **zip 级字节手术**：
  只改命中的三个部件，其余部件 `writestr` 原样搬运（保时间戳、压缩方式、包注释）。
- **`_clone_info` 千万别复制 `flag_bits`**：源包若带 data descriptor 标志位（bit 3），而写出时不写
  descriptor，沿用该标志会产出**损坏的 zip**（读取方按错长度一路读下去）。名字编码不受影响——
  `ZipInfo._encodeFilenameFlags()` 会自己给非 ASCII 名字补 UTF-8 标志。
- **删除图片本体前必须全包扫 `.rels` 反查引用**：同一张 `xl/media/imageX.png` 可能既被背景引用、
  又被 `xl/drawings/_rels/*.rels` 引用（浮动 logo）。只解除背景引用、保留本体，才不会误删用户内容。
  被删部件在 `[Content_Types].xml` 里的 `Override` 也要一起清（`Default` 按扩展名无需处理）。
- **`.xls` 不做检测是有依据的**（不是偷懒）：LibreOffice 把带背景的 xlsx 转成 xls 后，Escher 里
  **连 blip（图片数据）都没有**（`msofbtDgg` 记 0 drawing、Dg 里只有一个空 SpContainer），
  说明旧格式的背景图存储形态本身就随实现而异、无稳定判据；加上两个插件的 .xls 路径都是
  "xlrd 读成二维表 → 重新生成 xlsx"，产物天然不含背景图。如实说明比硬猜好。
- **失败姿态 = fail-open**：畸形包 / 加密 zip（`flag_bits & 0x1`）/ 解压超 256MB（防 zip 炸弹）/
  任何解析异常 → **原字节返回 + 照原样继续流程**，原因写进报告 `note`。背景清理是增值步骤，
  不该让一个畸形文件把业务链路卡死。
- **`report["bytes"]` 要按"实际删除的图片本体"统计**：最初按引用次数累加，两张表共用一张图时会翻倍。

## 优化方案吸收《压缩算法评估（DS）》（v1.2 修订）

`docs/信息传输格式开销评估与优化方案.md` 至 v1.2。三处修正/加深：

1. **视频双重 base64**（原报告漏算一层）：`build_envelope` 的 JSON（fmt=file 时 data 已 base64）→
   `encode_to_video` → `_qrformat_encode` 对每块再 base64 = 1.78×，叠加 FEC = 2.96×，
   每码净载荷仅 990 B（最优 2940 B 的 34%）。修法 = 协议 v2 二进制直载（JZ2 前缀 + rawBytes/binaryData，
   静态 −26%/视频 −45%）；**Base45 降级为备选**（修不了双重 base64）。
2. **已压缩容器直压无收益 ≠ 无路可走**：拆包重组（解包→条目名+内容拼流→LZMA2）docx −75%/xlsx −49%/zip −27%，
   rebuild 模式（字节不一致但打开等价），APP 用系统 ZipOutputStream 重建零依赖。
3. **两个新风险**：信封无 CRC32（HANDOFF:618）+"能解出≠读对"（cv2 回读对高熵满容量载荷 3/3 失败+截断）→
   S2（fmt=file 试压）落地后载荷变高熵，**生成端自检须升级逐字节比对 + 每码载荷 ≤85–90% 容量**。

其它合入：压缩器 zlib→LZMA2（B 端内置 lzma / A 端 org.tukaani:xz 1.10 纯 Java 168.6KB 0BSD，16MB 字典；
长重复文本最高 −86%，docx 精简正文 45 页→7 码）；多码 px/模块 ≥3 底线（4 留余量）且指"拍摄后图像"像素、
2×3 最优；实时流多码前置=先提分析分辨率。落地顺序改为 5 批：1 桌面端 zlib 试压+白名单 → 2 配置层+静态多码
→ 3 协议 v2（二进制直载+CRC32+mode+k-of-m 接线）→ 4 LZMA2+拆包重组+pdf/ppt 精简提取 → 5 扩展格式。
