## 信息传输插件深度分析 → docs/信息传输优化方案0917.md

代码走查 + 实测（脚本 `.workbuddy/tmp/it_diag.py`、`it_diag2.py`），定位 **22 项缺陷**
（🔴5 / 🟠10 / 🟡7），给出 4 批次 18 项方案（T16–T33，接续既有 TODO 批次号）。
**重点：这是增量分析，T01–T12 已落地项不重复。**

实测确认的关键事实（后续谈优化直接引用，别再重测）：

- **P1（收益最大）`qr.make()` 自动选 mask = 154ms，显式 `mask_pattern` = 34ms（4.4×）**。
  根因：qrcode 的 `best_mask_pattern()` 对每帧跑满 8 次 makeImpl，而每帧数据都不同。
  传 `mask_pattern` 即跳过（`best_mask_pattern()` 首行 `if self.mask_pattern is not None: return`）。
- **P2 逐帧 zxing 回读自检 90ms/帧（占 32%）**，可抽样到 ~9ms。
- 单帧账（v25/1100B）：make154 + zxing90 + PNG17 + imdecode13 + cvtColor8 ≈ **282ms**；
  T20(固定mask+矩阵直出)+T21(抽样) → **≈47ms，6.0×**；1000 帧 282s → 47s。
- **R2 v1 路径无完整性校验 → 静默产出错误数据**：60KB/237帧(k=142,m=237)注入单帧污染，
  `reassemble_qrtransfer` 不报错且结果 ≠ 原始；同条件 v2 靠 CRC 判坏帧→按缺失→FEC 恢复成功。
  影响面含 `PROTOCOL_V2=False` 降级、存量旧码、**trajectory-convert 等外部插件 v1 流**。
- **R1 静态多页零冗余**（= 既有 T14）：7 页丢任意 1 页全废。p=0.99 时 100 页成功率仅 36.6%、
  200 页 13.4%。与视频 67% 冗余形成断层，无中间档。
- **R4 v1 静态分页缺 PAYLOAD_SAFETY**：`_single_capacity` 只减 16B → 用到理论容量 94–99%，
  而视频/v2 路径是 62–78%。当前被 `PROTOCOL_V2=True` 掩盖，降级即复现。
- **S1 ZIP 解压炸弹（可外部利用，最严重安全项）**：`/decode` zip 分支无条目数/解压总量/
  压缩比限制。实测 0.99MB zip → 1000MB 解压（1008×），峰值内存 ~1GB，在 20MB 上传限制内。
  注意 `_zip_pack_stream`(L980) 有 `len(infos)>0xFFFF` 检查——**封装路径做了、解析路径漏了**。
  修法要点：用 `info.file_size`（central directory 里的解压后大小）**在读取前**拦截。
- **E1 前端帧全量预载（必现级）**：`index.html:1126 startJobStream` 一次性 new Image() 载全部帧。
  v15 2.3MB/帧 → 1000 帧 2.21GB；v25 5.10GB；v40 11.67GB。改滑动窗口（窗口5）→ ~26MB。
- **R3 生成端静默降级**：`_render_verified_qr` 8 个 mask 全验证失败仍落盘返回成功（mock 解码器
  全 False 实锤）。且 zxing/cv2 缺失时 `_zxing_can_decode` 直接 `return True` 跳过验证。
- **P5 PPT 逐字节滑描**：20MB 外推 ~15s 纯 CPU（`while i+8<=n: ... else: i+=1`）。
- **P4 xz(9|EXTREME) 是 zlib 的 6× 耗时**但多省 85–90%；`_compress_best` 无条件双跑，
  rebuild 路径跑 4 次。
- 已验证**无 bug** 的项（别再当问题报）：`_fec_plan` 扫描 206 个 size，`1≤k≤m≤256` 恒成立，
  实际冗余稳定 67–70%。

排期建议：**P0 = T26(ZIP炸弹) + T31(前端内存)**，均为独立小改动、可最先合入；
P1 = T17/T18/T19（纯后端可靠性）+ T16(=T14，需两端同步) + T20/T21（性能收益最大）。
未改 T13(png/jpg)、T15(packJPG/喷泉码) 的优先级判断，维持观察项。

## 每码设置口径定稿：秒 → 重复帧数（commit 4c3f9db，回归 49/49 + 45/45）

- 背景：真机验证 2b 素材（frame_repeat=1，0.067s/码）也能读 → 用户改需求，
  把上一轮的 display（秒，0.2-2）口径换成 **frame_repeat（帧，3-30）**，更贴近底层。
- `/encode` 参数 `display` → `frame_repeat`（int，默认 CAMERA_FRAME_REPEAT=5）；
  实际显示秒数 = repeat/15 由后端换算并回显 `display` 字段（前端轮播仍吃秒数，
  命名未改）；REPEAT_MIN=3（0.2s 下限依据不变）/ REPEAT_MAX=30（2s）。
- 默认 5 帧 = 旧行为，缺省零变化；estimate_output 本就按 repeat 折算无需改。
- 前端输入框整数 step=1（3-30，默认 5），提交 frame_repeat；
  frameMsOf(job) 按结果 display 秒 ×1000 动态步进，回退 333ms。
- 经验：回归日志里 OpenH264/pypdf 噪声是 stderr 先落盘、测试 stdout 缓冲到
  进程退出才出现——别把"日志只有噪声"误判为失败，等结论行（`通过 ===`/`PASS=`）。
