## LibreOffice 核心组件安装报「自检失败」—— 定位、加固、复验

### 现象与首轮判断
用户报目标机安装 LibreOffice 核心组件失败，提示「自检失败」。
旧脚本（`aea8894` 那版）在自检不过时只打印 `[失败] 自检未通过：未产出 xlsx（退出码 N）`，
**不打印 soffice 自己的输出** —— 等于把唯一的线索丢掉了，远程无法定位。

### 本机对照复现（结论：脚本逻辑本身没问题）
- 模拟目标机跑旧流程：rc=0，解压 12.7s，自检通过，marker 写入 → **本机能过**，故障在环境侧。
- 排除「中文 / 非 ASCII 路径」假设：写 `build/lo-sim/test_paths.py` 做三变体对照
  （A 纯 ASCII + 原始 URI ｜ B 中文路径 + 原始 URI ｜ C 中文路径 + 百分号编码 URI）→ **三个全过**。
  LibreOffice 26.8 能处理原始 UTF-8 的 file URI，**不需要**改 URI 编码。
- 查核心包：`presets` 13 条完整；VC 运行时随包（`System64/vcruntime140*.dll`、`msvcp140*.dll`）
  → 排除「缺 presets」「缺 VC++ 运行库」这两个静态假设。

### 关键测量（`build/lo-sim/test_timing.py`，连做 4 次全新 profile）
- 稳态 **18~22 秒**；刚解压 + 杀软仍在扫描时 **27~72 秒**（PowerShell 路径实测 72.1s）。
- 唯一临时 profile ⇒ **每次**转换都要重新初始化 profile，这是"稳态也要 20s"的原因。
- ⇒ 旧自检超时 180s 在慢机器上会被击穿 →「自检失败」的一大来源。

### 故障注入验证（本轮最高价值的一条）
删掉 `presets\` 制造残缺树后重跑：
`退出码=77` + `stderr: LibreOffice 26.8 - Fatal Error: 无法启动应用程序。安装无法完成。`，
**失败那一次耗时 173.7 秒** —— 离旧超时 180s 只差 6.3 秒。
→ 新脚本据此自动重解压并复检，**22.0 秒通过**（自愈生效）。

## 真机日志到手：根因锁定为 VC++ 运行时不在 `program\`（10:00–10:10，提交 `5c3be43`）

用户回传真机日志（Win10 Pro 19045，非开发机），**决定性数据**：

```
[自检] 退出码=-1073741502  耗时=1.3s  产物=（无）  profile已初始化=False
```

`-1073741502` = **`0xC0000142` = STATUS_DLL_INIT_FAILED**。配合"1.3 秒退出 + stdout/stderr
全空 + profile 目录都没建"，结论明确：**进程死在 DLL 加载阶段，还没跑到 LibreOffice 的代码**。
（解压 7.5s、2824 条目齐全、磁盘余 217GB，前置条件都没问题。）

### 根因
官方 MSI 用 `msiexec /a` 管理安装解包时，本该**装进 System32** 的「VC++ 2015-2022 运行库」
只能落在解包树的 **`System64\` 子目录**；而 soffice.bin 的 DLL 搜索顺序是
「**进程主目录（`program\`）→ System32 → …**」，`program\` 里完全没有这套 DLL
（实测 program/ 下 153 个 DLL，无一命中 vcruntime/msvcp/concrt）。
- 目标机**已装** VC 运行库 → System32 兜底 → 能用（**开发机就是这种**）；
- 目标机**没装或版本不匹配** → 加载阶段即死 → `0xC0000142`。

⚠ **这解释了为什么之前所有"实测通过"都是假阳性**：开发机装了完整版 LibreOffice，
System32 里有这套库；组件从来**没有在干净机器上验证过**（HANDOFF 未实测项之一）。

### 本机对照实验（`build/lo-fix/exp.py`，已随测试树删除）
| 实验 | 结果 |
| --- | --- |
| 本机 System32 | **有** vcruntime140/140_1/msvcp140/msvcp140_2/concrt140 → 差异来源 |
| A 现状（VC 只在 `System64\`） | PASS 41.7s（靠 System32 兜底） |
| B 把**垃圾字节**写成 `program\vcruntime140.dll` | **FAIL `0xC000012F`，0.1s，零输出，profile 未建** —— 与真机**同族签名**；并证明 `program\` **优先于** System32 |
| C 把 `System64\` 的 10 个 DLL 补进 `program\` | **PASS 26.4s** |

### 修复（`5c3be43`）
- 安装器新增 `Repair-VcRuntime` / `Step-RepairVcRuntime`：**自检之前**自动把 `System64\` 的
  10 个 DLL 补齐到 `program\`，日志写 `[补齐]` 一行；幂等、免管理员、不动系统目录；
  自愈重解压后重新补齐；`-VerifyOnly` 保持"不改动任何文件"（只检查 + 提示去掉该开关重跑）。
- 失败分类表补齐 NTSTATUS 退出码：`0xC0000142` / `0xC0000135` / `0xC000007B` / `0xC000012F` /
  `0xC0000005`（原表只有 `0xC0000135`，真机这次遇到的码落到了"泛泛建议"分支）。
- `build-libreoffice-core.py`：`System64` 加入 `MUST_KEEP`（是这套修复的**唯一来源**）。
- `build-offline-component.ps1`：使用说明新增 `0xC0000142` 排障条目。

**端到端复验**：清空 `program\` 的 10 个 DLL（模拟真机）→ 重跑安装器 →
`[补齐] … 10 个` → **自检 19.5s 通过**。组件包已重建（162.8 MB，包内 ps1 与源逐字节一致，
sha256 `9f5bef86416db414`）。`build/lo-fix` 测试树已清（559.7 MB）。

### 本次的经验教训
**"在开发机上通过"不等于"在目标机上通过"** —— 当被测组件依赖系统级运行时（VC++ 运行库、
字体、UCRT）时，开发机往往因为装了完整版软件而"意外满足"依赖，产生系统性假阳性。
凡涉及"离线组件 / 免安装 / 便携"的场景，验收必须在**干净机器**上做。

### 待办

- 另需验证：目标机是否本来就装过**旧版** VC++ 运行库（若装了，更能确认是"版本不匹配"

## 信息传输：xlsx 精简提取只读出首格 —— 根因是 `<dimension>` 失真（10:50–11:10）

用户报 `660.xlsx` 在**精简传输**路径只提取了第一行第一列。根因不在我们的代码逻辑，
而在 openpyxl 只读模式的取数口径。

### 根因
`660.xlsx` 的 `xl/worksheets/sheet1.xml` 声明 `<dimension ref="A1"/>`，
但实际有 **A1:A4 四行**（工具写出的失真声明；Excel 本身容忍，因为该元素只是"提示"）。
`openpyxl.load_workbook(read_only=True)` **依赖该声明确定遍历范围** → `max_row=1` → 只读出 A1。
实测复现：`dimension='A1:A1' → 读出 1 行 ['近十五天凌晨所在位置']`。

### 修复（`_extract_xlsx_rows`，`routes.py`）
1. `ws.reset_dimensions()`（openpyxl ≥3.0.4，`hasattr` 守卫）清掉声明，改按 `sheetData` 实际扫描；
2. **必须配套"补齐行宽"**：清掉声明后 openpyxl 不再按声明宽度补齐稀疏行（行变"参差"，
   如 `['onlyA']` 而非 `['onlyA', None, None]`），故统一补到最大列宽，保持二维数组矩形契约。
   —— 只做第 1 步会**引入回归**（实测：稀疏行样例与"普通模式基准"不一致），两步必须成对。

### 验证（全部实测通过）
- 边界样例 5 类（声明过小/过大/缺失/稀疏/稀疏+正确声明）**全部与普通模式基准逐字节一致**；
- **回归用例已固化**：`test_protocol_v2.py` 新增第 9 节（14 个断言，含真实 660.xlsx 存在时校验），

## 知识库 Word 预览三缺陷：定位 + 实施修复（17:00–17:30）

用户反馈 Word 预览三处显示问题：「仿宋GB2312 笔画竖过细」「部分文字加粗（原文未加粗）」
「单元格文字穿模」。前一日（09-12）已完成排查定位，今日**按方案实施修复**。

### 根因（复现实验证实，非推测）
- `vendor/dhr/renderer/css.py:14` 的 CJK fallback 链：`目标字体 → Times New Roman → Microsoft YaHei`。
- 本机（及多数未装公文字体的客户端）**没有 仿宋_GB2312** → 直接落到 `Microsoft YaHei`（黑体）。
  Canvas 像素签名实测墨量：**雅黑 138131 vs 仿宋 53860，差 2.56 倍** → 中文整段变黑体，
  肉眼即「原文没加粗却显示加粗」；数字/英文走 TNR（细）又造成同行粗细不均。
  （复现：`kb_fs_sample.docx` + `set viewport` + Canvas `getImageData` alpha 求和。）
- `vendor/dhr/renderer/__init__.py:374-380` 的 `_row_html()` 给 `<tr>` 写了
  `height:Npx;overflow:hidden` —— **`overflow` 对 `display:table-row` 无效**，精确行高失效；
  且 base CSS 未重置 `<p>` 默认 margin（浏览器 `1em 0`）进一步撑高单元格。
  实测：设定 27px 行高 → 实际渲染 49/67/49px。

### 决策：后端 HTML 后处理，vendor 零改动（B-7）
三处缺陷全在 vendor 输出层，但按「vendor 零改动拷贝」约定不在 vendor 内打补丁（升级要重打、
易漏）。改为在 `office_render.render_word()` 出口做后处理 `_polish_word_html()`，与既有 5 条
vendor 补丁互不影响。

### 实施
- `office_render.py` 新增 `_polish_word_html()` 三步：
  - `_patch_font_fallback()`：在目标字体与 `Microsoft YaHei` 之间插
    `"FangSong","仿宋","SimSun"`；覆盖 6 种 GB2312 写法 + 裸 `仿宋`。
  - `_patch_table_overflow()`：清 `<tr>` 上无效的 `overflow:hidden`（保留 `height`）。
  - `_patch_css()`：追加 `.kbdoc p{margin:0}`、`td/th{word-break:break-all;overflow-wrap:anywhere}`、
    `td>p:only-child{overflow:hidden}`，带标记 `/*kbdoc-patch*/`。
- `routes.py`：`PREVIEW_CACHE_VERSION` **3 → 4**。**这是让修复真正生效的关键**——目标机上
  历史文档已有 v3 缓存，不递增版本它们会继续返回未修补的 HTML。
- `test_routes_preview.py` 第 0b 节：新增 6 项补丁回归断言。
- **前端无需改动**（补丁在服务端完成，前端拿到的是已修补 HTML），资源版本号不递增。

### 关键踩坑（勿重犯）
1. **裸 `"仿宋"` 不能放进 `_FANGSONG_NAMES`**：它**既是查找键又是插入值**，二次处理会
   自我匹配 → 重复注入（实测第二遍链变成 `"仿宋","FangSong","仿宋","FangSong"...`），

3. **`<tr>` 清理必须限定在标签内部**：用 `<tr\b[^>]*>` 全标签正则。先前用

4. **验证断言口径**（假阴性陷阱）：`font-family:` 声明串**本身含双引号**，用 `[^;}"]+`

   别用 `<tr\b`（会命中 CSS 里的选择器文本）。
5. **对照"引擎原产物"须直调 `dhr.convert()`**：`render_word()` 的返回已经过补丁，
   拿它做前后对照看不出差异。

## 知识库「异步下载源」开关点不动 —— 修复（18:25–18:55，阶段 11）

### 现象与根因（真机复现）
用户报「开关按钮无效」。用 `elementFromPoint` 命中测试复现：
```
元素命中(滑块中心) = <SPAN.slider>
=> 是否命中 <label>? false
点 .slider 后 checked: false -> false     ← 点那个"按钮"，纹丝不动
点左侧文字 后 checked: false -> true       ← 只有点文字才有效
```
**根因不是 CSS 写坏，是标记结构选错**：`.slider` 是 `position:absolute;inset:0` 的
覆盖层——视觉上它就是用户要点的"按钮"，但它盖住了隐藏 `<input>`，而它自己既不是
`<label>` 也不转发点击；唯一能激活 checkbox 的是左侧文字上的 `<label for="m-dl-switch">`。
**自定义开关必须让 `<label>` 直接包住 `<input>`**，不能靠 `for=` 指向被覆盖层遮住的 input。

### 修法
- `app.js`：整行改 `<label class="form-row switch-row">` 直接包住 input + `.slider`。
- `style.css`：`.switch-row` 加 `cursor:pointer` + hover 反馈；`.switch` 不再需要 label 语义。
- 版本 `style.css?v=29→30`、`app.js?v=19→20`。

### 验证（关键：真实指针点击，不是程序化 .click()）
起隔离实例（伪造 `jztools_admin.routes.get_session_user` 返管理员，否则插件 API 全 401）：

| 动作 | `checked` | `#m-dl-row` | slider 背景 |
| --- | --- | --- | --- |
| 初始 | false | `form-row hidden` | — |
| 点 `.switch .slider` | **true** | `form-row` | `rgb(92,107,192)` accent |
| 再点 | false | `form-row hidden` | `rgb(207,212,220)` |
| 点文字 label | true | `form-row` | accent |

提交链 FormData 含 `file=Demo.pdf` + `download_file=Demo.doc`。
全量回归 `test_routes_preview.py` **EXIT=0**，含新增第 6 节静态契约断言。

### 关键踩坑（已写进 HANDOFF §7.3-20/21）
1. **首次实现只做了程序化自测**：`slider.dispatchEvent(new MouseEvent('click'))` 与
   `el.click()` 在修复前也"看起来能过"，**只有真实指针点击才暴露"点滑块无效"**。
   → 浏览器验证一律用 agent-browser 的 `click` 命令，不要只用 eval 里的 `.click()`。
2. **agent-browser 会话不跨命令**：任何非浏览器命令（如 `echo`）或跨 `;` 的独立调用
   都会重置页面（元素变 null）。必须把 `open → click → eval → screenshot` 放在**同一次
   `&&` 链**内。
3. 隔离实例做 E2E 必须伪造 `get_session_user`，否则静态资源全 200 但页面被重定向到
   登录页（`/login?next=...` → 404），表现为"资源都正常但页面是 404/登录页"。
