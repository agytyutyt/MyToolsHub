# 2026-09-15 工作日志

## 插件热插拔评估 v2.1：W0 打包探测（实测通过）

承接 9-14 的 `docs/插件热插拔-容器化改造评估.md`。评估里列了三个"不先定就必返工"
的决策点，其中 **D1（sidecar 的 Python 依赖从哪来 = 能否产一个共享 `_internal` 的
独立 exe）是整条 sidecar 路线的唯一技术前提**。本次把它做实了，11/11 断言全绿。

### 做了什么

在临时目录（未入库，污染零）搭了一个最小双入口实验，写法刻意对齐 `JZToolsHub.spec`：

- `probe.spec`：两个 `Analysis` → 两个 `EXE` → **同一个 `COLLECT`**
- `probe_host.py`（宿主）+ `probe_sidecar.py`（sidecar）+ `probe_common.py`（模拟未来的
  `jz_plugin_sdk`）+ `probe_single.spec`（单入口对照组，用来量增量）
- 依赖只用 `collect_all("cryptography")`（abi3 C 扩展，代表本项目最典型依赖类型）
- 契约：sidecar 起随机端口 HTTP → stdout 打 `JZRT|1|<port>` → 校验 `X-JZ-Token`

### 实测结论（数字都写进评估文档附录 A 了）

- **共享 `_internal` 成立**：两个 exe 的 `sys._MEIPASS` 完全相同，`_internal` 只有一份
- **入口增量 3.00 MB / +9.7%（一次性）**：31.04 MB → 34.04 MB，而 `_internal` 一点没变大
  （28.13 MB 共用），新增的就是第二个 exe 本身（2.99 MB = bootloader + 它自己的 PYZ）
- **冷启动 431 ms**（stdlib + cryptography；真实 sidecar 要 import Flask，粗估 0.6~2 s）
- `CREATE_NO_WINDOW` + `stdout=PIPE` **可读握手行**（Windows 上最容易翻车的一处，实测没翻）
- Token 校验生效：无 Token → 401（回环端口的信任边界只能靠它）

### 两条修正（推翻了评估草稿里的表述）

1. **包体成本是一次性的，不是按插件线性增长**。因为做"一个通用 sidecar 入口"（由
   `runtime.json` 决定加载哪个插件），不是每插件一个 exe → 11 个插件也只要这一个入口。
2. **不需要改 `build-deploy.ps1`**：第 132 行 `Copy-Item -Recurse (Join-Path $Dist
   "JZToolsHub\*") $AppDir` 是整目录搬运，新 exe 自动带上 → W6 的一部分工作量归零。

### 顺带确认的

`hashicorp/go-plugin` 的 `MagicCookie` 只防"被双击执行"，不防攻击；本项目必须把它
升格为真实凭据（一次性随机 Token 经环境变量注入，**不走命令行**，避免
`wmic process list` 泄密）。

### 踩坑（探针设计错误，与打包机制无关，但值得记）

连续两次写出"天然不可能相等"的跨进程指纹断言：
① 用 `Fernet.generate_key()` → 密钥随机；
② 改成固定密钥后又去摘要 **Fernet token** → token 内含时间戳 + 随机 IV，照样不等。
**跨进程一致性指纹必须对随机源免疫**：只取确定性输出（这里是 `sha256(PBKDF2(...))`），
加解密往返另作可用性断言，不要混进指纹。

### 剩余

D2（任务表外置，否则空闲回收/停止插件会丢用户长任务）与 D3（握手 Token 落地）
仍是硬前置；R1（打包风险）已消解，原定的"同一 exe 加 `--jz-sidecar` 参数"回退方案
不需要了。主体（W1~W7，约 24~33 人日）尚未开始，等立项决策。

## 第十一轮：插件包校验失败不再只报「HTTP 400」（admin 1.3.1）

### 现象
目标机上传 `JZToolsHub-插件-admin-v1.3.0.zip` → 页面只显示「校验未通过：HTTP 400」，
看不到任何原因，现场无法自助处理。

### 根因（两个）
1. **前端吞错误**：`admin-common.js` 的 `api()` 抛错只取 `data.error`，而插件包校验失败
   的响应体是 `{ok:false, errors:[...]}`，没有 `error` 字段 → 退化成 `HTTP 400`。
2. 真实被拒原因（沙箱复现可枚举）：
   - 同版本重装（目标机已是该版本，多半是**前一次其实应用成功了**又传了一次）
   - 主程序版本过低 / 程序目录缺 `version.json`（我本地仓库就是后者，所以本地一直复现 400）
   - 包在传递中损坏 → 哈希不符

沙箱复现结论：**标准目标机（admin 1.2.0 + 主程序 1.9.0）下 1.3.0 包校验是通过的**，
所以问题在环境差异，不在包本身。

### 修复（commit 5a1771f）
- 后端：`upload` / `apply` 的 400 响应**同时给 `error` 摘要**（`"；".join(errors)`）。
- 前端：`api()` 兜底拼 `errors[]`，并给 error 对象挂 `err.errors`；插件管理页新增
  `errListHtml()` / `rejectHint()`：逐条列原因 + 按类型给下一步
  （勾「强制」/ 先升主包 / 检查部署目录 / 重拷原包别解压重压）。
- 前端资源戳：admin-common.js v5(v2)→v6、admin-plugins.js v2→v3（7 个入口页同步）。
- 测试：断言 400 响应必须带 `error` 摘要，防再次退化。

### 验证
- 两套 Python 测试全绿；浏览器实测：再传同版本小包 →
  显示「• 同版本重装：包与已装版本都是 1.0.0（确需重装请勾选「强制」）」+ 处置建议。
- 新包 1.3.1 在目标机 admin=1.2.0 / 1.3.0 两种状态下**均校验通过**（1.3.1 自身才拒同版本）。

### 产物
`deploy/插件包/JZToolsHub-插件-admin-v1.3.1.zip`（0.11 MB / 25 文件，
sha256 a719fd33739b9529175ae0732ee4d00d4a8970610b4beccd292c7e5b48761c74）。

### 文档同步
- README 新增 **§3.4「插件包：只升级一个插件（出包 + 目标机更新）」**：出包前置与参数、
  产物与登记、两条更新入口、**校验被拒排查表**、回滚；§12 补两条排查项；§6.6 指向 §3.4。
- HANDOFF：状态头、§2.2 插件包产物表、§10.2 快速命令、§7.3 新增踩坑 #17（api 吞 errors）。

### 本机坑（记牢）
- **沙箱 safe-delete 会拦"批量删除 >50 项"**：上传 25 文件的插件包时，服务端清理 staging
  会命中阈值 → 进程被中断，浏览器只看到 `Failed to fetch`（不是产品 bug）。
  **验证插件包请用只有 3 个文件的小包**（`test_admin_plugin_manager.make_package` 造）。
- 服务端进程崩时看日志：把输出重定向到 Windows 路径再读（`/tmp/x.log` 在 Bash 与 python 间不通）。
