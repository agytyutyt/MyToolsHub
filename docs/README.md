## 4. 文档模板（四段固定覆盖）

**每份文档必须回答这四段**——可以是本章节，也可以是指针（推荐指针，见 §6 的体量纪律）：

```markdown
| 文档属性 | 内容 |
| --- | --- |
| 状态 | 现行 / 已完成 / 已取代（被 <文件>） |
| 最后核对 | YYYY-MM-DD（对照 <代码路径>） |
| 作用域 | 单插件 / 跨插件 / 框架 / 交付 |
| 随包 | 是 / 否 |
| 覆盖范围 | 本文负责哪些事实 |
| 不覆盖 | 哪些事实在别的文档（给出指针） |
| 关联文档 | 上游/下游文档 |

## 0. 速览
| 四段 | 落点 |
| --- | --- |
| 接口契约 | 本文 §x / `plugins/<id>/README.md` / 《插件设计规范.md》§y |
| 实现路径 | 本文 §x + 代码 `path:line` |
| 当前实现状态 | 本文 §x「实施记录」/ `HANDOFF.md` §2 |
| 后续优化方向 | `docs/plan/信息传输优化TODO清单.md` Txx / 本文 §「已知限制」 |
```

四段的含义（按文档类型可变通，但不得缺项）：

- **接口契约**：对外承诺的不变量——HTTP 路径与请求/返回结构、数据结构与字段、
  交付物形态（包结构、命令、文件名）。手册类文档的"接口契约"= **命令与产物契约**。
- **实现路径**：事实落在哪个文件的哪一段，关键调用链，为什么这么切分。
- **当前实现状态**：已落地 / 未落地 / 降级行为，并注明核对日期与验证方式。
- **后续优化方向**：明确指向活清单条目或「已知限制」，不写空泛的"未来可以…"。

## 5. 命名与生命周期规范

- **命名**：`<主题>-设计文档.md`（设计契约）、`<主题>-评估.md`（一次性选型）、
  `<主题>-TODO.md`（活清单）、`<主题>-手册.md`（操作流程）。
  废弃 `todolist` 写法，统一 `TODO`。
- **状态三态**：`现行`（默认，不写横幅）/ `已完成` / `已取代`。
  后两者**必须**在正文首部加横幅，并链接现行替代文档。
- **归档触发**（满足任一即归档，动作 = 加横幅 → 移入 `docs/archive/` → 更新本索引）：
  ① 结论被其他文档吸收；② 被新版本文档取代；③ 清单全部勾完；④ 是时点审计报告。
- **最后核对日期**：改功能后回写文档时必须顺手更新该字段（口径见 `HANDOFF.md` §10.1）。

## 6. 体量纪律（控制 token 消耗）

1. **单份文档目标 ≤ 400 行**；超过时优先"拆主题 + 指针"，不要堆附录。
2. **不复制契约**：协议字段、接口清单、命令、版本基线一律引用落点，只写"本主题特有的部分"。
3. **不内嵌完整源码**：代码块只放关键片段（≤ 20 行）+ `文件:行号` 指针；
   完整实现以 `android-app/`、`plugins/` 源码为准（详见 `docs/archive/` 中审计报告的 D5 项）。
4. **不写滚动流水账**：进展写 `HANDOFF.md` §3 与 `.workbuddy/memory/` 当日日志，文档只留结论。
5. **一次只维护一处**：发现两处说同一件事，保留权威落点、另一处改指针（§3 覆盖矩阵）。

## 8. 随包口径（与打包脚本的耦合点）

| 内容 | 是否随包 | 依据 |
| --- | --- | --- |
| `docs/README.md` + `docs/guide/` + `docs/design/` | ✅ 是 | `tools/build-deploy-local.py` 的 `COPY_DIRS`/`COPY_FILES`；`build-deploy.ps1` §3.2 |

| `tools/dev/`（开发验证服务：伪造 admin 会话，绝不能上目标机） | ❌ 否 | 同上，`exclude_dirs` 的保留名 `dev` |

> 出包后 `tools/verify-package.py` 会断言"内部文档层与插件测试脚本未随包"，漏改会被拦下。
