## 0. 结论速览

1. **分类结果（17 个存量插件）**：类 A 6 个（admin、store、knowledge-base、shared-docs、notice-board、case-report）、类 B 8 个（B-light 纯前端 5：base64、color-picker、json-formatter、md5-generator、map-marker；B-heavy worker 3：info-transfer、trajectory-convert、qr-video-decode）、类 C 3 个（file-filter、trajectory-sketch、character-graph）。判定依据=逐插件取证后端的数据依赖（服务器数据权威 / jz_llm / 跨用户共享状态 / 纯本地计算），见 §1.2。
2. **四条改造模式**（§2）：M-A 服务器插件原样双包上架（A 类，零代码改动）；M-B1 纯前端本地包（B-light，零源码改动）；M-B2 worker 本地包（B-heavy，源码零改动 + manifest 变体 + 依赖组件包联动）；M-C 双包拆分（C 类，服务器工件增补少量 API 端点 + 客户端工件新写本地计算后端）。
3. **源码单一真源**（§2.1）：B 类不复制源码——本地包由出包工具从 `plugins/<id>/` **派生**（manifest 自动变体 + 构建期 API 基址改写，Q1 已拍板）；C 类服务器工件保持 `plugins/<id>/` 原位增补，客户端工件后端新写于 `client-plugins/local-<id>/`、frontend 复用服务器插件目录。红线 2（浏览器功能不减）由「服务器版一律保留」保证（**过渡期口径**——浏览器端退役为后续规划，见 §6.1）；改写可靠性由《插件设计规范》§16.10 **L-13 前端 API 路径书写纪律**（硬性，违反即出包红）保底。
4. **框架增补项**（§2.5）：F1 客户端身份注入（镜像会话 → provider + `X-JZ-User` 头，B/C 本地插件的 `_viewer()`/任务归属生效）；F2 依赖组件包补齐（qrcode/olefile 等缺项，复用 `build-dep-component.ps1`）；F3 B-heavy 长任务 `resident: true` 语义确认（内存任务表 + 轮询型前端必须常驻）；F4 本地包出包工具增强（`-From` 派生 + `--api-rewrite` 基址改写 + **L-13 静态检查**）；F5 清单降级合并（离线网格入口，Q3 配套）；F6 worker idle 回收（Q6 已拍板方向，与懒加载组合，后续批次）。
5. **实施建议**（§4）：底座已齐（批次 4/8/8b），插件侧分三批——批次 9 = F1–F5 + 三类各一试点（base64 / qr-video-decode / file-filter）；批次 10 = B 类放量 + A 类上架；批次 11 = C 类收尾 + 全量验收。**§4 为建议排期，尚未排入 TODO 清单**；后续升级优化方向已登记 TODO 清单 O3–O6（Q6 拍板 F6 idle 回收+懒加载收尾 / Q5 C 类拆分收尾 / Q7 worker 迁移排序 / Q3 浏览器端退役规划）。

## 1. 分类口径与总表

### 1.1 判定口径

三类定义（GLM 方案 §1.2，2026-10-05 需求⑨后口径）与商店 runtime 的映射（商店设计 §3.5）：

| | 类 A（runtime=server） | 类 B（runtime=local） | 类 C（客户端工件=hybrid 包 `local-<id>`，服务器工件=`<id>` API 型后端包） |
| --- | --- | --- | --- |
| UI | 中继直出（可装前端包本地直出） | 本地直出 | 本地直出 |
| 业务逻辑 | 服务器 | 本地（纯前端或 worker） | 本地简单逻辑 + 服务器复杂/敏感操作 |
| 服务器数据 | 权威在服务器 | 无 | 有，经 `jz_relay`（框架级白名单面 + `own()` 自身命名空间） |
| 离线 | 不可用 | 完全可用 | 降级可用 |

逐插件判定问题（按序问，命中即停）：

1. **插件是否承载服务器数据权威**（跨用户共享状态、按用户/部门权限范围的持久数据、全员广播内容、服务器密钥/审计）？→ 是 = 类 A。
2. **是否零服务器交互**（后端只用临时任务目录、不 import jz_llm、前端不调框架 API）？→ 是 = 类 B（有 Python 后端 = B-heavy worker；纯前端 = B-light）。
3. **其余** = 类 C：本地可承载的计算（文件解析/过滤/渲染）留在本地，需密钥（大模型）或共享状态的步骤经 `jz_relay.own()` 交服务器工件。

核心插件例外：admin、store 虽按判据落 A，但走 `CORE_PLUGINS` 白名单随主体分发（可单独升级、不可卸载、不进商店目录自卖）。

### 1.3 与 GLM 方案 §1.2「典型场景」行的出入说明

GLM §1.2 的示例行把 trajectory-sketch、file-filter、知识库列为类 A 典型——那是 2026-10-03 v3 的示意，早于需求⑨（类 C 归 server、双包模型）拍板。按现行定义：知识库仍为 A（共享文档库是数据权威），而过滤器/速写的过滤计算本地可承载、脱敏场景下本地化有实质收益（敏感表格不出机），星图解析本地可承载，三者改判 C。适配排期上允许「先 A 后 C」过渡（§4），不影响商店先开张。

## 2. 通用改造模式

### 2.1 源码布局与单一真源

| 类别 | 源码位置 | 本地工件来源 | 服务器工件来源 |
| --- | --- | --- | --- |
| A / B-light / B-heavy | `plugins/<id>/`（现状不动） | 出包工具**派生**（§2.5 F4）：manifest 自动变体 + API 基址构建期改写 | `build-plugin-package.ps1` 既有链（自动产出前端包，T-O2-9 已落地） |
| C | 服务器工件=`plugins/<id>/`（增补少量端点）；客户端工件后端=**新增 `client-plugins/local-<id>/`** | `client-plugins/local-<id>/`（backend + manifest）+ frontend 复用 `plugins/<id>/frontend/`（出包工具 `-FrontendFrom`） | `build-plugin-package.ps1` 既有链 |

- **B 类不复制源码**：服务器版与本地版共用同一份 frontend/backend。前端对 API 基址的适配由出包工具在**构建期**完成（`--api-rewrite`：把 `api/<id>` 路径字面量改写为 `/api/local/local-<id>/api/<id>`；对 `"…"`/`'…'`/反引号三种字面量生效，与 C-3 缓存戳同属构建期产物变换，非壳注入 fork，红线 3 不破）。**Q1 已拍板（2026-10-06）采用本机制**，其可靠性由《插件设计规范》§16.10 **L-13** 硬性保底：前端路径必须以「根绝对 + 连续字面量 `/api/<id>/…`」书写，动态拼接/硬编码来源/跨插件路径均为禁用模式，出包静态检查命中即红。
- **C 类**：服务器版保持完整（浏览器路径照旧 = 红线 2），增补的 API 端点对浏览器无害；客户端工件只新写后端（本地计算 + `own()` 代理），计算核心（如 `core.py`/`filter_local`）按本仓「同源副本各自演进」的既有先例（轨迹速写 `filter_local` ← 过滤器 `core.py`）落副本并在文件头登记同源出处。
- `client-plugins/` 为新增顶层目录（与 `plugins/` 平行），仅承载 C 类客户端工件源码；B 类与 A 类不产生新源码目录。

### 2.2 M-A：服务器插件原样上架（6 个）

1. 出包：`build-plugin-package.ps1` 常规出包 → 自动获得后端包 + 前端包（同版本成对，链已备）。
2. 上架：admin 商店管理面上传双工件 → 元数据（runtime=server、requires 从 manifest 提取）→ 审核 → 发布（后端包发布即部署到服务器；桌面端「安装」=装前端包）。
3. 桌面端：未安装=页面中继直出（零安装即用）；安装=前端包落 `server-frontends\<id>\` 本地直出、API 照旧中继。
4. 可选增量：按 `服务端插件运行架构-设计文档.md` 做 worker 迁移（E 架构真机项「逐插件切换」），与商店上架正交——迁移只改运行位置，不改类别与包形态。

### 2.3 M-B1：纯前端本地包（5 个）

1. 出包：`build-local-plugin-package.py -From plugins/base64 --derive-local`（F4 增强后）→ 产出 `JZClient-本地插件-local-base64-v<版本>.zip`：
   - manifest 变体自动生成：`id` 加 `local-` 前缀、`runtime: "local"`、`kind: "local"`（无 backend、无 mount）；
   - 前端原样（零 API 调用，无需改写，`--api-rewrite` 空转无害）。
2. 上架：runtime=local 条目；无依赖声明。
3. 客户端：安装落 `local-plugins\local-<id>\`，页面本地直出，离线完全可用（map-marker 的外网瓦片除外，页面明示，与浏览器一致）。

### 2.4 M-B2：worker 本地包（3 个）

1. 源码零改动（`import jz_api`/`import jz_deps`/`import jztools_data` 由客户端 kernel 垫片承接，打包布局已保证 worker 进程 sys.path 含 kernel 目录）。
2. manifest 变体（F4 派生时从服务器 manifest 转换 + 人工确认）：

```jsonc
{
  "id": "local-info-transfer",
  "runtime": "local",
  "kind": "local",                  // 规范 §16.1 口径：类 B 一律 kind=local；entry.backend 有值 ⇒ worker 子进程
  "entry": { "frontend": "index.html", "backend": "backend/routes.py" },
  // mount 不声明：走默认挂载 /api/local/local-info-transfer，能力层剥除后 worker 内即见
  // /api/info-transfer/*（后端 API_PREFIX 原样）——显式 mount 须以 /api/local/<id> 开头、
  // 仅用于额外剥子前缀，本方案不使用（规范 §16.11；capability_app.py 派发实现）
  "resident": true,                 // ★ 内存任务表 + 前端轮询型插件必须常驻（executor 既有语义）
  "timeout_ms": 600000,             // 视频/编解码长任务放宽
  "requires": { "python_packages": [ /* 原样保留：客户端对 runtime\pylibs 组件三态预检 */ ] }
}
```

3. 前端 API 基址构建期改写（F4 `--api-rewrite`）：`/api/info-transfer/…` → `/api/local/local-info-transfer/api/info-transfer/…`（能力层剥 `/api/local/<id>` 后 worker 内看到的路径与服务器一致，后端零感知）。
4. 数据落点：`.task_cache` 经 kernel `jztools_data` 垫片自动落客户端数据根（`~\.jztoolshub\`，`get_data_root_dir` 既有解析链）；任务归属经 F1 身份注入生效（未注入时垫片降级为匿名，归属校验按既有空 owner 兼容逻辑放行）。
5. **懒加载（Q6 已拍板，随适配实施）**：info-transfer/trajectory-convert 的 `import cv2` 推迟到首个视频类任务——空闲 worker 驻留为 ~30MB 轻量态；可用性旗标改由 jz_deps 判定数据源取（不再以顶层 import 成败为准）；qr-video-decode 仅 zfec 不需要。`resident: true` 首期仍必需（F6 idle 回收落地前的过渡形态，两者组合后稳态=轻量骨架常驻、重依赖只在干活窗口驻留）。
6. 依赖组件包联动：requires 逐项对应 dep-slot 条目（§3 各插件列明），上架时依赖与插件同目录可见，preflight 预检 + 联合安装（商店设计 §3.5 ①②）。
7. 出包与上架同 M-B1；**验收重点 = 离线全流程 + 长任务轮询（resident 存活/超时/崩溃回包）**。

### 2.6 M-C：双包拆分（3 个）——通用端点拆分口径

**服务器工件**（`plugins/<id>/` 增补，浏览器路径零感知）：

| 增补端点（模式） | 语义 |
| --- | --- |
| `POST /api/<id>/llm/match-columns` | 无状态 LLM 匹配：`{headers, keep_columns}` → 逐表头建议（内部走 `jz_llm`，请求线程解析会话——中继附用户会话，与浏览器权限一致）；**同时把建议落映射库/建议缓存**（单一写方仍在服务器） |
| `POST /api/<id>/mappings/lookup` | 批量查表：`{headers}` → 逐表头 `{target, status}`（confirmed/suggested/rejected/未匹配），供本地引擎免整表拉取 |
| `GET/POST /api/<id>/config`、`/mappings/*` 既有端点 | 不改——客户端工件后端对这组端点做**透明代理**（经 `own()`），前端管理界面零改动 |

**客户端工件**（`client-plugins/local-<id>/`，kind=hybrid 进程内注册；id=`local-<id>`，本地端点挂 `/api/local/local-<id>`）：

- `backend/`：本地计算段（引擎副本）+ 代理段（config/mappings 管理端点经 `jz_relay.own("local-<id>")` 转发）+ 计算中的服务器步骤（LLM 建议/查表）改调 `own()`；
- `frontend/`：复用 `plugins/<id>/frontend/`，构建期基址改写（F4）；
- manifest：`kind: "hybrid"`、`entry.mount: "/api/local/local-<id>"`（§16.1 类 C 必填）、`server_data: true`（安装时数据出机明示——红线 5 既有口径）、requires 仅声明**本地段**依赖；
- 离线降级：本地计算段照常（过滤 hard/精确模式、文档解析、报告生成）；触达服务器段的操作显式报「服务器暂不可用，本地部分可继续」（GLM §1.2 降级 UX 口径）。

三个 C 插件的拆分明细见 §3.15–§3.17。

## 3. 逐插件适配方案

> 每条给出：目标形态 / 改动清单 / 数据与依赖 / 验收要点。改动清单只列**增量**；「无」即零代码改动。

### A 类

**3.1 admin（M-A，免适配）**：核心插件，`CORE_PLUGINS` 白名单内随主体分发，不进商店目录。E 架构下维持主进程内运行（管理面托管 supervisor，不宜反向受其托管）。

**3.2 store（M-A，免适配）**：核心插件（批次 8 已随包）。商店页在桌面端经中继直出 + `/local-api/store/*` 闭环，均已落地。

**3.3 knowledge-base（M-A）**：改动=无（出包上架即得双工件）。桌面端装前端包后阅读页本地直出，文档流/Office 预览（服务端渲染）/上传管理经中继。验收：预览大文档经中继流式透传不缓冲（批次 3 承诺）；离线时显兜底页。可选增量：worker 迁移（预览渲染是 CPU 段，迁移后隔离性更好）。

**3.4 shared-docs（M-A）**：改动=无。协作/presence 全服务器权威；前端纯 HTTP 轮询已核（无 WebSocket/SSE），中继兼容。验收：双端（浏览器+桌面）同时编辑一篇文档的 presence 与内容同步正常。

**3.5 notice-board（M-A）**：改动=无（公告读组织架构 `/api/org/tree` 走框架面）。**已完成 E 架构 worker 迁移试点**（批次 8b）；上架时 `deps_mode=shared`。验收：worker 形态下公告发布/已读、工具清单可见性正常（台架 8 项已验，补真机项）。

**3.6 case-report（M-A）**：改动=无。记录按用户/部门权限范围存服务器（`scoped_records`）、LLM 抽取与 xlsx 导出全服务器侧。验收：mine/all 双范围视图经中继一致；离线时显兜底页。说明：未来「离线录入暂存、联网同步」属新需求（需冲突处理设计），本轮不做。

### B-light 类（M-B1，全部零源码改动）

**3.7 base64 / 3.8 color-picker / 3.9 json-formatter / 3.10 md5-generator**：改动=无。F4 派生出包 → 上架 runtime=local。验收：离线安装后四工具全功能可用；服务器版条目并存（浏览器路径不减，§6 Q3）。

**3.11 map-marker（M-B1）**：改动=无。特别项：①高德 Key 用户自填存浏览器本地（localStorage），本地包路径下同样生效；②离线时地图瓦片不可用、二维码识别与轨迹 JSON 处理照常（纯前端）。验收：装包后标点/识别/轨迹功能与浏览器版一致；断外网时页面可开并明示地图不可用。

### B-heavy 类（M-B2）

**3.12 info-transfer（M-B2，本类样板）**：

- 改动=仅一处源码增量：**懒加载改造**（Q6，`import cv2`/`import numpy` 从模块顶层后移到首个视频类任务内，可用性旗标改由 jz_deps 判定数据源取）；manifest 变体见 §2.4 示例（resident=true、timeout_ms=600000、mount 不声明走默认挂载）。
- 端点面：encode/decode/export/formats/status/task/download/image/frame 全部本地 worker 承载（grep 证实前端只调自身 `/api/info-transfer/*`）。
- 依赖（dep-slot 条目）：cv2、numpy、zfec、zxingcpp、qrcode、olefile、openpyxl、pypdf、docx、xlrd（F2 盘点缺项补齐）。
- 数据：`.task_cache` → 客户端数据根；任务归属经 F1 生效。
- 验收：**敏感数据不出机**——抓包核实封装/解析全流程无出机流量（唯一外联应为高德等与本插件无关的页面级请求，本插件应零外联）；视频码流模式（cv2/zxingcpp）离线全流程；encode 长任务轮询期间 worker 常驻不重生。

**3.13 trajectory-convert（M-B2）**：同 3.12 模式（含同款懒加载改造）。依赖：cv2、numpy、zfec、qrcode、openpyxl、xlrd。与 3.12/3.14 组成「转换→封装→解码」数据链，三件**同批迁移、联动验收**（convert 产出 QR 视频喂给另两件解码回读，产物逐字节比对）。

**3.14 qr-video-decode（M-B2，轻量样板）**：同 3.12 模式；后端仅 zfec 重组（依赖最简：zfec，wheel 已备），**无重依赖、不需要懒加载改造**（仅参与 F6 的任务态外置与 idle 回收）。注意：jsQR 逐帧扫码在客户端 WebView2 内的 Web Worker 执行，与浏览器同款，无新增渲染风险；大视频（>500MB）场景补一组性能抽测。验收：与 trajectory-convert 联动回读；任务 TTL（30min）语义本地一致（外置后按落盘时间戳延续）。

### C 类（M-C）

**3.15 file-filter（M-C，C 类样板，建议首批）**：

- **拆分原则**：过滤计算本地化（脱敏表格数据不出机——本插件转 C 的核心收益）；LLM 与映射库留服务器（Key 不落本机；映射库是跨用户共享状态：加权转正投票、remap 失配管理员复核）。
- 服务器工件（`plugins/file-filter/` 增补两个端点，浏览器零感知）：
  - `POST /api/file-filter/llm/match-columns`：`{headers, keep_columns}` → 建议（内部 `llm_client.match_columns`），并把 suggested 落映射库（单一写方不变，`bump_stats` 同点）；
  - `POST /api/file-filter/mappings/lookup`：`{headers}` → 逐表头 `{target, status}`。
  - 既有 `/config`、`/mappings/*`（confirm/reject/delete/clear/export/remap/vote/recheck）不改，供客户端工件代理。
- 客户端工件 `client-plugins/local-file-filter/`（kind=hybrid、server_data=true）：
  - 本地段：`core.py`/`bg_image.py` 同源副本 + `/preview`、`/filter`、`/result`、`/download` 本地实现（任务线程池本地化；`mode=llm` 时对 miss 表头调 `own().post("/api/file-filter/llm/match-columns")`，再调 `/mappings/lookup` 复用确认级建议——与现行 `decide` 流程等价，仅 LLM/查表两步改为远端）；
  - 代理段：`/config`、`/mappings/*` 经 `own()` 透传（前端管理页零改动）；
  - requires（本地段）：openpyxl、xlrd。
- 数据归属：config.json 与 mappings.json 留服务器（权威）；`.task_cache`/上传暂存落本地数据根（原始表格不出机——代理段转发的仅是表头字符串与统计，不含表格数据，验收抓包核实）。
- 验收：离线 hard/精确/正则/双重精确过滤全流程可用；llm 模式联网时与浏览器路径结果一致、离线时明示降级；映射确认后跨端（浏览器+桌面）互相可见（共享库）；**表格文件零出机**（抓包仅见表头/查表流量）。

**3.16 trajectory-sketch（M-C）**：

- 拆分：本地段=分析引擎（`engine/`+`filter_local` 副本）+ 上传/分析/结果/报告下载（`.task_cache` 本地）+ config（GET 服务器权威 + 本地缓存离线兜底）；服务器段=仅 LLM 辅助匹配。
- 服务器工件增补：`POST /api/trajectory-sketch/llm/match-columns`（同 3.15 模式；本插件无映射库，建议不落库，即取即用）。既有 `/config` 供代理。
- requires（本地段）：openpyxl、xlrd。
- 验收：离线 v2/v3 分析全流程 + 速写报告生成；llm 辅助过滤联网生效/离线明示；config 离线时用最近缓存（首装无缓存用随包默认值——`config_store`「代码默认值=配置同源」既有机制）。
- **实施状态（2026-10-09）**：✅ 已实施（v1.3.0 双包 + 客户端工件；服务器端点/客户端网关/配置权威与缓存/验证记录见 TODO 清单批次 11 行）。llm 联网生效尚需管理员配置大模型后复验。

**3.17 character-graph（M-C，优先级最低，可后置甚至维持 A）**：

- 拆分：本地段=docx/pdf 解析（docx、pypdf 副本）+ Three.js 渲染 + 任务管理；服务器段=LLM 抽取。
- 服务器工件增补：`POST /api/character-graph/extract`：`{text, filename}` → 图谱 JSON（内部 `jz_llm`）；`/prompt`、`/config`、`/status` 供代理。
- 客户端工件：`/analyze` 拆两段——本地解析出全文 → `own().post("…/extract")` → 本地组装任务结果；离线时解析完成但抽取明示降级。
- 优先级说明：解析后的全文与原文档信息量相当，本地化的敏感收益有限、离线价值低（无 LLM 出不了图谱）——**建议排在两个样板验证之后**；若排期紧张可先以 M-A 上架（零改动），后续再拆。
