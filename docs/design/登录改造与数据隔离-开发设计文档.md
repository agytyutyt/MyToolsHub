## 1. 需求清单

| 编号 | 需求 | 验收标准（做完后如何检查） |
| --- | --- | --- |
| R1 | 提供用户登录功能，超时自动登出 | 未登录访问任意页面跳转 `/login`；登录后连续 30 分钟无任何操作，再刷新页面时被要求重新登录 |
| R2 | 用户登录才能使用相应功能 | 匿名（未登录）状态下：页面一律重定向到登录页；所有 `/api/*` 接口返回 401 |
| R3 | 用户归属"单位—部门"，各单位、部门间数据隔离 | A 单位用户在共享文档/战果录入中看不到 B 单位的任何数据；A 单位甲部门用户看不到乙部门的部门级数据 |
| R4 | 共享文档支持挂靠"单位 / 部门 / 私人"三级 | 单位文档本单位全员可见；部门文档本部门可见；私人文档仅本人可见；管理员账号可看到全部文档 |
| R5 | 战果录入默认看本人战果，可切换查看同部门战果 | 默认列表只有自己录入的记录；点「本部门」后能看到同部门其他人的记录；不能看到外部门记录 |
| R6 | 其他模块用户数据不互通 | 各纯前端工具不受影响；有持久化数据的插件按第 4.6 节规范执行归属过滤 |
| R7 | 提供用户密码修改功能 | 用户菜单中出现「修改密码」入口，输入旧密码 + 新密码（≥6 位）即可修改，旧密码错误时报错 |

**明确不在本期范围内**（防止范围蔓延）：数据库迁移、多实例部署、单点登录、手机验证码登录、共享文档细粒度编辑权限（本期"可见即可协作编辑"）、战果录入类别学习库按单位隔离。

## 2. 现状分析

### 2.1 架构现状

系统是"一切皆插件"的 Flask 单体应用：

```
浏览器
  │
  ▼
app.py（Flask 主程序）
  ├── 静态资源 /static/**            ← 首页 index.html、工具外壳 tool.html
  ├── /tool/<id>                     ← 工具外壳页（iframe 加载插件前端）
  ├── /plugin/<id>/<file>           ← 直接暴露 plugins/<id>/frontend/ 下的文件
  ├── /api/tools**                   ← 工具注册表读写（首页卡片、排序、启停）
  └── 启动时调用 register_plugin_backends()
        └── 扫描 plugins/*/backend/routes.py，调用其 register(app) 注册路由
              （插件以模块名 jztools_<插件id> 导入，例如 admin → jztools_admin）
```

与本次改造相关的两个插件的现状：

**admin 插件（管理后台，核心基础设施，始终加载）**
- 数据文件：`config/admin.json`（gitignore），层级为 **单位(units) → 部门(departments) → 用户(users)**，另有角色表 `permissions`。
- 已实现：`/login` 登录页、`/api/login`（校验密码写入 Flask session）、`/api/logout`、`/api/session`（返回当前用户信息）、单位/部门/人员/角色四套 CRUD。
- 已实现的拦截（`before_request`）：
  - `_enforce_tool_access()`：对**已登录的非超管**按权限点拦截无权限的工具；
  - `_protect_admin_ops()`：首页布局写操作需登录。
- **缺口**：匿名访问不拦截（R2 不满足）；session 没有任何超时机制（R1 不满足）；`get_session_user()` 只返回单位/部门的**名称**，没有 id（R3/R4/R5 需要用 id 判定归属）；没有自助修改密码（R7 缺失）。

**shared-docs 插件（共享文档）**
- 每个文档是 `plugins/shared-docs/backend/data/<id>.json`，**没有任何归属字段**，所有人共享同一批文档。
- "当前用户"由前端 localStorage 里**自报姓名**（`sd_user`）传给后端，仅用于展示在线列表和 updated_by，不可信。

**case-report 插件（战果录入）**
- 每条记录是 `plugins/case-report/backend/data/<rid>.json`，同样**没有录入人字段**，所有人共享台账。

**其他插件盘点**

| 插件 | 是否持久化数据 | 结论 |
| --- | --- | --- |
| json-formatter / base64 / md5-generator / color-picker | 否（纯前端计算） | 无需改动 |
| map-marker | 否（演示数据已被 gitignore） | 无需改动 |
| qr-video-decode | 否（解码全程内存态） | 无需改动 |
| character-graph | 是（backend/config.json 全局密钥配置） | 属全局配置而非用户数据，无需隔离 |
| trajectory-convert | 是（backend/.task_cache 任务缓存，随机任务 ID + 定期清理） | 临时产物、ID 不可猜测，风险低；按 4.6 节规范加可选的归属校验 |

### 2.2 能力缺口对照

| 需求 | 现有能力 | 需要新增/改造 |
| --- | --- | --- |
| R1 登录+超时 | 有登录，无超时 | 服务端空闲超时检查 + 前端轮询感知登出 |
| R2 强制登录 | 仅拦截部分写操作和权限点 | 全局白名单式登录拦截 |
| R3 组织隔离 | 组织结构已有，上下文缺 id | 扩展 `get_session_user()`，插件内做归属过滤 |
| R4 文档分级 | 无归属概念 | 文档 schema 加 `scope`，API 过滤 + 前端选择器 |
| R5 战果范围 | 无归属概念 | 记录加 `created_by` 等，列表/汇总按范围过滤 |
| R6 其他隔离 | — | 制定并落实归属标签规范 |
| R7 改密码 | 仅管理员可重置 | 新增自助改密接口 + 用户菜单纯前端弹窗 |

## 3. 总体设计

### 3.1 设计原则

1. **一切皆插件的架构不变**。鉴权能力继续放在 admin 插件里，其他插件通过跨插件导入获取用户上下文（这是现有代码已在用的模式，见 `app.py` 中 `_filter_visible_tools` 的 `from jztools_admin.routes import get_session_user`）。
2. **鉴权在框架层，数据过滤在插件层**。"是否登录""能用哪些工具"由 admin 插件的 `before_request` 统一拦截；而"能看到哪些文档/记录"属于业务逻辑，由各插件自己在查询时过滤。两层各司其职，低能力团队更容易分工。
3. **数据归属用"标签"而不是目录**。不给每个用户建一个数据目录，而是在每条 JSON 记录上打归属标签（`created_by` / `unit_id` / `department_id` / `scope.level`）。原因：现有代码全是"扫目录→逐个读 JSON"的模式，打标签只需改过滤器函数，改动面最小。
4. **服务端永远不信任前端传入的身份**。所有归属信息从 session 取，前端传来的 user 字段一律忽略或仅作展示。
5. **存量数据保守迁移**。历史文档/记录没有归属信息，一律划给超级管理员账号 `admin`，宁可先看不见，也不能泄露。

### 3.2 核心概念

**① 用户上下文（User Context）**

登录后，`jztools_admin.routes.get_session_user()` 返回的字典就是"当前用户上下文"，是全系统判定身份的唯一权威来源。本次扩展后：

```python
{
  "username": "zhangsan",        # 登录名（唯一 ID）
  "name": "张三",                 # 显示名
  "role": "普通角色",
  "unit": "第一分局",             # 单位名称（展示用）
  "unit_id": "unit-a1b2",        # 单位 ID（数据过滤用）★ 新增
  "department": "二大队",
  "department_id": "dept-c3d4",  # 部门 ID（数据过滤用）★ 新增
  "modules": ["user"],           # 可访问的管理后台模块
  "super_admin": false,          # 是否超级管理员（拥有全部 4 个模块的角色）
  "permissions": ["json-formatter", ...],  # 可用的工具 ID 列表
}
```

> **为什么 super_admin 很重要**：拥有全部管理模块（unit/department/user/permission）的角色视为超级管理员，即通常说的"管理员账号"。R4 中"管理员可查看全部文档"就落在 `super_admin == true` 上，不需要单独开白名单。

**② 归属标签（Ownership Tags）**

凡是要持久保存的用户数据，创建时必须打上：

```json
{
  "created_by": "zhangsan",
  "created_by_name": "张三",
  "unit_id": "unit-a1b2",
  "department_id": "dept-c3d4"
}
```

共享文档额外多一个 `scope.level`（`unit` / `department` / `private`）表示挂靠层级。

**③ 可见性规则（一张表说清 R3/R4/R5）**

记当前用户为 U（单位 `u(U)`，部门 `d(U)`，登录名 `n(U)`），一条数据为 X：

| 数据 | 可见条件（满足其一） |
| --- | --- |
| 共享文档 · 单位级 | U 是超管，或 `X.unit_id == u(U)` |
| 共享文档 · 部门级 | U 是超管，或 `X.department_id == d(U)` |
| 共享文档 · 私人 | U 是超管，或 `X.created_by == n(U)` |
| 战果记录（本人视图） | U 是超管，或 `X.created_by == n(U)` |
| 战果记录（本部门视图） | 本人视图全部 + `X.department_id == d(U)` 且 `X.unit_id == u(U)` |

> 注意：部门匹配必须同时比对 unit_id——虽然当前部门 ID 全局唯一，但同时比对可以防御未来部门被移动单位后产生的脏数据。

**写操作（改名/删除/覆盖保存）比读更严**：

| 操作 | 允许的人 |
| --- | --- |
| 共享文档：查看、协作编辑内容 | 可见即可编辑（单位/部门文档本单位/本部门成员都能编辑，符合"共同编辑"定位）；私人文档仅本人 |
| 共享文档：重命名、删除、改挂靠层级 | 仅 创建者 或 超级管理员 |
| 战果记录：查看、下载 | 按 R5 视图规则 |
| 战果记录：修改案件名、删除 | 仅 录入人本人 或 超级管理员 |

### 3.3 总体流程

改造后，任何一个 HTTP 请求进入 Flask 后的处理顺序：

```
请求进入
   │
   ▼
[admin 插件 before_request 链]（框架层，一次实现全局生效）
   1. _touch_or_expire_session()      ★ 新增：空闲/绝对超时则清空 session（R1）
   2. _enforce_login()                ★ 新增：白名单之外一律要求登录（R2）
   3. _enforce_tool_access()          已有：非超管按权限点拦工具（保持不变）
   4. _protect_admin_ops()            已有：布局写操作需登录（保留，语义被 2 包含）
   │
   ▼
[具体路由]
   ├─ 平台路由（/api/tools** 等）：正常执行
   └─ 插件路由（shared-docs / case-report / …）：
         第一步 from jztools_admin.routes import get_session_user 取上下文
         第二步 用 3.2-③ 的可见性规则过滤数据          ★ 各插件自行实现（R3~R6）
         第三步 写操作时把归属标签盖在数据上
   │
   ▼
响应（401 / 403 / 404 / 200）
```

前端配合：

```
index.html / tool.html / 各插件页面
   └─ 每 60 秒 GET /api/session
        ├─ 返回 {user: {...}}：一切正常
        └─ 返回 {user: null}：说明服务端已把会话作废
             → 弹提示「登录已过期」→ 整页跳转 /login?next=当前地址   ★ R1 前端侧
```

### 3.4 配置变更

`config/admin.json` 顶层增加 `session` 节（首次启动自动生成，也可手工调整）：

```json
{
  "secret_key": "…",
  "session": {
    "idle_minutes": 30,
    "absolute_hours": 12
  },
  "units": [...],
  "permissions": [...]
}
```

| 键 | 含义 | 默认值 |
| --- | --- | --- |
| `idle_minutes` | 空闲超时（分钟）：连续这么久没有任何请求，自动登出 | 30 |
| `absolute_hours` | 绝对有效期（小时）：无论多活跃，登录满这么久必须重新登录 | 12 |

> 双层超时的意义：只设空闲超时的话，只要页面开着定时轮询就永远不掉线（轮询本身也算请求）。所以必须叠加一个"绝对有效期"兜底。**轮询请求要设计成"续期但不免检"**，见 4.1。

## 4. 详细设计与实现

以下按需求逐条展开。每节都给出：改动文件清单 → 实现步骤 → 关键代码 → 自测方法。

> 代码均兼容 Python 3.8。片段中出现的函数名（如 `load_admin_config`、`find_user`、`encrypt_field`）都是 `plugins/admin/backend/routes.py` 中**已经存在**的函数，直接复用即可。

### 4.1 R1：登录与会话超时自动登出

#### 原理速览（给不熟悉 Flask session 的同学）

Flask 的 session 是**签名 Cookie**：数据存在浏览器 Cookie 里，服务端用 `SECRET_KEY` 签名防篡改。所以：
- "让用户下线" = 服务端下次收到这个 Cookie 时把它清空（`session.clear()`）；
- "过期时间" = Cookie 本身的有效期（`PERMANENT_SESSION_LIFETIME`）+ 我们自己记录的时间戳判断。

本项目 `SECRET_KEY` 已持久化在 `config/admin.json`（重启不掉线），这一点保持不变。

#### 改动文件

| 文件 | 改动 |
| --- | --- |
| `plugins/admin/backend/routes.py` | ① 登录时写入时间戳；② 新增 `_touch_or_expire_session()` 挂到 before_request；③ register() 里读取 session 配置并设置 `PERMANENT_SESSION_LIFETIME` |
| `plugins/admin/frontend/js/admin-common.js` | `renderUserMenu` 里启动 60s 轮询（首页、工具壳、admin 页共用此文件，一处改全局生效） |
| `config/admin.json`（自动生成） | 新增 `session` 节 |

#### 实现步骤

**第 1 步：常量与配置读取**（routes.py 顶部区域）

```python
import time
from datetime import timedelta

SESSION_IDLE_MINUTES = 30    # 空闲超时默认值
SESSION_ABSOLUTE_HOURS = 12  # 绝对有效期默认值


def _session_settings(cfg):
    """读取会话超时配置，返回 (idle_minutes, absolute_hours)。"""
    s = cfg.get("session") or {}
    try:
        idle = int(s.get("idle_minutes") or SESSION_IDLE_MINUTES)
    except (TypeError, ValueError):
        idle = SESSION_IDLE_MINUTES
    try:
        absolute = int(s.get("absolute_hours") or SESSION_ABSOLUTE_HOURS)
    except (TypeError, ValueError):
        absolute = SESSION_ABSOLUTE_HOURS
    return max(1, idle), max(1, absolute)
```

同时在 `ensure_admin_config()` 生成的初始 dict 中加入 `"session": {"idle_minutes": 30, "absolute_hours": 12}`。

**第 2 步：登录成功时记录时间戳**（修改现有 `admin_api_login` 成功分支）

```python
        now = time.time()
        session.clear()               # 先清空再写入，防会话固定攻击
        session.permanent = True
        session["user"] = found[2]["username"]
        session["login_at"] = now     # ★ 绝对有效期基准
        session["last_active"] = now  # ★ 空闲超时基准
```

**第 3 步：超时检查钩子**

```python
def make_session_guard(idle_minutes, absolute_hours):
    """生成会话守卫：空闲超时 / 绝对超时则强制登出，否则滑动续期。"""
    def guard():
        if not session.get("user"):
            return None
        now = time.time()
        expired = (
            now - session.get("last_active", 0) > idle_minutes * 60
            or now - session.get("login_at", now) > absolute_hours * 3600
        )
        if expired:
            session.clear()
            return None
        session["last_active"] = now   # 滑动续期：活跃用户的空闲计时归零
        return None
    return guard
```

**第 4 步：register() 中装配**

```python
    idle_minutes, absolute_hours = _session_settings(cfg)
    app.config["PERMANENT_SESSION_LIFETIME"] = timedelta(hours=absolute_hours)
    app.before_request(make_session_guard(idle_minutes, absolute_hours))
```

**第 5 步：前端轮询**（admin-common.js 的 `renderUserMenu` 内追加）

```javascript
  // 会话心跳：每 60 秒确认一次登录状态，过期则整页跳登录
  if (!window.__sessionPoller) {
    window.__sessionPoller = setInterval(async () => {
      try {
        const res = await fetch('/api/session', { credentials: 'same-origin' });
        const data = await res.json().catch(() => ({}));
        if (!data.user) {
          clearInterval(window.__sessionPoller);
          alert('登录已过期，请重新登录');
          window.location.href = '/login?next=' + encodeURIComponent(location.pathname);
        }
      } catch (e) { /* 网络抖动忽略，等下一轮 */ }
    }, 60000);
  }
```

注意两点：
- `/api/session` 保持现状：匿名时返回 **200 + `{user: null}`**（不要改成 401，否则轮询和 `api()` 封装的行为都要跟着变）；
- 轮询放在 `renderUserMenu` 里意味着只有渲染过用户菜单的页面才有心跳。首页/工具壳都已接入；插件 iframe 页面不需要自己发心跳——Cookie 在浏览器层面是同一个，顶层页面被登出后 iframe 内的下一次 API 调用自然拿到 401。

#### 自测方法

1. 把 `config/admin.json` 的 `idle_minutes` 临时改成 `1`，重启服务；
2. 登录后放置 70 秒，刷新首页 → 应跳到 `/login`；
3. 改回 30，登录后持续操作（点击切换页面）超过 1 分钟 → 不应掉线（滑动续期生效）。

### 4.2 R2：强制登录（白名单机制）

#### 设计

把"默认放行、个别拦截"反过来："**默认拦截、白名单放行**"。白名单只保留登录闭环自身必需的路径和无数据的静态资源：

| 白名单路径 | 为什么放行 |
| --- | --- |
| `/login` | 登录页本体 |
| `/api/login`、`/api/logout`、`/api/session` | 登录动作 / 退出 / 心跳探测本身 |
| `/static/**` | CSS/JS/图片，不含业务数据（首页 HTML 虽然能拿到，但它的数据全部来自需要登录的 `/api/tools`） |

#### 实现

在 admin 插件 routes.py 新增（替换掉现在 `_enforce_tool_access` 之前的位置即可，两者共存）：

```python
PUBLIC_PATHS = ("/login", "/api/login", "/api/logout", "/api/session", "/favicon.ico")
PUBLIC_PREFIXES = ("/static/", "/plugin/admin/css/", "/plugin/admin/js/")


def _enforce_login():
    """R2 强制登录：白名单之外的路径一律要求已登录。

    - API 请求返回 401 JSON（前端 AdminCommon.api 会自动跳登录页）；
    - 页面请求 302 到 /login 并携带 next 参数，登录后原路返回。
    """
    path = request.path
    if path in PUBLIC_PATHS or any(path.startswith(p) for p in PUBLIC_PREFIXES):
        return None
    if get_session_user() is None:
        if path.startswith("/api/"):
            return jsonify({"error": "未登录或登录已过期"}), 401
        return redirect(url_for("admin_login", next=request.full_path))
    return None
```

register() 中注册顺序**必须是先超时守卫、再登录拦截**：

```python

    app.before_request(_enforce_login)
    app.before_request(_protect_admin_ops)
    app.before_request(_enforce_tool_access)
```

- `_filter_visible_tools()`（app.py）中 `if info is None ... : return tools` 分支实际上永远不会命中了，可保留不动（防御性）；
- `main.js` 里悬浮球「编辑位置/隐藏工具」原来"未登录引导去登录"的逻辑可以简化为直接可用（既然能打开首页必然已登录），但**不必删**，留着无害。

#### 自测方法

1. 开无痕窗口直接访问 `/`、`/tool/shared-docs`、`/api/tools`、`/api/case-report/records`：
   - 前两者应 302 到 `/login?next=…`；后两者应返回 401 JSON；
2. 登录后再访问，原路回到 `next` 指向的页面；
3. 登录页样式、脚本正常加载（白名单生效）。

### 4.7 R7：修改密码

#### 后端（admin 插件 routes.py 新增）

```python
    @app.post("/api/account/password")
    @login_required
    def account_change_password():
        """自助修改密码：校验旧密码 → 新密码 ≥6 位且不得与旧密码相同。"""
        data = request.get_json(silent=True) or {}
        old_pwd = data.get("old_password") or ""
        new_pwd = data.get("new_password") or ""
        if len(new_pwd) < 6:
            return jsonify({"error": "新密码长度不能少于 6 位"}), 400
        cfg = load_admin_config()
        info = get_session_user()
        found = find_user(cfg, info["username"])
        if found is None:
            return jsonify({"error": "账号不存在"}), 404
        _unit, _dept, user = found
        if not check_password_hash(decrypt_field(user.get("password")), old_pwd):
            return jsonify({"error": "原密码错误"}), 400
        if old_pwd == new_pwd:
            return jsonify({"error": "新密码不能与原密码相同"}), 400
        user["password"] = encrypt_field(generate_password_hash(new_pwd))
        save_admin_config(cfg)
        return jsonify({"ok": True})
```

复用点：`login_required` 装饰器、Fernet 加密存储、werkzeug 哈希校验，全部是现成函数。修改后**保持当前会话有效**（Flask session 里只存 username，不存密码指纹），不做强制重登，减少复杂度。

#### 前端（admin-common.js 的 renderUserMenu）

用户菜单加一项「修改密码」，点击弹出 modal（复用现成的 `openModal`）：

```html
<form id="pwd-form">
  <label>原密码 <input type="password" name="old" required></label>
  <label>新密码 <input type="password" name="new" minlength="6" required></label>
  <label>确认新密码 <input type="password" name="confirm" minlength="6" required></label>
  <button type="submit">保存</button>
</form>
```

提交逻辑：两次新密码一致性前端先校验 → `POST /api/account/password` → 成功 toast「密码已修改」，失败红字显示 error。

#### 自测方法

旧密码故意输错 → 报"原密码错误"；新密码 5 位 → 前端拦截；改密成功后退出登录，用新密码能登、旧密码不能登。

## 6. 数据结构与迁移方案

### 6.1 变更汇总

| 文件 | 变更 |
| --- | --- |
| `config/admin.json` | 顶层新增 `session` 节（ensure 时自动补齐，旧文件缺失也不报错——读取处有默认值兜底） |
| `plugins/shared-docs/backend/data/*.json` | 每个文档新增 `created_by` / `created_by_name` / `scope{level,owner,owner_name,unit_id,department_id}` |
| `plugins/case-report/backend/data/*.json` | 每条记录新增 `created_by` / `created_by_name` / `unit_id` / `department_id` |

### 6.2 迁移策略（一次性、幂等、随启动执行）

沿用 admin 插件已有的 `migrate_xxx(cfg)` 模式：**启动时跑一遍，发现缺字段才补，补完原子写回**。这样部署零手工操作，重复重启也不会重复迁移：

```
register(shared-docs):  with _LOCK: migrate_doc_scope()
register(case-report):  ensure_files(); with _LOCK: migrate_record_owner()
```

迁移规则（保守优先）：

| 存量数据 | 迁移结果 | 理由 |
| --- | --- | --- |
| 历史共享文档 | 私人文档，owner=admin | 无法追溯创建人与受众；admin 超管可见全部，需要共享时管理员手动改挂靠 |
| 历史战果记录 | created_by=admin，unit/department 为空 | 同上；超管可见不依赖组织字段 |

回滚方案：新字段均为**增量字段**，旧代码读取时直接忽略未知键，因此任意时刻回滚到旧版本不会报错，只是失去过滤能力。

## 9. 安全注意事项

1. **越权一律 404**：数据类接口对"存在但不可见"的资源返回 404，避免枚举探测（页面类可 403）。
2. **身份只认 session**：归属字段一律服务端注入；请求体里的 `user`/`username` 字段仅可作展示用途（本期起 shared-docs 连展示也不再信任请求体）。
3. **会话固定防护**：登录成功先 `session.clear()` 再赋值。
4. **加密存储延续**：新密码继续走 `generate_password_hash` + Fernet 双层处理，与现有 `config/admin.json` 格式完全兼容，`migrate_admin_encryption` 无需改动。
5. **HTTPS**：内网 HTTP 部署时 Cookie 明文传输，建议正式环境至少在网关层启用 TLS；启用后可在 Flask 补 `SESSION_COOKIE_SECURE=True`（列入部署检查单，不在本期代码内强开，避免本地调试踩坑）。
6. **暴力破解（可选增强，暂不实施）**：可在内存中对连续失败 ≥5 次的 username 做 5 分钟锁定。当前内网场景风险可控，先记录不开发。
7. **日志脱敏**：access log 不要打印请求体（现有 setup_access_logging 只记 path/status，保持即可），避免密码进日志。

## 10. 附录

### 附录 A：名词解释

| 名词 | 含义 |
| --- | --- |
| session（会话） | Flask 用签名 Cookie 保存的"当前登录者是谁"的信息，浏览器关了再开仍在（直到过期） |
| 滑动过期 | 每次操作都把"空闲计时"清零；只有真正闲置才会超时 |
| 绝对有效期 | 从登录那一刻算死的上限，防止"永远挂着"的会话 |
| 超级管理员 | 角色的 modules 等于全部 4 个管理模块的账号，代码里对应 `super_admin: true` |
| 权限点 | 用户字段 `permissions`，值为 tools.json 里的插件 ID 列表，控制"能用哪些工具" |
| 归属标签 | 落盘数据上的 `created_by/unit_id/department_id(/scope)` 字段集合 |
| 白名单 | 强制登录模式下显式放行的路径清单 |

### 附录 B：FAQ

**Q1：为什么不引入数据库？**
现有全部插件基于"一记录一 JSON 文件 + 原子替换写"，规模（百级文档/千级记录）远没到瓶颈。本期聚焦权限与隔离，保持存储不变可以把改动集中在"过滤逻辑"这一层，风险最小。

**Q2：用户调部门后，他之前录入的战果还算谁的？**
还算他的（`created_by` 不变）。但他在新部门看"本部门"时看不到旧部门的记录——这正是"部门间隔离"的期望行为。管理上需要挪动历史数据时，由超管批量改记录的 `department_id`（后续可做个管理小工具，本期不做）。

**Q3：前端把按钮藏起来了，是不是就不用做后端校验了？**
不是。前端显隐只为体验，**每一道闸都必须落在后端**（本文所有规则均已指定后端返回码）。测试时一律绕过界面用 curl/直连 URL 验证。

**Q4：iframe 里的插件页面收到 401 怎么办？**
跳转要用 `window.top.location.href` 让**整个页面**去登录页，否则登录页会嵌在小框框里。

**Q5：`/api/session` 匿名时为什么返回 200 而不是 401？**
它承担"心跳探测"职责：前端靠 `data.user === null` 判断被登出。若返回 401，`AdminCommon.api()` 会立刻抛错跳转，轮询逻辑反而不好写。特例保留。

**Q6：为什么超管的"改挂靠"不改文档的 unit_id/department_id？**
只动 `scope.level`、保留原组织信息的语义是"把这个文档提升/降级共享范围"，而不是"把文档搬到另一个单位"。后者目前没有业务诉求，刻意不做。
