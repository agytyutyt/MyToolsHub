# 主体与插件解耦 · 设计文档

> 目标：把**项目主体**（框架 + 运行环境 + 核心插件）与**业务插件**分成两个可独立升级的交付物——
> 主体升级只替换主体文件、不触碰任何插件代码；插件以「插件包」为分发单元单独加载 / 停用 / 卸载 / 升级，
> 两者靠一份显式的**版本契约**（`plugin_api`）衔接，而不是靠"一起发版"。

## 0. 一页速览

**结论：解耦可行，且"插件独立升级"的基础设施已经建好；本次要补的是"主体独立升级"这一半。**

现状是**单向的**：插件能单独升级（插件包链路已落地，冻结模式自重启已真机验证；真实插件的现场升级演练
仍待做，见 `HANDOFF.md` §4 P1-15.1），但主体升级仍会把 15 个业务插件一起覆盖到目标机
（`build-deploy.ps1:136` 整目录复制 `plugins/`，`install.ps1:368-382` 整体覆盖）。
本方案把这条链路补成**双向**：主包不再内嵌业务插件，主体升级因此从机制上不可能碰到插件代码。

| 三条边界判据（P-1~P-3，用于今后新增模块的归类） | 说明 |
| --- | --- |
| P-1 框架必需 | 主体启动、鉴权、插件加载、壳页渲染所必需 → 随主体 |
| P-2 无插件也成立 | 不依赖任何业务插件即可独立工作 → 随主体 |
| P-3 稳定共享面 | 被多个插件共享、且属于"插件可依赖的稳定契约" → 随主体并纳入 `plugin_api` 承诺 |

**必须同时补的四件事**（否则解耦即引入新故障，见 §5/§8）：

| 缺口 | 后果 | 补法 |
| --- | --- | --- |
| 无插件版本 / 依赖门控 | 主体升级先于插件升级时老插件可能直接崩；"插件能不能跑"无人核对 | §5：主体侧启动门控（版本 `min_app_version`+`plugin_api`、依赖三态判定），不满足**不加载并标记**，不拖垮整站 |
| 主体反向依赖插件 | `app.py` 与 10 个插件 `import jztools_admin.routes`——主体/插件/插件内部模块三层缠绕 | §8 S0：依赖倒置（新增主体模块 `jz_api.py` + admin 注册 provider + 垫片） |
| 无依赖可见性 | 现场装完才发现缺 `numpy`/LibreOffice；插件声明了什么、本机装了什么、能不能跑，全靠猜 | §5.3 依赖声明（三类）+ 已安装依赖清单 + 逐依赖徽标 + 添加期检测（不阻断） |
| 主体升级不可回滚 | 现状 `install.ps1` 只覆盖、无备份，主体升坏只能重装 | §6：升级前自动备份主体到数据根 `backups\app\` + `-Rollback` |

**`admin` 的定位（本次修订）**：随主包分发、**可单独升级**（保留插件包，主体升级对它走与业务插件相同的防回退判定）、
**不可卸载**（它是登录 / 鉴权 / 权限 / 后台 / 插件管理本身，卸载即自锁）；**首次安装只有 admin**，业务插件由插件集安装。

**四个阶段**（§8，每阶段可独立上线、独立回退）：

| 阶段 | 内容 | 是否动结构 |
| --- | --- | --- |
| S0 | 版本与依赖门控 + 依赖声明与判定 + **已安装依赖清单** + 逐依赖徽标 + 添加期检测（不阻断）+ `admin` 定位调整 + 依赖倒置 + 插件间独立（第一处修补：org API 提升主体）+ 健壮性 + 顺手清理 | 否 |
| S1 | **物理解耦**（核心交付）：主包只带 admin；插件集包；主体备份/回滚 | 是 |
| S2 | **插件间独立收口**：修补两处遗留跨插件协作（各自实现一份）+ 构建期 C-11 拦截 + 后台卸载入口 | 部分 |
| S3 | （可选，需 PoC）依赖组件包，把仅插件使用的 `cv2`/`numpy` 移出主体 | 是 |

**收益与代价（诚实口径）**：收益是**升级边界清晰**——主体升级不再有覆盖/降级插件的风险，
插件缺陷修复不必等主包发版；外加两项新能力：**依赖可见**（插件声明依赖与版本，后台看得到"装了什么、
差什么、能不能跑"）与**插件间独立**（两处遗留跨插件协作各自实现一份，仓库内零跨插件调用）。
主包体积的收益很小（`plugins/` 在 zip 内约 16 MB，剥离后省 13~16 MB），
**体积质变要等 S3**（`_internal` 中仅 `cv2`+`numpy` 就约 157 MB，且只服务于 2 个插件）。
代价是：全新装机多一步「装插件集」；必须长期维护版本与依赖契约；S2 要把两处遗留跨插件协作改成
各自实现一份（多一份同源副本的维护成本，RK-12）。

## 1. 需求与边界

| 编号 | 需求 |
| --- | --- |
| D-1 | **主体升级只动主体**：一次主体升级不得新增、删除、修改任何业务插件目录中的文件。 |
| D-2 | **插件生命周期独立**：插件的安装、停用、卸载、升级都不需要重新分发主体。 |
| D-3 | **零数据风险**：两条链路都不得触碰数据根中的用户数据（沿用既有底线）。 |
| D-4 | **可离线完成**：内网无外网，介质为 U 盘 / 共享盘，全流程不联网。 |
| D-5 | **可校验可回退**：主体与插件各自有备份与回滚；升级前拒绝即零写入。 |
| D-6 | **不破坏现状**：现有 16 个插件、现有目标机、现有数据根在迁移过程中全程可用。 |
| D-7 | **依赖可见**：插件声明所需依赖与版本；后台可查看本机**已安装依赖（含版本）**与每个插件的依赖满足情况，满足项绿色、未满足项红色带 ×。 |
| D-8 | **添加不被依赖阻断**：添加插件时检测环境依赖，不满足则**弹窗提示并继续完成添加**；该插件保留在列表中并标注不可运行，待依赖补齐后恢复。 |
| D-9 | **插件间独立**：插件之间互不依赖——不得 import 其他插件的模块（规范 B-7 禁令不变）、不得把另一个插件声明为依赖、不得在后端调用其他插件的接口；现有的两处跨插件协作全部修补消除（§5.4）。 |

**不做**（本期边界）：

| 不做 | 原因 / 替代 |
| --- | --- |
| 后端热重载（换后端代码不重启） | 后端由 importlib 在启动时注册（`app.py:550-570`），进程内换代码需重启；现有自重启编排已把重启做到 5~10 秒自动完成。零重启方向见 `docs/eval/插件热插拔-容器化改造评估.md`。 |
| 插件市场 / 公网在线更新 | 离线场景，用共享盘 `index.json`（已落地）。 |
| **自动安装依赖**（含自动装被依赖的插件） | 只做"检测 → 提示 → 标注 → 门控"，不代装（离线环境）；依赖组件包与依赖插件由管理员按指引装。 |
| **插件间依赖**（A 依赖 B 的核心模块） | **不做**：插件间保持独立，规范 B-7 的既有禁令（禁止 import 其他插件后端模块）**不变**。已有的跨插件协作（`trajectory-sketch` → `file-filter` 的 HTTP 面）保留现状、不得新增；确有协作需求时应把能力**提升为主体模块**或**合并为一个插件**。 |
| 主体增量更新（差分包） | 属主包职责，与解耦正交。 |
| 把 `admin` 完全外置 | 见 §3.5：定位为"随主体的核心插件"，可单独升级但不可卸载。 |

## 2. 现状与耦合点

### 2.1 主包体积构成（v2.1.2 实测）

zip 本体 124.3 MB（解压 265.6 MB / 3031 条目）；`deploy\JZToolsHub-v2.1.2\` 解压目录 272 MB：

| 一级项 | 体积 | 占比 | 说明 |
| --- | --- | --- | --- |
| `_internal/` | 235 MB | 86.4% | Python 运行时 + 框架第三方依赖（`cv2` 114M / `numpy`+`numpy.libs` 43M / `PIL` 15M / `pandas` 13M / `cryptography` 11M …） |
| `JZToolsHub.exe` | 20 MB | 7.4% | 入口（`app.py` 冻结于此） |
| `plugins/` | 17 MB | 6.3% | **全部 16 个插件**（`map-marker` 9.58M / `knowledge-base` 4.01M / `character-graph` 1.30M，其余 12 个合计约 2M） |
| `tools/` | 516 KB | 0.2% | 含 `tools/dev`（伪造 admin 会话的验证服务，规范明说**不能上目标机**）与 `__pycache__` |
| `docs/` | 432 KB | 0.16% | guide + design + 索引 |
| `static/` | 188 KB | 0.07% | 壳页 + 共享前端 |
| `wheels/` | 68 KB | 0.02% | **无运行时消费方**，仅构建机重建 zfec 用 |
| `runtime/` | 不存在 | — | 已解耦为独立离线组件包（682 MB 在仓库，不入主包） |

> 对照：`runtime/` 已于 v1.9 移出主包（zip 648 MB → 128 MB），是本方案"剥离"路线的成功先例；
> 本次是把同样的思路用在 `plugins/` 上。

### 2.2 六处耦合点（解耦要处理的全部障碍）

| 编号 | 耦合点 | 证据 | 影响 |
| --- | --- | --- | --- |
| K-1 | **主包内嵌全部插件**，升级时整体覆盖 | `build-deploy.ps1:136`；`install.ps1:368-382` | 主体升级会覆盖已单独升级的插件（现靠 `install.ps1:329-354` 防回退兜住，属"补丁"而非"结构"） |
| K-2 | **主体反向依赖 admin 插件内部模块** | `app.py:278`、`app.py:698`：`from jztools_admin.routes import get_session_user` | admin 缺失时主体鉴权降级；admin 内部文件名成为事实上的框架 API |
| K-3 | **10 个插件依赖 admin 插件内部模块** | `plugins/{case-report,character-graph,file-filter,info-transfer,knowledge-base,notice-board,qr-video-decode,shared-docs,trajectory-convert,trajectory-sketch}/backend/routes.py` 的 `from jztools_admin.routes import …` | 插件 → 插件内部文件，路径与签名是隐式契约，admin 重构即全量断裂 |
| K-4 | 插件间调用（后端 HTTP + 前端跨插件） | `trajectory-sketch/backend/filter_bridge.py:50-54`（调 `/api/file-filter/apply`，且需自己读 `tools.json` 判断对方启用）；`notice-board/frontend/app.js:68`（调 `/api/admin/org-tree`） | **两处全部修补消除**（D-9 / §5.4）：前者在本插件内自带一份同样的过滤实现；后者把组织架构树提升为主体 API 后改调主体。修补后仓库内零跨插件调用 |
| K-5 | 插件引用主体共享静态资源 | `static/js/jz-icon.js` 被 admin / case-report / character-graph 引用；`static/css/style.css` + `static/icons/` 被 admin 引用 | 主体资源变更会打断插件；需纳入 `plugin_api` 承诺面（FC-5） |
| K-6 | 插件依赖主体 `_internal` 的第三方包 | `JZToolsHub.spec:18-37` 的 `PACKAGES`（17 个包）是插件依赖白名单唯一真源，`tools/build-plugin-package.ps1` C-4 据此校验 | 插件升级受主体依赖集约束（U-2）；主体瘦身时可能误删插件要用的包 |

另有两处**健壮性缺口**（解耦后会被放大，S0 一并修）：

- `app.py:390-400 load_manifests()` 与 `load_registry()` 无异常保护——一个截断的 `manifest.json` 会让 `/api/tools` 500。
  解耦后插件目录由外部介质写入，坏文件的概率上升。
- 插件加载失败只进日志与 `_plugin_load_errors`（`app.py:621-627`），**前端不可见**（`HANDOFF.md` §4 P1-13 同款）。

## 3. 边界划分：什么随主体打包

### 3.1 判据（P-1~P-3）

新增任何模块时按顺序判定：**框架必需（P-1）→ 无插件也成立（P-2）→ 稳定共享面（P-3）**，
三条命中任一即随主体；反之（单一插件专用、可独立演进、体积随功能增长）即外置为插件。

### 3.2 主体清单（随主包打包）

| 模块 | 现状位置 | 体积 | 判定 | 备注 |
| --- | --- | --- | --- | --- |
| `JZToolsHub.exe` | 程序目录 | 20 MB | P-1 | 入口，`app.py` 冻结于此 |
| `_internal/` | 程序目录 | 235 MB | P-1 | Python 运行时 + 框架依赖；**一期保持**（§3.4） |
| `app.py` | 仓库根 | — | P-1 | 壳页路由 / 插件加载器 / 注册表聚合 / 静态路由 / 访问日志 / 托盘 / 自重启助手 |
| `jztools_data.py` | 仓库根 | — | P-1 | 数据根解析 / 模板同步 / 状态文件 / 插件模板补键 |
| `static/` | 仓库根 | 188 KB | P-1 + P-3 | 壳页 `index.html`/`tool.html`、`main.js`/`tool.js`；**`jz-icon.js` 属共享面**（K-5） |

### 3.3 剥离清单（不随主包）

| `runtime/` | 682 MB | 维持现状 | 已是独立离线组件包，不在本方案范围 |

### 3.4 第三方依赖层：一期保持随主体，二期可选外置

- **现状**：`JZToolsHub.spec:18-37` 的 `PACKAGES` 是"插件可用第三方包"的唯一真源，全部打进 `_internal`；
  插件包构建期 C-4 校验只允许 `PACKAGES ∪ 插件自带 vendor/ ∪ 标准库`（《插件设计规范.md》U-2）。
- **一期决策：不动**。理由：① C 扩展（`cv2`/`numpy`）外置需先做可行性 PoC（DLL 依赖链与冻结环境的
  `sys.path` 注入）；② 插件包会从"通常 < 10 MB"变成 100 MB+ 级，与"插件包轻量、便于介质传递"的定位冲突；
  ③ 离线现场多一步"装依赖组件"就多一个失败点。
- **配套承诺（FC-6）**：`PACKAGES` 在 `plugin_api` 不变期间**只增不减**——主体可以新增依赖，不得删除
  已被插件使用的依赖；确需删除时必须提升 `plugin_api` 并在发布说明中列出受影响插件。
- **二期（S3，可选）**：新增「依赖组件包」形态（`JZToolsHub-依赖组件-<id>-v<版本>.zip` → 装到
  `<程序目录>/runtime/pylibs/` → 主体启动时注入 `sys.path`），复用离线组件包的既有机制
  （`tools/offline-components.json` + `tools/build-offline-component.ps1` + 免管理员安装脚本骨架）。
  届时 `cv2`+`numpy`（约 157 MB，仅 `info-transfer`/`trajectory-convert` 使用）可移出主体。
  **前置条件是 §5.3 的依赖声明与判定先在 S0 落地**：没有"声明 → 实测 → 缺依赖门控"这条链，
  外置依赖就是盲拆（插件会静默不可用）。

### 3.5 `admin` 的定位：随主体的核心插件（可单独升级、不可卸载）

事实：admin 已被特殊化——始终加载且跳过 `enabled` 检查（`app.py:639-641`），被主体 import（K-2），
被 10 个插件 import（K-3），在 `tools.json` 中 `hidden: true` 不显示为工具卡片。
它承担的是**框架能力**（登录 / 会话 / 组织架构 / 权限拦截 / 后台 / 插件管理 / 自重启编排），
而不是业务功能。

**三条规则**（本方案采用）：

| 规则 | 内容 | 实现点 |
| --- | --- | --- |
| 随主包分发 | 主包 `plugins/` 内**唯一**目录；manifest 增补 `"core": true`；仍走标准插件契约（`manifest.json` + `register(app)`），保留"一切皆插件"理念 | §7 #1 组装白名单 |
| **可单独升级** | 继续用 `build-plugin-package.ps1` 出 admin 插件包；主体升级时 admin **与业务插件同规则**——走既有防回退判定（`install.ps1:329-354`：登记版本更高则跳过覆盖），不再"以主包为准覆盖" | §7 #5、§6 步骤⑥ |
| **不可卸载** | 它是登录 / 鉴权 / 权限 / 后台 / 插件管理本身，卸载即自锁（无管理入口、无鉴权）。安装器 `-Uninstall admin` 与后台卸载入口**双重拒绝**；`-PurgeEntry` 同样不得作用于 admin | §7 #17 |

**首次安装只有 admin**：装完主体后首页工具列表为空（admin 是隐藏卡片），安装完成时提示
"请安装插件集或逐个安装插件包"（§4.1 插件集）。

> 远期可选（不属本方案）：把 admin 的框架内核（会话 / 鉴权 / 权限 / 组织架构）上移主体模块
> （`jz_auth.py`），admin 只保留管理界面——届时"不可卸载"的理由才真正消失。admin 后端体量大
> （`routes.py` + `plugin_admin.py` + `batch_io.py`），单独立项。

## 4. 插件管理应以何种方式

**一句话：分发单元统一为「插件包」，管理入口保持三条（离线脚本 / 后台页面 / 共享盘索引），
三者共用同一套校验规则；本次只补两个缺口——「插件集」（首装介质）与「卸载 / 兼容状态」（管理面）。**

### 4.1 三种分发物（各司其职，互不越界）

| 分发物 | 内容 | 谁产出 | 现状 |
| --- | --- | --- | --- |
| **主包** `JZToolsHub-v<版本>.zip` | 主体（§3.2，含核心插件 admin） | `build-deploy.ps1` | 已有，S1 收窄 |
| **插件包** `JZToolsHub-插件-<id>-v<版本>.zip` | 单个插件代码快照（`plugin-package.json` + `SHA256SUMS` + `payload/plugins/<id>/`）；**含 admin**（可单独升级，§3.5） | `tools/build-plugin-package.ps1` | **已有，格式不变**（详见 `docs/design/插件独立升级方案-设计文档.md` §4） |
| **插件集** `JZToolsHub-插件集-<名称>-v<日期>.zip`（新增） | `index.json` + N 个插件包 + `.sha256` + `安装插件集.bat` | `tools/build-plugin-set.ps1`（新增） | 新增：解决"主包不含插件后，新机首装从哪来" |

**离线组件包**（`JZToolsHub-离线组件-*.zip`）维持现状，不属本方案。

### 4.2 三条管理入口

| 入口 | 适用 | 现状 | 解耦后要补 |
| --- | --- | --- | --- |
| 离线脚本 `tools/plugin-upgrade/install-plugin.ps1` | U 盘 / 共享盘、无浏览器 | 已有 `-List` / `-DryRun` / `-Rollback` / `-Uninstall` / `-Force` / `-PurgeUnknown` 等 | 新增 `-Set <目录>`：读 `index.json` 逐个应用（跳过已最新/更高版本），任一失败继续其余并汇总；全部成功统一重启一次 |
| 后台「插件管理」（admin 插件） | 管理员浏览器操作 | 已有盘点 / 上传 / 应用 / 回滚 / 启停 / 索引 / 批量 / 重启（`plugins/admin/backend/routes.py:1461-1686`，核心逻辑 `plugin_admin.py`） | ① 新增**卸载**（现状只有停用；`admin` 自身不可卸载，§3.5）；② 新增**「已安装依赖」清单**（框架包 / 外部组件 / 插件自带，含版本，§5.3 D-7）；③ 插件列表新增**兼容性列**与**逐依赖徽标列**（满足绿色 / 不满足红色带 ×）；④ 添加插件时**依赖检测弹窗**（不满足可"仍然添加"，D-8）；⑤ 顶部「N 个插件需升级 / K 个不可运行」横幅 |
| 共享盘索引 `index.json` | 多机批量收敛 | 已有 `check_updates` / `batch_apply`（阶段三已落地） | 不变（索引条目随 S0 增补 `api_version` 字段，与插件包同步，§7 #9） |

三条入口的校验规则**单点定义**在既有文档 §4/§5.3，两侧实现同源（`test_plugin_admin.py` 交叉验证用例钉住），
本方案不新增第二套规则。

### 4.3 生命周期语义（解耦后的口径）

| 动作 | 触发 | 是否需重启 | 真源 / 约束 |
| --- | --- | --- | --- |
| **加载** | 主体启动扫描插件根 | — | 通过 `manifest.json` + **版本与依赖门控**（§5.2 / §5.3）才加载；插件之间互不依赖、加载顺序无关；失败隔离（已有）；前端资源磁盘直读（`app.py:659-665`），**前端改动无需重启** |
| **停用** | `tools.json` 置 `enabled:false` | 否 | 只影响后端注册与卡片显示；代码与数据保留（规范 §11） |
| **升级** | 插件包 → 校验 → 备份 → 三分法替换 → 登记 | 含 `backend/**` 改动则**是**（自动重启，5~10 秒） | 既有链路，不改 |
| **卸载** | 脚本 `-Uninstall` / 后台「卸载」 | 是 | **顺序铁律**（规范 §11）：先删/停注册条目 → 备份数据 → 再删目录；数据默认保留；**`admin` 不可卸载**（§3.5） |
| **回滚** | 脚本 `-Rollback` / 后台回滚 | 是 | 从数据根 `backups\plugins\<id>\` 取最近一份，整目录恢复 |

### 4.4 状态与真源（每个事实一个落点）

| 事实 | 真源 | 位置 |
| --- | --- | --- |
| 插件当前版本 | `plugins/<id>/manifest.json` 的 `version` | 程序目录（判定以此为准） |
| 已应用版本 / 备份 / 模板指纹 / 待重启标记 | `config\.app_state.json` 的 `plugins.<id>` | 数据根（提示与门控用；与目录不一致时告警） |
| **已安装依赖及版本** | `config\installed-deps.json`（构建期生成，主体升级时更新）；依赖组件另见 `runtime\pylibs\manifest.json`（S3） | 程序目录（只读，随主包分发） |
| 启停 / 名称 / 排序 / 授权 | `config\tools.json` | 数据根（运行时权威；仓库内为模板） |
| 备份 | `backups\plugins\<id>\*.zip`（插件）、`backups\app\*.zip`（主体，S1 新增） | 数据根（与程序目录解耦，程序目录被替换也不丢） |

### 4.5 兜底：目录即插件（保留，不推广）

手工把插件目录拷进 `plugins/` 仍能被扫描加载（规范 §12「零代码接入」）。解耦后该路径**保留为兜底**，
但后台插件列表标记「未登记」（无 `code_sha256` / 无备份），并提示"用插件包正式安装以获得备份与回滚"。

## 5. 兼容性契约：主体对插件的承诺面

解耦把"插件与主体同包发版"的隐式同步，换成"显式版本契约"。契约分两部分：**承诺面**（主体不改什么）
与**门控**（主体怎么拒绝不匹配的插件）。

### 5.1 框架承诺面（FC-1~FC-9，`plugin_api = 1` 的内容）

| 编号 | 承诺 | 现状落点 |
| --- | --- | --- |
| FC-1 | 加载契约：`plugins/<id>/backend/__init__.py` + `routes.py` 导出 `register(app)`；可选钩子 `home_card()` | `app.py:550-570`、`app.py:631-636` |
| FC-2 | 数据面：`jztools_data.get_data_root()` / `get_data_root_dir()` / `get_data_root_file()` 签名与语义不变 | `jztools_data.py:170-190` |
| FC-3 | **会话工具面（新增）**：`jz_api.get_session_user()` / `set_operation()` 由主体提供，与 admin 是否加载无关 | 新增（§8 S0），取代 K-2/K-3 的隐式契约 |
| FC-4 | HTTP 面：`/api/<id>/...` 前缀、`/plugin/<id>/<entry>` 静态路由、`/tool/<id>` 壳页、框架级组织架构 API `/api/org/tree`（§5.4 提升）、未登录 401 兜底 | `app.py:654-665`；admin 拦截 `routes.py:523-580` |
| FC-5 | 共享静态资源：`/static/js/jz-icon.js`、`/static/css/style.css`、`/static/icons/*.svg` 路径与行为不变 | `static/` |
| FC-6 | 依赖白名单：`PACKAGES` **只增不减** | `JZToolsHub.spec:18-37` |
| FC-7 | 配置模板：`plugins/<id>/**/*.template.json` 的自动补键（指纹门控）语义不变 | `jztools_data.py:493-631` |
| FC-8 | **依赖声明面（新增）**：`manifest.json.requires` 字段语义、`GET /api/<id>/status` 的 `deps` 段、`GET /api/admin/plugins` 的 `deps` 字段（见 §5.3） | 新增（§8 S0） |
| FC-9 | **已安装依赖清单（新增）**：`config/installed-deps.json` 的字段与只读语义；`GET /api/admin/deps` 返回该清单（见 §5.3） | 新增（§8 S0） |

**破坏性变更纪律**：主体改动 FC-1~FC-9 任一项 → `plugin_api` 递增，且主体**必须同时兼容上一版
`plugin_api`**（一个版本窗口）；窗口内后台提示"插件需更新"，窗口结束后门控硬拒绝。

### 5.2 版本字段与门控矩阵

- 主体 `version.json` 新增 `plugin_api`（整数，初值 `1`）；由 `build-deploy.ps1` 写入、`install.ps1` 保留。
- 插件包 `plugin-package.json` 新增 `api_version`（构建期由出包工具写入当前主体的 `plugin_api`）；
  `min_app_version`（已存在）继续表示"最低主体版本"。
- **两处清单的分工**：`manifest.json`（插件代码内）是**运行时真源**，主体启动时读它做门控；
  `plugin-package.json`（分发包内）是**分发期真源**，安装器在写盘前读它做拒绝。
  同名字段（`version` / `api_version` / `min_app_version` / `requires`）由构建期硬校验相等——
  沿用既有"包清单镜像代码清单"的约定（`docs/design/插件独立升级方案-设计文档.md` §4.5）。
- 主体启动时（`register_plugin_backends` 内，加载前）逐插件门控：

| 插件声明 vs 主体 | 行为 |
| --- | --- |
| `min_app_version > version.json.app` | **不加载** + 标记「需升级主体」，后台可见；不拖垮整站 |
| `api_version > version.json.plugin_api` | **不加载** + 标记「插件需更新」（正常流程不该出现，属"先升插件后降级主体"的兜底） |
| 两者均满足 | 正常加载 |
| `manifest.json` 缺失 / 不可解析 | 跳过 + 告警（§2 健壮性缺口，S0 修） |
| `tools.json` 中 `enabled:false` | 不加载（现状，与门控正交） |

> 门控是**主体侧**的兜底：插件安装器（`install-plugin.ps1` / 后台 apply）已在安装时拒绝
> `min_app_version` 不满足的包；门控覆盖的是"先装插件、后回滚主体"这条反向路径。

### 5.3 依赖声明与可运行性判定

**问题**：解耦后"插件能不能在本机跑起来"不再由"同包发版"保证，必须由**插件声明 + 主体实测**
共同判定，并在后台一眼可见（能加载 ≠ 能运行：依赖缺失时插件可能整体不可用，或按 B-4 降级）。

**三类依赖**（每类都有"声明"与"实测"两侧；**不含"依赖的插件"——插件间保持独立，见 D-9**）：

| 类别 | 声明（插件侧） | 实测（主体侧） | 缺失后果 |
| --- | --- | --- | --- |
| 框架第三方包 | `requires.python_packages[{name,version,required}]` | 已安装依赖清单 `config/installed-deps.json`（构建期生成：包名 + 实际版本） | `required` 缺失 → 不可运行（不加载）；可选缺失 → 降级 |
| 插件自带依赖 | `requires.vendored[{name,version}]` | 插件目录内 `backend/vendor/<name>` 存在性 | 同上分级 |
| 外部程序组件 | `requires.external[{id,version,required}]`（如 `libreoffice`） | `runtime/manifest.json` + 实际探测（复用 `plugins/knowledge-base/backend/office_render.py:113-178` 的候选路径算法） | 同上分级 |

**`manifest.json` 增补 `requires` 字段**（未声明视为"无第三方依赖"，与现状兼容）：

```json
"requires": {
  "api_version": 1,
  "min_app_version": "2.2.0",
  "python_packages": [ { "name": "openpyxl", "version": ">=3.1", "required": true } ],
  "vendored": [],
  "external": [ { "id": "libreoffice", "required": false } ]
}
```

**判定三态**（主体启动时逐插件求值，与版本门控同一处、同一次）：

| 状态 | 条件 | 行为 |
| --- | --- | --- |
| `ok` 可运行 | 全部 `required` 满足 | 正常加载 |
| `degraded` 降级 | `required` 满足、部分可选依赖缺失 | 加载；插件列表与卡片标"功能降级"（插件自身按 B-4 优雅降级，如 knowledge-base 缺 LibreOffice 时 `.doc` 预览降级） |
| `blocked` 不可运行 | 任一 `required` 缺失 | **不加载** + 记录缺失清单；列表红 ×；首页卡片不出现；依赖补齐后重启自动恢复 |

**添加期检测（D-8：提示但不阻断）**——两个入口同一份判定：

| 入口 | 检测时机 | 不满足时 |
| --- | --- | --- |
| 后台「插件管理」上传 / 批量 | `inspect_package` 阶段（写盘前） | **弹窗**列出缺失项与影响（哪些功能不可用、需装什么），提供「仍然添加」/「取消」；选「仍然添加」→ 照常备份、替换、登记，完成后该插件状态为 `blocked` |
| 离线脚本 `install-plugin.ps1` | 只读校验阶段（既有拒绝点之后、写盘之前） | 控制台打印缺失清单与影响，**默认继续**；`-SkipDepCheck` 跳过检测、`-StrictDeps` 改为中止（供批量脚本用） |

> 与既有拒绝点（版本 / 哈希 / 路径安全）的区别：那三类是**完整性**问题，拒绝且零写入；
> 依赖缺失是**环境**问题，允许"先装插件、后补依赖"，故不阻断添加。

**版本比较语义（刻意从简）**：只支持 `>=x.y.z` 与精确 `x.y.z` 两种写法（三段式数值比较，
主体内 `jz_deps.py` 自实现，不引入 `packaging`——它不在 `PACKAGES` 白名单内）。
更复杂的 PEP 440 区间**不支持**：构建期校验直接拒绝，避免"声明了却判不准"。

**声明的真源与交叉校验（防声明漂移）**：
`manifest.json.requires` 是**运行时判定输入**（随代码走）；`plugin-package.json.deps` 是**构建期实测**
（扫描 `backend/**/*.py` 的 import 生成，已有）。出包工具新增校验 **C-10**：实测结果必须被声明覆盖
（实测有、声明无 → **拒绝出包**，提示补声明；声明有、实测无 → 警告，可能是条件导入）。既有 C-4
依赖白名单校验保留不变。

**展示面（同一份判定结果，四处复用）**：

| 位置 | 内容 |
| --- | --- |
| 后台「插件管理」→「已安装依赖」清单（D-7） | 本机依赖全量清单，分类显示**名称 + 版本**：① 框架包（`numpy` / `openpyxl` / `cryptography` …，读已安装依赖清单）② 外部程序组件（LibreOffice / Chrome：已装 + 版本 + 路径，或"未装"）③ 插件自带（如 `knowledge-base` 的 vendor 引擎） |
| 插件列表（插件总览） | 每行基本信息之外新增「依赖需求」列：**逐依赖一个徽标**——满足 = 绿色，不满足 = **红色带 ×**（如 `numpy ✅`、`libreoffice ❌×`）；悬停/展开显示「声明要求 vs 实际版本」与缺失原因 |
| 后台顶部汇总 | `可运行 N / 降级 M / 不可运行 K`；不可运行项给出缺失清单与修复指引（装依赖组件 / 升级主体） |
| 首页工具卡片 + 接口 | 不可运行插件卡片不出现、降级插件显示角标（同 `plugin_errors` 口径，`HANDOFF.md` §4 P1-13）；`GET /api/admin/plugins` 每项增补 `deps: {status, missing[], detail[{name, kind, require, actual, state}]}`，`GET /api/admin/deps` 返回已安装依赖清单，`GET /api/<id>/status` 增补 `deps` 段（11 个后端插件中已有端点的 10 个补齐，缺的按 B-4 补上） |

**已安装依赖清单**（"当前已安装的依赖及版本"的真源）：构建期由 `build-deploy.ps1` 生成
`config/installed-deps.json`（`{generated_at, python, packages:{name: version}}`，来源为打包解释器的
`importlib.metadata`），随主包分发、随主体升级更新；现场只读该文件即可展示，无需 `pip`
（冻结 exe 运行时不带 pip，且 `_internal` 内的 `.dist-info` 不保证完整）。
S3 落地后，依赖组件（`<程序目录>/runtime/pylibs/`）自带一份 `manifest.json` 声明其名称与版本，
判定时与主清单合并展示。

**规范增量（拟并入《插件设计规范.md》下一版）**：

| 编号 | 级别 | 条款 |
| --- | --- | --- |
| M-4 | 应当 | manifest 新增 `requires` 字段（三类依赖：框架包 / 自带 vendor / 外部程序），语义同本文 §5.3；未声明视为无第三方依赖 |
| U-7 | 必须 | 声明必须覆盖后端实际 import 的第三方包与 `backend/vendor/` 内容（构建期 C-10 强制），并如实标注 `required`；声明缺项即拒绝出包 |
| B-4 修订 | — | `GET /api/<id>/status` 返回体增补 `deps` 段（三类依赖可用性），供后台汇总 |
| B-7 重申 | — | 禁止 import 其他插件后端模块的禁令**不变**（唯一例外仍是 admin 的会话工具）；**明确禁止**把另一个插件声明为依赖（本文 D-9）；新增构建期 C-11 扫描拦截 |
| S-9 | 应当 | `backend/vendor/` 内的自带依赖需在 `requires.vendored` 登记名称与版本 |

### 5.4 插件间独立：两处遗留协作的修补（D-9）

**规则**：插件之间**互不依赖**——不得 import 其他插件的模块（规范 B-7 禁令不变）、不得声明"依赖另一个插件"、
不得在后端调用其他插件的接口。协作需求的正规出口只有两个：把能力**提升为主体模块**，或**合并为一个插件**。

**现状两处遗留协作，全部修补消除**：

| # | 遗留协作 | 现状证据 | 修补方式 |
| --- | --- | --- | --- |
| 1 | `trajectory-sketch` 后端调 `file-filter` 的 `/api/file-filter/apply` | `plugins/trajectory-sketch/backend/filter_bridge.py:50-54`（进程内 `test_client` / 回环 `requests` 双路），并读 `config/tools.json` 判断对方是否启用（`:72-90`） | **在该插件下自带一份同样的过滤实现**：把过滤算法与后处理规则（`keep_columns` / `post_rules`）落到 `trajectory-sketch/backend/` 内，删除 `filter_bridge.py` 的 HTTP 路径与 `tools.json` 读取；两处为**同源副本、各自独立演进**（不保证一致，见 RK-12） |
| 2 | `notice-board` 前端调 `/api/admin/org-tree` | `plugins/notice-board/frontend/app.js:68` | **不复制**（组织架构数据在 `admin.json` + `.admin_key` 加密，复制会把密钥处理带进业务插件，违背 SEC-2 精神）：把组织架构树**提升为主体 API** `/api/org/tree`——admin 在 `register(app)` 时经 `jz_api` 注册 provider、主体暴露路由，notice-board 改调主体路由（与 S0 的依赖倒置同一条思路） |

**修补后的状态**：仓库内**零跨插件调用**（后端 import / HTTP / 前端三处均无）；新增跨插件依赖由构建期
C-11 扫描 `backend/**/*.py` 的 `jztools_<其他 id>` import 拦截（§7 #20）。

**为什么"副本"优于"引用"**（第 1 条）：仓库已有先例——`file-filter/backend/bg_image.py` 与
`trajectory-sketch/backend/bg_image.py` 是完全相同的两份副本（注释写明"因 B-7 禁 import 而复制"）。
本次沿用同一做法：代价是副本可能漂移（RK-12），收益是两插件可各自独立升级、互不牵连。

**改动成本与验收**：第 1 条含后端改动 → 递增 `manifest.version`（U-1）并重启；第 2 条含前端改动 →
递增入口页 `?v=N`（F-2）。功能等价性由 AC-22 验收。

## 6. 主体升级流程（解耦后）

```
[开发机] build-deploy.ps1 ──► JZToolsHub-v<新版本>.zip（不含业务插件）
   │  组装：exe + _internal + static + config 模板 + plugins/admin + 脚本 + 文档
   │  自检：包内 plugins/ 仅含核心插件白名单；模板/依赖/清理规则同步
   ▼
[目标机] 一键安装.bat ──► install.ps1
 ① 定位目标目录（注册表 → %LOCALAPPDATA% → -InstallDir）与数据根（指针）
 ② 只读校验：源包结构（exe/version.json）、主体版本、可写性
 ③ 停服（仅当本来在运行；记录 was_running）
 ④ 【新增】备份主体 → 数据根 backups\app\<旧版本>-<时间戳>.zip
     内容：exe + _internal + static + config 模板 + 脚本 + version.json
     不含：plugins\（属插件）、不含数据根（用户数据）
     保留最近 1 份（_internal 约 235 MB，压缩后约 120 MB —— 体积换可回滚，见 §9 RK-7）
 ⑤ 覆盖式替换主体文件；源包无 plugins\<id>\ 的插件 → 目标机该目录与其登记**一律不动**
 ⑥ admin 走**与业务插件相同的防回退判定**：登记版本更高则跳过覆盖（已单独升级的 admin 不被回退）；
     未单独升级时随主体更新并校正登记。其余插件登记不动
 ⑦ 启动（仅当 was_running）→ 版本与依赖门控（§5.2 / §5.3）
     → 冒烟：/api/tools 200 + 各已加载插件 /status
 ⑧ 后台「插件管理」呈现：已装 N / 需升级 M / 不可运行 K（含依赖未满足的红 × 项）
     —— M/K 项分别给出共享盘、上传、装依赖的入口
```

回滚：`install.ps1 -Rollback`（S1 新增）= 停服 → 解压最近一份主体备份覆盖 → 启动 → 冒烟。
插件不受影响（备份不含 `plugins/`），回滚后已升到更高 `api_version` 的插件会被门控标记（§5.2），不会崩。

### 11.2c 真机缺陷修复：外部组件探测必须与插件同口径（2026-09-20）

**现象**（真机反馈）：目标机已安装 LibreOffice（数据根 `plugins/knowledge-base/config.json` 里
`pdf.soffice_path = D:\LibreOffice\program\soffice.exe`，文件确实存在），但后台仍把 knowledge-base
标为「降级」。

**根因**：`jz_deps._probe_external()` 只查了「环境变量 `XHR_SOFFICE` → 程序目录 `runtime/libreoffice/**`」，
**没有读插件配置里显式指定的 `office.soffice_path` / `pdf.soffice_path`**——而那一档是知识库插件
（`office_render._configured_soffice()`）**优先级最高**的解析来源。于是出现"插件能用、徽标报缺失"的
**假降级**：插件侧 `soffice_available()` 返回 `True`，框架侧却判 `missing`。

**修复**：`jz_deps` 新增 `_configured_soffice_paths(app_dir, plugin_id)`，与 `office_render` 同口径
（数据根 `plugins/<id>/config.json` 优先 → 程序目录插件目录；`office.*` 新键优先 → 兼容 `pdf.*`），
并插到探测链的**第二档**（环境变量之后、随包副本之前）。修复后实测：插件 `soffice: True` 与
框架 `status: ok` 一致。

**教训（写进纪律）**：**判定的探测逻辑必须与被判定方的实际解析逻辑逐档对齐**，否则会产生
"假降级"——它比"漏报"更糟：管理员会照着错误提示去重复安装已经装好的组件。
新增任何 `external` 探测时，先读被依赖方（插件/组件）的解析代码，把它的候选路径按同样优先级复刻。
