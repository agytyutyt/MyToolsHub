## 1. 参与者与「什么该共享」

通过二维码视频交换数据的实现共四处（+ 一个 APP 端）：

| 实现 | 角色 | 代际 |
| --- | --- | --- |
| `plugins/trajectory-convert/backend/routes.py` | 编码 | **v1-only** |
| `plugins/map-marker/frontend/generate_qr_stream.py` | 编码（离线生成脚本） | **v1-only** |
| `plugins/info-transfer/backend/routes.py` | 编码 + 解码 | v1 + v2（`PROTOCOL_V2` 开关，:230） |
| `plugins/qr-video-decode/backend/routes.py` + `frontend/worker.js` | 解码 | v1（Python 侧消费前端解出的分块）+ v2（JS 侧解析 `JZ2`） |
| `android-app/InfoParse/.../protocol/Jz2.kt` | 解码（APP） | v2 |

- **插件之间零依赖**（规范 B-7 / C-11）：协议是**唯一**该共享的东西，共享的形式是**本文 + 测试向量**，不是代码。四份实现继续各自存在、各自出包、各自升级（报告 §六 已撤回「合并」建议）。
- **改协议的义务**：改动 §2/§3/§5 任何字段 = 一次跨端变更，必须四处同步 + 重生成 `testdata/protocol/` 向量 + 跑一致性台架。只改一端会**静默坏**（解码端只会报「帧头不合法」或读出错位数据），这正是本文存在的理由。

## 2. v1 帧头（base64 三段）

一码的载荷文本 = `prefix(12 字符) + data(base64)`：

| 段 | 位置 | 原始字节数 | base64 后 | 含义 |
| --- | --- | --- | --- | --- |
| 帧序号 | 0–3 | 3 | 4 字符 | 当前帧索引（FEC share 索引） |
| 总帧数 | 4–7 | 3 | 4 字符 | 总帧数 `nframes` |
| FEC 参数 | 8–11 | 2（`k<<8 \| m`） | 4 字符 | `k`=原始分块数、`m`=含冗余的总块数 |

- 常量：`SIZE_INDEX = 3`（头字段字节数）、`SIZE_PREFIX = 4`（3 字节 → 4 base64 字符）、`SIZE_DATASIZE = 4`（数据段前的 4 字节大端长度前缀）、`BYTE_ORDER = "big"`。
- **数据段**（第 12 字符之后）base64 解码后 = `原始数据长度(4B 大端) + 该块字节`；重组后按长度前缀截断（多余零填充丢弃）。
- 压缩：v1 **只有 zlib**，标记在 JSON 信封里（`zip: 1`），不在帧头。

## 3. v2 `JZ2` 二进制帧（帧头 21 字节，全大端）

`帧 = 头(21B) + meta + payload`

| 偏移 | 长度 | 字段 | 取值 / 含义 |
| --- | --- | --- | --- |
| 0 | 3 | `magic` | `b"JZ2"` |
| 3 | 1 | `version` | `2`（`JZ2_VERSION`） |
| 4 | 1 | `flags` | 见下 |
| 5 | 3 | `seg_index` | 段索引 |
| 8 | 3 | `seg_count` | 段总数 |
| 11 | 2 | `meta_len` | meta 字节数 |
| 13 | 4 | `body_len` | payload 字节数 |
| 17 | 4 | `crc32` | 见 §3.3 |

### 3.1 flags 位义

| 位 | 名称 | 值 | 含义 |
| --- | --- | --- | --- |
| bit0–1 | 压缩算法 | `0`=none / `1`=zlib / `2`=xz(LZMA2) | `JZ2_COMP_NONE/ZLIB/XZ`（`routes.py:236-238`） |
| bit2 | rebuild | `0x04` | `0`=exact（字节一致）/ `1`=rebuild（内容等价重建，如 docx→结构化文本） |
| bit3 | FEC | `0x08` | `0`=信封帧（envelope）/ `1`=FEC share 帧 |

- 设计稿里「mode(1B)」独立字节**未落地**，rebuild 语义挤在 bit2 —— 记为现状，不要按设计稿实现。

### 3.2 meta 形状（按帧类型二选一）

- **信封帧**（bit3=0）：`fmt(1B) + orig_len(4B) + name_len(2B) + name + ext_len(1B) + ext`
  `fmt` 枚举：`text=0 / markdown=1 / word=2 / excel=3 / file=4`（`JZ2_FMT_CODES`）。
  `orig_len` 除写入 meta 外，解码端还会对还原后的长度做**二次校验**。
- **FEC share 帧**（bit3=1）：`k(1B) + m(1B)`。

### 3.3 CRC32 覆盖范围（易错点，逐字照做）

```
crc = zlib.crc32( 头的前 17 字节 + meta + payload ) & 0xFFFFFFFF
```

- **参与**：`magic/version/flags/seg_index/seg_count/meta_len/body_len`（偏移 0–16）+ 完整 meta + 完整 payload。
- **不参与**：crc 字段自身（偏移 17–20）——计算时它是「尚未拼接」状态，**不是置零参与**。
- JS 端同口径（多项式 `0xEDB88320`），实现见 `frontend/worker.js:121-124`，独立参考实现见 `tools/e2e/qrvd-v2-frame-e2e.js`。

### 3.4 压缩与分派

- 编码端对 payload 试算 none/zlib/xz，**取最小者**；xz 失败按 fail-open 退到 zlib（`routes.py:1255-1287`）。
- 解码端按 `flags & 0x03` 分派；**未知算法值必须报错**，不得静默当 none。
- 能力差异（合法）：`worker.js` 目前只支持 none+zlib，遇到 xz 或 rebuild 返回**能力限制**而非崩溃；Python 端三者齐全。

## 4. FEC 与分块规则

- 使用 `zfec`（k-of-m 擦除码）。**`k`/`m` 不是常量、也不由帧头布局决定**：由编码器按计划算出后**写进帧头**——v1 写第 3 段（`k<<8|m`），v2 写 share 帧的 `meta`（`k(1B)+m(1B)`）。解码端**只读帧头**。
- 参数推导（info-transfer `_fec_plan` :1776-1787、trajectory-convert `_fec_plan` :588-599，两端同构）：`target = ceil(size/(1-FEC_RATIO))` → `nblocks = ceil(target/256)` → `blocksize = ceil(target/nblocks)`，**`blocksize ≥ 256` 时 `nblocks += 1` 重算**（§6.1 修法①），最终 `m = blocksize`、`k = 补齐后长度 // nblocks`。上限常量 `MAX_FEC_M = 256` 只用于分组除法，**写进帧头的 `m` 恒 ≤ 255**。
- 零填充：尾块补 `b"\0"`；重组后按 4B 大端长度前缀截断。
- 载荷预算：
  - v1：`int(maxchunksize/4)*3`（保证 base64 反解无padding），info-transfer 再乘 `PAYLOAD_SAFETY`；
  - v2：`cap = byte_capacity - 21 - meta_len` 后取 `int(cap * PAYLOAD_SAFETY)`（v2 是二进制，不做 3 对齐）。

### 4.1 编码端本地调参空间（**不属互操作面**）

以下参数各端可不同，**解码端不感知**，不得当成 bug 去「修平」：

| 参数 | 各端现值 | 为什么允许分叉 |
| --- | --- | --- |
| `PAYLOAD_SAFETY` | **仅 info-transfer = 0.9**（:217）；其余端无此概念 | 只收紧**编码端**分块大小；解码从帧头读 `seg_n/k/m`，保守分块不影响重组。动因：高熵满载荷在部分解码器上整码失败（cv2 回读实测） |
| `FEC_RATIO` | trajectory-convert `0.1`（:60）；info-transfer `0.4`（:206） | 冗余度按传输介质风险自定（表格离线导出 vs 相机翻拍视频）；`k/m` 随帧头下发，互操作不受影响 |
| `BOX_SIZE` / `FRAMERATE` / 每码重复帧数 | 各端自定（如 it `BOX_SIZE=10`、traj `=8`；it `CAMERA_FRAME_REPEAT=5`） | 纯渲染/视频面，不进协议 |
| 二维码 `version`/纠错等级 | 各端自定，但必须与它申报的 `byte_capacity` 自洽 | 容量决定分块，分块结果进帧头 |

## 5. 版本字段与兼容策略

- **代际判别**：内容前 3 字节是否 `b"JZ2"`（`routes.py:1595` 等多处；JS `worker.js:163-167`）。是 → v2，否 → v1。
- **v2 内版本**：`frame[3] != 2` → **直接拒绝**并抛「JZ2 协议版本不受支持」（`routes.py:1429-1430`、`worker.js:111`）。**没有降级路径**——新增版本必须同步升级所有解码端，或另行设计协商。
- **v1 仍在使用**：trajectory-convert 与 map-marker 只产 v1；info-transfer 可 `PROTOCOL_V2=False` 回退出 v1；qr-video-decode 对两代通用。故**任何 v1 面的改动同样是跨端变更**。

### 6.1 建档时发现的互操作缺陷①：`m = 256` 时 FEC 参数申报溢出（**已实施（2026-10-09，commit fe37997）**）

> 以下「现象 / 后果 / 复现条件 / 三端分叉」为**修复前**史实保留；修法见本节末。

- 现象（修复前）：帧头第 3 段用 `(k << 8) | m` 表示 k/m，`m` 实际只有 8 位可用；但 `MAX_FEC_M = 256` 允许 `m = 256`。此时进位吃掉 k：例如 `k=230, m=256` 编码后，解码端读出的是 `k=231, m=0`。
- 后果（修复前）：该次传输**整体失败**（`validate_payload` 判「zfec 参数 k/m 非法」；直接进 `reassemble` 则 `nblocks = nframes // m` 除零）。
- 复现条件（修复前，实测）：trajectory-convert（`FEC_RATIO=0.1`）在 v15/L 下，数据恰为 **230 块**（≈ 87,020–87,400 字节）时 `m` 落到 256；229 块与 231 块都正常，即**窄边界**。info-transfer（`FEC_RATIO=0.4`）在 307 块同样落到 256。
- 三端还互不相同（修复前）：`info-transfer` / `trajectory-convert` 得 `AAIA`（数值进位），`map-marker` 把 `m` 当单字节截断得 `AAEA`。
- 已采用修法（**2026-10-09 拍板 ①**；决策记录见 `docs/plan/20261009承接执行手册（面向执行模型）.md` §B-13）：编码端把 `m` 上限收到 255——
  - `info-transfer._fec_plan`（:1776-1787）与 `trajectory-convert._fec_plan`（:588-599，本次从 `_fec_encode` 抽出、与 info-transfer 同构）：推导值 `blocksize ≥ 256` 时把 `nblocks` 加一再重算，`m` 必回落 ≤ 255（复现输入 230 块 → `nblocks=2, k=115, m=128`）；
  - `map-marker/frontend/generate_qr_stream.py`：候选 `k` 上限取在 `MAX_FEC_K = 170`（该脚本 `m = k + k//2`，170 → 255），顺带堵住旧回退路径产出超大 `k/m` 的口子；
  - **帧头字节布局、`(k<<8)|m` 表示、`encode_fecinfo` 基元、解码端（`qr-video-decode`）与移动端 APP 一律未动**。未选②（第 3 段改 `k(1B)+m(1B)` 两段独立字节）——属**协议面变更**，四端 + APP 必须同步升级。
- 兼容性：修复只改变「原本必定失败」那一小撮窄边界输入的 `k/m/帧数`，能解码的旧产物不受影响，**无需重生成历史视频**（与 §6.2 相反）。
- 现状登记：`testdata/protocol/v1_headers.json → defect_m256` 已置 `status=fixed`（`cases` 保留修复前史实——低层基元直接传 `m=256` 至今仍产出被破坏的字符串，不参与断言），修复后形态在 `derivation_guard`；**台架 C6**（复现输入 230 块：帧头回读 `m ≤ 255` + 编码→解码逐字节一致）与 **C7**（traj/it 参数推导 1..4000 扫描恒不产出 `m=256` + map-marker `k` 上限生效）自此为**回归断言**。

### 6.2 建档时发现的互操作缺陷②：map-marker 生成脚本的块→组映射与解码端不同构（**已修复（2026-10-09，commit 4cb938e）**）

> 以下「现象 / 复现条件 / 后果」为**修复前**史实保留；修法见本节末。

- 现象（修复前）：`generate_qr_stream.py` 把数据块**连续**切进各组（组 g = 块 `g*k … g*k+k-1`），而 trajectory-convert / info-transfer / qr-video-decode 一律**跨步**分组（`data_list[i::nblocks]`）。
- 复现条件（修复前）：`nblocks > 1`。map-marker 的 `find_k` 刻意把 `nblocks` 推向 50–500，所以**只要数据跨多个 FEC 组就会命中**；`nblocks == 1`（小数据）时两者同构、可正常解码。
- 后果（修复前）：**静默坏**——解出的字节长度正确（4B 长度前缀仍有效），内容错位（实测 2952 字节输入在第 373 字节起错位，2232 字节不同）。这比报错更难发现。
- 该脚本头部自述「协议与 QR-transfer 兼容，生成的视频可被 qr-video-decode 插件解码」，与修复前的实现不符。
- 现状登记：`testdata/protocol/v1_roundtrip.json → known_defect_multigroup` 已置 `status=fixed`；**已转回归断言（台架 C3–C5 断言往返逐字节一致）**。
- 已采用修法：**跨步切片**（`data_list[i::nblocks]`，与其余三端同构，仅改该脚本、不动协议字段），向量同步重生成。**旧产物提示保留**——此前用旧脚本生成的视频需用新脚本重生成。

> 两处都属「只改一端会静默坏」的典型，正是本报告 C3 立项要防的问题。**缺陷②已修（2026-10-09，commit `4cb938e`）；缺陷①已按拍板的修法①实施（2026-10-09，commit `fe37997`）**——两处的台架断言都已由刻画转为回归（C3–C7），向量与本节同步回写。§6 的缺陷面自此清空，新增分叉须先改本节再动实现。

## 7. 一致性台架与测试向量

- 向量目录：`testdata/protocol/`
  - `v1_frames.json` / `v2_frames.bin` + `manifest.json`：固定输入下的标准编码帧与期望解码结果；`generate.py` 是**生成脚本**（来源与重生成方式见 `testdata/protocol/README.md`）。
  - 向量的**权威产出端 = info-transfer**（唯一同时具备 v1/v2 编解码的实现）；其余实现作为**被驱动方**产出同输入帧序列并与向量比对。
- 台架：`tools/e2e/qr-protocol-consistency.py`
  - v1：分别驱动 trajectory-convert / info-transfer / map-marker 生成脚本产帧 → 与向量比对 → 再喂给 qr-video-decode 的重组函数，断言还原输入（跨实现往返）。
  - v2：info-transfer 造帧与向量比对；解析断言覆盖 Python 端与 `worker.js`（Node 在场时经 `__qrvdTestHooks` 交叉验证，缺 Node 则明确 skip 不伪装成通过）。
  - 台架在宿主侧，不构成插件间依赖（不出包、不进 C-11 判定面）。
- **改动协议时的验收动作**：重生成向量 → 跑台架 → 更新本文 §3/§6。

## 8. 后续优化方向

1. **v1 常量形态归一**：map-marker 写字面量、qr-video-decode 缺 `SIZE_INDEX`，核对只能靠人读；建议各端补齐同名常量（仍不共享代码），使 §6 可机器比对。
2. **v2 版本协商**：当前「非 2 即拒」意味着升级 JZ2 版本会让旧解码端全量失败且报错笼统；可考虑在 meta 内申报兼容区间。
3. **`worker.js` 的 xz/rebuild 能力**：JS 端补齐 xz 与 rebuild 分派后，§3.4 的能力差异表应同步收窄。
4. **APP 端纳入核对**：`Jz2.kt` 是第 5 份实现，目前只在本文 §1 登记、未被台架驱动（无 Kotlin 运行环境）；真机验收时应加一次向量往返。
