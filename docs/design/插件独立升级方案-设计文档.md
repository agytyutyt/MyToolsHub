## 0. 一页速览

**结论：可行，且基础设施已具备。** 关键事实：

1. **插件代码与插件数据天然分离**——代码在程序目录 `plugins/<id>/`，用户数据全部经
   `jztools_data.get_data_root_dir()` 落盘到数据根目录（`%USERPROFILE%\.jztoolshub\plugins\<id>\`，
   见 `jztools_data.py:143-168`）。因此"替换插件代码"**不触碰任何用户数据**，
   这是单独升级能安全落地的根本前提。
2. **插件是纯粹的文件组合**——`manifest.json` + `frontend/` + `backend/`，
   后端由 `app.py:550 _load_backend_module()` 经 importlib 启动时加载（`app.py:573
   register_plugin_backends()`），失败隔离。所以升级 = 换文件 + 重启（R-4）。
3. **已有两套可复用的同款机制**：
   - 目标机安装器范例：`tools/offline-runtime/install-libreoffice-core.ps1`
     （定位安装目录 → 校验 → 覆盖式解压 → 自检 → `-Uninstall` / `-Force`，全程免管理员、零副作用）；
   - 版本门控同步范例：`jztools_data.sync_templates()`（`jztools_data.py:447`）+
     `install.ps1` 的 `Sync-ConfigTemplates`，都是"按版本只同步一次 + 保留用户配置"。

**方案一句话：** 新增「插件包」这第三种分发物（与主包、离线组件包并列），
由 `tools/build-plugin-package.ps1` 在开发侧产出，目标机有两条等价入口：

- **管理界面（推荐）**：超管上传 zip → 程序自动校验、备份、替换、停服重启，全程无需解压或敲命令（§9）；
- **离线脚本**：`install-plugin.ps1`（U 盘/共享盘场景，双击即可，30 秒完成并有可核验结论）（§5）。

判定、校验、备份、替换、模板补键、状态登记、回滚全部脚本化，两条入口共用同一套校验规则（§4/§5.3）。

**必须同时补的三处链路缺口**（否则单独升级会被静默破坏）：

| 缺口 | 后果 | 补法 |
| --- | --- | --- |
| 主包升级无条件覆盖 `plugins/`（`install.ps1` 整体复制） | 单独升级过的插件被**静默降级**回主包内嵌版本 | §7：`install.ps1` 增加"插件版本防回退" |
| 配置模板同步按**应用版本**门控（`jztools_data.py:447`） | 插件单独升级后新配置键**永远不下发** | §8：同步改为"应用版本 + 插件版本/模板哈希"双门控 |
| 无插件版本可观测性 | 升级前后无法核对、出错无法定位 | §5.2/§8.1 状态登记 + `-List` 体检 + 后台展示 |

| 四段覆盖 | 落点 |

## 1. 需求与边界

### 1.1 需求

| 编号 | 需求 |
| --- | --- |
| N-1 | **单插件粒度**：一次只升级一个插件，不动其它插件、不动主程序（exe/_internal）。 |
| N-2 | **离线可用**：目标机无外网，升级介质为 U 盘 / 内网共享盘，全流程不联网。 |
| N-3 | **零数据风险**：升级不得修改、删除、移动数据根目录中该插件的任何用户数据。 |
| N-4 | **可校验**：升级前能验证包完整性、目标机适用性（版本/框架版本/依赖），拒绝时**不做任何写操作**。 |
| N-5 | **可回退**：升级失败或发现缺陷时，能一条命令回到升级前状态。 |
| N-6 | **免管理员**：与既有安装/组件安装一致，普通用户权限即可完成（程序目录在 `%LOCALAPPDATA%`）。 |
| N-7 | **覆盖插件全生命周期**：新增插件（首次安装）、升级、卸载也走同一套工具与校验。 |
| N-8 | **可审计**：升级动作留痕（谁、何时、从哪个版本到哪个版本、包 sha256），可事后核对。 |

### 1.2 边界（本期不做）

| 不做 | 原因 / 替代 |
| --- | --- |
| 主程序（`JZToolsHub.exe` / `_internal/`）的增量更新 | 属主包职责，`install.ps1` 已覆盖；插件包只声明 `min_app_version`，不满足即拒绝。 |
| 公网在线更新源 / 自动检查更新 | 目标机内网离线；一期用文件介质，三期用内网共享盘索引（仍不外联）。 |
| 插件后端热重载（不重启换后端代码） | 属长期方向，见 `docs/archive/容器化与插件热插拔-评估与实施设计-v1.0-已被取代.md`（v1.0，Linux 容器前提）与现行 `docs/eval/插件热插拔-容器化改造评估.md`；本方案明确「有后端改动则重启」。 |
| 插件依赖的在线 `pip install` | 冻结 exe 运行时不带 pip；改为**依赖自包含约束**（§11 U-2），构建期强制校验。 |
| 插件间依赖解析 / 依赖安装顺序 | 现有插件彼此独立，一期不引入依赖图。 |
| 插件包数字签名（PKI） | 一期用"sha256 冻结值 + 可信介质"；签名列为三期增强（§10）。 |

## 2. 现状分析

### 2.1 已有基础（可直接复用）

| 机制 | 位置 | 对本方案的价值 |
| --- | --- | --- |
| 插件目录契约（`manifest.json` / `frontend/` / `backend/`） | 《插件设计规范》§4、§5；`app.py:390 load_manifests()` | 插件包 payload 就是该目录的快照，无需新格式。 |
| 插件后端动态加载 + 失败隔离 | `app.py:550 / 573` | 单个插件坏掉不影响整站；升级失败最坏情况是"该插件不可用"，可回滚。 |
| 插件数据一律走数据根目录 | `jztools_data.py:143-168`；各插件 `routes.py` 的 `get_data_root_dir("plugins", id, ...)` | 代码替换与数据零耦合（N-3 的保证）。 |
| 静态资源路由 `/plugin/<id>/<file>` | `app.py:659 plugin_assets()` | 前端改动**无需重启**即生效（但有 1 天强缓存，受 F-2 约束）。 |
| 后端依赖白名单（打包期 collect_all） | `JZToolsHub.spec` 的 `PACKAGES`（14 项）+ `build-deploy.ps1` §1.5 前置检查 | 是"哪些依赖可被插件使用"的现成权威清单，构建期校验据此比对。 |
| 插件目录清理规则（打包期） | `build-deploy.ps1` §3.2（删 `data/` `.task_cache/` `__pycache__/` `out/` `*.pyc` `config.json`）+ §3.2.1 模板自检 | 插件包的排除清单直接沿用，保证两条链路一致。 |
| 组件安装器范例（免管理员、可卸载、有自检） | `tools/offline-runtime/install-libreoffice-core.ps1` | `install-plugin.ps1` 沿用其骨架（`Resolve-AppDir` / `Expand-PayloadZip` / `-Uninstall` / `-Force`）。 |
| 配置模板同步（版本门控、保留用户配置） | `jztools_data.py:401 _sync_templates()` / `:447 sync_templates()` / `:357 _merge_tools()`；`install.ps1 Sync-ConfigTemplates` + `Merge-DeepKeys` | 升级后"新配置键下发"的语义已有既定实现，扩展门控条件即可（§8）。 |
| 版本防呆先例 | `build-deploy.ps1`（版本号不变即中止，`-Force` 可越过） | 插件包的"版本必须递增"校验同款思路，运维心智一致。 |
| 依赖自包含先例 | `plugins/knowledge-base/backend/vendor/`（`office_render.py:38-45` 把 `vendor/` 插入 `sys.path`） | 证明"插件自带第三方依赖"在本框架下可行，U-2 以此为标准做法。 |
| 运维动作契约 | 《插件设计规范》§11 生命周期、§12.4 速查、§13 V-1~V-7 | 升级/卸载的既有规则（先删注册条目、后备份数据、再删目录）必须被脚本遵守。 |

### 2.2 能力缺口

| 编号 | 缺口 | 影响 |
| --- | --- | --- |
| G-1 | 插件**没有分发单元**：`plugins/<id>/` 目录即代码，无"插件包"这一产物，也没有对应的构建工具。 | 每次升级只能重出整包（122 MB 级）。 |
| G-2 | 插件**版本纪律未落地**：`manifest.json.version` 自 v1 起就有（规范 V-1），但框架不消费，现实里多个插件长期停在 `1.0.0`（本次核查 16 个插件中 9 个为 `1.0.0`，且是否随改动递增无任何校验）。 | 升级判定缺依据；降级/重复升级无法识别。 |
| G-3 | **主包升级会回退插件**：`install.ps1` 把 `plugins/` 整体 `Copy-Item -Force` 到目标目录（不删多余文件），会把单独升级过的插件覆盖回主包内嵌版本。 | 单独升级的成果在下次整包升级时静默丢失——这是本方案最大的现实风险。 |
| G-4 | **配置模板同步按应用版本门控**：`sync_templates()` 只在 `version.json.app` 变化时执行。插件单独升级不改应用版本 → 插件新配置键永不下发，用户配置实际"缺键"。 | 插件升级后功能异常且难排查。 |
| G-5 | **前端强缓存**：`/plugin/` 下 `.js/.css` 下发 1 天强缓存，`.html` no-cache（规范 F-2）。升级后若未递增 `?v=N`，用户长期看到旧前端。 | "升级了但没变"的假故障。 |
| G-6 | **无插件版本可观测性**：站内看不到插件当前版本/上次升级时间/数据占用；运维无 `-List` 式体检。 | 升级前后无法核对，出事无法定位。 |
| G-7 | **依赖边界不可见**：插件能用哪些第三方库，只体现在 spec 的 `PACKAGES` 里；插件作者新增一个 import，开发机上（有全量 site-packages）一切正常，目标机上才 `ImportError`。 | "能跑通本地、到现场挂"的典型故障。 |

### 2.3 三条不可违反的底线（后续所有设计以此为准）

> **底线一（数据零触碰）**：升级流程只允许写程序目录 `plugins/<id>/`、数据根目录的
> `backups/` 与状态文件；**禁止**读写数据根目录 `plugins/<id>/` 下的任何内容（只读校验也不做）。
>
> **底线二（先校验后写入）**：任何拒绝判定（版本、哈希、框架版本、路径安全）必须发生在
> 第一次写操作之前；拒绝时目标机现场与升级前逐字节一致。
>
> **底线三（可回退）**：每次升级前必须留下同一份可用于回滚的完整旧版快照；
> 没有备份成功的升级一律视为失败并中止。

## 3. 方案总览

### 3.1 三阶段演进

| 阶段 | 形态 | 交付物 | 需要改应用代码 | 适用 |
| --- | --- | --- | --- | --- |
| **阶段一** | 离线脚本升级（本次核心） | `tools/build-plugin-package.ps1`（开发侧）+ `tools/plugin-upgrade/install-plugin.ps1`（目标机侧，随包分发） | 极少：仅两处链路补强（`install.ps1` §7、`jztools_data.py` §8），不动插件框架运行时 | 现场运维（U 盘 / 共享盘拷贝后双击） |
| **阶段二** | 应用内升级（管理后台） | admin 插件新增「插件管理」页 + 4 个接口 + 自重启编排 | 是 | 管理员拿到包后从浏览器上传安装 |
| **阶段三** | 批量与索引 | 共享盘 `index.json` + 一键检查/批量升级 + （可选）包签名 | 是 | 多台机器、多插件统一运维 |

阶段一不依赖任何应用侧新功能即可独立交付；阶段二是同一套校验规则的服务端实现
（规则单点定义在 §4，两处实现必须一致）。

### 3.2 三种分发物的定位

```
JZToolsHub-v1.9.0.zip                      ← 主包：exe + _internal + 全部插件 + 框架（约 122 MB）
JZToolsHub-离线组件-LibreOffice核心-*.zip   ← 离线组件包：外部程序（Chrome / LibreOffice），随需安装
JZToolsHub-插件-<id>-v<version>.zip        ← 插件包（本方案新增）：单个插件的代码快照（通常 < 10 MB）
```

三者互不越界：插件包**永不**包含 exe、`_internal/`、`runtime/`（外部组件）、
`config/tools.json` 全文（只带注册片段）。

### 3.3 升级一次到底发生了什么

```
[开发机]  build-plugin-package.ps1 ──► 插件包.zip (+ .sha256 旁挂)
                │  取源：部署目录或仓库工作区（含未入库的交付资产）
                │  校验：id 一致 / 版本递增 / ?v=N 递增 / 依赖白名单 / 排除运行态数据
                ▼
[介质]    U 盘 / 内网共享盘（离线）
                ▼
[目标机]  安装插件.bat ──► install-plugin.ps1
   ① 定位程序目录（注册表 InstallLocation → %LOCALAPPDATA%\JZToolsHub → -InstallDir）
   ② 只读校验：包结构 / schema / sha256 / 本机插件版本 / min_app_version / 升级路径
   ③ 停服务（仅当它本来在运行；记录 was_running）
   ④ 备份旧版插件目录 ──► 数据根 backups\plugins\<id>\<id>-<旧版本>-<时间戳>.zip
   ⑤ 替换代码：按清单删除"旧版有、新版无"的文件，覆盖写入新文件
   ⑥ 登记状态：config\.app_state.json → plugins.<id> = {version, code_sha256, ...}
   ⑦ 启动服务（仅当 was_running）→ 冒烟：GET /api/<id>/status 与 /api/tools
   ⑧ 应用启动时（§8）：插件级模板补键（ensure-keys）自动执行
                ▼
[结论]    控制台打印：旧版本 → 新版本 / 文件增删改统计 / 备份路径 / 回滚命令 / 自检结果
```

## 4. 插件包规范（新增契约）

### 4.1 包结构

产物文件名：`JZToolsHub-插件-<id>-v<version>.zip`

```
JZToolsHub-插件-knowledge-base-v1.1.0.zip
├── plugin-package.json          # 【必须】包清单（机器可读，字段见 4.2）
├── SHA256SUMS                   # 【必须】逐文件校验清单（payload 内所有文件，格式同规范 S-6）
├── 升级说明.md                   # 【必须】人工可读：变更点 / 是否需重启 / 回滚方法 / 已知限制
├── 安装插件.bat                  # 【必须】双击入口（调用同目录 install-plugin.ps1）
├── install-plugin.ps1           # 【必须】目标机安装器（构建时从仓库 tools/plugin-upgrade/ 原样拷贝）
└── payload/
    └── plugins/<id>/            # 【必须】插件目录快照（已剔除运行态数据，规则见 4.4）
        ├── manifest.json
        ├── README.md
        ├── frontend/…
        └── backend/…
```

包旁挂 `JZToolsHub-插件-<id>-v<version>.zip.sha256`（zip 本体的 sha256，供介质传递后核对）。

> **payload 路径必须严格等于 `payload/plugins/<id>/`**，且包清单 `id` 与
> `manifest.json.id`、目录名三者一致（规范 M-3 / R-1）。安装器据此拒绝任何形状不符的包，
> 从根上避免"解压到错误位置"。

### 4.2 `plugin-package.json` 字段定义

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `schema` | ✅ | 固定 `1`。后续不兼容变更时递增，安装器拒绝未知主版本。 |
| `kind` | ✅ | 固定 `"plugin-upgrade"`（与离线组件包等区分）。 |
| `id` | ✅ | 插件 ID，必须匹配 `^[A-Za-z0-9_-]+$` 且与目录名/manifest 一致。 |
| `version` | ✅ | 本包版本（= `manifest.json.version`，构建时硬校验相等）。 |
| `upgrade_from_min` | — | 允许直升的最低本机版本（含）。低于它必须先升到中间版本（防跳版）。缺省不限制。 |
| `upgrade_from_max` | — | 允许直升的最高本机版本（含）。高于它属降级，拒绝（`-Force` 可越过）。缺省不限制。 |
| `requires_restart` | ✅ | 后端或 manifest 有改动为 `true`；纯前端包为 `false`（构建时自动判定，可用 `-RequiresRestart` 覆盖）。 |
| `min_app_version` | — | 要求的主程序最低版本（读目标机 `version.json.app`）。不满足即拒绝，提示先升主包。 |
| `built_at` / `built_from` | ✅ | 构建时间与源码溯源（`{commit, dirty}`，与 `build-deploy.ps1` 的 version.json 溯源字段同款）。 |
| `python` | — | 构建机解释器版本（信息性）。 |
| `tools_entry` | — | 新插件首次安装时写入 `config/tools.json` 的注册条目（`{id,name,description,category,enabled,order}`）。**安装器只在"全新安装"时消费它**：目标机已有该插件时一律忽略（避免覆盖现场已调整的启停/排序/文案），确需更新文案用 `-UpdateEntry` 显式要求。 |
| `config_templates` | — | 需要下发的配置模板清单：`[{src, dst, mode}]`，`mode ∈ {ensure-keys, overwrite}`（语义同 `jztools_data._TEMPLATE_SYNC`）。默认按包内实测自动生成。 |
| `deps` | ✅ | 依赖声明（构建期扫描自动生成，人工复核）：`{stdlib_only, vendored:[…], framework_packages:[…]}`。 |
| `code_sha256` | ✅ | payload 代码指纹：对"SHA256SUMS 中每行 `相对路径\0sha256`"按字典序拼接后再取 sha256。用于状态登记与升级前后比对。 |
| `size_bytes` / `file_count` | ✅ | payload 体积与文件数（拒绝异常大包时可人工核对）。 |

> `files` 清单**不**放进 `plugin-package.json`——文件级明细只在 `SHA256SUMS` 中维护一份，
> 避免两处漂移；安装器同时消费两者（前者元数据、后者文件清单）。

### 4.3 `SHA256SUMS` 格式

沿用规范 S-6 的既有形态，一行一个文件，路径相对 payload 根、一律 `/` 分隔、按字典序：

```
a1b2c3…  plugins/knowledge-base/frontend/app.js
d4e5f6…  plugins/knowledge-base/manifest.json
```

### 4.4 打包排除规则（代码与数据的边界）

**排除**（命中即剔除，构建后打印被剔除清单供审计）：

| 类别 | 模式 | 依据 |
| --- | --- | --- |
| 运行态数据 | `data/`、`.task_cache/`、`out/`、`*.log` | 规范 S-3；`build-deploy.ps1` §3.2 同款 |
| 本机配置（含密钥） | `config.json`（精确名）、`config.local.json`、`.env` | 规范 S-3；注意**模板不叫 config.json**（命名纪律，见 `jztools_data.py:74`） |
| 构建产物 | `__pycache__/`、`*.pyc`、`*.pyo`、虚拟环境、`node_modules/` | 规范 S-4 |
| 开发杂物 | `*.tmp`、`*.bak*`、`*.orig`、`.DS_Store`、`Thumbs.db` | — |

**保留**（即使未入库 git 也必须进包）：`frontend/` 下的视频、字体、地图数据等交付资产
（例：`plugins/map-marker/frontend/*.mp4`、`yunfu*.json` 均被 `.gitignore` 忽略但属交付物）。
**因此取源优先级为 `-From <dir>` > 部署目录 `deploy\<DeployName>\plugins\<id>` > 仓库工作区
`plugins\<id>`，且禁止用 `git archive` 生成 payload。**

**必须有**：`manifest.json`、`frontend/<entry>`（entry 指向的文件真实存在）、`backend/__init__.py`
（若有 backend）、`backend/routes.py`、`README.md`（规范 S-5）。

**只读随包资产必须保留**：插件目录内的只读数据文件属于交付资产，随包保留——
例：`plugins/case-report/backend/org_units.json`（只读，`case-report/backend/routes.py:152`
仅以 `"r"` 打开）必须进包，不得被排除规则误伤。

> **关于"插件目录里会不会有运行时数据"**：若干插件的代码里存在"`jztools_data` 不可用时
> 回退到模块目录"的兜底分支（`trajectory-sketch/backend/config_store.py:59`、
> `knowledge-base/backend/office_render.py:86`、`trajectory-sketch/backend/report_store.py:41`）。
> 该分支只在源码开发环境生效；部署形态（冻结运行，`jztools_data` 始终可用）下运行时数据
> 一律进数据根目录，插件目录是纯代码。**"插件目录整体可替换"据此成立**；
> 但为了留出安全余量，替换阶段采用三分法而非简单覆盖（见 §5.2.2 阶段 D）。

### 4.5 版本纪律（本方案成立的前提）

1. `manifest.json.version` 是插件版本的**唯一权威**（`plugin-package.json.version` 与它相等是硬校验）。
2. 语义化版本，含义同规范 V-1（修订=修复 / 次版本=兼容增强 / 主版本=不兼容）。
3. **任何对外发布的插件改动都必须递增版本**——由构建工具强制（同 `build-deploy.ps1` 的
   版本防呆理念：同号重打需显式 `-Force`，且会打印警告）。
4. 纯前端改动同样必须递增（它与 F-2 的 `?v=N` 递增是两个独立动作：前者管"版本判定"，
   后者管"缓存失效"，构建工具**两个都校验**）。
5. 主包升版时把已单独升级的插件内容并入主包（§7），保持两处版本一致，避免版本漂移。

## 5. 阶段一：离线单插件升级（核心交付）

### 5.1 目标机操作手册（人工口径）

```
1. 从介质取到 JZToolsHub-插件-<id>-v<新版本>.zip 与同名 .sha256 旁挂文件
2. （可选但推荐）先体检：powershell -ExecutionPolicy Bypass -File install-plugin.ps1 -List
3. 解压 zip 到任意临时目录
4. 核对 zip sha256（certutil -hashfile <zip> SHA256 与旁挂文件比对）
5. 双击「安装插件.bat」（内部以 -ExecutionPolicy Bypass 调用 install-plugin.ps1）
6. 阅读控制台结论：版本变化 / 文件统计 / 备份路径 / 自检结果
7. 浏览器 Ctrl+F5 强刷一次（前端强缓存，规范 F-2）
```

出问题时：`双击「安装插件.bat」` 无参数是"安装包"，**回滚**用
`powershell -ExecutionPolicy Bypass -File install-plugin.ps1 -Rollback <id>`。

### 5.2 `install-plugin.ps1` 设计

#### 5.2.1 命令面

```powershell
# 安装 / 升级（包在同目录或 -Package 指定）
powershell -ExecutionPolicy Bypass -File install-plugin.ps1 [-Package <zip|目录>]
# 体检：列出全部插件的 程序目录版本 / 状态登记 / 备份 / 数据占用
powershell -ExecutionPolicy Bypass -File install-plugin.ps1 -List
# 只演算不落盘：打印将发生的增/删/改/重启判定/备份路径
powershell -ExecutionPolicy Bypass -File install-plugin.ps1 -DryRun
# 回滚到最近一次升级前
powershell -ExecutionPolicy Bypass -File install-plugin.ps1 -Rollback <id> [-BackupFile <zip>]
# 卸载插件（遵守规范 §11：先删/停注册条目 → 备份数据 → 再删目录；数据默认保留）
powershell -ExecutionPolicy Bypass -File install-plugin.ps1 -Uninstall <id>
# 覆盖开关
-Force              # 越过"同版本/降级/upgrade_from 区间"限制（仍强制校验 sha256）
-ExpectedSha256 <h> # 包本体哈希（与旁挂文件/发布记录核对）
-InstallDir <dir>   # 指定程序目录（默认自动探测）
-NoStart            # 升级后不自动启动服务
-Hot                # 不停服务（仅当 requires_restart=false 时允许，见 5.7）
-PurgeUnknown       # 删除"新旧清单都没有"的未知文件（默认保留并列出，见阶段 D）
-UpdateEntry        # 升级时也用包内 tools_entry 更新注册条目的名称/描述/排序（默认忽略）
-PruneBackups [n]   # 只保留最近 n 份备份（默认 3）
```

#### 5.2.2 执行流程（伪代码）

```powershell
# ---------- 阶段 A：定位与只读校验（对目标机目录绝不写盘；仅解包到 %TEMP% 暂存）----------
$appDir  = Resolve-AppDir                       # 注册表 InstallLocation → %LOCALAPPDATA%\JZToolsHub → -InstallDir
$pkgRoot = Expand-ToTemp $Package               # zip 解到 %TEMP%\jz-plugin-<id>-<ts>\
$meta    = Read-Json "$pkgRoot\plugin-package.json"
Assert ($meta.schema -eq 1 -and $meta.kind -eq "plugin-upgrade")
Assert ($meta.id -match '^[A-Za-z0-9_-]+$')
Assert (Test-Path "$pkgRoot\payload\plugins\$($meta.id)\manifest.json")
Assert (Read-Json manifest).id -eq $meta.id -and .version -eq $meta.version
Assert (-not $ExpectedSha256) -or ((Get-FileHash $Package).Hash -ieq $ExpectedSha256)

$installedVer = (Read-Json "$appDir\plugins\$($meta.id)\manifest.json").version   # 不存在则 $null（全新安装）
$appVer       = (Read-Json "$appDir\version.json").app
$state        = Read-Json "$dataRoot\config\.app_state.json"                        # 只读

Assert-VersionRules $installedVer $meta $state      # 见 5.3 判定矩阵（唯一拒绝点集中在此）
Assert-AllFilesHash $pkgRoot                        # SHA256SUMS 逐文件校验（不通过即中止）
Assert ((-not $Hot) -or (-not $meta.requires_restart)) "该包含后端改动，-Hot 被拒绝（见 5.7）"

# ---------- 阶段 B：停服务 ----------
$wasRunning = $null -ne (Get-Process -Name JZToolsHub -EA SilentlyContinue)
if ($wasRunning -and -not $Hot) { Stop-JZService }
if ($Hot) { Warn "热升级：仅替换前端文件，页面需 Ctrl+F5" }

# ---------- 阶段 C：备份（底线三：升级必先备份）----------
$backupDir = "$dataRoot\backups\plugins\$($meta.id)"
if ($installedVer) {                                # 升级：备份旧代码目录
    Compress-PluginDir "$appDir\plugins\$($meta.id)" "$backupDir\$($meta.id)-$installedVer-$ts.zip"
    Assert (Test-Path "$backupPath") "备份失败 → 中止，不做任何替换"
} else {                                            # 全新安装：备份将要被合并的 tools.json
    Copy-Item "$dataRoot\config\tools.json" "$backupDir\tools.json-$ts.bak"
}

# ---------- 阶段 D：替换代码（只动 plugins\<id>\；三分法，不盲目覆盖）----------
$newFiles = Parse-Sha256Sums $pkgRoot               # 新版清单（相对 payload 根）
$oldFiles = Get-ChildItem -Recurse -File "$appDir\plugins\$($meta.id)" |
              Select-Object -Expand RelativePath   # 目标机现存文件
$baseFiles = if ($backupPath) { Read-ZipEntryList $backupPath } else { @() }   # 升级前基线（备份 zip）
foreach ($f in $oldFiles) {
    $rel = Strip-ToPayloadRelative $f                # plugins\<id>\frontend\old.js → payload 相对
    if ($newFiles -contains $rel) { continue }        # 新版仍有 → 由下方覆盖
    if ($baseFiles -contains $rel) {
        Remove-Item -Force $f                         # ① 旧版有、新版无 → 删除（防陈留旧模块被 import）
    } else {
        $unknown += $f                                # ② 两版都无 = 用户/第三方放进来的文件
    }
}
if ($unknown) {
    # 默认保留并列出；确认确属废弃残留后才允许清理（-PurgeUnknown）
    Warn "以下文件不在新旧任何版本清单内，已保留：`n  $($unknown -join "`n  ")"
    if ($PurgeUnknown) { $unknown | ForEach-Object { Remove-Item -Force $_ } }
}
foreach ($f in $newFiles) { Ensure-ParentDir; Copy-Item -Force }   # ③ 新版清单 → 覆盖写入

# ---------- 阶段 E：状态登记（成功后记录）----------
$state.plugins[$meta.id] = @{
    version      = $meta.version
    code_sha256  = $meta.code_sha256
    installed_at = (Get-Date -Format o)
    installed_by = "install-plugin.ps1/$scriptVer"
    backup       = $backupPath
    package_hash = (Get-FileHash $Package).Hash
    templates    = @{}          # 由应用启动时补全（§8）
}
Write-JsonUtf8NoBom "$dataRoot\config\.app_state.json" $state
# 注：全新插件安装时若 $meta.tools_entry 非空，合并进数据根 config\tools.json（保留用户启停/排序）

# ---------- 阶段 F：启动与冒烟 ----------
if ($wasRunning -and -not $NoStart) {
    Start-Sleep -Milliseconds 800
    Start-Process -WindowStyle Minimized -WorkingDirectory $appDir "$appDir\JZToolsHub.exe"
    Wait-Http "http://127.0.0.1:5000/api/tools" -TimeoutSec 60        # 就绪探测
    Assert ((Invoke-RestMethod "…/api/tools").tools | ? id -eq $meta.id)   # 列表可见
    Try-StatusEndpoint "…/api/$($meta.id)/status"                     # 有 /status 才深检（§5.6）
}

# ---------- 输出结论 ----------
"旧版本 → 新版本 / 增 x 删 y 改 z / 备份 <路径> / 回滚命令 / 自检：<PASS|FAIL>"
```

#### 5.2.3 实现要点（避坑清单）

| 要点 | 说明 |
| --- | --- |
| 解压复用既有三级策略 | 直接移植 `install-libreoffice-core.ps1` 的 `Expand-PayloadZip`（整包解压 → 逐条覆盖 → 兜底），避免 `.NET ZipFile` 无覆盖重载的老坑。 |
| 路径穿越防护 | 逐条 entry 校验：拒绝绝对路径、盘符、含 `..`、含 `:`；解压目标必须落在 `$pkgRoot` 之内（规范 SEC-1 精神）。 |
| 拒绝必须先于写入 | 全部 Assert 集中在阶段 A（对目标机的第一次写操作是阶段 C 的备份；之前只有 `%TEMP%` 解包）；`-DryRun` 走完 A 并演算阶段 D 的增删改清单即退出（底线二）。 |
| 备份必须可独立恢复 | 备份是"整个旧插件目录的 zip"，不依赖任何增量信息；`-Rollback` 只需解压它就回到旧版。 |
| 删除旧文件的必要性 | 后端是 importlib 动态加载，残留的旧模块/旧路由文件可能被导入导致诡异行为；因此"旧版有、新版无"的文件必须删——但判定要用**备份 zip 里的基线清单**做三分法（旧有新无=删 / 两版都无=用户新增，默认保留），而不是"目标机上一切不在新版清单里的都删"。 |
| 不启动"本来没运行的服务" | 与离线组件的"零副作用"一致：`was_running=false` 时升级完就结束，不动机器状态。 |
| 端口/主机可配置 | 冒烟探测读取 `JZTOOLS_PORT` / `JZTOOLS_HOST` 环境变量（`app.py` 消费同名变量），缺省 5000/127.0.0.1。 |
| 幂等 | 同包重复执行默认被版本规则拒绝（同号须 `-Force`）；`-Force` 重装不产生错误状态。 |
| 无 BOM / CRLF | 写 JSON 一律 UTF-8 无 BOM（`ConvertTo-Utf8NoBom` 同款）；脚本自身按仓库 `.gitattributes` 规则处理。 |

### 5.3 升级判定矩阵（唯一的拒绝点）

| 目标机现状 | 包声明 | 行为 |
| --- | --- | --- |
| 插件不存在 | 有 `tools_entry` | **全新安装**：写入代码 + 合并注册条目（`enabled` 取条目值，建议新插件默认 `false` 由管理员显式启用，见 §11 U-6） |
| 插件不存在 | 无 `tools_entry` | **拒绝**：提示"包未携带注册条目，请用 `-Register` 或先在 tools.json 登记" |
| 已装 = 包版本 | — | **拒绝**（同号重装需 `-Force`）——与 `build-deploy.ps1` 版本防呆同理 |
| 已装 < 包版本 | 在 `[min, max]` 内 | **升级**（正常路径） |
| 已装 < 包版本 | 低于 `upgrade_from_min` | **拒绝**：提示先升级到中间版本（不允许跳版） |
| 已装 > 包版本 | — | **拒绝**（防降级；确需降级用 `-Force`，并提示"降级后数据兼容性由插件负责，规范 V-3/V-7"） |
| 任意 | `min_app_version` > 本机 `app` | **拒绝**：提示先升级主包（`install.ps1`） |
| 任意 | SHA256SUMS 任一不符 | **拒绝**：提示介质损坏或包被篡改，重取介质 |
| 任意 | 程序目录版本 ≠ 状态登记版本 | **警告**（说明目录被手工改动过）后按程序目录版本执行规则；`-DryRun` 会显式列出该不一致 |
| 服务在运行 且 包 `requires_restart=true` | — | 允许，但提示"将短暂停服，建议在维护窗口执行" |

> 补充两条口径：① 目标机**已有**该插件时，包内的 `tools_entry` 一律忽略（`-UpdateEntry` 例外），
> 升级不改动现场的名称/描述/排序/启停；② 判定用的"已装版本"以**程序目录** `manifest.json` 为准，
> 状态登记只用于提示与模板门控（状态与目录不一致时警告，见 R-8）。

### 5.4 备份与回滚

- 位置：数据根目录 `backups\plugins\<id>\<id>-<version>-<yyyyMMdd-HHmmss>.zip`
  （放数据根而非程序目录：程序目录会被整包升级替换/清理，备份必须与之解耦）。
- 保留：默认最近 3 份，`-PruneBackups n` 调整；`-List` 显示占用。
- 回滚：`-Rollback <id>` 取最近一份，走"停服 → 解压覆盖 → 状态回写为旧版本 → 启动 → 冒烟"，
  并打日志 `rollback to <version> by <user>`。
- 卸载：`-Uninstall <id>` 的顺序遵守规范 §11——① `tools.json` 条目置 `enabled:false`
  （或按 `-PurgeEntry` 删除）→ ② 备份该插件（含数据目录**只读打包**一份到 `backups\plugins\<id>\data-*.zip`，
  由操作者显式 `-BackupData` 触发）→ ③ 删程序目录 `plugins\<id>\` → ④ 提示数据根目录数据仍保留及彻底清理方法。

### 5.5 前端缓存的处理（G-5）

| 层 | 机制 | 责任方 |
| --- | --- | --- |
| 构建期 | `build-plugin-package.ps1` 对比上一版，若 `.js/.css` 内容变化而入口页 `?v=N` 未递增 → **报错中止**（`-SkipCacheCheck` 越过） | 开发侧（§6.2） |
| 安装期 | 纯前端包输出提示"无需重启；请 Ctrl+F5" | 安装器 |
| 运行期 | F-2 既有约定不变（改了 JS 必须递增 `?v=N`） | 插件作者（规范） |

### 5.6 冒烟与验收口径（安装器自动执行）

1. `GET /api/<id>/status` 返回 HTTP 200 且 JSON 可解析（现有 11 个后端插件中 10 个已提供该端点，
   规范 §14 亦要求新增插件提供；缺失该端点的插件降级为"HTTP 200"判定并打印
   "该插件未提供 /status，跳过深度自检"）。
2. `GET /api/tools` 中该插件条目存在且 `enabled` 状态与升级前一致。
3. 首页 `/tool/<id>` 返回 200 且 iframe 入口页 `/plugin/<id>/<entry>` 返回 200。
4. 失败处理：打印失败项 + 备份路径 + 回滚命令，**不自动回滚**（避免"升级失败又被回滚"的二次抖动；
   回滚由操作者决定），退出码非 0 供批处理判断。

### 5.7 重启策略

| 场景 | `requires_restart` | 安装器行为 |
| --- | --- | --- |
| payload 含 `backend/**` 或 `manifest.json`（后端/清单有改动） | `true` | 停服 → 替换 → 启动 → 冒烟（R-4：后端路由只在启动时注册一次） |
| 纯前端插件（本仓库现有 5 个：base64 / color-picker / json-formatter / map-marker / md5-generator） | `false` | 默认仍停/启一次（一致性、避免读到半新半旧的文件）；`-Hot` 可不停服直接替换，随后提示 Ctrl+F5 |
| 有后端但本次只改前端 | `false` | 同上；`-Hot` 可用 |
| 目标机服务本来没在运行 | — | 全程不启动（与离线组件的"零副作用"一致，`was_running` 判定） |

判定与执行分离：`requires_restart` 由**构建工具自动判定**（比较旧包的 payload 是否含 `backend/**`
变化 + `manifest.json` 变化），允许人工 `-RequiresRestart` 覆盖；安装器只读不猜。
`-Hot` 的边界必须由安装器强制（`requires_restart=true` 时拒绝并说明原因），否则会出现
"后端代码已换、进程仍是旧路由"的假升级。

## 7. 链路补强：主包升级不得回退插件（G-3）

`install.ps1` 目前把源目录 `plugins\` 整体覆盖到目标目录。若目标机上某插件已被单独升级
（版本更高），整包升级会把它静默降级。**必须在 `install.ps1` 增加保护**：

```powershell
# 位于「复制项目文件」之前，安装/更新分支内
$stateFile = Join-Path $DataRoot "config\.app_state.json"
if (Test-Path $stateFile) {
    $state = Get-Content $stateFile -Raw -Encoding UTF8 | ConvertFrom-Json
    foreach ($p in $state.plugins.PSObject.Properties) {
        $id  = $p.Name
        $reg = $p.Value.version                                    # 数据根登记的"已应用版本"
        $src = Join-Path $Source "plugins\$id\manifest.json"        # 主包内嵌版本
        if (-not (Test-Path $src) -or -not $reg) { continue }
        $pkg = (Get-Content $src -Raw -Encoding UTF8 | ConvertFrom-Json).version
        if (Compare-SemVer $reg -gt $pkg) {
            Write-Warning "  插件 $id 已被单独升级到 $reg（主包内嵌 $pkg）→ 跳过覆盖，保持现状"
            $skipPlugins += $id
        }
    }
}
# 复制时排除 $skipPlugins 的目录（Copy-Item 按子项逐个复制，天然可跳过）
```

配套要求：

1. **`-ForcePluginOverwrite`**：显式要求"以主包为准"时使用（用于把单独升级的插件
   正式并回主线），使用时打印将被覆盖的插件清单。
2. **覆盖后清状态**：对以主包为准覆盖的插件，把 `state.plugins.<id>` 的版本改为主包内嵌版本
   （否则状态与实际不符，下次判定会误判）。
3. **幂等**：状态文件不存在/损坏 → 跳过保护并打印提示（不影响安装主流程）。
4. **提示语明确**：升级完成时若发生过跳过，输出"注意：N 个插件因版本更高未随主包更新"，
   并给出统一收敛的方法（下版主包并入更高版本，或 `-ForcePluginOverwrite`）。

## 8. 链路补强：插件级配置模板同步（G-4）

现状：`jztools_data.sync_templates()` 只在 `version.json.app` 变化时执行一次模板同步
（`jztools_data.py:447-466`）。插件单独升级不改应用版本 → 模板同步不触发。

### 8.1 设计：双门控（应用版本 OR 插件版本/模板哈希变化）

在既有 `config\.app_state.json` 中扩展插件段（保持 `last_app` 语义不变，向下兼容）：

```json
{
  "last_app": "1.9.0",
  "plugins": {
    "knowledge-base": {
      "version": "1.1.0",
      "code_sha256": "…",
      "installed_at": "2026-09-14T16:20:00+08:00",
      "installed_by": "install-plugin.ps1/1.0.0",
      "backup": "backups/plugins/knowledge-base/knowledge-base-1.0.0-20260914-161500.zip",
      "package_hash": "…",
      "templates": { "backend/config.template.json": "ab12cd34ef56ab78" }
    }
  }
}
```

启动时新增 `sync_plugin_templates()`，接线位置与既有模板同步同处：`app.py:48` 的
`jztools_data.sync_templates()` 之后（同在 `init_data_root()` 内，早于
`register_plugin_backends()`）：

```
for each 程序目录 plugins/<id>/**/*.template.json:      # 现有 4 个模板均位于 backend/
    rel  = 相对插件目录的路径（如 backend/config.template.json）
    h    = 文件内容 sha256 前 16 位
    已记录 = state.plugins[id].templates[rel]
    if 已记录 == h:  continue                       # 幂等：模板没变就不打扰用户
    目标 = 去掉文件名中的 ".template" 后映射到数据根同名位置
           （backend/config.template.json → plugins/<id>/config.json；
             backend/prompt.template.json → plugins/<id>/prompt.json）
    按 _TEMPLATE_SYNC 同款模式同步
       · 默认 ensure-keys（只补缺失键，保留用户 LLM 配置等）
       · 模板声明   "_mode": "overwrite" 时覆盖（旧文件先备份 .bak-old，
         用于「默认提示词随插件版本演进」这类应自动生效的模板）
    记录 state.plugins[id].templates[rel] = h
    写回状态文件
```

要点：

- **同一份模式语义**：直接复用 `_ensure_deep_keys` / `_merge_tools` / overwrite 三个既有实现，
  不新建第二套配置合并逻辑。模式取值优先级：① 模板内 `_mode` 字段 →
  ② `plugin-package.json.config_templates[].mode` → ③ 缺省 `ensure-keys`。
- **与 `_TEMPLATE_SYNC` 的分工**：硬编码清单继续负责框架级文件（`config/tools.json` 等，
  `jztools_data.py:76-94`），插件模板改由"自动发现 + 模板哈希门控"负责——两条路径共用同一批
  模式实现，不再要求"新增带模板的插件时必须手工登记清单"（这正是 G-4 的成因）。
- **`tools.json` 也纳入**：插件包携带 `tools_entry` 且是全新插件时，`plugin-upgrade` 安装器
  在停服状态下合并注册条目（复用 `_merge_tools` 语义：按 id 合并，已有条目保留用户值）；
  应用启动时的模板同步对 `config/tools.json` 继续走 `merge-tools`（补新工具/新分类，不覆盖用户启停）。
- **状态写权限**：安装器与应用都会写该文件，但**永不同时**（安装器运行前先停服；
  应用在启动早期写）。写入用"临时文件 + `os.replace`"原子替换（同 `save_admin_config()`
  的既有做法，`plugins/admin/backend/routes.py:131`）。
- **手工覆盖目录的场景也被覆盖**：即使用户没走安装器、直接拷贝了插件目录，只要模板哈希变了，
  下次启动即可补键——这条让"零代码接入"（规范 §12）在插件升级场景下同样成立。

| --- | --- |

| `restart_message` | 给管理员看的中文说明（源码模式"不自动重启"、用户关闭自动重启、自动重启失败等分支各不相同） |

前端 `waitAndReload()`：先等 4 秒（给旧进程退出留出时间），再每 1.5 秒 `GET /api/admin/plugins`，
拿到任意非 5xx 响应即刷新（401 也算"起来了"，刷新后跳登录），最多等 90 秒兜底刷新。

### 9.3 自重启编排（Windows 冻结场景）

```python
# 仅 frozen 模式可用；源码模式提示手工重启（开发有自动重载）
exe = sys.executable
helper = os.path.join(tempfile.gettempdir(), "jz-restart-%d.cmd" % os.getpid())
with open(helper, "w", encoding="gbk") as f:      # cmd 默认代码页
    f.write('@echo off\r\n')
    f.write(':wait\r\n')                           # 等旧进程退出，最多 30s
    f.write('tasklist /FI "PID eq %d" | find "%d" >nul && '
            '(timeout /t 1 /nobreak >nul & goto wait)\r\n' % (os.getpid(), os.getpid()))
    f.write('cd /d "%s"\r\n' % base_dir)           # 工作目录必须是程序目录
    f.write('start "" /min "%s"\r\n' % exe)
    f.write('del "%%~f0"\r\n')
subprocess.Popen(['cmd', '/c', helper], creationflags=DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP,
                 close_fds=True, cwd=base_dir)
threading.Timer(0.5, lambda: os._exit(0)).start()  # 与托盘"退出服务"同款收尾（app.py:824）
```

要点：先回 HTTP 响应再退出；helper 轮询 PID 而非固定延时（避免端口未释放导致启动即失败）；
`start` 必须带 `cd /d <程序目录>`（托盘/快捷方式同款工作目录约定）。

**自动重启的触发时机**（`plugins/admin/backend/routes.py: _maybe_auto_restart`）：

| 入口 | 触发条件 |
| --- | --- |
| `/api/admin/plugins/apply` | `ok=true` 且 `restart_needed=true` 且 `auto_restart≠false` |
| `/api/admin/plugins/rollback` | `ok=true` 且 `auto_restart≠false`（整目录替换，一律需重启） |
| `/api/admin/plugins/batch-apply` | 全部插件应用成功（`ok=true`）且汇总 `restart_needed=true`；有失败则**跳过**重启，交由管理员决定 |

三个入口共用同一个开关与同一段编排，因此无论从哪条路径换代码，"重启"这一步的行为完全一致。

> **为什么是"先替换、后停服"，而不是"先停服、再替换"？**
> 提前停服会让"替换失败"直接变成"服务起不来"；而先替换再重启时，替换阶段出任何异常服务都还活着，
> 管理员可以重试或回滚。停服与重启在本实现里是同一次 `os._exit` + 助手拉起，
> 对外表现为「短暂不可用 5~10 秒」，与"先停服"的可用性差异可以忽略。

### 9.4 安全条款（阶段二新增）

| 编号 | 条款 |
| --- | --- |
| PU-1 | 上传与 apply 仅超管（复用 admin 的 `get_session_user` + 超管判定），并记入访问日志与状态文件的操作者字段。 |
| PU-2 | zip 解压前逐 entry 校验（绝对路径/盘符/`..`/`:`）；解压后逐文件 sha256 与 `SHA256SUMS` 比对，全部通过才允许 apply。 |
| PU-3 | 体积与数量上限：zip ≤ 300 MB、解压后 ≤ 600 MB、entry 数 ≤ 5000；超限拒绝（防 zip 炸弹与误传整包）。 |
| PU-4 | staging 目录只允许位于数据根 `.staging/`，apply 目标只允许程序目录 `plugins/<id>/`；禁止任何其它路径写入（底线一）。 |
| PU-5 | 上传的 zip 与解压产物在 apply 成功后清理（保留备份 zip）；失败保留 staging 供排查，`.staging` 目录随 `-List`/后台可见并可手工清理。 |
| PU-6 | 前端上传限制：仅接受 `.zip` 且 `plugin-package.json.kind == "plugin-upgrade"`；不做任何"从 URL 拉包"的功能（离线原则）。 |

## 10. 阶段三：批量与索引（内网共享盘）

1. **索引文件**：共享盘 `\\<share>\JZToolsHub\插件包\index.json`——由构建工具从入库的
   `tools\plugin-packages.json`（发布登记，含 sha256 冻结值）导出并附上 `changelog`，
   与本地 `deploy\插件包\index.json` 同一格式。两者是"登记（入库）→ 索引（发布）"关系，
   内容不重复维护：

```json
{
  "schema": 1,
  "updated_at": "2026-09-14T17:00:00+08:00",
  "packages": [
    { "id": "knowledge-base", "version": "1.1.0", "file": "JZToolsHub-插件-knowledge-base-v1.1.0.zip",
      "sha256": "…", "size": 7340032, "min_app_version": "1.9.0", "requires_restart": true,
      "published_at": "2026-09-14T16:50:00+08:00", "changelog": "修复字符缩进；见升级说明.md" }
  ]
}
```

2. **检查更新/批量升级**（管理后台）：读取索引 → 与本地各插件版本对比 → 列出可升级项
   （含 `requires_restart` 汇总）→ 勾选后**顺序应用、全部成功后自动重启一次**（全部为纯前端包则零重启）；
   任一失败则跳过自动重启，保留现场交由管理员决定。
3. **包签名（可选增强）**：`plugin-package.json` 的 detached 签名（证书 + 公钥内置在程序目录），
   安装器验签后再执行；不引入 CA 依赖的过渡方案：把 `index.json` 的 sha256 冻结值
   作为"发布记录"（与 `tools/offline-components.json` 的 sha256 冻结值同一理念）。
4. **回执**：批量升级结束输出每台机器/每个插件的"期望版本 vs 实际版本"对照，供运维留档。

## 12. 安全、完整性与风险登记册

### 12.1 完整性链条

```
发布方：zip 旁挂 .sha256 + tools\plugin-packages.json 冻结值 + 升级说明.md 中的变更摘要
   ↓ 介质（U 盘/共享盘）
操作者：certutil -hashfile <zip> SHA256 与旁挂文件比对
   ↓ 解压
安装器：SHA256SUMS 逐文件校验（payload 全部文件）
   ↓ 应用后
状态文件：记录 code_sha256 / package_hash / installed_by / installed_at
```

任一层不符即中止且不改动目标机（底线二）。sha256 只证明"与发布时一致"，
不证明来源真实性（与 `tools/offline-components.json` 的既有说明一致）；签名留待阶段三。

### 12.2 风险登记册

| 编号 | 风险 | 概率 | 影响 | 对策 |
| --- | --- | --- | --- | --- |
| R-1 | 主包升级把单独升级的插件覆盖回旧版（G-3） | 高 | 高 | §7 防回退保护 + `-ForcePluginOverwrite` + 升级后提示 |

## 附录 C：与《容器化与插件热插拔》方案的关系

> 该专题两份文档：v1.0 已归档（Linux 容器前提，`docs/archive/容器化与插件热插拔-评估与实施设计-v1.0-已被取代.md`，

### D.2 相对设计的偏差（均为实施中的修正，建议以本节为准）

| 编号 | 设计原文 | 实施结果 | 原因 |
| --- | --- | --- | --- |
| D-1 | 取源优先级 `-From` > 部署目录 > 仓库工作区 | 默认取**仓库工作区**（`plugins/<id>`），`-From` 可覆盖；未再默认取部署目录 | 仓库工作区同时含已入库代码与未入库交付资产（如 map-marker 的 mp4），且不会因部署目录陈旧而发出旧代码 |

| D-5 | 安装器参数表（§5.2.1） | 新增 `-DataRoot`、`-BackupFile`、`-PurgeEntry`、`-BackupData`、`-UpdateEntry`、`-PurgeUnknown`；`-PruneBackups` 默认 3（0=不清理） | 运维实际需要：自定义数据根、指定回滚点、卸载语义分级 |

| D-7 | 规范增量编号 `U-1..U-6` | 定稿为 `U-1..U-6`（`插件设计规范.md` §15） | 设计文档初稿写作 `UP-x`，实施时统一为规范内的 `U-x`（两者已同步） |
| D-8 | 模板目标映射"去掉 .template 后缀" | 明确为：**取文件名**去 `.template.` 标记后落到数据根插件目录根（`backend/config.template.json` → `plugins/<id>/config.json`） | 与既有 `_TEMPLATE_SYNC` 的四条登记完全一致，避免出现 `backend/config.json` 这种错位 |

**自重启编排**（§9.3 的落地）：写一个 ASCII 内容的 `jz-restart-<pid>.cmd` 到 `%TEMP%`，
内容为「轮询本 PID → 等进程退出 → `cd /d <程序目录>` → `start "" /min <exe>` → 自删」；
以 `DETACHED_PROCESS|CREATE_NEW_PROCESS_GROUP` 分离启动，随后 `threading.Timer(0.6, os._exit)` 退出。
助手内容全 ASCII、路径用 GBK 写盘（中文路径可用）；轮询 PID 而非固定延时（避免端口未释放）。

### E.3 相对设计的偏差与实施中发现的问题

| 编号 | 设计原文 | 实施结果 | 原因 |
| --- | --- | --- | --- |
| E-1 | 上传后 `apply` 依据前端回传的"计划"执行 | `apply` 只接受**文件名**，服务端重新跑一遍 `inspect_package` 再应用 | 不信任前端传来的任何状态；文件名限定在数据根 `.staging/uploads/` 内（`basename` 校验，拒绝路径穿越） |
| E-2 | 服务端实现"必须逐条一致"但未指定落地方式 | 关键规则（重启判定、三分法基线、版本窗口）在两侧同源注释互相指路，并用 `test_plugin_admin.py` 的**交叉验证用例**（PS 出包 → Python 校验/应用）钉住格式约定 | 两条实现最容易漂移的是"包格式约定"与"重启判定"；用测试而非文档约束 |
| E-3 | 重启判定 = `backend/**` 或 `manifest.json` 变化 | **改为只看 `backend/**`**（两侧同步收口） | 交叉验证用例发现：`manifest.json` 每次请求都会被 `load_manifests()` 重读、前端资源也是磁盘直读——把 manifest 计入重启条件会让纯前端包被误判为"需重启" |
| E-4 | 三分法基线：状态登记缺失时"退回备份快照口径" | 改为**保守口径**：无基线时只清理 `backend/*.py` 残留，其余文件一律保留并列出 | 备份快照=升级前磁盘现状（含用户/第三方文件），拿它当基线会把用户文件当旧版删掉。实测中 sandbox 目录里的 `backend/out/`、`__pycache__` 等 50 个文件正是靠这条规则被保住 |
| E-5 | 管理后台需自行处理"重启生效" | 新增 `restart_pending` 状态 + 启动时清除（`app.py`）+ 页面横幅与"立即重启服务"按钮 | 页内应用后进程仍跑旧代码；不标记会让管理员误判"升级没生效" |
| E-9 | 应用后由管理员手工点「立即重启服务」 | **改为自动**：`apply` / `rollback` / `batch-apply` 成功且需重启时直接走 `_maybe_auto_restart()`，页面轮询等待后自动刷新；页面保留「应用后自动重启服务」开关（默认开） | 用户要求"上传即完成"；重启这一步漏点会让插件静默不生效，是最容易出错的人工环节 |
| E-6 | （未设计）测试如何安全地起应用 | 新增 `JZTOOLS_DATA_ROOT` 环境变量 + Flask 测试客户端方案；测试内断言 `get_base_dir()==沙箱` 并复核仓库插件目录未被改动 | 全栈测试最大的风险是"测到真实数据根/真实仓库"；沙箱隔离用断言钉死 |
| E-7 | 出包工具生成变更说明 | 修掉 git 输出编码：临时把 `[Console]::OutputEncoding` 切到 UTF-8 | PS 5.1 按 GBK 解码子进程 stdout，实测 changelog 变"鏇存柊…"乱码（索引与升级说明.md 都受影响） |
| E-8 | 页面样式 | 新增 `.settings-card.wide`（盘点表用）与 `.plugin-banner[hidden]{display:none}` | 浏览器实测发现两处视觉缺陷：表格被 720px 表单宽度裁掉；`.plugin-banner{display:flex}` 覆盖了 `hidden` 属性导致空横幅常驻 |
