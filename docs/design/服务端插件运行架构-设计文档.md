## 1. 拍板历程与威胁模型（决策留痕）

**三轮收敛（2026-10-05，完整论证见对话留痕）**：

| 轮次 | 方案 | 结论 |
| --- | --- | --- |
| ① | 进程内 register(app)（初评推荐：部署链/鉴权/mount 全现成） | **否决**——无进程隔离，插件崩溃连坐主应用不可接受（需求⑩前提） |
| ② | D 主应用内嵌执行器（子进程，客户端 executor 移植） | **否决**——崩溃隔离达成，但生命周期/部署/熔断全长在主应用，主应用自升级仍靠 `--wait-restart` 自举 |
| ③ | **E 管理进程 + 并列进程（定稿）** | 业界 supervisor 形态（systemd/supervisord 同构；参照架构 dsh「壳管理本地服务」同款）；生命周期外置，主应用自身也成受管对象 |

**威胁模型校准**（为什么隔离是必要的）：Python 层异常 Flask 可接住（单请求 500、进程存活）；真正连坐主应用的是 **native 段错误（cv2/numpy 级）、OOM、失控循环拖死线程池、模块级状态污染**——Python 进程内对前两类无任何可靠隔离手段，这是进程隔离的根本理由，不是工程偏好。

**前提事实**：会话为签名 Cookie 且 `SECRET_KEY` 持久化于配置（`routes.py:974`）→ **重启不掉登录**；重启的真实代价 = 秒级窗口 + 在途请求被打断。

## 2. E 架构总图与 supervisor 契约

```
supervisor（轻量 Python：stdlib+psutil，不 import 任何重库；Windows 服务化=NSSM/最小包装）
├─ 受管① 主应用（主包 Flask+waitress）——唯一 HTTP 入口
├─ 受管②…⑩ 插件后端包 worker（每插件一个自有 Flask 实例进程，register(app) 契约保留）
└─ 职责：启动编排 / 健康探针 / 崩溃拉起+熔断（连续 N 次失败自动下线+告警）/
        升级=停旧→替换→健康→起新（失败回滚） / 停用清理 / 孤儿收割（Job Object） / 日志归集
```

- **受管单元**：主应用与全部 server 后端包 worker 并列注册；单元描述=名称/启动命令/健康探针 URL/重启策略/依赖环境（shared 或 venv 路径）。
- **控制接口**：主应用 → supervisor，localhost + 独立令牌（或命名管道 ACL）；动作=`status / start / stop / restart / apply(包) / rollback(单元)`；admin 商店管理页的部署运行面板是该接口的薄客户端。
- **升级编排**：停旧 → 替换（复用 inspect/apply 校验+备份逻辑）→ 健康探针 → 起新；失败自动回滚到备份并告警。**主应用升级同口径**（supervisor 编排，插件 worker 存活）。**worker 单元不打 `restart_pending` 标记**（2026-10-05 拍板）：该标记语义是「代码已换、进程未换」（进程内形态）；worker 由编排即时重启、即时生效，打标会让管理页出现假「待重启」徽标（商店部署面板在读它）。实施口径：supervisor 的 apply = `inspect_package`（校验）+ 备份 + 自管替换，**不走 `apply_package` 全链**；过渡期（插件仍在主应用进程内）才走既有全链。
- **熔断**：连续 N 次（建议 3）崩溃/健康失败 → 单元下线（主应用对失败插件兜底 503），告警 + 管理页可见，人工/管理页恢复。
- **孤儿收割**：子进程纳入 supervisor 的 Job Object（kill-on-close）；supervisor 由服务管理器拉起，自身升级最后执行。**代价与配套（2026-10-05 拍板）**：kill-on-close 意味着 supervisor 崩溃 = 全平台（含主应用）同死——这是用「无孤儿」换「全量重启」，**必须**配套服务恢复策略（NSSM/SCM 失败自动重启）作为 T-O2-11d 的验收项；拒绝该配套则放弃 kill-on-close（二选一，不做无兜底的全有）。
- **服务化**：NSSM 或 pywin32 最小包装注册为 Windows 服务；注意服务账户的共享盘映射等环境差异。

### 2.1 端口确定（2026-10-05 研究拍板：分配一次、持久化回注册表、长期占用）

**交换契约先行（对页面零影响）**：前端包与后端包之间**无直连**——交换 = 页面同源相对路径 fetch（`/api/<id>/*`）+ 会话 Cookie 逐跳透传。端口只被三方需要：worker（绑定）、supervisor（探针）、主应用（反代路由表）；页面 / 能力层 / jz_relay 全程不感知端口，E 改造对前端包、store 页、能力层零改动。

| 方案 | 结论 |
| --- | --- |
| A 静态手配 | 否决——加插件要手工排号，多机部署易撞 |
| B 每次启动动态分配 | 否决——端口随重启漂移，主应用反代缓存失效，请求路径被迫同步查 supervisor |
| **C 分配一次持久化（定稿）** | supervisor 首次为单元 `free_port()` 挑选（限配置段，如 5101–5199，段随 supervisor 安装配置）→ **原子写回注册表** → 此后固定；worker 经环境变量 `JZ_WORKER_PORT` 接收（自己不做任何端口决策） |
| D 管道 / AF_UNIX | 否决——waitress 仅支持 TCP，换 server 违背「worker=自有 Flask+waitress」契约 |

**配套口径**：
- **冲突即报错不起**（不静默换号）：换号打破主应用反代缓存，宁可单元起不来进告警，由人处理；
- **主应用反代路由表**：启动读注册表建 `<server插件id> → port` 内存映射；`status` 控制动作返回当前端口，**仅在管理动作（apply/rollback/熔断恢复）后刷新**，两次管理动作之间缓存恒正确（C 方案端口不随重启变）；
- **升级不换端口**：apply 编排 = 停旧 → 替换 → 同端口起新 → 健康；失败回滚同端口再起旧版，对反代透明；
- **既有先例同源**：客户端能力层 `free_port()+port.txt`（`client_main.py:36,118`）、主应用 `JZTOOLS_PORT` 覆盖（`app.py:1241`）——本方案把两先例收拢到 supervisor 一处；
- **端口不是授权边界**：127.0.0.1 只解决不出本机，本机进程仍可直连；防线=主应用完整鉴权管线（登录/超时/权限点全在 before_request）+ worker 会话自验（§3）双卡。探针路径 `/_worker/health` 为无 Cookie 可用的公开路径，只回 `{ok, plugin, version}` 状态、不含业务数据。

## 3. 身份与通信

- **反代拓扑**：客户端/浏览器 → 主应用（鉴权管线：admin 鉴权门照常）→ 主应用反代 → worker（端口仅绑 127.0.0.1）。
- **身份 = 共享 `SECRET_KEY` + Cookie 原样透传 + worker 会话自验**：worker 侧实现「会话自验版 session_user provider」（验签名 Cookie 得身份）——业务插件经 `jz_api.get_session_user()` **零改动**（实测 `session` 直摸仅 admin 一家，身份读取已收敛 `jz_api` 门面——解耦设计 FC-3/K-3 的现成红利）。滑动续期（`session["last_active"]`）经反代 Set-Cookie 回传，照常生效。
- **R2 简化**：共享密钥不扩大信任面（进程内插件本就读得到 SECRET_KEY，同信任域）；自建签名信任头方案废弃，降级为「端口绑定 + 会话自验」。
- **Flask 上下文盘点**：

| 上下文成员 | 本项目实际用途 | E 形态下 |
| --- | --- | --- |
| `request` | 全部插件的数据入口 | 原样可用（worker 自有 Flask 收到转发请求） |
| `session` | 仅 admin 直摸；业务插件走 `jz_api` | 原样可用（共享密钥 + Cookie 透传） |
| 主应用级 `before_request` | admin 鉴权门 | 留主应用；worker 自验会话兜底 |
| `g` / `current_app` / `config` | 插件内少用 | worker 复制同一份配置 |
| `url_for` / 模板 | 前端零硬编码 origin 纪律 | 无损 |
| `jz_api` / `jz_deps` / `jztools_data` / `jz_llm` | 框架门面与数据根约定 | 前三者随包可 import；**`jz_llm` 接入为唯一适配工作项**（provider 注入或经主应用 /api/llm 中转） |

- **契约固化**：插件规范增补「禁用主应用全局钩子/全局单例，一切经 register(app) 收到的 app + jz_api」；构建期扫描直摸 `session`/`current_app` 的写法（C 系检查扩展）。
- **通信契约固化（2026-10-05 端口研究随拍，三条）**：
  1. **反代路由前缀 = 插件规范 mount**：只转发 `/api/<已装 server 插件id>/*` 与 `/plugin/<id>/*`（非 `local-` 前缀且未命中客户端本地伺服清单）；C 系构建期检查增补「server 插件 API 前缀必须 = `/api/<id>`」，防插件自注册怪前缀绕过路由表；
  2. **流式逐跳 spool**：反代段复用 T03 口径（请求体按确切 Content-Length 落临时文件转发）——大文件穿「能力层 → 主应用 → worker」三跳不失真；
  3. **版本漂移门控不变**：前端本地副本可能落后于 worker——同版本成对发布 + `api_version` 门控 + 中继直出兜底（商店文档 §3.5.1 原口径）。

### 3.1 worker 会话 provider 设计（2026-10-05 研究拍板）

**注入机制零新增**：`jz_api.register_providers()`（`jz_api.py:47`）即端侧扩展点，worker 引导件调一次，`jz_api.py` 零改动（GD8"端侧差异走 register_providers"的既定落点）。**禁 fork worker 专用 jz_api**。

**问题**：签名 Cookie 只存 `user`（用户名）+ `login_at`/`last_active`（`routes.py:1046`），插件要的是全量信息 dict（`get_session_user()` 每请求现算，`routes.py:496`）——worker 无法从 Cookie 重建。

| 候选 | 结论 |
| --- | --- |
| worker 读 admin.json 自足重建 | 否决——权限逻辑两处真源必漂移；Fernet 密钥散播到每个 worker；账号数据归属破坏 |
| 胖 Cookie（登录塞全量 dict） | 否决——破坏「权限变更即时生效」既有性质；admin 会话 schema 被框架化 |
| 代理附自建身份头 | 不重开——即 R2 已拍板废弃的信任头方案 |
| **自验 + 回环（定稿）** | 本地验签做鉴权锚点 + 每请求回环取信息 |

**两级 provider（session_user）**：
1. **鉴权锚点（本地零 IO）**：worker Flask 设同一 `SECRET_KEY` → `flask.session` 自动验签解码 → `session["user"]` 得用户名；无 → None。这就是「会话自验」本体；
2. **信息面（每请求回环）**：带原请求 Cookie 回环 `GET 127.0.0.1:<主应用>/api/session`（既有公开端点，返回 `{"user": 全量dict}`）→ 原样返回。回环走本机环回，亚毫秒级；dict 为同一请求链上现算，**与主应用视角零陈旧**。

其余 provider 落法：`set_operation`=worker 本地写请求上下文 g（worker 自有访问日志）；`org_tree`=回环 `/api/org/tree` + **30s TTL 缓存（拍板：做）**（组织树低频、无即时性诉求）；`user_llm_*`=随 `jz_llm` 接入点定（首期可不注册，降级 None）。

**职责切分与契约（四条）**：
- 主应用 = **鉴权权威**（会话守卫/强制登录/权限点全在代理跳 before_request）；worker = 验签 + 消费。直连 worker 的旁路请求由 worker 验签兜住（401）；
- worker 对 `config/admin.json` **只读 `secret_key` 单字段**（共享密钥存放点），其余字段归 admin——"共享密钥不扩大信任面"（R2）的操作化；
- worker 对会话**只读**：不 re-sign、不写 `last_active`、回环响应的 Set-Cookie 丢弃（续期由主应用跳完成）；
- **回环失败 → None（fail-closed，按未登录；拍板）**——半真身份比"未登录"更易让插件逻辑走岔；`jz_api` 既有降级语义兜住，插件无感。worker 引导件在 `register(app)` 之前完成 provider 注册。

**SECRET_KEY 轮换联动（拍板）**：首期口径 = 轮换密钥**需重启平台**（supervisor 编排全量重启 worker，会话全失效重登）；二期可选 = supervisor 监视 admin.json 的 secret_key 变化自动滚动重启（`register(app)` 前置注册使得滚动重启即可生效，无需热重载密钥）。

## 4. 依赖与 venv（拍板口径）

- **默认共享运行时**：主包解释器 + `runtime/pylibs` 共享槽 + 内核库（与现状同构）。
- **venv = 可选项**：要求特殊依赖版本的插件允许 venv 拉起（worker 以 `venv\Scripts\python.exe` 启动，supervisor 按单元描述指定解释器），**商店目录条目标注**（catalog 条目 `deps_mode: shared|venv`）。后端包上架时携带依赖 wheel 清单，部署时 `pip --no-index --find-links` 离线建环境（机器校验含依赖闭包完整性 + wheel tag 预检——O1 文档同款设计）。
  **wheel 清单包格式（2026-10-05 补规格，T-O2-12c 前置）**：`plugin-package.json` 增可选 `venv` 节（`deps_mode=venv` 的后端包必带）：

  ```jsonc
  "venv": {
    "python": "3.14",                  // 目标解释器基线（与主包一致）
    "wheels": ["pkg-1.0-cp314-cp314-win_amd64.whl", "..."],   // 闭包清单 = payload/wheels/ 内文件
    "wheel_sha256": {"<文件名>": "<sha256>"}                   // 防篡改旁挂
  }
  ```

  机器校验：① wheel 文件实际存在于 `payload/wheels/` 且与清单一一对应（闭包完整性）；② wheel tag 预检（`cp314*` / `py3-none-any`，O1 口径）；③ sha256 逐一对上。出包链（build-plugin-package.ps1）增产 `payload/wheels/` 收集与 `venv` 节生成（`-VenvWheels <目录>` 参数）；部署时 supervisor 建环境 → `pip --no-index --find-links payload/wheels` 装清单 → 以 venv 解释器拉起 worker。venv 与主包 Python 基线绑定：基线升级 = venv 随包重建。
- **venv 不是沙箱**：隔离版本、不隔离行为；行为防线 = 审核 + 鉴权管线。
- **与客户端 O1 slots 的分化**：服务器求官方标准（磁盘宽裕、进程已隔离），客户端求省盘（embeddable + `.slots`，已拍板零内核改动）；`requires` 三态判定两端共用。
- **注意**：Python 基线升级 = 全部 venv 重建（策略：解释器基线随主包，venv 随包重建）；venv 不改善 import 冷启动（0.5–2s）。

## 5. 热插拔语义（按形态，插件改造选型参考）

| 形态 | 装载/卸载/停用 | 升级生效 |
| --- | --- | --- |
| 服务器后端包（E：独立 worker 进程） | supervisor 启停，**热**（主应用与其余插件零影响） | supervisor 停该 worker→替换→健康探针→起新版；**该插件秒级窗口，其余零影响**；纯前端变更本就热（静态每请求伺服） |
| 服务器既有进程内插件（16 插件迁移前现状） | 需重启 | 优雅重启（`--wait-restart` 页内自重启现成 `app.py:1159`；`requires_restart` 构建期自动判定，纯前端 `-Hot` 不停服——升级方案 §5.2/§5.7） |
| 客户端类 B（worker） | 全热（L1/L2 即时） | 全热（L3：按需 spawn/常驻收割，T20） |
| 客户端类 C 客户端工件（hybrid） | 装卸/停用即时（子应用派发） | 能力层秒级重启（会话镜像持久化免重登；模块级 reload 不可靠、不做） |
| 客户端类 A 前端包 | 即时（本地伺服路由开关） | 即时（装新版即生效） |

## 6. 16 插件改造影响与主应用兜底

**实施中修正的设计细节（回写口径）**：
1. **熔断 = 双计数器**（§2 修正）：探针连败（进程存活但探针不通）与**快速崩溃连击**（稳定期窗口内再次退出）任一达阈值即熔断——路由触发型毒插件每次重启后探针都正常，单一探针计数器永远到不了阈值；崩溃连击仅在「存活超过稳定期（缺省 60s）」后清零。
2. **监控语义三条**（§2 修正）：`_applying` 抑制集——apply 停换起窗口监控整体跳过（否则编排必被误熔断）；未托管单元（未启动/人工已停）不探针不计数（proc=None ≠ 死亡）；死亡记账幂等（同一进程只记一次，记账后即摘出进程表）。
3. **apply 顺序**（§2 修正）：备份 → 停旧 → **验端口** → 替换 → 起新——先验端口会被自己的运行中 worker 占住误判冲突；「冲突报错不起」指外来占用。
4. **端口占用探测 = connect 而非 bind**（§2.1 修正）：Windows TIME_WAIT 残留连接（最长 ~4 分钟）会让 bind 探测误报，worker 停换起被卡死；connect 只认真实监听者。
