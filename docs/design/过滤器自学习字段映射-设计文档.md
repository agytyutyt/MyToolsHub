## 1. 问题与目标

### 1.1 现状

大模型过滤模式（`mode=llm`）每次运行都把**全部表头 + 保留名单**一次性交给 LLM
（`llm_client.match_columns`），返回 `{表头: 名单字段 or ""}` 后：

- 结果**用完即弃**：同模板的下一份文件要重新调一次 LLM（单次 2~30s，超时上限 120s），
  两个过滤 worker 容易排队；
- 判定**没有把关**：模型说删就删，判错直接产出错误结果文件（模型输出还受
  temperature=0.1 的随机性影响，同一批列两次判定可能不同）；
- 硬过滤只做精确同名匹配，语义相近的表头（「时间」↔「开始时间」）完全依赖 LLM。

### 1.2 目标（初步想法 + 完善点）

原始想法：LLM 解析结果记录下来下次直接读；LLM 可能判错，由用户把关，把关后的最终结果
也记录，便于直接读取过滤。

完善后的目标：

| # | 目标 | 相对初步想法的完善 |
| --- | --- | --- |
| G1 | **分级信任**：用户确认过的映射 > LLM 建议 > 无映射。确认过的直接查表过滤，零 LLM | 初步想法只有"记录→直接用"一层；未确认的建议直接当真相会用错 |
| G2 | **把关前移**：映射建议在**上传预览**就可见可改（来源徽标），结果页再做一轮复核确认 | 初步想法未说把关发生在哪；复用既有预览胶囊交互，不加新步骤 |
| G3 | **负映射也要学**：「确认该列无关、删除」同样入库，垃圾列下次直接删，不再进 LLM | 初步想法只学了"匹配到谁"，漏了"确认无关"——否则每个无关列每次都要 LLM 判 |
| G4 | **LLM 只问未命中的子集**：prompt 变小，省钱省时；结果回写为"建议"级 | 初步想法隐含全量跳过，未考虑 miss 子集的增量学习 |
| G5 | **陈旧防护**：名单（keep_columns）变更后，指向已删除目标的映射自动失配标记，不悄悄命中 | 初步想法未考虑名单会变 |
| G6 | **非交互调用保守**：`/apply` 程序化接口默认只吃"已确认"映射，不吃"建议" | 其他插件调用没有把关环节，不能继承建议级的信任 |
| G7 | **评测集副产品**：确认映射即黄金评测集，一键导出，接上"内网开源模型（laya）替代云 LLM 前先建评测集"的既定计划 | — |

## 2. 关键设计决策

| 决策 | 取舍 | 结论 |
| --- | --- | --- |
| 建议级映射是否直接生效？ | 生效=拿到速度收益；不生效=每次仍要 LLM 或人工 | **生效但降级标注**：建议级映射参与过滤（与现状"LLM 判完直接用"同信任档，不劣化），但预览/结果里标"模型建议"，用户任何明确动作即升级为"已确认" |
| 把关环节放哪？ | 独立审批页=重流程；嵌入预览=顺手 | **嵌入既有预览 + 结果页复核区**：预览胶囊显示来源徽标，结果页列出本次用到的映射供 ✅确认 / ✏️改指 / ❌否决 |
| 缓存键的粒度？ | 全局 vs 按模板分域 | **v1 全局**（键=归一化表头），冲突时弹窗处置；按模板分域（表头集合指纹）留待冲突率数据说话（§7-3） |
| 同名异义冲突？ | 静默覆盖=危险；拒绝=难用 | **弹窗处置**：替换全局映射，或本次临时指定（不入库） |

## 3. 总体设计

### 3.1 匹配管线（`run_filter` 内逐列判定）

```
对每个表头 h（保留名单 keep、用户点掉集合 exclude）：
  ① h ∈ exclude                       → 删除（用户决定优先，既有口径不变）
  ② confirmed[key(h)] 且 target 仍在当前名单
       target=""（确认删除）           → 删除 source=confirmed_drop
       target≠""                       → 保留 source=confirmed
     （confirmed 排在 exact 之前：UI 会把预填保留的列传回 columns，若 exact 自匹配
       先行会把确认映射的来源标注与命中统计遮蔽——confirmed 是用户把关过的最强依据）
  ③ h 与名单某字段精确同名（既有逻辑）  → 保留 source=exact
  ④ 压缩键二次查找（去内部空白后 casefold，仅 confirmed）→ 同 ②（对付「开 始 时间」类脏表头）
  ⑤ suggested[key(h)] 且 target 有效   → 保留 source=suggested（预览可见可改）
  ⑥ 未命中的表头子集 → **一次** LLM 调用（prompt 只含未命中表头）
       返回值经名单白名单过滤（既有防幻觉逻辑）+ rejected 表拦截后
       回写 mappings（status=suggested），本次按其值过滤（source=llm，
       判定删除的列同样进 mappings_used——负映射首轮即可把关）
```

要点：

- **rejected 拦截**：用户否决过的映射对（表头→目标）不再入库；LLM 再建议同一对时按
  未匹配处理，避免同一错误建议反复回锅。
- **读时校验**：命中条目的 target 必须仍在当前 `keep_columns` 里，否则视为失配
  （orphaned）不参与匹配——名单改了，缓存不能装作没看见。
- **确定性**：缓存命中路径无随机性，同一文件两次运行结果一致（现状 LLM 有温度抖动）。

### 3.2 数据结构（`data/plugins/file-filter/mappings.json`）

```json
{
  "version": 1,
  "updated_at": "2026-09-26T12:00:00",
  "stats": {"llm_calls": 12, "llm_saved": 87, "hit_exact": 120,
            "hit_confirmed": 540, "hit_suggested": 96, "misses": 130},
  "entries": {
    "开始时间": {
      "key": "开始时间",
      "sample": "开始 时间",
      "target": "开始时间",
      "status": "confirmed",
      "source": "llm",
      "model": "deepseek-v3",
      "prompt_ver": 1,
      "hits": 8,
      "created_by": "zhang", "created_at": "2026-09-26T11:00:00",
      "confirmed_by": "zhang", "confirmed_at": "2026-09-26T11:05:00"
    },
    "备注2": { "target": "", "status": "confirmed", "...": "确认删除（负映射）" }
  },
  "rejected": { "身份证号": { "籍贯": "2026-09-26T10:00:00" } }
}
```

- 键 = 归一化表头（`core.clean_text` + casefold，与硬过滤同一口径）；`sample` 留最近一次
  原文便于人读；压缩键（去内部空白）加载时在内存里建第二索引，不落盘。
- 每条约 250B；写入沿用 `save_config` 的 tmp + `os.replace` 原子写；模块级
  `threading.Lock` 保护读改写（与 `TASKS_LOCK` 同模式）；进程内持有副本，首次读文件，
  之后写穿。
- 条目上限（`mapping_limit`）**管理员可配**：默认 10000、范围 100~100000（config.json，
  管理面板「映射记忆」块设置）。到顶只拦**自动新增**建议——已有条目的更新与用户
  confirm/改指不受限，调低不删除已有条目（不采用主动清理策略，见 §7-4）。
- `stats` 命中计数器让管理员能看见"省了多少次 LLM"。

### 3.3 把关交互（升级为 confirmed 的三条路径）

| 路径 | 动作 | 记录 |
| --- | --- | --- |
| 结果页复核区 | 对本次用到的映射点 ✅确认 | status→confirmed，记 confirmed_by/at |
| 结果页复核区 / 预览 | 点 ✏️改指名单中另一字段 | target 更新为用户指定值，status→confirmed；旧 pair 进 rejected |
| 结果页复核区 / 预览 | 对"建议删除"的列点确认，或对建议保留的列点 ❌否决 | target=""（负映射）或 pair 进 rejected |

口径：**用户明确动作才算确认**；建议被采纳但用户没点任何东西 → 停留 suggested，
`hits`+1。用户在预览里手动翻转某列为保留但无语义对应时，仅对本文件生效（走既有
columns/exclude 机制），不强行造映射。

**UI 提交口径（P1 实测修正）**：前端只有**用户手动点掉**的列才进 `exclude`（最终否决）；
未动过的删除预判不进 exclude——否则大模型模式永远学不到新映射（预判画了删除线的列
全部被否决，LLM 根本没机会判定）。这也是 v1.3 提示文案「画删除线的字段若与保留字段
语义相关仍会被保留」一直未真正成立的根因，本次一并修正。切换模式/上传时按当前模式
回填预判（用户手动点过的胶囊不回填）。

### 3.4 接口增量（前缀 `/api/file-filter`，B-2）

| 接口 | 方法 | 权限 | 说明 |
| --- | --- | --- | --- |
| `/mappings` | GET | 管理员 | 列表（status/q 过滤），含 orphan 标记、stats、`limit`（自动学习上限）与 `count`（当前条数）（管理面板用） |
| `/mappings/confirm` | POST | 登录 | `{items:[{key,target}]}`，操作员在复核区确认；冲突时返回 409 由前端弹窗 |
| `/mappings/reject` | POST | 登录 | `{key,target}` 进 rejected、条目删除或降级（操作员复核动作） |
| `/mappings/delete` | POST | 管理员 | 删除单条 `{key}`（POST+请求体而非 DELETE 路径：表头可能含 "/"，进路径不安全） |
| `/mappings/export` | GET | 管理员 | `?format=jsonl\|csv` 导出黄金评测集 |
| `/mappings/recheck` | POST | 管理员 | 匹配修正（P3b）：建议级条目（含失配）分批交 LLM 重判，写回建议级；**confirmed 不动**；单飞行，并提 409 |
| `/mappings/recheck/<task_id>` | GET | 管理员 | 轮询修正任务：`{status, processed, total}`；done 附 `diffs`（old→new）与 `outcomes` |

权限口径（已拍板，见 §7-1）：**识别/复核环节的操作员（登录用户）确认字段过滤判定**；
**学习记忆的修改维护（编辑目标、删除、清空、导出、orphan 重新指派）归管理员**——与
keep_columns 的管理口径一致。
| `/preview`（既有） | — | — | 响应逐列增加 `match_source`；建议映射预填进预判 |
| `/result`（既有） | — | — | `kept` 每项增加 `source`；新增 `mappings_used`（本次用到的建议/确认映射，供复核区） |
| `/apply`（既有） | — | — | 新增可选参数 `use_suggested`（默认 false：只吃 exact+confirmed） |

## 4. 落地方式（分阶段）

## 5. 性能预估

| 场景 | 现状 | 改造后 |
| --- | --- | --- |
| 同模板第 2+ 份文件（缓存全命中） | LLM 全量调用 2~30s（上限 120s）+ token 费用 | **<50ms**（内存查表+一次原子写），LLM 0 次，worker 不占坑 |
| 混合模板（部分列命中） | 每次全表头进 prompt | 仅未命中子集进 prompt，**token 省 60%~90%**，调用次数不变、单次更快 |
| `/apply` 程序化调用 | 同步等 LLM，秒级~ tens of 秒 | confirmed 命中时**毫秒级**返回 |
| 存储与内存 | 无 | 每条约 250B，1 万条 ≈ 2.5MB；加载 <10ms、写入 <5ms、常驻内存 <5MB |
| 最坏路径（全 miss） | — | 与现状等价（prompt 还更小），无退化 |

调用次数模型：设文件流共 N 份、不同表头集合 T 种（N≫T），LLM 调用从 **O(N) 降为
O(T + 新增表头批次)**。周期性上报（同一模板反复来）场景首份冷启动、之后命中率≈100%；
零散异构文件常见列（姓名/时间/证件号）也能命中 60~90%。

## 6. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 缓存污染（错误确认传播到所有后续文件） | 来源徽标全程可见；审计字段（谁确认/何时/来源模型）；管理页可改可删；rejected 防回锅 |
| 名单变更后语义漂移 | 读时校验 target 有效性，orphaned 标记 + 管理页"重新指派"（名单改名后一键把旧映射改指新名） |
| 同名异义（「时间」在不同表里指开始/结束） | 冲突弹窗处置；观察冲突率再决定按模板分域（§7-3） |
| 压缩键误合并 | 压缩键仅作 confirmed 之后的兜底档，且要求名单内存在精确同名 target 才生效 |
| 建议级映射误用 | `/apply` 默认不吃建议；交互路径建议可见可改，不静默 |
| 并发写坏文件 | 进程内锁串行化 + tmp/`os.replace` 原子替换（沿用 `save_config` 模式） |

## 7. 决策记录（2026-09-26 已拍板）

1. **确认权限 → 操作员确认、管理员维护**：识别完成后操作员（登录用户）在预览/复核区
   确定哪些字段过滤，确认/否决动作记录姓名可审计；学习记忆的修改维护（编辑目标、删除、
   清空、导出、orphan 重新指派）归管理员，接口权限按 §3.4 落实。
2. **`/apply` 默认策略 → 保守默认保留**：已核实仓库内**无调用方**——轨迹速写解耦后自带
   `filter_local.py`（解耦文档 K-4/D-9，修补后零跨插件调用）。`/apply` 保留只吃
   exact+confirmed 的保守默认，`use_suggested` 作为可选参数留作未来调用方显式放宽，
   现状不影响任何人。
3. **模板分域时机 → 接受排期**：v1 全局键 + 冲突弹窗，待线上冲突率数据出来再评估按
   表头集合指纹分域。
4. **清理与上限（2026-09-26 拍板）→ 不采用主动清理策略**（不做 180 天未命中自动清理）；
   条目上限管理员可配（`mapping_limit`，默认 10000、范围 100~100000），到顶只拦自动
   新增建议，确认/改指不受限，调低不删除已有条目。
5. **二次确认拦截范围（2026-09-27 拍板）→ 只拦建议级判定**：精确同名、已确认映射
   （含确认删除）直接生效不拦；LLM 新判定与未确认建议进二次确认。防止 LLM 误判的同时
   避免记忆热后重复确认的摩擦（§8.1）。
6. **匹配修正边界（2026-09-27 拍板）→ 不动已确认条目**：重判范围=建议级（含失配建议）；
   结果写回建议级持久化，管理员逐条/全部**采纳后才升级 confirmed**（§8.2）。
7. **确认删除压过名单同名字段（2026-09-27 拍板）→ 允许，带提示与标记**：操作员确认删除
   保留名单内的同名字段时，确认前弹提示（后果跨文件持续生效）；管理面板对该条目挂
   「名单内」徽标，删除该记忆条目即恢复名单效力（§8.1）。

## 8. P3 设计（2026-09-27 拍板，待实施）

### 8.1 提案式二次确认 + 否决记忆联动（P3a）

**目标**：LLM 误判不得静默进入产出文件；用户的最终决策反向写入记忆。

**判定分类**（前端按 `/result` 的 kept/removed_detail source 字段划分，后端零改动）：

| source | 类别 | 行为 |
| --- | --- | --- |
| exact / confirmed / confirmed_drop / excluded / empty / hard_unmatched | verified | 直接生效，只读展示 |
| llm / llm_drop / suggested / suggested_drop | **proposal** | 进二次确认，可切换 |

**交互流程**（双重过滤缺省化后大模型判定始终参与；大模型不可用降级为仅精确匹配时全
verified，不出现确认块）：

```
提交过滤（管线照旧）→ 任务 done
  ├─ 无 proposal 列 → 不出现「最终确认」块，直接下载（记忆热后的常态）
  └─ 有 proposal 列 → 结果区出现「最终确认」块：
        proposal 列 = 可切换胶囊（保留/删除，来源徽标沿用）；
        verified 列 = 只读 chips；
        [✓ 确认并下载]
```

「✓ 确认并下载」的动作序列（前端）：

1. **决策写记忆**（把关动作，用户明确决策才算确认的口径不变）：
   - 采纳的建议（保留）→ `POST /mappings/confirm {key,target}`（升级 confirmed）；
   - 建议保留改删除 → `POST /mappings/reject {key,原target}` + `confirm {target:""}`
     （负映射 + 原对进 rejected 防回锅）；
   - 建议删除改保留 → `confirm {key,用户选的名单字段}`（409 冲突弹窗沿用）；
2. **名单内删除提示**（§7-7）：待删除列名 ∈ 当前保留名单时，确认前
   `window.confirm` 警示"将跨文件持续生效并优先于名单"；
3. **重跑折算**：确认区调整过的列并入 exclude（改删）/columns（改留），与预览的
   touched 机制合并，带 staged_id 重跑 `/filter`——已确认映射命中缓存，重跑毫秒级；
   无调整则直接下载已生成文件（建议级条目被采纳后，本次文件按建议过滤的结果与
   用户决策一致，无需重跑）。

预览环节同步收口：预览 chip 手动点掉**且该列原判定为 verified（exact/confirmed）**时，
提交前同样弹名单内删除提示（口径与确认区一致）。

### 8.2 匹配修正（P3b，管理员功能）

**目标**：管理员一键让 LLM 复核记忆中的建议级条目，产出 diff 供采纳，结果持久化。

| 项 | 设计 |
| --- | --- |
| 触发 | 管理面板「🔍 匹配修正」按钮 → 范围确认框（仅建议级+失配；**已确认条目一律不动**，§7-6） |
| 接口 | `POST /mappings/recheck`（管理员）→ 异步任务；`GET /mappings/recheck/<task_id>` 轮询进度与结果 |
| 范围 | `status=suggested` 全部条目（含 orphan 失配——借机让 LLM 重新映射到当前名单） |
| 执行 | 每批 100 条串行调 LLM（输入= sample 原文表头 + 当前 target + 当前名单；输出 `{"mappings":{...}}`；名单白名单过滤 + rejected 拦截防回锅） |
| 写回 | 新结果**写回建议级**（覆盖原 suggested、更新 model/prompt_ver/时间；rejected 拦截的对不写回）——"写入映射表持久化"成立且不翻案 confirmed |
| 产出 | diff 清单 `{key, sample, old_target, new_target}` 一次返回；前端展示「原映射 → 新建议」表 |
| 采纳 | 逐条「采纳」或「全部采纳」→ 走既有 `confirm`（confirmed_by 记管理员；409 冲突弹窗沿用）；不采纳的建议条目保持写回后的新值 |
| 量级 | 100 条/批约 3~5k tokens、10s 内/批；2000 条 ≈ 20 批、1~3 分钟（异步进度条） |

### 8.3 映射表单列手风琴 + 滚动（P3c，布局按真实数据形态修订）

> 初版为主从分栏（左分组右明细）；按真实数据形态——**名单可达数千条、单字段映射通常
> 仅数十条**——修订为**单列手风琴**：主从的"宽明细"优势不存在，分栏反而挤压表格宽度。

- **结构**：保留名单逐项为可折叠节点（原生 `<details>`，带已映射计数徽标）+ 虚拟分组
  节点：「确认删除」（target="" 全部，含「名单内」徽标）、「失配」（orphan）、「未学习」
  （名单中既无正向映射、也无自身学习记录的字段——暴露覆盖缺口；大名单时只罗列前 50 个）、「全部条目」；
- **懒渲染**：初始只建 summary 行（1500 节点实测 64ms），子表在首次展开时构建——渲染
  压力与名单长度相关、与映射总量解耦；展开状态跨刷新保持；
- **过滤框两层口径**：字段名命中 → 显示该节点全部条目；仅条目命中 → 该节点自动展开
  且只显示命中条目；「未学习」按字段名过滤；搜索词残留时（浏览器表单恢复）过滤态可见；
- **滚动**：手风琴容器 `max-height`（420px）+ `overflow-y:auto`；上传预览胶囊区、复核区
  同口径加滚动上限；
- **数据源**：沿用 `GET /mappings` 全量 + 前端分组（1500 名单 + 万条映射实测流畅；
  名单超 5000 字段建议配合过滤框使用；接近上限 10 万的极端场景再评估虚拟滚动/后端分页，
  记远期 TODO）。

## 9. P4 设计（2026-09-27 拍板，待实施）

### 9.1 决策记录

8. **加权统计转正（2026-09-27 拍板；判据经实施期修正）**：被动采纳计票——建议级条目
   积累 keep/drop 票，**同向 ≥5 票且零翻转 → 自动升级 confirmed**（confirmed_by 记
   「加权转正」，可追溯可人工推翻）；显式确认（✓）维持立即转正不降级。
   ※ 初稿的「Wilson 下界 ≥0.95」在 5 票时数学上不可达（5/5 一致的下界仅 0.57，需 73 票），
   实施期改为同向一致票数判据，Wilson 比率保留为展示指标。
9. **删除→保留翻转 → 待重映射（2026-09-27 拍板，取代"仅本次保留"方案）**：翻转时票
   +1（keep）、条目转 `remap` 状态——退出负建议判定路径、管线临时保留（来源标注
   「待重映射」）、纳入失配分组与匹配修正范围，由管理员经 LLM 重匹配后最终确定。
   依据：用户明确说留的列被系统反复删，比多留一列等管理员确认更不可接受。
10. **匹配修正范围校准（2026-09-27 拍板，回归初衷）**：默认只复核**失配**（orphan 名单
    变更 + remap 待重映射）；"包含全部建议级"作为可选扩展参数。空失配且未选扩展 → 400。
11. **confirmed 加权治理（2026-09-28 拍板）**：已确认映射对后续用户同样开放异议——
    非管理员的改指/否决**不立即覆盖**，条目降级回建议级（现任目标不变）、异议计一票，
    进入重议；**连续同向 ≥5 票（streak）重新转正**。加权机制由此覆盖全部记忆状态：
    个别用户的特殊需求只值一票、只影响其当前文件，集体共识决定记忆走向；管理员
    改指/否决维持立即生效（记忆维护者例外）。

### 9.2 加权统计（转正机制，含 confirmed 治理）

- 条目新增 `keep_votes` / `drop_votes` / `flips` / `streak`（连续同向票数）/ `last_vote_dir` /
  `last_vote_at` / `dissent_by` / `dissent_at`（schema 向后兼容：旧文件加载缺省 0/空）；
- 计票点：确认流四态 + 被动采纳 + **confirmed 异议**——采纳保留 → keep+1（并 confirmed）；
  采纳删除 → drop+1（并 confirmed 负映射）；保留→删除翻转 → drop+1（rejected + 负映射）；
  删除→保留翻转 → keep+1 + 转 remap；整批确认中未翻转的建议项 → 各 +1 票不改状态；
  **非管理员对 confirmed 的异议 → confirmed 降级回建议级（现任目标不变）+ 异议方向计一票**；
- 转正判据（每次计票后评估）：建议级 + **连续同向票 streak ≥5**（方向变化即清零重计）：
  - 与条目自身方向一致 → 升级 confirmed（负建议转确认删除）；
  - **反向多数同样定论**：keep 建议被连续 5 张 drop 票 → 转确认删除；负建议被连续 5 张
    keep 票（集体说留但无目标）→ 转 **remap 待重映射**（交管理员重匹配定目标）；
  - 早期一次异议只重置 streak，后续共识可重新定论；持续分歧（来回翻转）→ 停留建议级
    持续提案（翻转率 = 冲突信号，交管理员 / 模板分域）；
- 展示：手风琴明细加「票数」列（保留票/删除票）；转正条目徽标「加权转正」；被异议降级的
  条目徽标「重议中」（记 dissent_by/at）；
- **收尾补全（2026-09-28）**：① remap 的反向多数——连续 5 张 drop 票 → 集体定论删除；
  ② 被动采纳**按用户去重**（同一用户同一条目只计一次，防单人刷票；显式动作不受限）；
  ③ **orphan confirmed 纳入匹配修正**（名单变更的已确认失配：LLM 新目标有效 → 降级建议级
  进 diff 待采纳）；④ 预览 remap 预填（待重映射徽标/预保留，消除预览-结果不一致）；
  ⑤ 治理统计行（加权转正/重议中/有翻转）；
  ⑥ 异议降级后复核行补 ✓ 入口（提交人可立即改主意）。

### 9.3 待重映射（remap）

- 触发：最终确认中"删除→保留翻转"（用户不指目标）；
- 管线行为：remap 条目**临时保留**该表头（matched 标注「待重映射」，source=remap_keep），
  不进负建议判定、不逐轮进 LLM（remap 期间该表头视为已决：保留）；
- 失配分组：orphan 与 remap 合并展示，徽标区分「名单变更」/「待重映射」；
- 重映射闭环：recheck（默认范围=失配）→ LLM 从名单重匹配 → 结果写回（remap → suggested，
  进 diff）→ 管理员采纳 → confirmed。

### 9.4 匹配修正范围校准

- `POST /mappings/recheck` 默认范围 = 失配（orphan suggested + remap）；请求体可选
  `scope: "all_suggested"` 扩展为全部建议级；空失配且未选扩展 → 400 提示；
- 前端范围确认框更新措辞（默认"仅失配条目"）。

### 9.5 样本值注入（准确性）

- 未命中子集每列注入前 3 个非空样本值（单个截断 20 字符），提示词版本升至 PROMPT_VER=2
  （落库归因）；prompt 体积可控（miss 子集 × 3 值）。

### 9.6 测试要点
