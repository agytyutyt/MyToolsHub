## 0. 结论速览

1. **商店 = 主包第二核心插件**（需求①）：id=`store`，走 admin 的定位先例——随主体分发（`CORE_PLUGINS` 白名单入列）、可单独升级、不可卸载；**独立完整用例** = 自有 frontend + backend + 数据，浏览器与桌面端同页可用，不依赖 admin 即可浏览。
2. **两类别 + 三条 runtime**（需求②④）：商店分**「依赖」「插件」**两个类别；条目上架时声明 `runtime`（`local` / `server` / `dep-slot`）与**依赖版本**（requires，从包 manifest 自动提取、上架表单确认）。
3. **管理面在 admin 后台**（需求③）：admin 插件新增「商店管理」页——上架 / 下架 / 审核 / 统计；机器校验复用各包链；审核状态机 = 待审核 → 已上架 → 已下架。
4. **解耦 = 数据即接口**（需求⑥）：插件清单存放于服务器端 `数据根\store\`（商店子系统数据区，非任何插件私有数据）：`catalog.json`（admin 写 / store 读）、`packages\`（admin 写 / store 读+分发）、`stats.jsonl`（store 写 / admin 读）；**每文件单一写方 + 原子写 + 零跨插件代码调用**（插件间独立铁律保持）。
5. **客户端拉包安装**（需求⑤）：商店页经中继直出（类 A 同款，页面只有一份）；安装按钮 `jz-shell` 门控；点击安装 → 同源 `/local-api/store/preflight` + `/install` → 能力层**以用户会话**从商店下载 API 拉包 → sha256 对 catalog → `pkg_install` 单入口 → 落位客户端安装目录 `local-plugins\<id>`（依赖类落 `runtime\pylibs`）→ 热插拔既有口径。
6. **v1 结论保留**：catalog 字段与共享盘 index.json 同构（商店 API 投影层保证客户端契约不变）；`install(pkg_source)` 单入口、哈希必校验、`relay_whitelist.json` 与商店正交（R2）。
7. **全生命周期同权（需求⑦，2026-10-05 补充）**：商店内可对插件**下载 / 安装 / 升级 / 卸载 / 停用**——停用只置禁用态，**包与数据保留在本地**，可随时启用恢复；操作**不区分管理员/办事员**（管理面同样不设角色门槛）；生命周期操作复用既有 `/local-api` 接口，商店页成为本地插件生命周期的主入口。
8. **server 插件双包模型（需求⑧，v2.2）**：server 插件 = **前端包 + 后端包**两个分发物（同版本号成对）——**后端包在发布环节自动部署运行到服务器**（走 admin inspect/apply 链，含备份回滚）；桌面端「安装」server 条目**仅指安装前端包**到客户端本地（页面本地直出、API 经既有中继）；未安装/停用/卸载时页面自动回退**中继直出**（零安装体验与浏览器路径不破坏）。
9. **隔离架构（需求⑩，v3.0）**：主应用与各 server 后端包**并列进程**运行，由独立**管理进程（supervisor）**统一托管（启动编排/健康探针/崩溃拉起+熔断/升级停换起/回滚/孤儿收割/日志归集；Windows 服务化）——插件 native 崩溃/OOM/失控循环**不连坐主应用**，主应用对失败插件兜底 503；身份=共享 `SECRET_KEY`+Cookie 透传+worker 会话自验（业务插件零改动）；依赖默认共享运行时，**venv 为可选项**（特殊依赖版本插件，商店目录标注 `deps_mode`）。

## 3. 总体设计

### 3.1 架构与解耦（需求 1/3/6）

```
服务器（主包，业务权威）
├─ admin 插件【写面】──上架/下架/审核/统计──► 数据根\store\          ← 解耦接口（数据即契约）
│                                              ├─ catalog.json      admin 写 ← store 读
│                                              ├─ packages\<包文件>  admin 写 ← store 读+分发
│                                              └─ stats.jsonl       store 写 ← admin 读
├─ store 插件【读面，核心插件】──只读 catalog/packages──► 只读 API + 页面 + 下载（统计落点）
└─ 会话中继（批次 3 既有）──► 桌面客户端（能力层 127.0.0.1）
       商店页经中继直出（同源）──安装按钮（jz-shell 门控）──► /local-api/store/preflight|install
                                              能力层以用户会话拉包 → sha256 → pkg_install 单入口
                                              → local-plugins\<id>（依赖类 → runtime\pylibs）
```

**解耦三律**（需求⑥「共用数据，但不干涉」的实现口径）：

1. **数据即接口**：两插件之间唯一的交互面是 `数据根\store\` 的三个契约物（§3.4），无 import、无后端互调、无前端跨插件 fetch（插件间独立铁律 / C-11 保持）。
2. **单一写方**：每个契约物只有一个写方（catalog/packages=admin，stats=store），另一方言只读；并发损坏由原子写（tmp + `os.replace`，同 `save_client_config` 模式）兜底，频率低（上架/下架级）无需加锁。
3. **数据区归属**：`数据根\store\` 是**商店子系统数据区**（框架级共享区，同 `config\tools.json` 的定位——系统数据、admin 维护、框架读），**不是** store 插件私有数据——避免复现「admin 跨插件写数据文件」的解耦反模式（20260929 质量报告 P0 项）；store 插件自己的私有数据（页面配置等）仍在 `数据根\plugins\store\`。

### 3.2 商店插件（读面，需求 1/2）

- **包形态**：常规 server 插件（`manifest.json` + frontend + backend `register(app)`），id=`store`，入 `CORE_PLUGINS`；`tools_entry` 注册进 `config/tools.json` → 主界面工具网格自动出现「插件商店」卡片，桌面端点击 → `/tool/store` → iframe 经中继直出（与类 A 插件完全同款，客户端零 fork）。
- **frontend（一个页面服务两端）**：「依赖」「插件」两类别页签 + 搜索 + 详情（名称/版本/体积/changelog/**依赖版本声明**/发布时间/来源）；操作按钮以 `html.jz-shell` 结构类门控（既有模式：本地插件管理入口同款）——浏览器路径可浏览 + 下载包文件，桌面端才出现安装/生命周期按钮（红线 2：浏览器功能不减）。
- **逐条目操作矩阵（需求⑦，状态感知）**：未装 → 「安装」（local/dep-slot）；已装且 catalog 版本更新 → 「升级」（hybrid 走秒级重启口径）；已装 → 「停用/启用」「卸载」；全部条目 → 「下载」。生命周期操作全部走客户端既有 `/local-api` 接口（§3.5/§4.3），**商店页由此成为本地插件生命周期的主入口**——原 local-admin 页降级为兜底入口（离线装包）与依赖页签（O1）。
- **backend（只读 + 统计）**：
  - `GET /plugin/store/api/catalog`：读 catalog.json，**防御性校验**（schema/字段/路径安全），按状态过滤（只出已上架版本），投影为 flat 条目（每 id 最新已发布版，字段与共享盘 index.json 同名同义 + runtime/requires 扩展）——客户端契约与 v1 兼容；
  - `GET /plugin/store/api/download/<id>/<version>`：流式回包文件（不全量缓冲），**落统计**（§3.4 stats.jsonl）；
  - 纪律：**catalog.json 与 packages\ 对 store 严格只读**；store 唯一可写的是自己的 stats。

### 3.3 admin 商店管理面（写面，需求 3/4）

admin 插件新增**「商店管理」页**（`admin-store.html` + admin 后端新模块 `store_admin.py`，admin 自有命名空间；与既有「插件管理」页并行不混用）：

| 功能 | 口径 |
| --- | --- |
| **上架** | 上传包文件 → **机器校验**（按包形态复用对应链：本地包=六连断言等价检查；服务器包=plugin-package.json 结构 + SHA256SUMS 抽查（**需求⑧：后端包+前端包两工件成对上传、同版本号**）；依赖包=组件包/槽包校验）→ 元数据表单（**类别 runtime**、显示名、描述、changelog；**依赖版本**从包 manifest requires 自动提取、人工确认；sha256/size 自动计算）→ 落 `packages\<规范文件名>` + 写 catalog（**待审核**） |
| **发布（含 server 部署）** | 审核通过即发布；**server 条目发布时由 supervisor 编排部署后端包**（校验→备份→停该 worker→替换→健康探针→起新版；部署失败=发布失败回退待审核并告警）——上传时绝不部署（保审核闸门）；该插件秒级窗口，主应用与其余插件零影响；local/dep-slot 条目发布即对客户端可见 |
| **部署运行管理（需求⑨⑩）** | server 后端包部署状态面板（=supervisor 控制接口薄客户端）：当前部署版本、部署历史（history 台账）、**重新部署**、**回滚上一版**（既有备份机制）；运行状态走 supervisor 健康探针；运行方式=E 并列进程（§3.9） |
| **审核** | 待审核队列 → 查看包详情与校验报告 → 通过（置已上架，记录 `{reviewer, at, note}`）/ 驳回（退回或删除）；**装机冒烟为审核必做项**（白名单外 jz_relay 取数等运行期问题在此暴露，见 R2） |
| **下架/回退** | 按版本粒度置已下架：下架最新版 = **回退**（可见性自动回落到最近已上架旧版，已装新版不提供降级）；下架全部版本 = 条目对客户端整体隐藏；均记 history（详见 §3.7 可见性规则） |
| **统计** | 读 `stats.jsonl` 聚合：按条目/版本/日的下载量、按用户（内网审计口径）；展示于管理页统计页签 |

版本语义：同 id 新版本 = 追加 `versions[]` 条目（同版本号重复上架拒绝，`--force` 语义不做——重包先下架）；catalog 中**每 id 最新已上架版本**即客户端可见版本。

**runtime ↔ 三类插件模型映射（GLM 方案 §1.2；需求⑨后口径）**：

| 商店 runtime | 三类插件 | 客户端工件（可安装） | 服务器工件（发布即部署） | 服务器交互方式 |
| --- | --- | --- | --- | --- |
| `server` | **类 A** | 前端包（纯静态） | 后端包（业务后端） | 页面与 API 全部服务器侧 |
| `server` | **类 C** | 前端包（静态 + **本地简单逻辑**，即现行 hybrid 形态：前端+进程内 register(app)/worker） | 后端包（**复杂/敏感操作**，API 型无页面） | 本地部分经 `jz_relay` 调**自身插件的服务器端点**（附用户会话）+ 框架级只读面 |
| `local` | 类 B | 单包（纯前端 / worker） | 无 | 无（离线） |
| `dep-slot` | —（非插件） | 依赖包 | 无 | — |

**安装语义矩阵**（需求②④的落点）：

| 条目 runtime | 类别 | 客户端行为 | 落点 / 生效 |
| --- | --- | --- | --- |
| `local` | 插件 | 安装按钮（jz-shell 门控） | `local-plugins\<id>`；worker 即时 / hybrid 升级秒级重启 |
| `server` | 插件 | 「安装」= **安装客户端工件**（类 A=前端包；类 C=前端+本地逻辑包，§3.5.1）；「下载包」仍可取后端包（服务器管理员） | 后端工件：发布即部署服务器（§3.8 进程内运行）；客户端工件：`<数据目录>\server-frontends\<id>\`（类 A 纯静态 / 类 C 另挂本地 mount），本地直出 + API 经中继 |
| `dep-slot` | 依赖 | 依赖类别一键安装（含插件安装时的联合安装） | 共享组件包 → `runtime\pylibs`（.pending）；版本槽包 → O1 触发后接 `pylibs\.slots`（同口径） |

依赖版本声明（需求④）的用途：catalog 条目 `requires` 驱动 preflight 预检与联合安装建议——「本机共享槽不满足 → 依赖类别存在 cv2 4.9 槽包 → 一键同装」，这是依赖类别与插件类别在安装流里的唯一耦合点，且全部发生在客户端本地判定。

**生命周期操作语义（需求⑦，除下载外均为客户端本机操作，天然不分角色）**：

| 操作 | 接口 | 语义与生效 |
| --- | --- | --- |
| 下载 | `GET /plugin/store/api/download`（服务器会话鉴权，不设角色） | 浏览器=普通文件下载；桌面端=落数据目录 `downloads\`（留档/转移，安装不经过此按钮——安装内含拉包） |
| 安装 | `POST /local-api/store/install`（§3.5 流程） | local / dep-slot；jz-shell 门控 |
| 升级 | 同安装（catalog 版本 > 已装版本时按钮亮起，`_ver_lt` 比对） | worker 即时；hybrid 走秒级重启口径（既有） |
| 停用/启用 | `POST /local-api/plugins/state`（**既有接口复用**） | 只置 `local_state` 禁用态：**包目录与数据根数据原样保留**（停用≠卸载），随时启用恢复；停用即从子应用/worker 摘除（L2 即时），本地 API 404「已停用」 |
| 卸载 | `POST /local-api/plugins/uninstall`（**既有接口复用**） | 删包目录；数据根内插件数据默认保留（与主包卸载语义一致，规范 §11 口径） |

### 3.5.1 server 插件双包模型（需求⑧，v2.2）

- **两个分发物（同版本号成对）**：
  - **后端包** = 既有服务器插件包**原样**（plugin-package.json + payload/，**仍含 frontend/**——服务器要靠它服务浏览器路径，部署链零改动）；
  - **前端包** = 新增工件 `JZToolsHub-<id>-前端-v<版本>.zip`（2026-10-08 改版前为 `JZToolsHub-前端-<id>-v…`）：frontend/ 静态文件 + `frontend-manifest.json`（**文件清单**，供能力层精确圈定本地伺服范围）。由服务器插件出包链同源顺带产出（T-O2-9）。
- **后端包**：审核通过**发布时**自动部署到服务器（admin inspect/apply：校验→备份→替换→按需重启；部署失败=发布失败回退待审核并告警）；**上传/待审核阶段绝不部署**（保审核闸门）；服务器侧卸载/回滚仍走 admin 插件管理（商店下架≠服务器卸载）。
- **前端包**：进商店目录，桌面端可安装——落位 `<数据目录>\server-frontends\<id>\`（与 `local-plugins\` 同级，随程序升级存活）；安装后该插件页面**本地直出**：能力层对「GET `/plugin/<id>/<文件>` 且路径命中已装前端包文件清单」的请求改本地伺服，**其余方法/路径照旧中继**（插件 API 全走既有中继通道）；**未安装/停用/卸载 → 自动回退中继直出**——零安装即用、浏览器路径（红线 2）完全不受影响。
- **类 C 的客户端工件（需求⑨）**：= 现行 hybrid 本地包形态（前端 + 本地简单逻辑：进程内 register(app)/worker），id 仍 `local-` 前缀、本地端点挂 `/api/local/<id>`；**服务器工件取同 id 去 `local-` 前缀**（如 `local-report-suite` ↔ `report-suite`），承载复杂/敏感操作，API 型无页面（浏览器路径零影响）。本地简单逻辑可离线运算，结果交服务器工件执行复杂/敏感操作。
- **jz_relay 白名单扩展（需求⑨）**：新增**自身插件命名空间**动态规则——类 C 本地部分可经 jz_relay 调用「自身 id 去 `local-` 前缀」的服务器端点（附用户会话，权限=用户本人）；框架级只读面（GET /api/tools*、/api/org/tree）不变；**其他插件端点仍 RelayError**（跨插件禁调用铁律不变）。本地运算结果上传服务器 = `server_data:true` 数据出机明示（既有口径）。
- **生命周期（需求⑦）全适用**：安装 / 升级（目录版本比对，前后端同版本成对发布，`api_version` 门控）/ 停用（=回退中继直出，本地副本保留）/ 卸载（删本地副本）。
- **server 条目 UX 修订（2026-10-08，真机反馈 + 口径确认）**：①**全部插件都提供「安装」「下载」两颗按钮**（按钮上不写说明文字；安装＝下载+安装、下载＝仅下载不安装）——server 条目的「下载」取**客户端工件（前端包）**（桌面端经能力层落 downloads\；浏览器路径 `?artifact=frontend`），**后端包不对用户暴露**（由管理员在上架/部署链留档）；按钮文案统一「安装 / 升级到」（不写「安装前端」），卡片体积只显示安装包（前端包）体积；②**安装/卸载只针对前端包**——插件上架后**默认在服务器端运行**，未装副本=中继直出；卸载=删本机前端副本、页面回退中继直出，**服务器侧后端包不卸**（不设"从主页隐藏/恢复显示"按钮；主页可见性仍由主界面「隐藏插件」单一入口负责）。
- **服务器端撤包口径（2026-10-08 拍板）**：服务器端后端包**只由商店管理里的 停用/卸载 撤下，且仅超级管理员可操作**（`/plugin/admin/store/srv-state` 停用/启用、`/withdraw` 卸载=撤下后端包）——「下架」只动客户端可见性、桌面端卸载只删前端包副本，两者都不碰服务器部署。**停用**=注册条目 enabled:false（清单/主页即时隐藏；路由随下次服务重启卸载；后端包保留，可随时启用）；**卸载**=撤下后端包（`plugin_admin.uninstall_plugin` 同源链：目录撤下、数据保留；E 形态插件先经 supervisor 停单元）——注册条目**保持启用**（工具清单由「目录缺失」自然隐藏），故「重新部署」即原样恢复、无需再点启用；两者均记 catalog history 台账，恢复路径=重新部署 + 重启服务。
- **依赖组件的服务器侧部署（2026-10-08 真机报告）**：商店「依赖」的**桌面端安装只落客户端**（`<客户端>
untime\pylibs`，供本地/混合插件后端）；**服务器侧插件**（shared-docs 需 python-docx/openpyxl/xlrd 等）需要组件在**服务器**（`<服务端>
untime\pylibs`）——口径与 server 插件一致：**上架（发布）即部署到服务器**（发布依赖条目时若已被某已上架 server 插件 requires 命中→自动部署；发布 server 插件时补装其 requires 命中的已上架依赖）；已上架历史条目用商店管理「**部署到服务器**」补装（同 `plugin_admin.install_component_package` 链，无需重启即生效），列表「服务器侧」列显示该组件的服务器端安装态。
- **本机移除显示口径（2026-10-08 真机定稿）**：桌面端「卸载」（server 条目）= 删本机前端包副本 **+ 在本机主界面移除该插件的显示**（记客户端数据目录 `config.json` 的 `hidden_tools`；`/api/tools` 合并时按本机清单过滤）；「安装」= 装回副本并恢复显示。**只影响本机**——不写服务器全局可见性、不加额外按钮、服务器端后端包与其运行状态一概不动。客户端端点：`GET/POST /local-api/plugins/hidden`（`/local-api/plugins` 响应回传 `hidden_tools`）。
- **版本漂移记账（RP8 扩展）**：已装前端副本可能落后于服务器后端——缓解=同版本号成对发布 + 商店升级提示 + `api_version` 门控 + 中继直出兜底。
- **红线 3 口径修订**：「壳不 fork、页面默认一份」保持——server 前端包是**需求方拍板的受控客户端副本**（用户经商店安装，非壳注入）；卸载/停用即回退中继单一真源。

### 3.6 与既有通道 / 红线的关系

- **共享盘通道保留**为离线兜底：`plugin_source` 配置 `{"type":"server"}`（默认，走商店插件 API）| `{"type":"share","index_path":…}`（共享盘索引，现状语义）；Source 抽象两实现，读取端零改动切换（接缝①）。
- **红线逐条核验**：红线 1（商店不含业务逻辑，路由裁决不变；**类 C 服务器交互面扩展=自身插件服务器端点（需求⑨，§3.5.1），其他插件端点仍不可达**）；红线 2（浏览器路径可浏览+下载；server 前端包安装按钮 jz-shell 门控，浏览器路径不可见不可用）；红线 3（壳不 fork、页面默认一份——server 前端包为需求⑧拍板的受控客户端副本，卸载/停用回退中继直出，§3.5.1）；红线 5（商店只分发代码包，类 C `server_data:true` 数据出机提示仍在安装时弹出；类 C 本地运算结果上传服务器同此明示）；红线 6（`local-` 命名空间 + mount 冲突拒装照旧）。
- **R2 白名单正交保留**：商店是分发面，`relay_whitelist.json` 是数据面闸门；商店下发的类 C 插件若需白名单外框架 API，须等客户端升级白名单（catalog 的 `api_version` 只门控 plugin_api，不覆盖白名单面）——审核装机冒烟必查项。

### 3.7 服务器端流程管理（状态机与台账）

**版本级状态机**（`versions[].status`；条目对客户端的可见性由「是否存在已上架版本」推导）：

```
            上架（机器校验通过）         审核通过                  下架
（出包） ──────────────────► 待审核 ──────────────────► 已上架 ──────────────────► 已下架
                              │  ▲                     │  ▲                     │
                          驳回│  │ 重提（须升版本号）   │  └── 重新上架（再走审核）┘
                              ▼  │                     ▼
                            已驳回
```

**可见性与回退规则**：

- **版本占号**：同 id 同版本号只要存在记录（含已驳回/已下架）即拒绝重提——问题包升版本号重来，保证版本号↔包内容一一对应；
- **可见性**：客户端 flat 投影 = 每 id「最新已上架版本」，存在已上架版本则可见，否则条目整体隐藏；
- **回退** = 下架问题新版即可（投影自动回落到最近已上架旧版；已装新版的客户端不提供降级——`_ver_lt` 语义天然保证不出现「升级到旧版」）；
- **元数据编辑**：name/description/changelog 可改（记 history）；`requires` 依赖声明随版本走——变更依赖须出新版本（它影响客户端预检与联合安装）。

**五段流程**（所有状态迁移在 admin「商店管理」页操作、原子写 catalog）：

| 阶段 | 动作 | 执行者 | 技术门禁 | 数据落点 |
| --- | --- | --- | --- | --- |
| 1 出包 | 各链出包 + 自校验（服务器插件/本地包/依赖包工具） | 插件开发者 | C 系构建校验（出包链内置） | 包文件 + sha256 旁挂（线下交付） |
| 2 上架 | 上传 → 机器校验 → 元数据表单（runtime 类别/依赖版本提取确认/changelog）→ 待审核 | 任意登录用户 | 按包形态复用对应链校验；版本占号检查；local 包 mount 冲突对已发布目录作提示性预检 | `packages\` 落文件；catalog 写 pending + submit 台账 |
| 3 审核 | 校验报告审阅 + **装机冒烟（必做）**：实机安装/升级走查、R2 白名单核查、依赖联合安装验证 | 任意登录用户（建议与提交者不同人——四眼为软约定，不作技术门槛） | 冒烟通过才可发布 | review + history 台账 |
| 4 发布/分发 | published 即对客户端可见；升级经商店页「升级」按钮到达（需求⑦） | — | — | flat 投影；`stats.jsonl` 累计下载 |
| 5 下架/回退/归档 | 按版本下架 / 回退 / 物理删除归档 | 任意登录用户；物理删除为线下维护动作 | — | status + history；`archive\` 归档（可选） |

**台账（过程留痕）**：全部记录在 catalog.json 版本条目内（`submit` + `review` + `history[]`，§4.1）——谁、何时、做了哪个迁移、校验与冒烟结论；**不设第四个契约文件**（单一写方纪律保持：admin 写 catalog、store 写 stats）。

**依赖包（dep-slot）流程差异**：状态机同上；第 2 段机器校验追加 wheel tag 预检（cp314 / py3-none-any，O1 口径）与 `requires_components` 一致性检查；第 3 段冒烟 = 装入验证客户端后验证共享槽/版本槽生效与依赖它的插件可用。

**与服务器插件部署链的衔接**：商店目录管「上架—审核—发布—下架」，**安装权威仍在 admin 三分法/批量升级**（升级方案 §5）。衔接增强项：E1 = `store_admin` 同步产出 schema-1 flat 的 `数据根\store\index-server.json`（仅 server 条目，字段与共享盘 index.json 同构）——admin 既有 `read_index`/`batch_apply`（`plugin_admin.py:1097`）零改造即可把商店目录当索引源（同插件读写自有产物，无铁律问题）；E2 = 管理页对 server 条目给「安装到本服务器」快捷入口（调 admin 既有 inspect/apply 链）。

> **v3.2「下架 vs 停用」组合口径与安装门（D22，2026-10-11 已实施）**：两个服务器侧动作语义
> 不同——**下架（delist）**只动 catalog 版本状态（影响未装者的可获取性；A 类服务器运行照旧）；
> **停用（srv-state，仅 A 类）**写 `config/tools.json` enabled=false（服务器功能全局下线）。
> 组合矩阵：下架×已装=照常可用；下架×未装=商店不可见、重新上架后可装（副本在=秒装）；
> **停用×已装=网格不显示**（全局下线优先于账号登记，副本保留、重启用自动恢复）；
> 停用×未装=商店条目仍在但**安装门拒绝**（preflight/install 对 server 条目校验 id 在服务器
> `/api/tools` 可见清单，不在 → 拒绝+「该插件在服务器端已停用或无权使用」）。C 类客户端工件
> 不受其服务器工件停用影响（离线降级语义照旧）；B 类无停用概念。完整矩阵与边界规则见
> `plan/20261011账号级插件安装与本地数据隔离-TODO（面向执行模型）.md` §2.6。

### 3.8 运行架构决策留痕与热插拔语义（需求⑨评估 → 需求⑩定稿）
