## 1. 校验口径（为什么有两种 md5）

- **`full`**：文件原始字节的 md5（含行尾）。Windows 下同一份内容可能因编辑器写成 CRLF/LF 而 `full` 不同——所以 `full` 只用于「同一目录内比对」和 vendor 文件（不编辑）。
- **`norm`**：把 `\r\n` 归一为 `\n` 后的 md5。**跨目录副本是否同源的判定用 `norm`**。
- 台账里凡标注「登记头」的条目：C 类客户端工件的文件头有 2 行「同源副本登记（…）」注释（规范 §16.15），它按各自源路径书写、必然不同，所以这类条目的判定口径是 **`norm` 去掉前 2 行**（记作 `tail3`）。
  ⚠ `tail3` **只适用于带登记头的那一份**；对无登记头的真源文件剥前 2 行会切掉真实代码行（实测会得到 `d9a61eb9…` 这种无意义值），真源用 `norm`/`full`。
- 校验命令（PowerShell/Git Bash 皆可，示例）：
  ```bash
  # norm（跨目录同源判定，真源与副本都用它）
  sed 's/\r$//' <文件> | md5sum
  # tail3（仅带 2 行登记头的 C 类工件副本）
  tail -n +3 <文件> | sed 's/\r$//' | md5sum
  ```
- **漂移定义**：同一「副本组」内应一致的校验值出现不同 = 漂移。处置只有两条合法出路——① 同步修（回到一致），② 在 §2 该条写下「有意分叉 + 理由 + 以谁为准」。**静默不一致视为缺陷。**

- **演进策略**：**各自独立演进**（非同步修）。声明位置：`plugins/trajectory-sketch/backend/filter_bridge.py:11-12`（「与 file-filter 的 `core.py` 同源副本、各自独立演进」）+ 两份 C 类工件文件首行登记头。

- **漂移处置**：**不比 md5**（比了也无意义，本就该不同）。约束改动的不是哈希而是**接口面**：`apply_filter(rows, mode, columns, post_rules, session)` 的入参/返回结构（`rows/kept/removed/mappings_used/replace_count/mode/warning`）四处必须同形，由 `plugins/trajectory-sketch/backend/test_filter_llm.py` 与 `tools/e2e/file-filter-c-tests.py` 各自钉住。改任一份时同步检查对端测试。

### 2.2 `bg_image.py`（工作表背景图片摘除，442 行 ×4 份，**同步修**）

| --- | --- | --- |
| `plugins/file-filter/backend/bg_image.py` | `57aac66b1758…` | `57aac66b1758…`（norm 与 full 同值，文件本为 LF） |
| `plugins/trajectory-sketch/backend/bg_image.py` | `57aac66b1758…` | `57aac66b1758…`（同上） |
| `client-plugins/local-file-filter/backend/bg_image.py` | `2b13265c0c81…` | `57aac66b1758…`（`tail3`） |
| `client-plugins/local-trajectory-sketch/backend/bg_image.py` | `1512a8f016ef…` | `57aac66b1758…`（`tail3`） |

- **现状**：4 份**实质同源**——两份服务器版逐字节相同；两份 C 类工件 = 服务器版 + 2 行登记头，**剥头后与服务器版同值**（四份的归一后基准都是 `57aac66b1758…`）。两份工件的登记头首行各自写明所本（`plugins/file-filter/...` / `plugins/trajectory-sketch/...`），这是它们 `full` 互不相同的唯一原因。
- **演进策略**：**同步修**。任一 bug 修复要同时落到 4 份（报告 §2.2 C4 建议 3：「bg_image.py 修 bug 时两份同步，直到任一方声明分叉」——现为 4 份）。
- **漂移处置**：核对口径 = 真源用 `norm`、带登记头的工件用 `tail3`，四份应全等于 `57aac66b1758…`；一旦某份不等且无声明，即漂移。回归：`python -m unittest test_bg_image`（覆盖 file-filter 侧行为）。
- **建档时点的新事实**：报告只登记了 ×2（服务器对）。建档实测发现 C 类工件拆分又派生了 2 份，共 4 份——这正是「无台账则漂移只能偶然发现」的例证。

### 2.4 QR 传输编解码四实现（**同源实现、非逐字节副本**）

报告 C3/C4 的「编码实现四份 / 帧头常量三份」：

| 路径 | 角色 | 体量 |
| --- | --- | --- |
| `plugins/trajectory-convert/backend/routes.py` | 编码端 | 帧头常量段 + 编码段（报告称 :481 起） |
| `plugins/info-transfer/backend/routes.py` | 编码端 + 解码端 | 帧头常量段 + `PAYLOAD_SAFETY`（:217）+ 分块 `_chunk_data` |
| `plugins/map-marker/frontend/generate_qr_stream.py` | 编码端（离线生成脚本） | 生成 QR 序列 |
| `plugins/qr-video-decode/backend/routes.py` | 解码端 | 帧消费/FEC 重建（报告称 :145-189） |

- **校验方式（不适用 md5，改用契约台架）**：四份文件是**各自插件的完整后端**，整体 md5 永远不同，比 md5 没有意义。可比的只有**协议常量段**——它的基准由 `tools/e2e/qr-protocol-consistency.py` 断言（四处实现必须对同一测试向量产出/接受同一帧），**基准值与逐字节布局的真源 = `docs/design/二维码传输协议-契约文档.md`**，不在本文复述。
- **演进策略**：协议面 = **同步**（帧头布局/FEC 参数/版本字段任一端改动必须四端齐改并跑一致性台架，否则静默坏）；实现面 = **各自演进**。
- **已声明的有意分叉**：`info-transfer` 的 `_chunk_data` 乘 `PAYLOAD_SAFETY = 0.9`（`plugins/info-transfer/backend/routes.py:217`，用于 :1569 与 :1752）。**这只收紧编码端的分块，解码端从帧头读 `seg_n/k/m`，不受影响**——属编码端本地调参空间，契约文档已把它划在互操作面之外。下一个改动者据此不必「修平」它。
- **漂移处置**：一致性台架红灯 = 协议漂了。定位顺序：先比对四处实现的帧头常量段与测试向量期望，再判是谁偏离契约（契约文档为唯一真源）。

### 2.6 任务/会话样板（`_viewer()` 等，11 份 routes.py，**成本记录**）

- **现状**：`grep -rl "def _viewer" plugins/*/backend/routes.py client-plugins/*/backend/routes.py` 命中 **11** 份（报告写作 6–10，建档时实测 11）。同类还有异步任务三件套（`task_id` + 轮询 + TTL 清理）约 6 份、前端 `toast/fetch/copy` 样板各 4–6 份。
- **演进策略**：**登记为成本，不作为整改项**（报告 §6.3 明确撤回合并）。它们是插件独立性的直接代价，宿主侧已有成功先例。
- **漂移处置**：不逐份比对。真正需要盯的是**语义口径**：会话取用户、任务归属校验（创建者或超管）、TTL 清理三处，跨插件行为应当一致；相关判定口径分歧已单独立项为代码质量整改清单 **D5**（放行版 vs 收紧版），需拍板而非靠台账收敛。

## 3. 与门禁的关系

- 出包链现在拦的是**耦合**（C-11 跨插件 import / C-4 依赖声明 / C-13+L-13 前端 API 路径纪律），**不拦重复**——重复是合法成本。
- 本文的基准值是「人工可核对的契约」：改动副本时对照 §2 的校验命令自证同步或声明分叉。
- 构建期自动漂移提示（warning，不阻断）尚未实施，见 §4。

## 4. 后续优化方向

1. **构建期 md5 漂移提示**：在 `tools/build-plugin-package.ps1`（与 C-11 同宿主）加一条 warning——对 §2.2/§2.3 这类「同步修」组比对 `tail3`/`full`，不一致时提示「副本已分叉，请确认是否为有意演进并更新台账」。报告建议 2，未开工。
2. **基准值入机读文件**：本台账是给人看的；若要门禁化，应把 §2 的基准值抽成 `tools/` 下的 json（避免 Markdown 表格成为断言源）。
3. **`_probe_fix` 类孤儿产物扫描**：C2 清出的孤儿 `.pyc` 属同类卫生问题，已由 `tools/e2e/lint-static-rules.py`（S12 门禁扫描器）覆盖后可考虑并入。
4. **不变式台架化**：§2.5 的三条不变式（不持 Key / 请求线程 resolve / 名单外丢弃）目前靠人工自查，可做成 AST 台架挂进 Q7 扫描器。

## 5. 维护纪律

- 新增同源副本时**必须**在本页加一条（路径对 + 演进策略 + 基准值），并在副本文件首行加登记头（规范 §16.15）。
- 同步修后**必须**更新该条基准值，否则下一次核对会出现假红灯。
- 有意分叉必须写清「以谁为准 + 为什么」，没有理由的分叉按缺陷处理。
