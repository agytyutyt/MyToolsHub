## 1. 校验口径（为什么有两种 md5）

- **`full`**：文件原始字节的 md5（含行尾）。Windows 下同一份内容可能因编辑器写成 CRLF/LF 而 `full` 不同——所以 `full` 只用于「同一目录内比对」和 vendor 文件（不编辑）。
- **`norm`**：把 `\r\n` 归一为 `\n` 后的 md5。**跨目录副本是否同源的判定用 `norm`**。
- 台账里凡标注「登记头」的条目：C 类客户端工件的文件头有 2 行「同源副本登记（…）」注释（规范 §16.15），它按各自源路径书写、必然不同，所以这类条目的判定口径是 **`norm` 去掉前 2 行**（记作 `tail3`）。
  ⚠ `tail3` **只适用于带登记头的那一份**；对无登记头的真源文件剥前 2 行会切掉真实代码行（实测会得到 `d9a61eb9…` 这种无意义值），真源用 `norm`/`full`。
- **`.py` 行尾基线 = LF（2026-10-16 决策）**：本仓 `.py` 一律 LF。`.gitattributes` 将声明 `*.py text eol=lf`（**当前尚未声明**，落地见 §4 第 5 条）。**这是 `full` 口径可用的前提**——`full` 含行尾字节，工作区 `.py` 若在 CRLF/LF 间漂移，就会出现 `norm`/`tail3` 全过、唯独 `full` 假红灯（2026-10-16 实测到 8 项，见 §4 第 5 条）。
  - 根因（**对 git 不可见，故不可能是「某次提交的改动」**）：本机 Git 系统级 `core.autocrlf=true`（`C:/Program Files/Git/etc/gitconfig` 默认值，非本仓设置）会把 `.py` 检出为 CRLF，而**提交时归一为 LF**；本仓又从未为 `.py` 声明 eol 规则 → 工作区实际行尾取决于「最后一次写它的是谁」：git 检出写 CRLF，而脚本以 `io.open(..., newline="")` 写入则得 LF（`tools/e2e/adapt-*.py` 即此写法）。两侧归一后相等，**永不进 diff**，只有按原始字节比对的 `full` 看得见。
  - 因此遇到 §2 某条 `full` 红灯而同一行 `norm`/`tail3` 绿灯时：**先判行尾，不要先判内容漂移**。
- 校验命令（PowerShell/Git Bash 皆可，示例）：
  ```bash
  # norm（跨目录同源判定，真源与副本都用它）
  sed 's/\r$//' <文件> | md5sum
  # tail3（仅带 2 行登记头的 C 类工件副本）
  tail -n +3 <文件> | sed 's/\r$//' | md5sum
  ```
- **漂移定义**：同一「副本组」内应一致的校验值出现不同 = 漂移。处置只有两条合法出路——① 同步修（回到一致），② 在 §2 该条写下「有意分叉 + 理由 + 以谁为准」。**静默不一致视为缺陷。**

### 2.4 QR 传输编解码四实现（**同源实现、非逐字节副本**）

报告 C3/C4 的「编码实现四份 / 帧头常量三份」：

| 路径 | 角色 | 体量 |
| --- | --- | --- |
| `plugins/trajectory-convert/backend/routes.py` | 编码端 | 帧头常量段 + 编码段（报告称 :481 起） |
| `plugins/info-transfer/backend/routes.py` | 编码端 + 解码端 | 帧头常量段 + `PAYLOAD_SAFETY`（:217）+ 分块 `_chunk_data` |

- **演进策略**：协议面 = **同步**（帧头布局/FEC 参数/版本字段任一端改动必须四端齐改并跑一致性台架，否则静默坏）；实现面 = **各自演进**。
- **已声明的有意分叉**：`info-transfer` 的 `_chunk_data` 乘 `PAYLOAD_SAFETY = 0.9`（`plugins/info-transfer/backend/routes.py:217`，用于 :1569 与 :1752）。**这只收紧编码端的分块，解码端从帧头读 `seg_n/k/m`，不受影响**——属编码端本地调参空间，契约文档已把它划在互操作面之外。下一个改动者据此不必「修平」它。
- **漂移处置**：一致性台架红灯 = 协议漂了。定位顺序：先比对四处实现的帧头常量段与测试向量期望，再判是谁偏离契约（契约文档为唯一真源）。

5. **`.py` 行尾统一 LF（2026-10-16 已拍板「B 方案」；文档先落，改动待统一开工）**

   背景：2026-10-16 全仓核对实测 `tools/e2e/ledger-drift-check.py` **8 项 `[DRIFT]`/25 项**，全部是 `full`（原始字节）红灯而 `norm`/`tail3` 全过 → 机制上即「内容未变、只差行尾」（成因见 §1）。C-15 只 Warn 不 Die，故每次出包都打警告但不阻断。

   **决策**：把 `.py` 行尾钉为 **LF**（与既有基准一致——§2.2/§2.8 已记「文件本为 LF，full=norm」），从根上消除这一整类假红灯，并让工作区字节在各机器间确定化。

   **统一开工批次（一次性做完，勿半途）**：
   1. `.gitattributes` 追加（带注释，与既有 bat/ps1 段同风格）：
      ```
      # Python 源码行尾统一 LF（跨目录副本按原始字节比对的前提；2026-10-16 决策，见 docs/design/同源副本台账.md §1）
      *.py text eol=lf
      ```
      **范围只声明 `*.py`**：8 项 DRIFT 全是 `.py`；`jsqr.min.js`（§2.3）目前一致且属 vendor（不编辑），暂时不动，若后续 `.js` 出现同类假红灯再评估。
   2. `git add --renormalize .` 把工作区 `.py` 重写为 LF。**这是仓库级操作，须单独开一批**，执行前确认无进行中的其它未提交改动（或先 commit 存档）。
   3. 复跑 `python tools/e2e/ledger-drift-check.py`：预期 8 项归零（既有基准本就按 LF 记录）。
   4. 若仍有 `[DRIFT]`：说明该条基准当初是按非 LF 记的 → 按 §5 用现值重记该条，再跑 `--sync-check` 双向对齐。
   5. 跑一次根回归 `python -m unittest discover -s . -t . -p "test_*.py"`（全量重写 `.py` 后必须跑），并确认出包链 C-15 由 Warn 转通过。

## 5. 维护纪律

- 新增同源副本时**必须**在本页加一条（路径对 + 演进策略 + 基准值），并在副本文件首行加登记头（规范 §16.15）。
- 同步修后**必须**更新该条基准值，否则下一次核对会出现假红灯。
- **`full` 红灯而同行 `norm`/`tail3` 绿灯时，先判行尾、再判内容**（§1）。§4 第 5 条统一开工后 `.py` 恒为 LF，这类假红灯不应再现；**若再现，是「有工具以 CRLF 重写了 `.py`」，要查写入方，不是改基准掩盖**。
- 有意分叉必须写清「以谁为准 + 为什么」，没有理由的分叉按缺陷处理。
