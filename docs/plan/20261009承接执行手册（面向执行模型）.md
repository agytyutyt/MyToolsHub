## 1. 全局规则（每卡通用）

### 1.1 环境
- 仓库 `D:\JZToolsHub`；Git Bash；分支 `desktop`；python 用 PATH 上的 `python`（3.14）。
- `deploy/`、`build/`、`dist/`、`runtime/` 在 `.gitignore`（产物不入库）；入库的只有源码/文档/登记文件（如 `tools/plugin-packages.json`）。
- 控制台出现 `LF will be replaced by CRLF` 是正常警告，忽略即可。

### 1.2 提交与出包纪律
1. 动手前 `git status --short`：有**非本卡**的未提交改动 → 停下报告（别合并提交）。
2. 提交只用显式路径：`git add <文件1> <文件2>`；**禁止** `git add -A` / `git add .`；**不 push**。
3. 提交信息中文、格式 `类型(范围): 摘要`（如 `fix(info-transfer): …`；`chore(registry): …`；`docs: …`）。
4. 出包类：**先 commit（脚本/源码）→ 再构建（产物）→ 再 commit 登记文件**。遇 `index.lock` 冲突重试一次。

### 1.3 验收与红灯
- 每卡「验收」的命令必须实跑并把**关键输出**贴进 §B 记录；全绿才可给卡打 ✅。
- 红灯（命令报错/期望不符/门禁拦截）= **停本卡**：写失败报告（§A3）→ 继续下一卡（除非下一卡依赖它）。

### 1.4 禁止事项（全局）
- 不改卡内未列出的文件；不改 `docs/archive/`（冻结留证）。
- `HANDOFF.md` §3 等**带日期的历史记录条目**不改（只改“现状”性描述，如 §10 结构表）。
- 不在工具会话里跑整包 `build-deploy.ps1`（已知 `Remove-ObjectNotBound` 类问题，见打包部署手册故障表）。
- 不删既有文件，除非卡片明确列出该文件。

  - **A 页面（本地条目可用）**：起服务后浏览器登录管理后台，商店管理页逐项上传；**本地条目（10 个）**可直接页面 `approve`（handler 对 `runtime != "server"` 无部署分支，零副作用）。上传接口参考 `POST /plugin/admin/store/upload`（multipart：`runtime/file/frontend_file/name/changelog`）。
    ⚠ **服务器条目禁止走页面/HTTP 点「通过」**：HTTP approve 会先执行 `deploy_backend_package(PROJECT_DIR, …)`（`plugins/admin/backend/routes.py:2418`），本机 `PROJECT_DIR`=仓库根 → 直接把包覆写进 git 工作区 `plugins/<id>/`。
  - **B 脚本（服务器条目唯一推荐路径；本地条目亦可用）**：一次性脚本放 `.workbuddy/tmp/`（**不入库**）。关键事实：**`store_admin.review()` 本身不部署**（见其 docstring：自动部署由 HTTP 层在 approve 前执行），所以脚本按 HTTP handler 同序补上部署步、但目标改用**隔离目录**——这正是官方台架的同款做法（`tools/e2e/store-batch8-tests.py:301` 就是传隔离 `base_dir`）：
    ```python
    # q3_publish_server.py（一次性；sys.path 与 store_admin 导入段照抄 tools/e2e/store-batch8-tests.py）
    import os, sys
    ROOT   = os.path.expanduser("~/.jztoolshub")                        # ★ data_root（store_admin 内部再拼 store/）；写成 .../store 会造出 store/store/ 影子目录
    TARGET = os.path.expanduser("~/.jztoolshub/tmp/q3-deploy-target")   # 隔离部署目标（仓库外）
    os.makedirs(os.path.join(TARGET, "plugins"), exist_ok=True)
    for pid, ver in (("file-filter", "1.6.1"), ("trajectory-sketch", "1.3.1")):
        # 若尚未上传：先 sa.submit(ROOT, "server", 后端zip路径, form, by="admin", frontend_zip_path=前端zip路径)
        dep = sa.deploy_backend_package(TARGET, ROOT, pid, ver)  # 校验→备份→替换；备份落 ~/.jztoolshub/backups/
        assert dep.get("ok"), (pid, dep)
        assert os.path.isfile(os.path.join(TARGET, "plugins", pid, "manifest.json")), "部署未落盘"
        res = sa.review(ROOT, pid, ver, "approve", by="admin")   # 发布（review 自身不部署）
        assert res.get("ok"), (pid, res)
        print(pid, ver, "deployed(isolated)+published OK")
    ```
    - **禁止**把部署目标用作仓库根（覆写工作区），也**禁止**用 `deploy/服务端/JZToolsHub/`（会把插件混进下次主包 zip，破坏「主包只带核心插件」）。
    - 本地条目亦可用 B：直调 `sa.submit` + `sa.review`（无部署步）。正式跑前先 dry-run：只调 `check_local_plugin_zip` / `check_server_backend_zip` / `inspect_package` 验包，不落库。
  - 若 A、B 都不可行 → 停本卡、写失败报告、交人工。
- 注意：「发布即部署」语义保持成立——B 的隔离部署就是对这条链的真实验证；**真机部署在目标服务器执行**（管理后台「部署到服务器」/ `POST /plugin/admin/store/redeploy`）。若报「依赖不满足」：依赖类目 11 个组件包应已全部 published，先核对再重试，仍不过则停卡报告。
