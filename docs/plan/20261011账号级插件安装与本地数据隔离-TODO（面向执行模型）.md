## 0. 需求与目标语义（2026-10-11 需求方）

**需求原文**：①同一目标机上，账号 A 卸载插件后账号 B 也被移除——账号间应相互独立；服务器端记录"账号安装了哪些插件"，登录后只显示已安装的插件；②桌面端同时读取本机已装与账号已装：两者匹配→正常可用；账号已装而本机未装→卡片灰色蒙版 +「从云端下载」，点击后下载安装；③插件包多账号共用，数据按用户独立——插件只负责业务逻辑，数据的调用/保存/隔离由桌面端能力层负责（实现形式未定，可引入 supervisor），对插件不可见，按账号+插件分类管理；④插件卸载后不显示"已从本机移除"徽标；⑤B 类徽标改「本地」，C 类徽标为「离线降级」。

**目标语义（终态）**：

| 面 | 终态 |
| --- | --- |
| 安装态归属 | **账号级**：服务器记录每账号的插件安装集合（版本/时间/来源/启停），是网格显示的唯一依据 |
| 网格显示 | 登录后网格 = 该账号已装集合 ∩ 可见性（权限点/全局启用）；本机副本存在 → 正常卡；缺失 → 灰蒙版卡（「从云端下载」，点击即装） |
| 机器副本 | 纯缓存，多账号共用（账号 A 卸载不删副本；B 装同插件秒级完成）；当前账号未装 → 该插件本地 API/页面在本会话不可达（404） |
| 数据 | 本地插件数据一律落 `<客户端数据目录>\users\<账号>\plugins\<id>\…`（插件经 `jztools_data` 零感知）；服务器侧数据本为账号权威（不动） |
| 徽标 | A 类「在线」、B 类「本地」、C 类「离线降级」、依赖「依赖」；卸载后不再出现「已从本机移除」 |

## 2. 方案设计

### 2.1 账号安装登记（需求①，服务端契约）

**数据归属**：`<数据根>\store\installs.json`——store 子系统数据区（与 catalog/packages/stats 同域），**单一写方 = store 插件**（store 此前唯一写点是 stats.jsonl，本项为其第二个写点，仍单写方；admin 只读展示可选）。

```jsonc
{"schema": 1, "updated_at": "…",
 "users": {"<username>": {"<plugin_id>": {
    "version": "1.6.4", "installed_at": "…",
    "source": "store|upload|migrated",   // 安装来源（审计用）
    "enabled": true                       // 停用=该账号不显示（随账号的启停，D4）
 }}}}
```

**API（store 插件新增，会话鉴权、不分角色——沿用"本机操作不分角色"口径）**：

| 接口 | 语义 |
| --- | --- |
| `GET /plugin/store/api/installs` | 本人登记全量 → `{"installs":{id:{…}}, "updated_at":…}` |
| `POST /plugin/store/api/installs` | `{action: install\|uninstall\|enable\|disable, id, version?, source?}`；另支持批量 `{action:"install", ids:[…]}`（迁移补种用，幂等） |

- 写侧原子写（`jztools_data.atomic_write_json`），读侧防御性解析（坏行跳过）；
- 卸载 = 删本人该 id 记录；**不触机器副本**（§2.3/§2.4）；
- 客户端未登录不调用（401 语义照旧）。

### 2.2 客户端双源合成与云卡（需求①②）

**账号上下文（客户端）**：能力层新增账号上下文——登录/续期（既有 `refresh_identity`/`/api/session` 回包）时缓存 `username`；登出（镜像清空信号）清空；**离线快照**：账号 + installs 全量落 `<客户端数据目录>\account-state.json`（含 ts），离线/服务器不可达时按快照显示（保证断网可用），联网后刷新覆盖。

**网格合成（`api_tools_merged` 扩展，`capability_app.py:1260`）**：

1. 取三源：服务器 `/api/tools`（A 类元数据，含权限点/启用过滤）＋ `GET /plugin/store/api/installs`（账号登记）＋ 本机扫描（`scan_frontends` + `scan_local_plugins`）；
2. 以**账号登记**为显示全集（需求①"只显示已安装"）：未登记 → 不进网格；
3. 逐条判定：

| 登记 | 本机副本 | 网格表现 |
| --- | --- | --- |
| 有 | 有 | 正常卡（A=在线直出前端副本/API 中继；B/C=本地直出） |
| 有 | 无 | **灰蒙版云卡**：`machine_present:false, cloud:true`；按钮「从云端下载」 |
| 无 | 有 | 不显示（副本=其他账号的缓存；本地 API/页面本会话 404 隔离） |
| 无 | 无 | 不显示（商店里可装） |

4. 云卡元数据来源：商店 catalog flat（`/plugin/store/api/catalog`，含 local/server 条目 name/icon/description/accent/version）；已下架条目的极端情况 → 以 installs 记录 + `/api/tools` 元数据降级（缺图标用默认），并在卡上标「条目已下架」提示重装。
5. 本会话可用性门：当前账号未登记的插件 → `_find_local`/hybrid 挂载与 `/plugin/local-*` 直出**按当时账号登记过滤**（404「未安装」），防"机器有副本即可越权用"（登记变化即时生效，无需重启）。

**云卡交互（`main.js` `toolCard`）**：`cloud:true` → 卡片加 `.tool-card-cloud`（灰蒙版 + 锁形提示），**不跳转** `/tool/<id>`；主按钮「从云端下载」→ `POST /local-api/store/install {id, version}`（既有链：拉包→sha256→pkg_install→落位→重扫）→ 成功后 `render()` 转正常卡。失败（离线/包缺失）给可读错误。CSS 与文案进 `static/css/style.css` + `main.js`（随客户端与主包双份，出包纪律照旧）。

**注（口径收窄登记）**：本模型下 A 类"未装=中继直出"不再作为网格入口（登记制取代），中继直出仅保留为已装副本缺失时的**技术兜底**（直链 `/tool/<id>` 仍可开）。此前 `浏览器退役批次 §7.3` 的"中继直出保留（零安装体验不变）"按本文件收窄——执行时回写三类适配 §6.1 与商店设计相应句。

### 2.3 本地数据按账号隔离（需求③）

**机制 = 账号数据根注入（对插件零感知）**：

- **插件可见数据根** = `<客户端数据目录>\users\<账号>\`（未登录/离线无快照 → `users\_anonymous\`）；插件照旧调用 `jztools_data.get_data_root_dir("plugins", <id>)`，落点自然变为 `…\users\<账号>\plugins\<id>\…`——**插件代码零改动**（规范 §9.1/S-1/B-5 已把数据路径收口到 `jztools_data`，这是本方案的现成抓手）。
- **进程内（hybrid）**：能力层在账号确定/变化时设置 `os.environ["JZTOOLS_DATA_ROOT"]`（`get_data_root()` 每次现读、不缓存 → 即时生效，`jztools_data.py:171`）；能力层自身文件（session.bin/config.json/downloads/local-plugins/server-frontends/geometry.json/plugin-audit.log）**不经** jztools_data，仍留机器级（已核）。
- **worker（子进程）**：executor 拉起 worker 时显式注入 `JZTOOLS_DATA_ROOT=<账号子根>`（不依赖父进程环境继承的时序）；**账号切换（登录/登出/换号）→ 停止常驻 worker**（下次调用自动冷启，数据根随新账号），防常驻进程持旧根写串数据。
- **机器级文件不动**：插件**代码**（local-plugins/server-frontends）保持共用（需求③"包可多账号共用"）；`downloads\`、日志、几何、会话镜像均机器级。
- **服务器侧数据**：本就是账号权威（登录鉴权 + C 类 `own()` 附会话取数），不动。
- **形态决策（D5）**：阶段一=能力层注入（进程内 env + worker env + 切号重启），**不新引进程**——能力层即"负责管理数据的进程"，对插件不可见；阶段二（可选，触发条件=需要跨账号并发/强隔离）再评估独立数据管理进程（复用 supervisor 形态件）。

**jz_deps 消费点复核**（`jz_deps.py:390-394`）：仅外部程序（soffice）路径探测；客户端重定向后扫描 `<users>\<账号>\plugins\*.config.json` 落空即回落程序目录——语义一致、无假降级，登记为已知即可（G3-4 复跑 deps-layout 台架背书）。

### 2.4 徽标与卸载显示（需求④⑤）

- **卸载显示**：卸载（A/B/C 统一）只移账号登记 + 本机副本保留为缓存；删除「已从本机移除」徽标与 `hidden_tools` 写入链（`store.js` 卸载分支不再 `setHiddenTool`；`/local-api/plugins/hidden` 端点与 `client_config.hidden_tools` 退役——一次性迁移消费见 G2-5）。
- **徽标拆分**（`store.js:humanRuntime` 改为读条目而非仅 runtime）：`server`→「在线」；`local` ∧ `server_data=true`（C 类客户端工件）→「离线降级」；`local` ∧ 无 server_data（B 类）→「本地」；`dep-slot`→「依赖」。
- 商店卡「已安装」态 = **账号登记**（不再是本机态）；本机缺副本时按钮区补「下载到本机」（灰蒙版同款语义，复用云卡 CSS）。

### 2.5 兼容与发版顺序（硬约束）

- **服务端先、客户端后**（与上一批次相反）：新客户端依赖新 API；`GET installs` 404 时客户端**降级为旧行为**（本机副本驱动网格、不合成云卡、不写登记），不崩不白屏；旧客户端对新服务器不受影响（不调用新 API）。
- `installs.json` 缺失（老数据根）→ 读侧视为空登记；首次登录迁移补种见 G2-5。

## 7. 风险与边界

1. **发版顺序反转**：本批必须**服务端先、客户端后**（新客户端依赖 installs API）；客户端对 404 有降级（G2-7），两侧可独立滚动升级。
2. **体验变化需提前沟通**：新账号空网格 + A 类也要装一次（登记制取代零安装直出）——升级说明必写（G4-4），D1 可选自动补种。
3. **迁移窗口**：旧机器升级后首个登录账号继承旧数据；多账号场景需手工复制（至少自身文件 `users\<A>\plugins\<id>` 目录树），D2 备选可留缺省包。
4. **worker 常驻与切号**：切号必须停 worker（G3-2），否则子进程持旧数据根写串——台架 5 覆盖。
5. **机器副本的安全性边界**：未登记账号的插件 API/页面本会话 404，但副本仍在磁盘（本机用户可读）——与既有内网信任域口径一致（本机=信任域），不做加密（D3 备注）。
6. **installs.json 并发写**：单写方（store 插件）+ 原子写 + 低频（安装级）——沿用既有纪律，不加锁。
7. **停用语义迁移**：机器级 `local_state` 退役时一次性映射到**当时账号**的 `enabled`（与 D4 一致），其他账号默认启用。
