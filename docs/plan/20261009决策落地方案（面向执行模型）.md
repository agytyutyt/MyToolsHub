#### L1-1 契约 §6.1：`m=256` 修法①（编码端把 m 上限收到 255）
- 目标：三个编码器**永不在帧头写出 m=256**（现在会进位吃 k → 解码端读出 m=0 → 整次传输失败）。
- 落点（先读后改，行号为参考）：
  - `plugins/info-transfer/backend/routes.py`（`MAX_FEC_M = 256` 在 :198；参数推导 `_fec_plan` 约 :1776-1791）
  - `plugins/trajectory-convert/backend/routes.py`（`:47`、参数推导约 :590-600）
  - `plugins/map-marker/frontend/generate_qr_stream.py`（k/m 推导与帧头打包处）
- 实施规则：保证推导出的 `m ≤ 255`。两种可选手法任选其一（报告里写明用了哪种）：
  a. 当推导值恰为 256 时把 `nblocks+1` 重算，使 m 落回 ≤255；
  b. 等价调整参数链使 m 不为 256。
  **禁止**改帧头字节布局、协议字段、解码端（qr-video-decode / 移动端 APP 一律不动）。
- 必须构造的复现/验收输入：trajectory-convert `FEC_RATIO=0.1`、v15/L、数据恰 **230 块（≈87,020–87,400 字节）**。
  修复前该输入帧头为 `(k<<8)|256`；修复后须满足：① 帧头回读 `m ≤ 255`（写一个最小断言即可）；② 该输入经编码→解码 `roundtrip 逐字节一致`。
- 台架与文档收尾：
  1. `testdata/protocol/v1_headers.json → defect_m256` 改为「已修复」形态（保留字段并注明修复前值，按 `testdata/protocol/README.md` 的重生成方法操作）；

### §B-7 L4-3 收尾一轮注记（2026-10-10，T24 / T25 / T35 / T20-P3）

1. **T24 早停阈值必须是 k+1 而不是恰好 k**：凑到恰好 k 就停会让每组都失去 T17 交叉校验所需的
   冗余，等于把「早停」变成「每次解析都降级成完整性未校验」。故 `need = k+1 if m > k else k`
   （无冗余时按 k 停）。`verified=True` 在有断言里保住。
2. **跳帧的安全网不是可选项**：重复节奏靠「新码帧号连续三段等距」推断，漂移时会**跳过头未解过的码**。
   收尾加的是「跳了帧却没能早停 → 丢弃本次结果递归回退全量扫描」，边界台架里「前 5 后 3」这一路
   正是靠它保住正确性（代价 +20% 时间，不换错数据）；非 FEC 视频 plan 恒 None，天然不跳帧。
3. **T25 的计数与占位必须同锁**：分「先查在飞数、再建任务」两步的话，并发提交会同时通过检查，
   8 的上限形同虚设（新用例直接断言「并发 20 个恰好受理 8 个」）。占坑口径含 `video_status=building`
   的按需视频——它走同一个 worker 池，不计入就是绕开上限。被拒请求不留任务痕迹＝无界堆积的出口。
4. **旧用例 `test_zz_encode_runs_cleanup` 的处理方式**：卡内第 3 条把清理改成 60s 窗口节流，该用例
   的接线断言会随窗口不确定性翻红；做法是**请求前把窗口清零**（窗口外必清理这一语义仍在断言里），
   没有放宽"必须调用清理"的断言本身——按铁律区分「规格变更」与"为变绿放宽"。
5. **T35 把卡片的假设证伪了**：卡片记的是"编码器默认码控/质量档位随运行形态漂移"，实测真因是
   **编码器候选回退**（avc1 → mp4v），v15/850px 生产档 4.88×、合成 19 码 10.4×、小码面 6.9×，
   比值随内容/分辨率落在 4.9–10.4× 正好包住卡片的"≤7×"；三组全帧回读都是满码、还原逐字节一致，
   即"用哪个编码器"只影响体积不影响可解性。**本机 OpenCV 5.0.0（venv 与冻结包 ffmpeg500 同一构建）
   完全不接受质量参数**：构造 params（6/7 参）、`open(...,params)` 均报 "takes at most 5 arguments"，
   `writer.set(VIDEOWRITER_PROP_QUALITY, q)` 返回 False 且 8 档逐一实测产物逐字节相同。
   因此没有假装"档位已固定"：只做能力内的显式尝试 + 如实记 `quality_pinned`，并把**实际编码器**
   透出成产物自身信息（`video_fourcc` / `video_quality` / `video_quality_pinned`，回退记 warning）。
   档位取 100（满档）而非"能解的最低档"：卡片硬门槛是「全帧解码成功率不降」，而本构建测不出档位梯度。
6. **T20 P3 的收益比卡片估的小一个量级**：卡片按"省掉 PNG 往返 ≈38ms/帧"写，实测 v25/1250px、606 帧
   只有 **239.8 → 220.2 ms/帧（1.09×，省 ≈20ms/帧）**——因为帧序列**恒落盘**（前端轮播与按需出视频的
   共同底座），能省的只有 imdecode 那一半，imencode 那一半就是产物本身。要再往下必须改"帧不再以 PNG
   落盘"，那已超出"只改视频帧路径"的本刀范围。两刀（双出口 / 免往返）各自与改造前模块对比：
   480 帧的帧 PNG 集合与 mp4 sha256 **逐字节一致**，v25 档 mp4 66408312B 与 PNG 合计 5851405B 两侧相同。
7. **口径纠偏（重要，供后续读数字时校准）**：本轮前面的台架把 `encode_to_video(payload, 2, …)` 的第二
