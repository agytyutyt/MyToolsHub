## 一、架构与数据链路梳理

### 1.1 模块划分

```
信息传输插件
├── 后端 routes.py
│   ├── 依赖探测层      (L68-167)  11 个可选依赖的 try-import 开关
│   ├── 文档提取层      (L366-820) 9 类格式 → 精简提取 / 原件直通
│   ├── 信封层          (L823-1235) v1 JSON 信封 / v2 JZ2 二进制帧（双协议）
│   ├── 编码层          (L1238-1870) 静态分页 / 视频分帧 + zfec FEC
│   ├── 解码层          (L1873-2095) zxing-cpp 优先、cv2 回退；v1/v2 自适应重组
│   ├── 导出层          (L2098-2169) 信封 → 原始文件 / docx / xlsx / csv / txt
│   └── 路由与任务层    (L2172-2677) ThreadPoolExecutor(2) + 内存 TASKS + 30min TTL
├── 前端 index.html     双 Tab（封装/解析）、多文件并发、轮询、全屏码面舞台、帧轮播
└── Android InfoParse   protocol/ (Jz2, Envelope, QrFrame, ZfecCompat) + scan/ (Camera, Image)
```

### 1.2 两条传输链路

| 链路 | 封装 | 冗余 | 完整性 | 解析 |
| --- | --- | --- | --- | --- |
| **静态二维码** | 信封帧按容量切片，每页独立 CRC | **0（无 FEC）** | CRC32/页 | 收齐 seg_n 页后拼 payload 解压 |
| **二维码视频流** | 4B 长度前缀 + 信封 → 分块 → zfec(k,m) → share 帧 | **67%（FEC_RATIO=0.4）** | CRC32/帧（v2）；v1 无 | k-of-m 逐组重组 |

**关键结构性观察：两条链路的容错能力是两个极端——静态 0%、视频 67%，中间没有任何过渡档位。** 这是后文 R1 的根因。

### 1.3 单帧耗时基线（实测，v25 / 1100B 载荷）

| 环节 | 耗时 | 占比 | 是否必要 |
| --- | --- | --- | --- |
| `qr.make()` 自动选 mask（内部试 8 次） | 154 ms | 55% | 可 4.4× 压缩 |
| `zxingcpp.read_barcodes()` 回读自检 | 90 ms | 32% | 可抽样 |
| `make_image()` + PNG 编码 | 17 ms | 6% | 可直出矩阵 |
| `cv2.imdecode(PNG)` | 13 ms | 5% | 纯浪费 |
| `cvtColor(gray→BGR)` | 8 ms | 3% | 可直出 3 通道 |
| **合计** | **≈282 ms/帧** | | |

## 二、问题诊断

> 标记：`🔴` 严重 `🟠` 中 `🟡` 低；`[实测]` 表示已用脚本验证，`[代码]` 表示代码走查确认。

### 2.1 可靠性（5 项）

#### 🔴 R1 · 静态多页零冗余：缺任意 1 页即全盘作废 `[实测]`

- **位置**：`_parse_scanned_codes` L1387-1394、`_parse_scanned_texts` L2083-2091
- **现象**：静态模式把信封切成 N 页，**没有 FEC、没有校验页**。`if len(v2_pages) < v2_total: raise`。
- **实测**：7 页样本，分别丢弃第 1 / 4 / 7 页 → 三次全部 `静态二维码页数不全：收到 6/7 张，请补齐后再解析`。
- **量化风险**：设单页识别成功率 p=0.99，N 页全部成功的概率 = p^N。
  - 10 页 → 90.4%；50 页 → 60.5%；**100 页 → 36.6%**；200 页 → 13.4%。
  - 原件传输大文档常态是几十到 200 页，**端到端成功率已低于可用线**。
- **对比**：视频链路有 67% 冗余，丢 30% 帧仍可还原。两条链路能力断层。
- **补充**：v1 静态多页拼接依赖 `"".join(parts)` 后 `json.loads`——任一页损坏则整体解析失败，且**无定位信息**（无法告知是第几页坏）。

#### 🔴 R2 · v1 协议路径无任何完整性校验 → 静默产出错误数据 `[实测]`

- **位置**：`reassemble_qrtransfer` L1988-2051（v1 重组）、`_qrformat_encode` L1482（v1 帧头 12 字符 base64）
- **现象**：v1 帧只有 4+4+4 字符的 base64 索引头，**没有 CRC、没有校验和**。zfec 是纯线性分组码，**不校验输入正确性**——一个被污染的 share 会被当成合法输入参与解码，输出整段错误数据。
- **实测**（60KB 载荷，v1，237 帧 k=142/m=237）：
  - 正常重组 → 数据正确 ✅
  - 单帧注入 1 字符污染 → **不报错，产出数据 ≠ 原始数据**（静默错误）❌
- **同条件 v2**：污染帧被 CRC32 判坏 → 按"缺失"处理 → FEC 从冗余中恢复 → **产出数据 == 原始数据** ✅
- **影响面**（不止于历史码）：
  1. `PROTOCOL_V2 = False` 降级开关打开时的所有产物；
  2. 存量旧二维码；
  3. **外部插件 v1 流**——`trajectory-convert` / `qr-video-decode` 产出的流仍走 v1 分支（`reassemble_any` 按魔数判别，无 JZ2 即走 v1）。
- **危害等级最高**：数据错了但用户不知道，导出文件损坏且不报错。

#### 🟠 R3 · 生成端静默降级：解码验证全失败仍返回成功 `[实测]`

- **位置**：`_render_verified_qr` L1679-1681（v2 分支）、L1693-1696（v1 分支）
- **现象**：8 个 mask 全部无法通过回读验证时，代码**仍然落盘 PNG 并正常返回**路径，注释写"理论不可达"。
- **实测**：强制 `_zxing_can_decode` 恒返回 False → 函数正常返回路径，文件生成 3468B，无任何异常/告警。
- **后果**：生成端"成功"、任务标记 `done`、用户下载到自家解析端读不出的码图；故障以"用户侧扫码失败"的形式暴露，排查成本极高。
- **触发条件并非不可能**：zxing/cv2 缺失时 `_zxing_can_decode` 直接 `return True` 跳过（L1637-1638），若目标机依赖不全，验证形同虚设。

#### 🟠 R4 · v1 静态分页缺少载荷安全系数 `[实测]`

- **位置**：`_single_capacity` L1699-1705 vs `_max_chunk_size` L1418 / `_max_chunk_size_v2` L1245
- **现象**：`PAYLOAD_SAFETY = 0.9` 只在视频路径与 v2 路径生效；**v1 静态路径只减了 16 字节常量**，实际用到理论容量的 94%–99%。
- **实测**：

| 版本 | 理论容量 | v1 静态（占比） | v1 视频 | v2 静态 | v2 视频 |
| --- | --- | --- | --- | --- | --- |
| v10 | 274 B | **258 (94%)** | 171 (62%) | 214 | 223 |
| v15 | 523 B | **507 (97%)** | 342 (65%) | 438 | 447 |
| v25 | 1276 B | **1260 (99%)** | 849 (67%) | 1116 | 1125 |
| v40 | 2956 B | **2940 (99%)** | 1983 (67%) | 2628 | 2637 |

- **风险**：立项目时明确记录"满容量高熵载荷在部分解码器下不稳定——cv2 回读可能整码失败甚至截断"（L180-181），但该认知未落实到 v1 静态路径。当前因 `PROTOCOL_V2=True` 掩盖，一旦降级回退即复现。

#### 🟠 R5 · FEC 冗余固定 67%，不随场景自适应 `[实测]`

- **位置**：`FEC_RATIO = 0.4` L178、`_fec_plan` L1455
- **边界健全性已验证**：扫描 206 个 size，`1 ≤ k ≤ m ≤ 256` 恒成立（**无 bug**，此处不提缺陷）。
- **但冗余是"一刀切"**：实测 size=10/50/100/500/5000 的实际冗余恒为 67%–70%。
- **问题**：静态 0% 与视频 67% 之间没有中间档；对"静态多页但只需少量冗余"的场景无解（R1 的直接症结）。

### 2.2 性能（7 项）

#### 🔴 P1 · `qr.make()` 自动选 mask 带来 4.4× 无谓开销 `[实测]`

- **位置**：`_qr_png_bytes` L1582-1593 → `qr.make(fit=False)` → `best_mask_pattern()` 内部试满 8 个 mask
- **实测**（v25）：自动选 mask **154 ms**；显式指定 `mask_pattern` **34 ms**。
- **根因**：qrcode 库的 Enigma 式惩罚分选优会对同一份数据跑 8 次 `makeImpl`。而本插件**每帧数据都不同**，等于每帧付 8 倍编码成本。
- **量级**：占单帧总耗时 55%，是整个编码链路**最大的单点开销**。

#### 🔴 P2 · 逐帧全量回读自检（90 ms/帧，占 32%） `[实测]`

- **位置**：`encode_to_video` L1556-1561
- **现象**：每帧渲染后都调 `_zxing_can_decode`（内部再做一次 `cv2.imdecode` + `read_barcodes`）。1000 帧 = 1000 次完整解码。
- **论证**：自检的目的是"发现渲染器/解码器对特定 mask+data 组合的缺陷"。但同一任务内所有帧共享 version / EC / box_size / 渲染器，**缺陷是渲染器的属性，不是单帧数据的属性**——用统计抽样即可覆盖，逐帧全检是过度设计。

#### 🟠 P3 · PNG 编码 → imdecode → cvtColor 往返，38 ms/帧纯浪费 `[实测]`

- **位置**：`_qr_png_bytes` L1592 → `encode_to_video` L1565-1566
- **现象**：矩阵 → PIL Image → PNG 字节 → `cv2.imdecode` →灰度→BGR。矩阵信息在 PNG 编解码中绕了一圈。
- **实测**：`get_matrix()` + `np.kron` 放大 = 149 ms（含公共的 147 ms `make()`），即矩阵直出几乎零成本；而 PNG 路径额外付 17+13+8 = 38 ms。
- **附带问题**：`BOX_SIZE=10` 固定 → v15 帧 770px、v40 帧 1770px（12 MB 位图/帧）。**帧分辨率随版本线性膨胀，既不随屏幕自适应，也直接放大 H.264 编码与磁盘压力**。

#### 🟠 P4 · 压缩试压无条件双跑，xz 单项即为 zlib 的 6 倍耗时 `[实测]`

- **位置**：`_compress_best` L951-966、`_xz_compress` L934
- **实测**（高冗余文本）：

| 输入 | zlib-9 | xz(9\|EXTREME) | 耗时比 | xz 额外收益 |
| --- | --- | --- | --- | --- |
| 1 MB | 2074 B / 11.3 ms | 300 B / 69.8 ms | **6×** | −85.5% |
| 4 MB | 8169 B / 40.8 ms | 760 B / 252.8 ms | **6×** | −90.7% |

- **问题**：
  1. 无条件先算 zlib 再算 xz，小数据也付双倍代价（小数据下 xz 收益往往 <5%，却付 6× 时间）；
  2. `rebuild=True` 时 `build_envelope_v2` 调用 `_compress_best` **两次**（L1139 + L1151），合计 4 次压缩；
  3. 无大小门槛、无采样预估、无提前退出。

#### 🟠 P5 · PPT 文本提取为逐字节 Python 滑描，20MB 约 15 秒 `[实测]`

- **位置**：`_extract_ppt_text` L696-712，`while i + 8 <= n: ... else: i += 1`
- **实测**：1 MB 随机流 0.79 s、8 MB 5.97 s → **20 MB 上限外推 ≈15 s**，且为纯 CPU 阻塞（GIL 内，会拖住整个 Flask 工作线程）。
- **放大效应**：无匹配的随机流是最坏情况；再叠加 `WORKERS=2`，两个并发请求即可让服务失去响应。

#### 🟠 P6 · 视频解析不跳帧，`frame_repeat=5` 造成 5× 解码浪费 `[代码]`

- **位置**：`decode_video_frames` L1930-1961，`while True: cap.read()` 全量逐帧
- **现象**：相机模式下每码重复 5 帧（`CAMERA_FRAME_REPEAT=5`），有效信息只占 1/5，但解析端对 5 帧全做解码 + 去重。
- **对照**：APP 侧 T09 已实现 k-of-m 早停，`VideoParseHelper` MP4 循环"满足即 break"；**桌面端 `decode_video_frames` 仍是全量扫描**，两端能力不对齐。

#### 🟠 P7 · 任务线程池为无界队列 + GIL 串行化 `[代码]`

- **位置**：`WORKERS = 2` L255、`_executor = ThreadPoolExecutor(max_workers=2)` L256、`_executor.submit` L2412
- **问题**：
  1. `submit` 无界，无拒绝策略；短时间大量提交会无限堆积（TASKS 只在下次 submit 时按 TTL 清理）；
  2. QR 编码是 CPU 密集，GIL 下多线程**无并行收益**，2 个 worker 只会互相争抢；
  3. 第 N 个任务的等待时间 = 前面全部任务之和，前端只有 `pending` 状态、**无排队位置提示**，用户只能干等。

### 2.3 安全性（7 项）

#### 🔴 S1 · `/decode` 的 ZIP 分支存在解压炸弹面 `[实测]`

- **位置**：`it_decode` L2584-2601
- **现象**：分支内**没有**条目数上限、解压后总量上限、压缩比校验（代码审计确认：无 `MAX_UPLOAD_BYTES`、无 `0xFFFF`、无累加计数）。`zf.read(info)` 把所有条目读入内存。
- **实测**：构造 200 个条目、每个 5 MB 零字节 → 压缩包 **0.99 MB**，解压后 **1000 MB**，压缩比 1008×，**完全在 20MB 上传限制内**；模拟遍历读取耗时 3.83 s，峰值内存 ≈1 GB（单请求，`WORKERS=2` 可叠加至 2 GB）。
- **对比**：插件自身在 `_zip_pack_stream` L980 有 `len(infos) > 0xFFFF` 检查——说明团队已有该意识，但**只在封装路径做了，解析路径漏了**。
- **危害**：单请求即可打满内存，是本项目最容易被利用的拒绝服务点。

#### 🟠 S2 · 上传"先读后判"，大小限制形同虚设 `[代码]`

- **位置**：`it_encode` L2394-2396、`it_decode` L2564-2566
- **现象**：`file_bytes = f.read()` 之后才 `if len(file_bytes) > MAX_UPLOAD_BYTES`。内存已分配完才拒绝。
- **建议**：改用 `request.content_length` 前置拦截。

#### 🟠 S3 · 文档解析未防 XML 外部实体（XXE） `[代码]`

- **位置**：`_extract_docx_text` L429（`python-docx`）、`_extract_xlsx_rows` L468（`openpyxl`）
- **现象**：两者底层为 lxml，解析**用户上传**的 OOXML。未显式禁用实体解析。
- **风险**：构造含 `<!DOCTYPE>` + `<!ENTITY SYSTEM "file:///...">` 的 docx/xlsx，可能读取服务器本地文件并回显到提取结果。
- **注**：需实测确认 lxml 默认行为后再定性；但作为**白名单内的用户可控输入**，应默认按不可信处理。

#### 🟠 S4 · pypdf 解密为纯 Python 实现，可作 CPU DoS `[代码]`

- **位置**：`_extract_pdf_text` L648-655（`reader.decrypt("")`）
- **现象**：pypdf 的 AES 解密是纯 Python，对 AES-256 极慢。构造加密 PDF 可让单个请求长时间占满 CPU，且配合 P7 的无界队列会迅速堆积。
- **叠加**：与 P5 同属"提取层 CPU DoS"，且都发生在**不需要登录即可触发**的路径（若部署未开启登录）。

#### 🟡 S5 · `download_name` 未过滤控制字符 `[代码]`

- **位置**：`it_download` L2497/2506/2511、`it_export` L2673
- **现象**：`name` 源自 `os.path.basename(f.filename)`（encode）或**二维码信封内的 `name` 字段**（export，攻击者完全可控）。`basename` 只去掉路径分隔符，不清理 CR/LF/NUL。
- **风险**：HTTP 响应头注入（需配合其他条件）；或诱导用户下载恶意扩展名文件。

#### 🟡 S6 · 无速率限制，配合 20MB 上传可打满磁盘 `[代码]`

- **位置**：`it_encode` / `it_decode` 均无频率限制
- **现象**：每次上传都会在 `_TASK_DIR` 落盘（视频原始文件、逐帧 PNG、ZIP、MP4），TTL 30 分钟。连续请求可在清理生效前写满磁盘。
- **放大**：相机模式 `frame_repeat>1` 时还会额外落盘整份逐帧 PNG 目录。

#### 🟡 S7 · CRC32 只防误码，不防篡改（无认证） `[代码]`

- **位置**：`_jz2_frame` L1094（CRC32）
- **现象**：CRC32 是**无密钥**检错码。攻击者可构造合法 CRC 的假帧（例如伪造 `fmt=file` + 恶意文件名的信封），接收端无法区分。
- **场景**：二维码是"离线传输"介质，链路假设为"空气隔离"，但码图可能被拍照传播、投屏替换。
- **缓解**：当前 `as_attachment=True` 已阻断最直接的浏览器渲染路径，实际风险有限；但若未来引入"扫码即执行/预览"，须先补认证。

### 2.4 错误处理与前端（3 项）

#### 🔴 E1 · 前端帧序列全量预载，1000 帧约 2–12 GB 内存 → 浏览器崩溃 `[实测]`

- **位置**：`frontend/index.html` `startJobStream` L1126-1138
- **现象**：`for (let i = 1; i <= count; i++) { const im = new Image(); im.src = ...; st.imgs.push(im); }` —— **一次性创建全部帧的 Image 并常驻**，且 `pauseAllStreams` 只清 timer、不释放 Image。
- **实测位图占用**（浏览器解码后，非 PNG 大小）：

| 版本 | 帧边长 | PNG | 位图/帧 | 1000 帧位图 |
| --- | --- | --- | --- | --- |
| v15 | 770 px | 3.4 KB | 2.3 MB | **2.21 GB** |
| v25 | 1170 px | 6.6 KB | 5.2 MB | **5.10 GB** |
| v40 | 1770 px | 12.8 KB | 12.0 MB | **11.67 GB** |

- **后果**：中大型视频流（数百帧）在多文件并发时极易触发标签页 OOM 崩溃。这是"相机传输模式"主路径上的**必现级**故障。

#### 🟠 E2 · 异常透出内部细节 `[代码]`

- **位置**：`_run_encode` L2280-2283、`_run_decode` L2315-2318
- **现象**：`except ValueError as e: set_task(..., detail=str(e))` —— 第三方库（olefile / openpyxl / pypdf / lxml）的异常文本**常含服务器绝对路径、内部字段名**，直接透出到前端。
- **对照**：同函数末尾的 `except Exception` 已做脱敏（只给 `type(e).__name__`），说明意图正确但**覆盖面不全**。

#### 🟠 E3 · 解析任务无取消接口，失败后临时文件不清理 `[代码]`

- **位置**：`_run_decode` L2291（无 cancel_check 参数）、`it_decode` L2573（`tmp_video` 落盘）
- **现象**：
  1. 视频解析是长时间任务，但**没有 `/decode/<id>/cancel`**（encode 有）；
  2. 解析失败时 `tmp_video` 不删除，只能等 30 分钟 TTL；
  3. 与 P6 叠加：解析慢 + 无法取消 + 文件残留。

#### 🟡 E4 · 解析异常统一吞为固定文案 `[代码]`

- **位置**：`it_decode` L2610-2611
- **现象**：`except Exception: return "解析失败，请确认二维码清晰完整"` —— 依赖缺失、磁盘满、编码错误全部返回同一句，排查只能翻服务端日志。

#### T16 · 静态多页引入可配置 FEC（解决 R1、R5）

**现状**：`_build_static_pages_v2` 纯切片，无冗余；`_parse_scanned_codes` 要求页全齐。

**改法**（复用现有 zfec，协议层最小侵入）：

1. 新增静态专属冗余参数 `STATIC_FEC_RATIO = 0.2`（默认 20%，可经 `encode` 表单 `static_fec` 覆盖为 0 / 0.1 / 0.2 / 0.3）；
2. `_build_static_pages_v2` 改为：切片 → `_fec_encode(chunks, fec_ratio=STATIC_FEC_RATIO)` → 每页封装为 `kind="env"` 但**新增 `JZ2_FLAG_STATIC_FEC = 0x10`**（bit4）标注，meta 追加 `k(1B)+m(1B)`；
3. 解析端 `_parse_scanned_codes` 识别该 flag：走与视频相同的 k-of-m 逐组重组，**收齐任意 k 页即可还原**；
4. 未置该 flag 的旧码走原逻辑，向后兼容。

**关键约束**：静态页是**离线人工递送**的介质，缺页是常态，因此默认冗余应高于视频的单位开销直觉——建议 **20% 起**（每 5 页多 1 页），兼顾"扫描页数"与"兜底能力"。

**预期效果**：

| 页数 | 当前成功率(p=0.99) | 20% 冗余后（缺 ≤20% 页可还原） |
| --- | --- | --- |
| 10 页 | 90.4% | ≈99.9% |
| 50 页 | 60.5% | ≈99.4% |
| 100 页 | 36.6% | ≈98.5% |
| 200 页 | 13.4% | ≈96% |

（按二项分布 P(X ≤ 0.2N) 估算，p=0.99）

**风险与验收**：
- 需两端同步发版（APP `Jz2.kt` 增加 flag 与 k-of-m 分支）；旧码零回归由 T01 保证；
- 验收：随机丢 10% 页注入测试，还原成功率 ≥95%；新增 `test_static_fec.py` 覆盖 k/m 边界与 flag 兼容。

> 本项与既有清单 **T14（静态多页纠错）** 目标一致，本文补充了量化依据与具体 flag 设计，可直接作为 T14 的实施方案。

#### T17 · v1 重组路径增加帧级校验（解决 R2）

**现状**：v1 帧无校验，污染帧静默破坏输出。

**改法**：**不动 v1 帧格式**（存量码与外部插件流必须保持兼容），改为在重组侧做**一致性交叉验证**：

1. v1 的冗余特性是 m−k > 0，即存在**冗余 share**。重组时对每个 FEC 组：先用 `blocks[:k]` 解码得到结果 R1；若该组还有第 k+1 个可用 share，则用它再解码一次得到 R2，比对 R1 == R2；不一致 → 判定该组数据损坏，抛明确错误（而不是返回错误数据）。
2. 所有组均无冗余 share 可用时（恰好收齐 k 个），无法交叉验证 → 在结果中返回 `verified: false` 标志，前端提示"数据完整性未经校验，建议重新采集"。
3. 同步给 `reassemble_qrtransfer` 的调用方（`_run_decode`）传递该标志到任务结果。

**预期效果**：
- 单帧污染 → 从"静默错误"变为"可检测"（有冗余时直接拒错；无冗余时明确告知未校验）；
- 存量码与外部插件 v1 流**零格式改动**即可受益；
- 与 T16 无依赖。

**风险**：额外解码开销约 +1/k（可忽略）；极端情况（某组恰好只有 k 个 share 且其中一个坏）仍可能漏检——此时至少已通过 `verified:false` 提示用户，优于当前完全静默。
**验收**：复用本文 R2 的注入脚本，断言"污染后要么报错、要么 `verified=false`，绝不返回与原始不一致的数据"。

#### T18 · 生成端验证失败不再静默降级（解决 R3）

**现状**：`_render_verified_qr` 全 mask 失败仍落盘返回。

**改法**：

1. 引入返回值语义：`_render_verified_qr` 返回 `(path, verified: bool)`；
2. 静态路径：验证失败 → **抛 `RuntimeError`**，任务置 `error`，文案明确"当前环境无法生成可解码码图（请检查 zxing-cpp / opencv 依赖）"；

4. 依赖缺失场景：`_zxing_can_decode` 当前 `return True` 跳过验证 —— 改为**在 `/status` 中显式暴露 `zxing: false`**，并在 `encode` 入口对 `PROTOCOL_V2=True` 且 zxing 不可用时**直接 503 拒绝**，而不是"跳过验证照常出码"。

**预期效果**：消除"生成成功但扫不出"的静默故障；依赖缺失在发码前即暴露，而非在用户侧暴露。
**验收**：mock 解码器全失败 → 任务状态为 `error` 且 detail 含"无法生成可解码码图"。

### 批次 7 · 性能提速

#### T20 · 固定 mask 直出矩阵（解决 P1、P3）— **收益最大**

**现状**：每帧 `make()` 自动选 mask 154 ms + PNG 往返 38 ms。

**改法**：

```python
def _qr_frame_matrix(data_bytes, version, err, mask_pattern, box_size=BOX_SIZE, border=4):
    """直接产出 BGR 画布，跳过 PIL/PNG/cv2 往返。"""
    qr = qrcode.QRCode(version=version, error_correction=err,
                       box_size=1, border=border, mask_pattern=mask_pattern)
    qr.add_data(data_bytes, optimize=0)
    qr.make(fit=False)                      # 显式 mask -> 跳过 best_mask_pattern 的 8 次试算
    m = np.array(qr.modules, dtype=np.uint8)
    big = np.kron((1 - m) * 255, np.ones((box_size, box_size), dtype=np.uint8))
    return np.repeat(big[:, :, None], 3, axis=2)   # 直接 3 通道，免 cvtColor
```

`mask_pattern` 取值策略（**三选一，建议 a**）：
- **(a) 帧序轮换** `mask = i % 8`：零额外成本，8 种图案均匀覆盖，统计上规避单一 mask 的解码器缺陷；
- (b) 首帧自动选优、后续复用：首帧付一次 8× 成本，后续全用该 mask；
- (c) 固定 `mask=0`：最快，但缺乏多样性。

**预期效果**（v25 单帧实测推算）：

| 环节 | 当前 | 优化后 |
| --- | --- | --- |
| QR 编码 | 154 ms | **34 ms** |
| 位图生成（PNG/矩阵） | 17 ms | **2 ms** |
| imdecode | 13 ms | **0** |
| cvtColor | 8 ms | **0**（直出 3 通道）|
| zxing 自检 | 90 ms | 90 ms（见 T21）|
| **小计** | **282 ms** | **126 ms** |

- **单独本项：2.2×**；与 T21 叠加 **≈6×**。
- 1000 帧视频：282 s → **47 s**（叠加 T21）。

**风险**：固定/轮换 mask 的惩罚分劣于自动选优，理论可读性略降。缓解：轮换策略 + zxing 自检 + 静态码仍走自动选优（静态码数量少，不敏感）。
**验收**：T01 回归全绿；新增"1000 帧随机数据视频，zxing 全帧回读成功率 ≥ 改造前"的对比用例。

#### T22 · 压缩试压策略优化（解决 P4）

**改法**：

1. **大小门槛**：`XZ_MIN_SIZE = 256 * 1024` —— 小于该尺寸直接跳过 xz（小数据下 xz 相对 zlib 的额外收益 <8%，却付 6× 时间）；
2. **采样预估**：大数据先取前 256 KB 试压，估算全量收益；若预估收益 <10%，跳过全量 xz；
3. **rebuild 路径复用**：`build_envelope_v2` L1139 与 L1151 的两次 `_compress_best` 中，zlib 结果可缓存复用，避免重复计算；
4. **可选**：把 xz 与 zlib 放到两个线程并行（`lzma.compress` 会释放 GIL）。

**预期效果**：小文件（<256KB，占实际使用大多数）压缩耗时**减半**；大文件在保持 −85%~−90% 收益的前提下节省采样与重复计算；rebuild 路径 4 次压缩 → 3 次。
**验收**：`test_protocol_v2.py` 试压选优用例全绿；新增"产物体积不劣于改造前"断言。

#### T23 · PPT 提取向量化（解决 P5）

pos = 0
while True:
    nxt = min((data.find(p, pos) for p in PATS if data.find(p, pos) >= 0), default=-1)

#### T24 · 视频解析跳帧与早停（解决 P6）

**改法**：

1. **早停**：`decode_video_frames` 增加 `should_stop(codes) -> bool` 回调；`_run_decode` 每积累 25 个新码尝试一次 `reassemble_any`，成功即停（与 APP 侧 T09 的 k-of-m 早停对齐）；
2. **跳帧**：解析到首个有效帧后可从帧头取得 `seg_n / k / m`，据此计算 `required = k * (seg_n // m)`；若已知 `frame_repeat`（可由接口参数传入，或由后端在任务结果中携带），则 `cap.set(cv2.CAP_PROP_POS_FRAMES, i)` 按步长跳转解码。

**预期效果**：解析耗时从"全量扫描"降为"够用即停"，相机模式（5× 重复帧）下**预计 3–5× 提速**；与上条叠加后大视频解析从分钟级进入秒级。
**风险**：跳帧步长与实际 `frame_repeat` 不匹配时会漏帧 —— 缓解：跳帧仅作为**加速尝试**，一旦某步未解出码则退回逐帧；早停本身已能覆盖大部分收益，**建议先只做早停，跳帧作为第二阶段**。
**验收**：截断视频（只保留前 60% 帧）仍能还原；完整视频解析耗时下降 ≥50%。

#### T26 · ZIP 解析资源上限（解决 S1）— **优先级最高**

**改法**：在 `it_decode` 的 zip 分支增加三重闸门——

```python
MAX_ZIP_ENTRIES = 500
MAX_ZIP_TOTAL_BYTES = 200 * 1024 * 1024   # 解压后总量
MAX_ZIP_RATIO = 200                        # 单条目压缩比

with zipfile.ZipFile(io.BytesIO(file_bytes)) as zf:
    infos = [i for i in zf.infolist()
             if not i.is_dir() and i.filename.lower().endswith((".png", ".jpg", ".jpeg"))]
    if len(infos) > MAX_ZIP_ENTRIES:
        raise ValueError(f"ZIP 内图片数量过多（上限 {MAX_ZIP_ENTRIES} 张）")
    if sum(i.file_size for i in infos) > MAX_ZIP_TOTAL_BYTES:      # 用 central directory 的解压后大小，无需解压
        raise ValueError("ZIP 解压后数据过大")
    for info in infos:
        if info.compress_size and info.file_size // info.compress_size > MAX_ZIP_RATIO:
            raise ValueError("ZIP 压缩比异常（疑似解压炸弹）")
        codes.extend(decode_image_file(zf.read(info)))
```

**要点**：**先校验 `info.file_size`（central directory 中已有解压后大小，无需实际解压）再读取**——这样在消耗内存前就完成拦截。

**预期效果**：本文构造的 1 MB → 1 GB 炸弹在**读取任何条目之前**即被拒；单请求内存占用封顶 200 MB。
**验收**：用本文炸弹样本断言返回 400 且服务端峰值内存 <100 MB。

### 批次 9 · 前端与错误处理

#### T31 · 帧序列改为滑动窗口（解决 E1）— **必现级故障**

**现状**：`startJobStream` 一次性预载全部帧 Image（1000 帧 ≈2–12 GB）。

**改法**：改为**滑动窗口预载**，窗口大小 5（当前 ±2）——

```javascript
const WINDOW = 5;
function ensureWindow(st) {
  for (let k = 0; k < WINDOW; k++) {
    const i = ((st.idx + k) % st.count) + 1;
    if (!st.cache.has(i)) {
      const im = new Image();
      im.src = `/api/info-transfer/frame/${st.job.taskId}/${i}`;
      st.cache.set(i, im);
    }
  }
  // 淘汰窗口外的引用，让浏览器可回收
  for (const [i, im] of st.cache) {
    if (Math.abs(i - (st.idx + 1)) > WINDOW) { im.src = ""; st.cache.delete(i); }
  }
}
```

配合：暂停/关闭时清空 `st.cache` 并置 `im.src = ""`（主动释放位图）。

**预期效果**：常驻位图从 N 帧降为 5 帧 —— **v25 场景 5.10 GB → 26 MB（降 99.5%）**；彻底消除大视频流的标签页 OOM。
**风险**：网络慢时可能出现"窗口内帧未加载完" → 缓解：`showNextJobFrame` 遇到未完成帧时等待而非跳过（当前逻辑是立即跳到下一张，会破坏 333 ms 步进节奏）。
**验收**：1000 帧任务下 Chrome 任务管理器内存占用 <200 MB；连续轮播 5 分钟无崩溃。
