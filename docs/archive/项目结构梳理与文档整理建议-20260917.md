## 0. 结论速览

**整体判断：代码侧的组织是健康的，"一切皆插件"在目录层面站得住；问题集中在「文档层」与「临时产物层」。**

| 维度 | 评价 | 主要问题 |
| --- | --- | --- |
| 源码 / 插件划分 | ✅ 良好 | 16 个插件自包含，目录约定统一，无跨插件 import 越界 |
| 构建 / 工具脚本 | ✅ 良好 | `tools/` 职责清晰，规则真源（`plugin-payload-rules.json`）单点 |
| **文档体系** | ⚠️ **有债** | 同主题多份并存、生命周期无标记、根目录与 `docs/` 分层混乱、同一命令三处重复、状态章节失效 |
| **文档交付口径** | ❌ **缺陷** | `docs/` 全量随包分发 → 内部评估稿、P0 修复方案、todolist 都会进交付包；插件的 `test_*.py` 也随包 |
| **临时产物** | ⚠️ 占空间 | `deploy/` 3.5G + `runtime/` 682M + `android-app/` 589M + `dist/` 254M ≈ 5.0G；`.bench_corpus/` 含 18 份文档副本 |
| **测试入口** | ⚠️ 分散 | 根目录 4 个 `test_*.py` + 插件内 5 个 + `tools/e2e/`，无统一 `tests/`，入口靠文档口述 |

**按影响排序的 5 件最该先做的事：**

1. 给 `docs/` 补**生命周期标记与文档索引**（消除"哪份是现行"的歧义）——成本最低、收益最大。
2. 明确**文档交付口径**，让 `docs/` 分层后只把交付层随包打（现在内部稿全在包里）。
3. 归档**已决/已完成/已取代**的文档（多码同屏、视频流 todolist、v1.0 容器化、Qwen/DS 压缩评估）。
4. 修 `HANDOFF.md` 的**失效状态章节**（§2.1 标"2026-09-14 核实"，实际已滞后 3 天、约 10 轮提交）。
5. 处理**同名文件冲突**（`docs/打包部署手册.md` ↔ `android-app/InfoParse/打包部署手册.md`）。

### S5 大体积产物与源码同盘（5.0 GB）

`deploy/` 3.5G（含 20 个历史 zip + 全量部署目录）、`runtime/` 682M、`android-app/` 589M、`dist/` 254M、`demo/` 71M、`build/` 64M。

**建议**：① 定期删除 `deploy/` 下已被取代的历史 zip（保留最近 2–3 个 + 当前上线版）；② 把 `deploy/`、`dist/`、`build/` 通过环境变量或直接在 `build-deploy.ps1` 参数里指向**仓库外的构建盘**（这也能顺带缓解"并发会话导致的 dirty 误判"）；③ `android-app` 定期 `gradlew clean`。**注意**：该改动会触及"两段式+增量合并"的本机打包流程（memory 记录），需与打包链路一起评估，不宜草率。

### S6 刻意的重复副本缺少统一登记

`plugins/file-filter/backend/bg_image.py` 与 `plugins/trajectory-sketch/backend/bg_image.py`（sha256 相同）、`plugins/map-marker/frontend/jsqr.min.js` 与 `plugins/qr-video-decode/frontend/jsqr.min.js`（sha256 相同）——这是规范 B-7「禁止插件间 import」下的**刻意重复**，`test_bg_image.py` 已断言防漂移。

**建议**：这是**正确的妥协**，不需改结构；但建议在 `插件设计规范.md` §14 质量自检清单或附录里增加一张表《刻意重复副本登记表》（副本对 / 同步命令 / 断言测试），让第三个同类场景出现时有章可循。`jsqr.min.js` 这一对目前**没有对应断言**，属于登记缺口。
