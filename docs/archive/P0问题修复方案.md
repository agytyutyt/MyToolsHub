## FIX-1 模板同步链路修复（P0-1 + P0-2）

### 问题本质

一个**命名冲突**引出了两个症状：

- 打包脚本 `build-deploy.ps1:67-69` 按名字删除 `config.json`，意图是清掉"含 API Key 的运行时配置"（本机残留）；
- 但 `trajectory-sketch/backend/config.json` 同时扮演"**随版本下发的模板**"角色，被同一条规则删掉；
- 于是：仓库里 6 条登记项有 4 条**源文件压根不存在**（2 个 `prompt.json` 已被删除、2 个 `backend/config.json` 被 gitignore 从未入库），剩下 2 条里 `trajectory-sketch` 那条又会在打包时消失 → **部署形态下 6 条只剩 `tools.json` 真正生效**。

**结论：不要试图"保住 config.json"，而要让模板不再叫 config.json。**

## FIX-3 发版版本号防呆（P0-4）

### 问题

`build-deploy.ps1:24-30`：未传 `-Version` 时**沿用上一版部署目录的版本号**。于是"重新打包"得到的 `version.json` 仍是 1.6，目标机 `sync_templates()` 判定未升级 → **全部模板同步被跳过**。这正是"重打包了但 prompt/配置没变"的机制性原因。

### 改动：`build-deploy.ps1`

参数段新增 `-Force`：

```powershell
param(
    [string]$Python = "python",
    [string]$DeployName = "JZToolsHub",
    [string]$Version = "",
    [switch]$Force          # 允许版本号与上一版相同（默认禁止）
)
```

版本号段替换为（注意：这段必须在下方"清理旧产物"**之前**执行，现有代码顺序已正确）：

```powershell
# 版本号：-Version 未指定时，从上一版部署的 version.json 自动递增 patch（1.6 → 1.7）
$PrevVer = ""
$oldVerFile = Join-Path $AppDir "version.json"
if (Test-Path $oldVerFile) {
    try { $PrevVer = (Get-Content $oldVerFile -Raw | ConvertFrom-Json).app } catch {}
}
if (-not $Version) {
    if     ($PrevVer -match '^(\d+)\.(\d+)$')            { $Version = "{0}.{1}"         -f $matches[1], ([int]$matches[2] + 1) }
    elseif ($PrevVer -match '^(\d+)\.(\d+)\.(\d+)$')     { $Version = "{0}.{1}.{2}"     -f $matches[1], $matches[2], ([int]$matches[3] + 1) }
    else                                                  { $Version = "1.0.0" }
    Write-Host "  [版本] 未指定 -Version，自动递增为 $Version（上一版：$($PrevVer)）"
}
if ($PrevVer -and $Version -eq $PrevVer -and -not $Force) {
    throw "版本号与上一版相同（$Version）→ 目标机 sync_templates() 会判定未升级并跳过全部模板同步。请指定更大的 -Version，或加 -Force。"
}
```

写入 `version.json` 时附上可追溯字段（`_read_version()` 只读 `app`，加字段安全）：

```powershell
$gitCommit = ""
try { $gitCommit = (git -C $Root rev-parse --short HEAD 2>$null) } catch {}
$verObj = @{ app = $Version; schema = 1; commit = $gitCommit; built_at = (Get-Date -Format "yyyy-MM-dd HH:mm:ss") }
$verObj | ConvertTo-Json | Out-File -FilePath (Join-Path $AppDir "version.json") -Encoding utf8
```

> 编码注意：这里用 `Out-File -Encoding utf8` 会带 BOM。既有脚本已有 `ConvertTo-Utf8NoBom` 辅助函数，**复用它**写 `version.json`，避免 Python `json.load` 遇 BOM 报错。

### 验证

```text
① 不传 -Version 跑一次 → 打印「自动递增为 1.7」并成功产出
② 显式 -Version 1.7（与包内 version.json 相同）→ 抛错中止
③ -Version 1.7 -Force → 放行
④ 包内 version.json 含 app/commit/built_at，app 为空时删除字段不影响启动
```

## FIX-5 插件后端加载失败隔离（P0-6，本轮新增）

### 问题

探针实测：两个插件各写 `def status()` → `register_plugin_backends()` 抛
`AssertionError: View function mapping is overwriting an existing endpoint function: status`；
而 `app.py:799-807` 的 `__main__` 段无 try/except、`register_plugin_backends` 内也无 per-plugin 隔离
→ **进程带 traceback 退出，整站无法启动**。这与规范 B-4「不得拖垮主进程」的精神相悖。

### 改动：`app.py`

模块级新增：

```python
# 插件后端加载失败记录 {插件id: "异常类型: 摘要"}
# 供启动日志排查与后续（可选）在 /api/tools 中回传；每次 register_plugin_backends 清空。
_plugin_load_errors = {}
```

`register_plugin_backends()` 内替换 `load_routes`：

```python
def register_plugin_backends(app):
    global _plugin_home_card_hooks
    _plugin_home_card_hooks = {}      # 每次启动重新收集，避免跨重启残留旧钩子
    _plugin_load_errors.clear()

    def load_routes(plugin_id):
        """加载单个插件后端；任何异常都被隔离，绝不影响其他插件与整站启动。"""
        try:
            routes = _load_backend_module(plugin_id)
            if routes is None:
                return False
            register = getattr(routes, "register", None)
            if not callable(register):
                _plugin_load_errors[plugin_id] = "未导出可调用的 register(app)"
                app.logger.error("插件 %s 的后端未导出 register(app)，已跳过", plugin_id)
                return False
            register(app)             # ← 冲突/导入错误都在这里被捕获
        except Exception as exc:
            _plugin_load_errors[plugin_id] = f"{type(exc).__name__}: {exc}"
            app.logger.exception(
                "插件 %s 的后端加载失败，已隔离：其他插件与整站启动不受影响",
                plugin_id,
            )
            return False

        app.logger.info(f"已注册后端插件：{plugin_id}")
        hook = getattr(routes, "home_card", None)
        if callable(hook):
            _plugin_home_card_hooks[plugin_id] = hook
            app.logger.info(f"插件 {plugin_id} 提供 home_card() 首页卡片内容声明钩子")
        return True
    # 以下 admin 无条件加载 + 按 enabled 遍历的部分保持不变
```

**必须写进代码注释的两条限制**（避免误以为"万无一失"）：

1. `register(app)` 中途抛错时，**已注册的路由会残留在 Flask 上无法回滚**——隔离只保证"整站起得来 + 错误可诊断"，不保证失败插件不留半个后端。根治仍靠命名前缀纪律（FIX-4 + 规范 B-22）。
2. `_load_backend_module` 用 `importlib.import_module` 取 `.routes`，**已缓存模块不会刷新**——同进程内重复调用会拿到旧代码。插件后端改动必须重启进程（与现有文档一致）。

### 可选增强（建议本轮不加，留作 P1）

在 `/api/tools` 响应中追加 `"plugin_errors": {...}`（默认空 dict，向后兼容），首页卡片对失败插件显示"暂不可用"。需同步 `static/js/main.js`，改动面比隔离本身大，建议独立提交。

## FIX-6 `install.ps1` 深度补键（P0-1 附带发现）

`jztools_data._ensure_deep_keys()` 是**递归**合并，而 `install.ps1:186-201` 只把模板的**顶层键**并进用户配置。两份实现不等价：

> 例：`case-report` 模板日后在 `llm` 下新增 `timeout` 键 → 走 app 启动的 `sync_templates()` 能补上；走一键安装则**补不上**。

### 改动：在 `install.ps1` 里加递归合并辅助

```powershell
function Merge-DeepKeys {
    param($User, $Template)
    foreach ($p in $Template.PSObject.Properties) {
        $v = $p.Value
        if ($User.PSObject.Properties.Name -contains $p.Name) {
            if ($v -is [PSCustomObject] -and $User.($p.Name) -is [PSCustomObject]) {
                Merge-DeepKeys -User $User.($p.Name) -Template $v
            }
            # 用户已有标量值：保留，不覆盖
        } else {
            $User | Add-Member -NotePropertyName $p.Name -NotePropertyValue $v -Force
        }
    }
}
```

`$cfgPairs` 循环体改为：

```powershell
$u = Get-Content $dst -Raw -Encoding UTF8 | ConvertFrom-Json
Merge-DeepKeys -User $u -Template $t
ConvertTo-Utf8NoBom -Path $dst -Json ($u | ConvertTo-Json -Depth 20)
```

> 若不想维护两份实现：也可把 `install.ps1` 的 ensure-keys 简化为「目标不存在则直接复制模板」，深度补键全部交给 app 首次启动的 `sync_templates()`。但要注意 `sync_templates()` 受版本门控（版本未变则不执行），因此**首次安装必须完成初始化**——两条路都可，推荐递归合并以避免语义分叉。
