## 0. 判定基线

设计给出的分层与本文采用的依赖方向约定：

| 端 | 层次（自上而下） | 本文约定的合法依赖方向 |
|---|---|---|
| 服务端 | 核心层 → 能力层 → 运行时 | 上层可依赖下层；**下层不得反向 import 上层**；同层之间只允许通过显式接口（provider / 注册表 / 门面）协作；插件（业务侧）只能依赖"稳定契约面"，不得依赖任一端内部模块 |
| 桌面端 | 交互层 → 核心层 → 能力层 → 运行时 | 同上；且**交互层不得越过核心层直连能力层/运行时** |

判"是否符合"的四档：**符合**（职责与依赖方向都干净）/ **基本符合**（职责对，边界靠约定而非结构）/ **偏差**（职责错位或存在越界依赖）/ **严重偏差**（反向依赖、跨层直取运行时内部）。

另设两条"纪律红线"作为加分/减分项：
- **N1 静态可验证性**：层级边界能否由目录 + import 规则静态检查出来（而不是靠注释声明）。
- **N2 单一真源**：同一职责是否在单一模块内实现（而不是散落在多个层）。

# 一、服务端

## 1.1 模块 / 目录 → 层级映射

| 路径 | 归属层级 | 判断依据 |
|---|---|---|
| `app.py` | 装配外壳（不属四层，等价于"宿主入口"） | 只做 Flask 实例装配、CLI 分派、启动编排；模块头自述"只做装配与路由" |
| `jz_host/dep_bootstrap.py` | 核心层 · 依赖管理 | 启动期依赖组件三连（应用暂存 → 注入 pylibs → 注册重扫回调） |
| `jz_host/access_log.py` | 核心层 · 上下文管理 | 请求上下文（客户端 IP / 操作标签 / 当前用户）、访问日志、gzip、安全头 |
| `jz_host/shell_gate.py` | 核心层 · 上下文管理 | 壳身份门：接入密钥生命周期（单一写方）+ 请求级准入 |
| `jz_host/plugin_loader.py` | 能力层 · 插件调用 | 注册表/manifest 扫描、版本依赖门控、`register(app)` 装配 |
| `jz_host/llm_routes.py` | 能力层 · 插件调用（框架能力路由） | `/api/llm/*` 路由挂载，本身不实现推理 |
| `jz_host/tray.py` | **交互层实现，却落在核心层包内** | 系统托盘图标 + 气泡通知（桌面 UI 行为），服务端进程无 UI 层仍带此件 |
| `jz_deps.py`（仓库根） | 核心层 · 依赖管理 | 依赖判定唯一入口：三态结论 + 版本门控 + 请求期标记重算 |
| `jz_plugin_host.py`（仓库根） | 核心层 · 依赖管理 / 能力层 · 插件调用（双职责） | `setup_dep_components`/`dep_components_status` 属依赖管理；`load_backend_module` 属插件调用 |
| `jztools_data.py`（仓库根） | 核心层 · 上下文管理 | 数据根解析/迁移、原子写、配置模板同步、插件待重启标记 |
| `jz_api.py`（仓库根） | 稳定契约门面（面向插件的 API 层，设计未单列） | provider 注册表：会话/操作标签/组织架构/用户 LLM/壳密钥 |
| `jz_worker.py` | 能力层 · 进程运行 | 一插件一进程：Flask 实例 + provider 注入 + `register(app)` + waitress |
| `supervisor/supervisor_core.py` | 核心层 · 进程管理 | `Supervisor` 容器：拉起/健康探针/熔断/重启/日志归集；`JobObject` 孤儿收割 |
| `supervisor/apply_chain.py` | 核心层 · 进程管理（升级编排） | 备份 → 落盘 → 健康检查 → 回滚 |
| `supervisor/venv_mgr.py` | 运行时 · 依赖运行 | venv 建环境 + wheel 离线闭包安装 + 幂等 marker |
| `supervisor/control_api.py` | 核心层 · 进程管理（控制面） | HTTP 控制接口：apply/rollback/clear-circuit/restart |
| `supervisor/mainapp_bridge.py` | **能力层 · 插件调用，却落在 supervisor 包内** | 主应用侧反代桥（import flask/requests），与 supervisor 进程的 stdlib 纪律相反 |
| `supervisor/__main__.py` | 运行时启动件 | supervisor 独立进程入口 |
| `runtime/pylibs`、`runtime/libreoffice`、`runtime/chrome` | 运行时 · 依赖运行 | 依赖组件包、外部程序组件（由 `jz_deps._probe_external` 探测） |
| `plugins/<id>/backend/routes.py` | 业务侧（插件） | 经 `register(app)` 契约被能力层装配 |
| `static/`（前端） | **交互层，物理位置在框架目录** | 首页/工具壳页等 UI |

## 1.2 逐层实现剖析

### 核心层

| 职责 | 实际实现位置 | 关键类 / 接口 | 是否符合 | 问题说明 |
|---|---|---|---|---|
| 进程管理 | `supervisor/supervisor_core.py`、`supervisor/apply_chain.py`、`supervisor/control_api.py`；`app.py` 的 `_run_restart_helper` | `Supervisor`（`_procs`/`_circuit`/`_applying`）、`JobObject.assign()`、`ensure_unit_port()`、`apply_chain.apply_package()`/`rollback_unit()`、`control_api.make_handler()` | **符合**（职责与实现质量高） | 主应用自身进程的生命周期不在本层内：由外部 NSSM/SCM 与 `install.ps1` 兜底，`app.py` 只提供 `--wait-restart` 自重启助手；**自身进程管理存在对外依赖，但属于刻意设计（supervisor 必须比受管对象更"不倒"）** |
| 依赖管理 | `jz_deps.py`（判定）、`jz_host/dep_bootstrap.py`（启动注入）、`jz_plugin_host.setup_dep_components`（pylibs/DLL 注入）、`jz_deps.refresh_flags/install_refresher`（请求期重算） | `jz_deps.evaluate()`、`evaluate_all()`、`read_version_json()`、`apply_pending_components()`、`register_component_rescanner()` | **符合** | 严守"仅标准库、不 import 插件"纪律；唯一毛刺是 `jz_deps.install_refresher(app, ...)` 接收 Flask app 对象（隐式耦合 Web 框架，但非 import 依赖） |
| 上下文管理 | `jztools_data.py`（数据根/迁移/模板同步）、`jz_api.py`（会话与权限 provider）、`jz_host/access_log.py`（请求上下文）、`jz_host/shell_gate.py`（接入密钥与壳身份） | `get_data_root()`/`migrate_data_root()`/`sync_templates()`、`jz_api.register_providers()`/`get_session_user()`/`get_org_tree()`、`access_log.parse_operation()`、`shell_gate.install()` | **基本符合** | ① 上下文管理分散在 4 个模块，无统一"上下文服务"入口；② `jz_api` 反向 import `jz_host.shell_gate`（见 §1.4 D-3）；③ `jztools_data` 物理上在仓库根，与 `jz_host/` 分裂，归属要靠约定识别 |

### 能力层

| 职责 | 实际实现位置 | 关键类 / 接口 | 是否符合 | 问题说明 |
|---|---|---|---|---|
| 插件调用 | `jz_host/plugin_loader.py`（进程内装配）、`jz_plugin_host.load_backend_module()`（动态加载）、`supervisor/mainapp_bridge.py`（worker 化插件反代）、`jz_host/llm_routes.py`（框架能力路由） | `register_plugin_backends()`、`_register_tool_plugin()`、`_load_plugin_routes()`、`_gate_state_of()`、`install_worker_proxy()`/`_proxy_to_worker()` | **基本符合** | ① 进程内加载与 worker 反代两套机制并存，切换靠"注册表里有无单元"隐式判定（`_register_tool_plugin` 中 `if plugin_id in worker_units: return`），是迁移期设计，但**能力层因此必须读运行时层的注册表**；② 加载失败隔离与门控三态实现完整，质量好 |
| 进程运行 | `jz_worker.py` | `run_worker()`、`_Loopback`（回环取会话/组织树）、`/\_worker/health` 探针 | **符合** | worker 不做端口/路径决策（全由 supervisor 经环境变量注入），边界干净；鉴权权威留在主应用，fail-closed |

### 运行时

| 职责 | 实际实现位置 | 关键类 / 接口 | 是否符合 | 问题说明 |
|---|---|---|---|---|
| 依赖运行 | `runtime/pylibs`（组件包 + `manifest.json`）、`runtime/libreoffice`、`runtime/chrome`、`supervisor/venv_mgr.py` 产出的 `<数据根>/venvs/<id>`、waitress/Flask/Python 解释器 | `venv_mgr.ensure_venv()`/`discard_venv()`、`jz_deps._probe_external()` | **基本符合** | ① "运行时"没有独立目录，按路径约定散布在 `runtime/`、数据根 `venvs/`、`supervisor/install/install-supervisor.ps1` 三处；② venv 形态仅源码态可用（frozen 无 site-packages），属已知限制 |

| 职责 | 实际实现位置 | 是否符合 | 问题说明 |
|---|---|---|---|
| UI 交互（服务端形态） | `static/`（index.html / tool.html / js）、`jz_host/tray.py` | **偏差** | 设计未给服务端设交互层，但实际存在：`tray.py` 是桌面 UI 组件却装在核心层包 `jz_host/` 内；`static/` 直接引用具体插件资源（见 §1.4 D-5） |

## 1.3 调用关系（依赖方向）

```
app.py（装配外壳）
  ├─→ jz_host.{dep_bootstrap, plugin_loader, access_log, shell_gate, llm_routes, tray}
  ├─→ jz_api / jz_deps / jztools_data / jz_plugin_host
  ├─→ jz_worker（--worker CLI 分派）
  └─→ supervisor.mainapp_bridge（install_worker_proxy）        ★ 装配期依赖，方向合法

jz_host.plugin_loader ──→ jz_deps（门控）、jz_plugin_host（加载）
                     ──→ supervisor.mainapp_bridge（worker 快照）   ★ 核心层 → 运行时层侧件
jz_api ──→ jz_host.shell_gate（懒 import）                          ★ 门面 → 核心内部实现
插件 backend/routes ──→ jz_api / jz_deps / jz_llm / jztools_data（合法）
plugins/admin/backend/store_admin ──→ supervisor.{mainapp_bridge, apply_chain}  ★ 业务插件 → 进程管理/运行时
supervisor.{supervisor_core, apply_chain, venv_mgr, control_api} ──→ 仅标准库（纪律达标）
supervisor.mainapp_bridge ──→ flask / requests / jztools_data                ★ 与同包纪律冲突
```

## 1.4 问题标注（证据级）

| 编号 | 类型 | 证据 | 说明 |
|---|---|---|---|
| D-1 | **越界依赖（严重）** | `plugins/admin/backend/store_admin.py`：`from supervisor.mainapp_bridge import supervisor_endpoint, worker_units_snapshot`、`from supervisor.apply_chain import validate_venv_node`、`from supervisor.mainapp_bridge import try_supervisor_apply` | 业务插件直接 import 进程管理层的实现模块。`admin` 是"核心插件"，但它对 supervisor 的依赖是**硬 import**，等于把运行时的部署形态（是否 worker 化、supervisor 端口/令牌）泄漏进插件；supervisor 缺包时该插件相关路径直接失败 |
| D-2 | 越界依赖 | `jz_host/plugin_loader.py` 的 `_worker_units_snapshot()`：`from supervisor.mainapp_bridge import worker_units_snapshot` | 核心层的插件装载器依赖"主应用侧反代桥"。该桥语义上属能力层，却装在 `supervisor` 包里，导致核心层 import 路径看起来是"核心 → 运行时" |
| D-3 | 越界依赖 | `jz_api.py`：`from jz_host import shell_gate`（`shell_token_info()` / `shell_token_reset()` 内懒 import） | 面向插件的稳定契约门面反向依赖核心层内部模块。作者已用懒 import 规避导入环，但方向仍是"契约面被内部实现穿透"；`jz_api` 模块头自述"仅标准库、导入无副作用、不得 import 任何插件"，未承诺不 import 核心内部 |
| D-4 | **目录归属错位** | `supervisor/mainapp_bridge.py`：`from flask import Response, jsonify, request`、`import requests`、`import jztools_data` | 该文件与 `supervisor_core.py` 模块头声明的"仅标准库、不 import 主包任何模块"纪律直接冲突。它被主包（`app.py`）与插件（`store_admin.py`）共享，却物理位于 supervisor 包内 —— 造成 D-1、D-2 两条越界的根因 |
| D-5 | 层级间耦合 | `static/index.html`（`href="/plugin/admin/css/admin.css"`、`src="/plugin/admin/js/admin-common.js?v=8"`）、`static/tool.html` 同 | 框架 UI 依赖具体插件 `admin` 的静态资源；插件未加载/改名/资源结构调整 → 框架自身样式与公共行为缺失 |
| D-6 | 职责错位 | `jz_plugin_host.py` 同时含 `setup_dep_components`/`dep_components_status`（依赖管理）与 `load_backend_module`（插件调用） | 一个模块横跨核心层与能力层。抽取时按"行为保持"从 `app.py` 搬出，未做职责再切分 |
| D-7 | 职责错位 | `app.py` 内 `_validate_reorder` / `_apply_reorder` / `_set_tool_enabled` / `_set_category_enabled` / `_filter_visible_tools`（约 200 行） | 装配外壳承载"工具可见性与排序"业务逻辑，应属交互/业务层或独立服务，无独立落点 |
| D-8 | 缺失层次 | 服务端无"上下文管理"统一入口 | 数据根（`jztools_data`）、会话（`jz_api` provider）、请求上下文（`access_log`）、壳身份（`shell_gate`）四处分治，无统一 Context 服务对象 |
| D-9 | 空壳/占位 | 未发现 | 服务端各层均有实质实现，无 `pass`/`TODO` 占位层 |

## 2.2 逐层实现剖析

### 交互层

| 职责 | 实际实现位置 | 关键类 / 接口 | 是否符合 | 问题说明 |

|---|---|---|---|---|

## 2.3 调用关系（依赖方向）

```
client_main（组合根）
  ├─→ client_config、single_instance（核心，方向合法）
  ├─→ plugin_executor（进程管理，但物理在能力层）
  ├─→ capability_app（能力）
  └─→ shell_window（交互；交互层由组合根装配，未反向依赖，OK）

shell_window（交互）──→ client_config（核心）                        方向合法
capability_app（能力）──→ client_config、session_mirror（核心）       方向合法
capability_app（能力）──→ pkg_install、plugin_source（核心/能力混合）  方向合法但职责混淆
capability_app（能力）──→ runtime\pylibs 直接读写                     ★ 能力层 → 运行时内部
capability_app（能力）──→ 实现账号上下文/插件装卸/自身重启             ★ 能力层吞噬核心层
plugin_executor（能力）──→ subprocess.Popen(运行时 python, plugin_host)  方向合法
plugin_host（运行时）──→ jz_plugin_host（共享核心）                    上层无关，OK
本地插件 ──→ jz_api / jz_deps / jz_relay（契约面）                    干净，无反向 import 客户端内部
static/index.html ──→ /plugin/admin/css|js                           ★ 交互层 → 具体插件
```

值得肯定：**本地插件侧纪律良好** —— `client-plugins/` 下两个插件只依赖 `jz_api`/`jz_deps`/`jz_relay`，未发现反向 import `capability_app`、`plugin_executor`、`client_config`。

# 三、统一偏差汇总（按严重程度排序）

| 序号 | 严重度 | 端 | 偏差 | 影响 | 主要证据 |
|---|---|---|---|---|---|
| 1 | **高** | 服务端 | 业务插件直接 import 进程管理/运行时层（admin → supervisor） | 部署形态泄漏进插件；supervisor 缺包即影响插件路径；supervisor 内部结构变更会波及插件 | `plugins/admin/backend/store_admin.py` 三处 import |
| 2 | **高** | 桌面端 | 能力层吞噬核心层 + 直取运行时内部（2228 行汇聚点） | 依赖装卸/账号上下文/进程管理无单一落点；运行时目录布局散落；任一块改动都动同一个巨型文件 | `client/capability_app.py` 全篇 |
| 3 | 中高 | 服务端 | `mainapp_bridge.py` 归属错位（在 supervisor 包内却 import flask/requests） | 破坏 supervisor"仅标准库"纪律；诱发 D-1/D-2 两条越界 | `supervisor/mainapp_bridge.py` import 段 vs `supervisor_core.py` 模块头 |
| 4 | 中 | 服务端 | 稳定契约门面反向依赖核心内部实现 | 插件 API 面不再"零依赖"，升级/替换核心实现时门面需同步改 | `jz_api.py` → `jz_host.shell_gate` |
| 5 | 中 | 桌面端 | 依赖/进程管理职责错位（executor 在能力层；依赖编排在能力层） | 层级语义与目录语义不一致，无法用规则约束 | `client/plugin_executor.py`、`capability_app.py` 依赖编排段 |
| 6 | 中 | 双端 | 框架 UI 直接依赖具体插件资源与身份 | 插件停用/改名 → 框架首页样式、公共 JS、侧边栏入口失效 | `static/index.html`、`static/tool.html`、`static/js/sidebar.js`；`capability_app._builtin_ids` |
| 7 | 中 | 双端 | 共享内核物理位置在仓库根，无 `kernel/` 源码目录 | 两端核心层归属歧义；客户端不自包含；打包靠 spec 复制维持一致 | `jz_*.py` 在根；`JZClient.spec` 复制清单 |
| 8 | 中低 | 桌面端 | `sys.path` / `sys.modules` 技巧绕开包边界 | 分层不可静态校验（N1 不达标），新人易误加错层依赖 | `client_main.py`、`capability_app.py` 注入 jz_relay |
| 9 | 中低 | 桌面端 | `PluginExecutor.shutdown()` 未接线 | 常驻 worker 清理依赖 OS；退出路径不干净 | 无调用点；`shell_window.py` 用 `os._exit(0)` |
| 10 | 低 | 双端 | 服务端缺"上下文管理"统一入口；桌面端上下文分治两处 | 上下文口径分散，新增上下文字段要改多处 | `jztools_data`/`jz_api`/`access_log`/`shell_gate`；`client_config`/`session_mirror` |
| 11 | 低 | 服务端 | `jz_plugin_host` 跨核心/能力双职责；`app.py` 承载业务路由 | 单模块跨层；外壳不像外壳 | `jz_plugin_host.py`；`app.py` 排序/可见性段 |
| 12 | 低 | 服务端 | `jz_host/tray.py` 是 UI 组件却装在核心层包 | 服务端（无 UI 层）带着桌面交互件 | `jz_host/tray.py` |

## 结论性评估

**存在偏差**（不是"完全符合"，也不是"基本符合"）。

- **骨架是对的、且实现质量不低**：服务端的进程管理（supervisor + JobObject + 熔断 + 回滚）、依赖判定（`jz_deps` 三态 + 版本门控）、worker 进程运行（`jz_worker` 零决策）、桌面端的子进程隔离执行（`plugin_executor` + `plugin_host`）与交互层（`shell_window`）都是干净的、职责明确的实现；**插件侧纪律尤其好**（服务端 17 个插件、桌面端本地插件均未反向 import 端内部模块）。
- **偏差集中在"边界维持手段"**：层级靠注释与模块头纪律声明，而不是靠目录与 import 规则强制执行。因此出现了 3 条实质越界（插件→运行时、能力层→运行时内部、门面→核心内部）和 1 个巨型汇聚点。
- **没有空壳层**：四层职责在两端均有真实实现，问题不是"没做"，而是"做在了错误的位置 / 被上层顺手代劳"。

> 全部建议均为"搬迁 + 加接口"，不改运行机制、不重写逻辑。
