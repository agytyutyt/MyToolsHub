# 压缩算法评估（DS）

> 目标：进一步压缩「信息传输」插件（`plugins/info-transfer`）大文件转换出来的**二维码量**，
> 并支持 PDF / JPG / PNG / ZIP 等**二进制格式**的离线传输。
> 评估日期 2026-09-15 · 代码基线 `plugins/info-transfer/backend/routes.py`（1794 行，工作区当前版本）
> 本报告全部结论都带实测数据，复现方式见 §10；未引用的数据一律标注「未见公开数据」。

---

## 0 结论摘要

**一句话**：这次要解决的不是「换一个更厉害的压缩算法」，而是**先修掉协议里的三处结构性浪费**，
再对 PDF / JPG / PNG / ZIP 每个格式配一个**格式感知的预处理器**——后者才是这四类新格式的收益主体，
通用压缩器对它们几乎无效（实测 0.5%~3%）。

### 0.1 推荐方案（按优先级）

| 优先级 | 措施 | 二维码量收益 | 工作量 | 触及面 |
| --- | --- | --- | --- | --- |
| **P1** | 帧/页**二进制直载**（去掉 base64 与 JSON 外壳，含视频的二重 base64） | 静态 **−26%**；视频 **−45%** | 中 | 协议 v2 + 网页端 + APP |
| **P1** | APP 收帧判据 `have >= n` → `have >= k`（让 40% 冗余成为真容错） | 视频再 **−40%** | 小 | 仅 APP |
| **P2** | 压缩器 `zlib-9` → **LZMA2**（`xz-java` 纯 Java 解码） | 文本类 −18%、PDF 图文 −20pp | 小 | B 端 + APP 加 1 个 jar |
| **P2** | Office / ZIP **拆包重组** | docx −75%、xlsx −49%、zip −27% | 中 | B 端 + APP 重建 |
| **P2** | PNG → **WebP 无损**（像素等价） | 截图 −83%、照片 −36% | 小 | APP 原生解码 |
| **P3** | JPEG → **packJPG**（字节精确无损） | −16% | 中（需 NDK） | APP 需 native |
| **P3** | 二维码**多码同屏**（r×c 非方形，见 §6.3） | 吞吐 **×2.2~4.0**（静态路径） | 小（静态 0 行 / 流式 1 行） | APP + B 端拼图 |
| **P3** | FEC `zfec 40%` → 喷泉码（wirehair/RaptorQ） | 冗余 40% → 0~2% | 大 | 协议 + 两端 |

> 视频一栏的推导：现行每帧链路膨胀 1.333（信封 base64）→ 1.333（帧 base64）→ 1.667（FEC）= **2.96×**；
> 去掉两层 base64 后只剩 FEC，每帧净载荷 967 B → **1764 B（−45%）**；再修掉收帧判据就是 2940 B（−67%）。

**打包后的净效果**（实测口径，v40 二维码；「默认通路」= 该格式今天实际走的那条路）：

| 场景 | 原始 | 现行 默认通路 | 现行 原件传输 | 推荐方案 | 降幅 |
| --- | --- | --- | --- | --- | --- |
| **Word 文档 151 KB** | 151 KB | 45 页（精简文本） | 71 页 | **7 码**（精简 + LZMA2 + 二进制）<br>14 码（保格式：拆包重组） | **−84%** / −80% |
| **Excel 表格 145 KB** | 145 KB | 24 页（精简二维数组） | 69 页 | **13 码**（精简）<br>26 码（保格式） | **−46%** / −62% |
| ZIP 压缩包 247 KB | 247 KB | —（只能原件） | 118 页 | **63 码** | −47% |
| PDF 图文混排 6.5 MB | 6.5 MB | 不支持 | 3155 页 / 6885 帧 | **1590 帧**（+2×3 同屏 → 402 画面） | −77%（对视频） |
| JPEG 照片 522 KB | 522 KB | 不支持 | 248 页 | **153 码** | −38% |
| PNG 截图 39 KB | 39 KB | 不支持 | 19 页 | **3 码** | −84% |
| PNG 照片 3.9 MB | 3.9 MB | 不支持 | 1902 页 | **145 码**（有损，需授权） | −92% |

> 注意 Word/Excel 的**默认通路本来就是「精简传输」**（提取文本/表格，丢格式），它比原件传输小得多
> （45 vs 71 页）。所以对已有格式，压缩器升级 + 协议瘦身的收益是 **45→7 页**；
> 「拆包重组」（§4.1）是给**必须保格式**的场景准备的，代价是 2 倍码数（14 vs 7），仍比今天小 80%。

### 0.2 三条必须说明的边界

1. **字节精确 vs 内容等价**：「拆包重组」与「PNG→WebP」只能保证**内容/像素等价**，无法还原原始字节；
   现行 README 承诺的「字节一致」只对 packJPG / LZMA / 纯压缩路线成立。建议信封增加
   `mode: exact | rebuild` 字段，UI 明示（详见 §7.3）。
2. **压缩救不了「大二进制」**：v40 单码净载荷 2940 字节，5 MB 文件即使压到 4.5 MB 仍要 1500+ 帧；
   6.5 MB PDF 的推荐方案仍是「约 9 分钟的视频流」（1590 码 × 5 帧重复 ÷ 15fps），**不是几次扫码**。
   想真正提速必须靠多码同屏（§6.3，静态路径 → 约 2.2 分钟）与更强信道码。
3. **接收端是手机**：所有变换都必须能在 Android 上逆运算。这一条否决了 zpaq / cmix / bsc / lrzip /
   precomp 全套 / lepton 等一大票高压缩比方案（§9）。

## 1 现状量化：二维码量花在哪里了

### 1.1 三条数据通路

| 通路 | 载荷形态（`fmt=file`，原件传输） | 膨胀 | 每码净载荷（v40-L） |
| --- | --- | --- | --- |
| 静态 | 文件字节 → base64 → JSON 信封 → 分页包装 | **1.33×** + JSON 壳 | **2160 B/页** |
| 视频 | 文件字节 → base64 → JSON 信封 → **再 base64** → 分块 → zfec 1.4× | **1.78× ×1.67 = 2.96×** | **990 B/帧** |
| 精简（文本/表格） | 文本 → zlib-9 → base64 → JSON 信封 | 压缩后 1.33× | — |

实测（真代码路径，`routes.py` 的 `extract_doc_raw` → `build_envelope` → `_build_static_pages`）：

```
docx 154,226 B → 信封 JSON 205,705 B（base64 膨胀 33%）→ 静态 v40-L = 72 页，首页 2915 B
单页容量 2940 B；每页有效载荷 ≈ 2160 B（去掉 JSON 壳后是 base64 字符）
```

> **注意**：`_pack_data`（`routes.py:660`）对 `fmt=file` **直接原样承载、一次压缩都不做**
> （原注释：「base64 高熵无收益」）。所以今天要传 PDF/JPG/PNG/ZIP，只有「base64 膨胀 33%」
> 这一个动作——这正是新增这四类格式必须先解决压缩的原因。

### 1.2 三处结构性浪费

**① 视频流对原件传输做了两次 base64（最严重）**

`routes.py:1350` 生成 `env_bytes = build_envelope(...)`（`fmt=file` 时 data 字段已是文件字节的 base64），
`routes.py:1389` 又把这个 JSON 交给 `encode_to_video(env_bytes, ...)`，而 `_qrformat_encode`
（`routes.py:792`）对每帧再做一次 base64。于是文件字节经历 base64 → JSON → base64，**净膨胀 1.78×**。
150 KB 的 Word 在视频流里要占 274 KB 的二维码容量。

**② 40% FEC 冗余在 APP 端是纯开销**

`FEC_RATIO = 0.4`（`routes.py:137`）→ 帧数 ×1.67。但 APP 的重组条件写死了「收齐全部 n 帧」：

```kotlin
// android-app/InfoParse/app/src/main/java/com/jztools/infoparse/protocol/QrFrame.kt:76
fun assembleSystematic(): ByteArray? {
    if (n == 0 || m == 0 || have < n) return null   // ← 要求所有帧（含全部校验帧）
```

校验帧在系统位路径里根本不参与重组（`QrFrame.kt:80-84` 只用 `s < k` 的 share），
所以这 40% 的帧**扫了也用不上**，只增加扫码时长。正确判据是 `have >= k`（`ZfecCompat` 已有兼容实现，
只是没有接线，`移动端APP.md:1250` 也把它列为待办）。

**③ zlib 的 32 KB 窗口是文本/容器类数据的天花板**

deflate 的匹配窗口只有 32 KB，超过窗口的重复（长文档内部的重复段落、
Office/ZIP 容器里多个相似 XML、PDF 里多个相似的 Flate 流）它一律找不到。实测（473 KB 真实中文技术文档，
17 篇）：zlib-9 = 188.3 KB（39.8%），LZMA2 = 154.7 KB（32.7%），**相对 −18%**，
而两者差的只是「窗口大小 + 熵编码器」。

### 1.3 二维码容量模型（评估基准）

`qrcode.util.BIT_LIMIT_TABLE[ERROR_CORRECT_L][version] // 8`，byte 模式：

| 版本 | 模块 | 字节容量 | 现行静态 净载荷/页 | 现行视频 净载荷/帧 | 二进制直载 净载荷/码 |
| --- | --- | --- | --- | --- | --- |
| 15（**前端默认**，`index.html:462`） | 77² | 523 | 335 B | 171 B | 507 B |
| 20 | 97² | 861 | 588 B | 285 B | 845 B |
| 30 | 137² | 1735 | 1244 B | 580 B | 1719 B |
| 40（上限） | 177² | 2956 | 2160 B | 990 B | **2940 B** |

> 口径：单位为「还原后得到的原始文件字节」。静态每页可放 `容量−16−60` 个 base64 字符；
> 视频每帧的实测 chunk 是 **2205 字节信封**（base64 后 2940 字符 + 12 字符帧头 = 2952，
> 占容量 2956 的 99.9%——**视频的容量利用率没问题，亏的是双重 base64 与 FEC**）。

> 前端默认版本是 **15**，不是 40。默认口径下 150 KB 的 Word：原件传输要 **461 页**、
> 精简传输要 **291 页**，两条路都远超 200 页硬上限（`_build_static_pages(max_pages=200)` 会直接报错
> 要用户调版本或改视频流）。所以下面一律用 **v40** 做对比口径，把「版本选择」和「压缩效果」两个变量分开。

## 2 评测口径

- **语料**：`.bench_corpus/`（docx 151 KB / xlsx 145 KB / zip 247 KB / PDF 文本 42 KB /
  PDF 图文混排 6.5 MB / JPEG 522 KB / PNG 截图 39 KB / PNG 照片 3.9 MB）
  ＋ 现场合成的「473 KB 真实中文文档（17 篇 md）」与「3000 行中文业务表格 CSV」。
- **压缩器**：都在**原始文件字节**上跑一次，比的是压缩后总字节数。
- **二维码换算**：严格按现行实现复刻——
  - 静态：`capacity = BIT_LIMIT_TABLE[L][v]//8 - 16`（`routes.py:934`），每页 JSON 壳约 60 B；

  - 方案列：二进制帧头 16 B，`net = capacity - 16`。
- **环境**：Python 3.14 / zstandard 0.25 / brotli 1.2 / py7zr 1.1.3 / Pillow 12.3 / pikepdf 10.13 /
  opencv 5.0 / zfec 1.6；`packJPGx64.exe`（`.bench_corpus/`）。
- **注意**：本报告**未读取**同目录下另一份评估文档，结论与数据均为独立实测。

## 3 通用压缩器实测

### 3.1 直接在原始文件上压（现阶段的等价物）

百分比 = 压缩后 / 原始。

| 语料 | zlib-9（现行） | LZMA2-9e | brotli-11 | zstd-22 | bzip2-9 | PPMd o12 |
| --- | --- | --- | --- | --- | --- | --- |
| docx 151 KB（容器） | 97.7% | 97.0% | **96.2%** | 96.8% | 99.3% | 99.6% |
| xlsx 145 KB（容器） | 92.7% | **89.5%** | 91.7% | 91.7% | 93.3% | 90.6% |
| zip 247 KB（容器） | 99.8% | 99.6% | 100.0% | **99.5%** | 100.2% | 102.4% |
| PDF 文本 42 KB | 73.8% | 72.9% | **72.0%** | 73.1% | 74.5% | 75.2% |
| PDF 图文 6.5 MB | 85.5% | 68.6% | **68.1%** | 68.5% | 82.8% | 69.3% |
| PNG 截图 39 KB | 64.8% | 63.6% | 64.8% | 64.4% | 70.2% | **63.0%** |
| PNG 照片 3.9 MB | 100.0% | 100.0% | **99.7%** | 99.9% | 100.0% | 100.1% |
| JPEG 522 KB | **99.5%** | 99.7% | 100.0% | 99.5% | 100.1% | 101.2% |
| 473 KB 中文文档 | 39.8% | 32.7% | **32.4%** | 33.5% | — | — |
| 3000 行 CSV 215 KB | 21.1% | **18.2%** | 18.4% | 19.1% | — | — |

**读法**：

- **对已经压缩过的容器（docx/xlsx/zip/jpg/png照片），换压缩器基本没用**（0~3%）。
  JPEG 上 brotli 甚至是 100.0%（膨胀），PPMd 101.2%。这些格式必须走 §4 的专用预处理器。
- **对文本类与 PDF，换压缩器立刻见效**：中文文档 −18%（相对 zlib），
  图文 PDF 从 85.5% 降到 68.6%——**单这一步就让 6.5 MB 的 PDF 少 1.1 MB**。
- **PPMd 没有性价比**：文本上比 LZMA2 好 0~2pp，但解码慢 27 倍（LTCB enwik9：546s vs 20s），
  而且**没有纯 Java 实现**（Apache commons-compress 的 `SevenZMethod` 里有 COPY/LZMA/LZMA2/DEFLATE/BZIP2，
  没有 PPMd），要上只能在 APK 里塞 NDK 版 p7zip。**排除**。
- **bzip2 全面落后**，无一项胜出。**排除**。

### 3.2 编码耗时（B 网 PC 端）

| 语料 | zlib-9 | LZMA2-9e | brotli-11 | zstd-22 |
| --- | --- | --- | --- | --- |
| PDF 6.5 MB | 0.20 s | 2.01 s | 18.77 s | 2.66 s |
| PNG 照片像素 12.5 MB | 0.13 s | 1.17 s | 49.87 s | 0.97 s |
| 473 KB 文档 | 0.04 s | 0.26 s | 0.86 s | 0.16 s |

压缩只在 B 网 PC 上做一次（且现在就在后台线程里，`routes.py` 的 executor），
LZMA2 的秒级开销完全可接受；**brotli-11 在几十 MB 级输入上要 20~50 秒，得配进度条**。

### 3.3 LZMA2 字典大小（决定 APP 端解码内存）

| 字典 | PDF 6.5 MB | PNG 像素 12.5 MB | 473 KB 文档 |
| --- | --- | --- | --- |
| 1 MB | 74.3%（+8.4%） | 31.6%（+3.3%） | 32.1%（±0） |
| 4 MB | 68.6%（+0.0%） | 30.9%（+0.8%） | 32.1%（±0） |
| 16 MB | 68.6%（±0） | 30.6%（±0） | 32.1%（±0） |
| 64 MB | 68.6%（基准） | 30.6% | 32.1% |

**16 MB 字典已经等于 64 MB 字典的效果**，解码端内存占用也小得多。**推荐 `dict_size = 1<<24`**。
（LZMA2 解码是流式的，手机端 6.5 MB 载荷约 0.1 s 级别。）

### 3.4 小文件：字典压缩（评估后**不推荐**）

实测 1.5 KB 的典型信封报文：

| 方案 | 大小 | 相对 zlib |
| --- | --- | --- |
| zlib-9 | 446 B | 基准 |
| brotli-11（内置 122,784 B 静态词典，RFC 7932 §8） | 333 B | 75% |
| zstd-22 | 389 B | 87% |
| LZMA2-9e | 384 B | 86% |
| **zstd-22 + 自训练 17.2 KB 字典** | **141 B** | **32%** |

看起来惊人，但**对本插件没有意义**：小载荷本来就是一个二维码装得下，
省 300 字节不改变任何一件事——除非它**恰好卡在页/帧边界**上。
为一个边界收益引入「字典随包分发 + 两端版本对齐」的复杂度不划算。**不推荐上字典**；
真要压小文件，brotli-11 的**内置**词典白送 25%，零额外成本。

## 4 格式专用预处理器（收益主体）

### 4.1 Office / ZIP：拆包重组

做法：解压 zip 容器 → 把「条目名 + 条目原始内容」拼成一个连续流 → 用强压缩器压这一个流。
接收端用 `java.util.zip.ZipOutputStream` 重建（Android 内置，零依赖）。

| 语料 | 原文件 | 容器直压（LZMA2） | **拆包重组 + LZMA2** | 中间态 | 收益 |
| --- | --- | --- | --- | --- | --- |
| docx 151 KB | 100% | 97.0% | **25.1%** (37.8 KB) | 1.29 MB | **−75%** |
| xlsx 145 KB | 100% | 89.5% | **51.4%** (74.6 KB) | 1.50 MB | **−49%** |
| zip（内含文本）247 KB | 100% | 99.6% | **73.1%** (180.5 KB) | 564 KB | **−27%** |

同一份重组流换其他压缩器（供选型）：xlsx 上 LZMA2 74.6 KB < brotli 84.1 KB < PPMd 85.5 KB < zstd 93.1 KB；
zip 上 PPMd 151.1 KB 最优（但见 §3.1，PPMd 排除）。
**结论：拆包重组 + LZMA2，收益 27%~75%，解码端只用系统 API。**

**与「精简传输」的关系**（重要，别用错场景）：

| 通路 | docx 151 KB | xlsx 145 KB | 保真度 |
| --- | --- | --- | --- |
| 精简传输（现行默认，提取文本/表格 + zlib） | 45 页 | 24 页 | 只保内容 |
| 精简传输 + LZMA2 + 二进制直载 | **18.1 KB → 7 码** | **37.0 KB → 13 码** | 只保内容 |
| 原件传输（现行 base64） | 71 页 | 69 页 | 保格式 |
| **原件传输 + 拆包重组 + LZMA2 + 二进制** | **37.8 KB → 14 码** | **74.6 KB → 26 码** | 保格式（重建容器） |

> 这是本次评估里**单位工作量收益最高**的一项，且对现有 Word/Excel 用户立刻见效。
> 需要注意：重组后重建的 zip **字节不等于原文件**（deflate 实现/时间戳/条目顺序可能不同），
> 但 Office/WPS 打开无差异——属于 §0.2 的 `rebuild` 模式。
> 想保字节精确只能走 preflate（见 §9），复杂度高得多。

### 4.2 PNG

| 语料 | 原始 | PNG optimize（无损） | **WebP 无损** | 像素解包+LZMA2 | WebP q80（有损） | AVIF q80 |
| --- | --- | --- | --- | --- | --- | --- |
| 截图 39 KB（1920×1080） | 100% | 97.6% | **17.0%** (6.6 KB) | 21.2% (8.3 KB) | 83.0% | 30.9% |
| 照片 3.9 MB（2560×1707） | 100% | 100.6% | **63.9%** (2.50 MB) | 97.8% (3.83 MB) | 10.4% (415 KB) | 13.3% |

**读法**：

- **截图 / 图表 / 界面图**：WebP 无损直接砍掉 83%，**像素完全一致**，Android 4.2.1+ 原生解码。
  这是纯赚，建议默认开启。
- **照片型 PNG**：WebP 无损省 36%（像素一致）；再往下只能有损（q80 省 90%），**必须用户显式授权**。
- 「像素解包 + LZMA2」对截图也有效（−79%），但比 WebP 无损差，且重建 PNG 需要复刻 filter/zlib 参数
  才能字节精确——**不如直接用 WebP 路线**。
- PNG→JPEG 是坑：截图转 JPEG q90 反而 **膨胀到 338.9%**。**不要做无条件转 JPEG**。

### 4.3 JPEG

JPEG 已是 DCT 熵编码，通用压缩器全部无效（§3.1）。无损重压只有专用编码器能赢：

| 方案 | 实测 | 说明 |
| --- | --- | --- |
| **packJPG**（`packjpg/packJPG`，LGPL-3.0） | 522.5 KB → **438.5 KB（−16%）** | 字节精确可逆；解压端 `packjpg/unpackJPG` 有 BSD-2 的**纯解压**仓库；需 NDK |
| brunsli（`google/brunsli`，MIT，活跃） | 官方口径 **−22%**，位精确还原 | lepton 的官方替代品；C++，需 NDK |
| libjxl 无损转码（`libjxl/libjxl`，BSD-3） | 官方口径 **−20%** | 需要 APK 集成 jxl 解码器（`oupson/jxlviewer`、`awxkee/jxl-coder` 有 Android 先例） |
| mozjpeg `jpegtran`（`mozilla/mozjpeg`） | 未见官方百分比（业界常引 ~5%） | 只做霍夫曼表优化，收益小 |
| lepton（`dropbox/lepton`，Apache-2.0） | 官方 22% | **已归档（2023-02）**，README 自述无力修复已报告安全漏洞。**排除** |

**结论**：JPEG 的无损收益 16%~22%，但要往 APK 里加 native 解码器。
**建议排在 P3**——先把零成本的协议与容器收益吃掉，JPEG 无损重压留到有明确需求时再做。

- **别小看「LZMA2 直压」这一步**：PDF 内部流虽是 deflate，但多个相似流之间的重复

### 5.1 候选解码器的 APK 体积（实测 jar/so 大小）

### 5.2 二进制直载在 Android 上的可行性

ML Kit 的 `Barcode.getRawBytes()` 能拿到字节模式二维码的**原始字节**，这是标准能力，
当前 APP 只用了 `rawValue`（UTF-8 解码文本）。网页端 `jsqr.min.js:342` 也已经产出 `binaryData`
（`decoded.bytes`），只是 `worker.js:33` 只读了 `res.data`。

**两端改动都很小，但必须端到端验收**：字节模式的 QR 在不同解码器下对 ECI/编码假设不同，
必须实测「B 端编码 → 手机扫 → 哈希一致」。

### 5.3 一个必须知道的风险：现行回读校验不可靠

`_render_verified_qr`（`routes.py:910`）用 OpenCV 回读校验二维码，判据只有「能否解码」，**不校验内容**。
实测 v40-L 满容量载荷（2953 字符，box=10）：

| 载荷 | cv2 回读长度（3 次） | 期望 |
| --- | --- | --- |
| base64(docx) 前 2953 字符 | 2953 / 2953 / 2953 ✅ | 2953 |
| base64(zlib(docx)) 前 2953 字符 | **0 / 0 / 0** ❌ | 2953 |
| 随机字节 2953（高熵） | **0 / 0 / 0** ❌ | 2953 |

同时观察到一次**能解码但内容截断**（返回 105 字符）的情况 —— 说明「能读出」并不等于「读对」。
好消息是真实接收端用的是 ML Kit / jsQR（比 OpenCV 的 detector 稳），
坏消息是**生成端的自检给不了正确性保证**。→ 参见 §9 验收建议。

## 6 信道层（视频流）

### 6.1 现行帧协议的开销

单位：每个二维码承载的**原始文件字节**（v40-L）。

| 通路 | 净载荷/码 | 相对最优 |
| --- | --- | --- |
| 现行静态 | 2160 B | −26% |
| 现行视频 | **990 B** | **−66%** |
| 二进制直载（无 FEC） | **2940 B** | 基准 |

视频流每码只承载 990 字节——是静态（2160）的 46%、最优（2940）的 34%，
全部亏在 §1.2 的两处浪费上（双重 base64 1.78× × FEC 1.67×）。
好在视频流不需要人工翻页/对焦，**单位时间的吞吐才是它的指标**；这两处浪费必须修——但都不是靠「选一个更强的压缩器」修的。

### 6.2 FEC 与喷泉码

- 现行 `zfec`（`tahoe-lafs/zfec`）是**固定率** Reed-Solomon：`m/k` 倍数据，解出需要 `k` 个块。
  现在取 40% 冗余，且 APP 端还要收满全部 `n` 帧（§1.2 ②）。
- 喷泉码（RaptorQ/wirehair）是**无率码**：官方口径「多数情况收到等于源符号数量即可解出」
  （RFC 6330 原文），实测开销 0%~2%。
  - `catid/wirehair`（BSD-3，C++ 活跃，libcimbar 在用）：「平均需要 N + 0.02 个包」；
  - `cberner/raptorq`（Apache-2.0，Rust，实测 K=10 时 0.0% overhead）。
  - **Android 端没有现成的 Kotlin/Java RaptorQ 库**（OpenRQ 仓库已 404），要落地得编 `.so`。
- **性价比判断**：先把「收全 n 帧」的判据修成 `have >= k`（一行改动，视频帧数 −40%），
  把 40% 冗余**降级为真正的容错储备**；换喷泉码留到后面再说。

### 6.3 多码同屏（详细评估）

#### 6.3.1 它减的是什么

必须先把收益定义清楚，否则容易和「压缩」混为一谈：

| 指标 | 单码 | r×c 同屏（以 2×2 为例） | 说明 |
| --- | --- | --- | --- |
| 二维码**符号个数** | N | N | **不变**——总数据量没变，只是挤到一张画面里 |
| 需要**拍照/翻页/轮播的画面数** | N | N/4 | 静态模式下这是人工操作次数 |
| **传输时长** | 4T | T | 流式模式下这是用户真正感知的成本 |

所以严格说：**多码同屏不压缩二维码量，它压缩的是时间与画面数**。
对「大文件要传 10 分钟」这个痛点，它的效果比任何压缩算法都直接。

#### 6.3.2 唯一的物理约束：每模块占几个像素

多码同屏不是免费的——把屏幕切成多格，每格只能分到一部分像素，
**每个模块能分到的像素数（px/module）随之下降**，而二维码检测对它有硬下限。
这是决定「能不能做、能做几格」的唯一关键量。

实测容差（1920×1080 屏、手机 1080p 采集，zxing-cpp 解码，单样本）：

| 每模块 | 干净 | 旋转 3° | 轻透视 | 旋+透 | +模糊 σ1.2 | +JPEG q60 |
| --- | --- | --- | --- | --- | --- | --- |
| **2 px** | ✅ | 1/3 通过 | 2/3 通过 | ✅ | ❌ **3/3 全部失败** | ❌ **3/3 全部失败** |
| **3 px** | ✅ | ✅ | ✅ | ✅ | ✅ **3/3 通过** | ✅ **3/3 通过** |
| 4~5 px | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |

（v20 / v30 / v40 各测一遍；2 px 那一行在模糊与压缩下是三个版本全灭。）

**重复运行的波动同样是证据**：2 px/模块 这一档多次重跑的结果在 3/4 ~ 9/9 之间跳
（如 v40 2×2 一次 4/4、一次 3/4；v25 3×3 一次 7/9、一次 5/9），
而 3 px/模块 及以上每次都是全解出——**这就是"可用"与"不可靠"的分界**。

> **结论：≥3 px/模块是底线，建议按 4 px 留余量。** 2 px/模块在"干净渲染"下能读，
> 但一上手持拍摄的模糊与 JPEG 压缩就崩——这正是"仿真能过、现场扫码失败"的典型陷阱。

**必须强调的口径**：上面这个 px/模块 是**拍摄后图像里**的像素数，**不是屏幕上的像素数**。
手机上拍到的画面里，显示器只占一部分（其余是墙面、桌面），
所以**屏幕上的每模块像素 = 拍摄后每模块像素 ÷ 显示器占画面的比例**。

举例：1080p 级照片里显示器占 85% 的宽度 → 1920 屏幕像素只映射到 1632 拍摄像素，
屏幕上 3 px/模块 实际只剩 **2.55 px**——正好落进"不可靠"区（实测解出率掉到 70%）。
所以：

- B 端生成布局时**必须按「拍摄后像素」反算**，而不是按屏幕分辨率；
- 界面要引导用户**把显示器拍满画面**（提高占比），这是最省事的提速手段；
- 有多余的像素余量时，优先给**更多码**，而不是让码更大（见 6.3.3）。

#### 6.3.3 网格比例：方形网格在 16:9 屏幕上浪费面积

**1. 面积利用率：方形网格不是最优**

二维码是正方形，显示器是 16:9——在每模块 4 px 的预算下，**单个 v40 码只占屏幕 36.6% 的面积**，
横向那一大块是白扔的（像素预算越紧，这个比例越低）。
用同一版本（v32）对比方形与非方形网格，最能说明「按屏幕特性调比例」的价值：

| 布局 | 单码 | 每屏载荷（拍摄后 1632×918，每模块 3 px） | 相对单码 | 说明 |
| --- | --- | --- | --- | --- |
| 1×1 v40 | 2956 B | 2956 B | 1.0× | 现状：正方形码只占 36.6% 面积 |
| 2×2 v32 | 1955 B | 7820 B | 2.6× | 方形网格，横向仍空着一大块（面积 56%）|
| **2×3 v32** | 1955 B | **11730 B** | **4.0×** | **同一版本只补一列 → +50%** |
| 2×4 v27 | 1468 B | 11744 B | 4.0× | |
| 3×5 v19 | 795 B | 11925 B | 4.0× | 面积利用率 92%，但 15 码/帧 |

最优比例的经验法则：**列数 ≈ 1.8 × 行数**（正好是 16:9 的宽高比），即 2×4、3×5 这类；
方形网格（2×2、3×3）永远差一档。但**列数也不是越多越好**，见下面的像素预算。

**2. 像素预算表（不同余量下的最优布局）**

下表的 px/模块 一律指**拍摄后图像里的**像素（见 6.3.2 的修正：显示器只占照片的一部分）。
以 1080p 级照片、显示器占画面 85%（有效 1632×918）为例：

| 像素预算 | 最优布局 | 单码载荷 | 每屏载荷 | 相对单码 | 实测解出 |
| --- | --- | --- | --- | --- | --- |
| 6 px（强抗劣化） | 1×2 v27 | 1468 B | 2936 B | 1.5× | 3/3 |
| **4 px（推荐）** | **2×4 v19** | 795 B | **6360 B** | **2.2×** | **3/3 全解** |
| 3 px（激进下限） | 2×3 v32 / 2×4 v27 / 3×5 v19 | — | 11.7~11.9 KB | **4.0×** | 3/3 全解 |

（验证条件：旋转 2° + 透视 + 模糊 σ1.0 + JPEG q70，每格 3 次试验。）

> 两个反直觉但重要的结论：
>
> 1. **像素越紧，多码同屏越赚**：3 px 时增益 4.0×，6 px 时只剩 1.5×。
>    因为单码在 16:9 屏上只用 37% 的面积，像素越紧，这份浪费越致命。
> 2. **同等收益下要选码数最少的布局**：3 px 档里 2×3 v32（6 码）、2×4 v27（8 码）、
>    3×5 v19（15 码）的每屏载荷几乎一样（11.7~11.9 KB），但手机要检测的码数差 2.5 倍——
>    **选 2×3**。码数越多，单帧检测耗时越长，越容易吃满 333 ms 的停留窗口。

#### 6.3.4 落地成本：静态模式 0 行代码，流式模式 1 行

这是本次评估里**改动最小**的提速手段，因为两端的架构早就为它留好了位置：

| 位置 | 现状 | 需要改什么 |
| --- | --- | --- |
| APP 图片解码（静态模式） | `ImageDecoder.kt:22-40` **已经遍历 `scanner.process()` 返回的整个列表**（注释写着「多码图取全部」） | **零改动** |
| APP 实时流（相机模式） | `CameraScanner.kt:121` 只取 `codes.firstOrNull()?.rawValue` | **改成遍历列表**（约 1 行） |
| 帧收集器 | `QrFrame.Collector` 本来就按 `idx` 去重（`QrFrame.kt:50/67`） | **零改动**——同一个码在一屏里被解到多次也只是覆盖同一个 slot |
| B 端 | 目前每码落一张 PNG（`_frames_dir`），前端按 `STREAM_FRAME_MS=333` 轮播（`index.html:1039-1052`） | 按 r×c 拼一张合成图（分辨率 = 屏幕分辨率），轮播逻辑不动 |
| ML Kit | `setBarcodeFormats(FORMAT_QR_CODE)`，`process()` 返回 `List<Barcode>`，官方支持一帧多码 | **零改动** |

**向后兼容是免费的**：老版本 APP 只会解出一屏里的某一个码，而每 333 ms 整屏都会换新码，
所以它仍以原有速率推进（不会卡住、不会出错），只是拿不到提速。可以做成分档开关。

#### 6.3.5 叠加后的整体效果（6.5 MB 图文 PDF）

现行数据由**插件自身的函数**实测得出（`_chunk_data` + `_fec_encode`，v40，相机模式每码 5 帧）：

| 阶段 | 码数 | 画面数 | 时长 |
| --- | --- | --- | --- |
| 现状（视频流） | 6885 | 6885 | **38.2 分钟** |
| + 二进制直载 + 去二重 base64 + LZMA2 | 1590 | 1590 | 8.8 分钟 |
| + **1×2 v40**（每模块 4 px，最稳） | 1590 | 795 | **4.4 分钟** |
| + **2×3 v32**（每模块 3 px，推荐平衡点） | 2410 | 402 | **2.2 分钟** |
| + 3×5 v19（每模块 3 px，15 码/帧） | 5998 | 400 | 2.2 分钟 |

> 注意第 4、5 行的**码数反而变多**（1590 → 2410 / 5998）：多码同屏要把版本降下来才够像素，
> 单码载荷变小了。但**画面数与时长才是用户感知的成本**——这正是 6.3.1 要区分两件事的原因。
> 3×5 与 2×3 时长相同却要多检测 2.5 倍的码，**没有理由选它**。

#### 6.3.6 业界参考实现

- `infrost/RaptorQR`（MIT，TS/WASM）：README 实测「V20 ×4 码并行 @30fps → 最高 300 codes/s，
  95.2 KB 用时 375 ms ≈ 254 KB/s」，与本节的量级一致（它每模块像素更充裕，因为解码在 WASM 本地做）。
- `UR-SillyB/AirFerry`（MIT，Rust+Kotlin）：与你们架构最接近——**同帧 4 码 + RaptorQ 喷泉码 +
  60 B 帧头 + symbol 1400 B + 最小版本 EC-L QR（1464 B 帧 → V27 125²）**，
  压缩层「Raw / Zstd Lv1 / Xz Lv9 三算法选优」。它的帧头只有 60 B 且**不套 base64**，
  可作为 §7.1 二进制帧设计的直接参照。
- `sz3/libcimbar`（MPL-2.0，6.4k★）：彩色码做到 106 KB/s，但解码端要 OpenCV + 彩色校准，成本高，不采纳。

#### 6.3.7 实时流路径的前置条件：分析分辨率（重要）

APP 的 `ImageAnalysis.Builder()`（`CameraScanner.kt:95`）**没有设置分辨率**，
于是使用 CameraX 的默认值 **640×480**（Android 官方文档原文：
"The default target resolution setting is 640x480"）。全 App 只有这一处 `ImageAnalysis.Builder()`，
没有任何 `setTargetResolution` / `ResolutionSelector`。

这决定了**两条路径的像素预算完全不同**，也是多码同屏能不能落地的分水岭：

| 路径 | 画面像素来源 | 显示器可用有效像素 | 多码同屏增益 |
| --- | --- | --- | --- |
| 静态（拍照解析） | `ImageDecoder` 按 `maxDim=2048` 载入（`ImageDecoder.kt:22`） | ~1632×918 | **2.2~4.0×** |
| 实时流（相机采集） | CameraX 默认 640×480，且未设置 | ~640×360 | **1.5~1.6×** |

在 640×360 的有效像素下，1×2 也只能用到 v20（每码 861 B）——
**实时流的多码同屏几乎不划算，除非先把分析分辨率提上去**。

这同时解释了另一件一直没被说明的事：**前端默认二维码版本是 15**（`index.html:462`）。
v15 只要 85 像素宽（77 模块 + 8 静区），在 480 px 高的分析画面里有 5.6 px/模块，很稳；
而 v40 的 185 模块在同样条件下只剩 2.6 px/模块——**正好落在 6.3.2 实测的"不可靠区"**。
默认 15 不是保守，是被分析分辨率锁死的。

**结论**：实时流要做多码同屏，前置动作是给 `ImageAnalysis.Builder()` 加
`.setTargetResolution(Size(1280, 720))` 或更高（CameraX 会取最接近的支持值）；
代价是 ML Kit 每帧处理时间上升，必须与 333 ms 停留窗口一起实测。
若暂时不动分辨率，**多码同屏应只做静态（拍照）路径**——那条路 APP 端本来就零改动。

#### 6.3.8 风险与前置验证

1. **手机端算力**：一帧解 4~6 码的耗时约为单码的 2~4 倍。必须实测「多码/帧的处理时间 < 333 ms 停留窗口」，
   否则提速会被手机吞掉。若吃紧，把停留时间从 333 ms 加到 500 ms，仍有 2~2.7× 净收益。
2. **视野与对焦**：一屏多个码要同时落在手机视野内（拍得远 → 每码更小），四角容易失焦/反光。
   建议把码阵集中在画面中央区域、外边距留够，而不是铺满整屏。
3. **屏幕像素的实际生效值**：若用户把浏览器缩放到 80%、或显示器不是 1080p，
   B 端按屏幕分辨率算出的布局会失准。生成时应读取实际屏幕像素，
   并引导用户**把显示器拍满画面**（提高占比 = 提高每模块像素，最省事的提速手段）。
4. **本节的实测是仿真**（缩放 + 模糊 + JPEG + 旋转 + 透视），不是真机拍摄：
   真机还有摩尔纹、卷帘快门、自动对焦延迟。**上线前必须用目标手机 + 目标显示器做一次真机验证**，
   建议验收口径：连续 200 屏，全部码解出的屏数 ≥ 95%。

## 7 推荐方案

### 7.1 阶段一：协议瘦身（无新依赖，纯代码改动）

| 改动 | 位置 | 收益 |
| --- | --- | --- |
| 信封 v2：二进制帧（`magic/ver/flags/页号/总数/长度` + 原始字节），不再 base64/JSON | `build_envelope` / `_build_static_pages` / `encode_to_video` | 每码载荷 2160 B → 2940 B（**−26%** 码数） |
| 视频路径去掉二重 base64（信封本体二进制化） | `routes.py:1350/1389` | 视频 **−45%**（967 → 1764 B/帧） |
| APP 收帧判据 `have >= n` → `have >= k` | `QrFrame.kt:76` | 视频 **−40%** |
| 信封增加 CRC32 + 原始长度 + `mode` 字段 | `parse_envelope` | 补齐 `HANDOFF.md:618` 的首要待办 |
| 版本兼容 | 新帧用独立前缀（如 `0x4A 0x5A 0x32`「JZ2」）；旧码仍按 `{` 开头解析 | 双端向后兼容 |

### 7.2 阶段二：压缩器与格式预处理（新依赖：B 端 `lzma`（内置），A 端 `org.tukaani:xz`）

| 格式 | 处理 | 收益 | 模式 |
| --- | --- | --- | --- |
| 文本 / md / CSV / Office 精简 | `zlib-9` → **LZMA2（16 MB 字典）** | −14%~−86%（载荷越长收益越大） | exact |
| `.docx` / `.xlsx` / `.zip` | **拆包重组 + LZMA2** | −75% / −49% / −27% | rebuild |
| `.png` | **WebP 无损**（照片型可选有损，需授权） | −83% / −36% | rebuild（像素等价） |
| `.pdf` | **LZMA2 直压**（+ 可选 pikepdf 重打包） | −20pp | exact（+rebuild 可选） |
| `.jpg` | 先直压；packJPG 放 P3 | 0% → −16% | exact |
| 通用判据 | 压缩后不小于原大小则保持原样（`_pack_data` 已有此逻辑，保留） | — | — |

**实现备注**：B 端用 Python 内置 `lzma`（`FORMAT_XZ` 或 `FORMAT_RAW` + `FILTER_LZMA2`），
A 端用 `org.tukaani:xz` 的 `XZInputStream`（raw 流用 `RawInputStream`，需两端约定 filter chain 与字典大小）；
**整份文件只压一次**，xz 容器那 60 字节开销可以忽略，
所以**建议直接用 xz 容器格式**，省掉 raw 流的参数协商——只有载荷小到几百字节时才值得换 raw。

### 7.3 需要产品决策的一点：字节精确性

现行 README 承诺原件传输「文件名与字节与原文档一致」。以下变换**做不到字节一致**：

| 变换 | 可保证 | 建议 |
| --- | --- | --- |
| LZMA2 / zstd / brotli / packJPG | **字节一致** | 默认开启，无提示 |
| Office/ZIP 拆包重组 | 内容等价（Office 打开无差异，哈希不同） | `mode=rebuild`，UI 标注「重建」 |
| PNG → WebP 无损 | 像素一致（哈希不同） | `mode=rebuild`，UI 标注 |
| PNG/JPEG 有损重编码 | 画质损失 | **必须用户逐次确认**，默认关闭 |

信封里的 `mode` 字段让接收端显示「还原方式」，也便于将来自查。

### 7.4 阶段三（可选）

- JPEG 无损：brunsli / packJPG（需 NDK，收益 16%~22%）；
- 多码同屏 r×c（静态路径吞吐 ×2.2~4.0，**改动最小的一项**：静态模式 APP 零改动、流式模式改 1 行，详见 §6.3）；
- FEC 换喷泉码（wirehair/RaptorQ），把 40% 冗余彻底降为 0~2%。

## 8 排除清单与理由

| 方案 | 实测/官方收益 | 排除理由 |
| --- | --- | --- |
| **cmix / paq8px / zpaq** | 比 xz 小 28%~45%（LTCB） | 解码需 14~31 GB 内存、数小时~数天；无 Android 实现 |
| **bsc / lrzip** | 比 xz 小 14%~19% | 无任何 Java/Android 实现，必须 NDK，收益不匹配 |
| **PPMd（7-Zip）** | 文本比 LZMA2 小 0~2pp；zip 重组小 16% | 无纯 Java 实现（commons-compress 无 PPMd）；解码慢 27× |
| **bzip2** | 全部落后 | 无一项胜出 |
| **precomp 全套** | silesia.zip 99.7%→69.7% | CLI + 许可混杂（内嵌 LGPL packJPG）；A 端要移植整条位精确重建链 |
| **preflate-rs** | 重建开销仅 0.01%~1.5% | 唯一「可移植的位精确 deflate 重建」，但收益本质是 zopfli 级（≈4%），对容器重组路线是重复建设。**备用**（若坚持字节一致） |
| **lepton** | 官方 22% | 已归档 + README 自述无力修复漏洞 + 无 Android 端口 |
| **zstd + 字典** | 小文件 −68% | 小文件本来就装得下，收益只在页边界；引入字典分发与版本对齐复杂度 |
| **MuPDF / Ghostscript** | — | AGPL-3.0 传染 + 体积；只可作 B 端工具 |
| **PNG → JPEG** | — | 实测截图转 JPEG q90 **膨胀到 338.9%** |
| **一体化瘦身 CLI**（pdfsizeopt / Leanify / ECT / image_optim / FileOptimizer） | 各类 3%~30% | 全是 PC 端编排器，A 端没有对应实现；只可借其思路，不能整体照搬 |

## 9 风险与验收建议

1. **端到端字节验收（最高优先级）**：现行链路无任何哈希校验。建议在信封里加
   `crc32 + orig_len`，APP/网页端还原后校验；把「B 端文件 → 二维码 → 手机还原」的
   SHA-256 一致性做成回归用例（对应 `HANDOFF.md:618`）。
2. **二进制直载要单独验收**：ML Kit `rawBytes` 与 jsQR `binaryData` 都要实测；
   建议先用「随机 1 KB 二进制」跑通再上真实格式。
3. **高版本二维码的解码余量**：实测 v40-L 满容量在 OpenCV 下不稳定（§5.3）。
   引入二进制直载后每码承载更多字节，若继续用 v40 会逼近解码器极限，
   建议**把「每码载荷」控制在容量的 85%~90%**（留出与现行 JSON 壳相当的余量），
   并让生成端自检升级为「回读内容逐字节比对」而不是「能读出即可」。
4. **有损变换必须显式授权**：照片 PNG（3.9 MB → 415 KB）收益最大，
   但画质损失不可逆，UI 要写清楚「压缩后画质下降」并默认关闭。
5. **上传上限**：现行 20 MB 上限。6.5 MB PDF 在方案下仍需 ~1600 帧，
   建议按「预计码数/时长」给出提示，超阈值时引导用户改用多码同屏（§6.3）或分卷传输。
6. **许可**：xz-java 0BSD、brotli MIT、WebP 平台 API、packJPG LGPL（仅当启用 P3 时注意动态链接合规）。
