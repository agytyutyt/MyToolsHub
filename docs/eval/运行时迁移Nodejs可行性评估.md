## 0. 速览

- **结论：不建议迁移。** 唯一确定性收益是框架自身启动耗时；阻塞点不在运行时语言，而在插件契约。
- **决定性论据**：插件交付的是 WSGI 应用（`register(app)` / `bp`），契约在三处加载点重复出现。保留契约 → Node 侧要么复刻 WSGI 派发语义、要么每插件旁挂 Python host，**两种都等于没换**。
- **最诱人的收益（多语言）不需要迁移即可获得**：现有插件协议已是语言中立。

## 1. 评估边界

- **仅框架层**。现有插件只作为"契约形态"的观察样例，不纳入评估、不计迁移成本。
- 假设的迁移形态：运行时层与能力层迁 Node.js，Python 保留为插件实现语言的一种依赖。

## 2. 维度一：技术可行性

**结论：需要调整的抽象层覆盖运行时、核心层（依赖管理大部失效）、能力层（进程运行/插件调用）；核心层进程管理反而可移植。**

### 2.1 逐层影响

| 抽象层 | 迁移影响 | 依据 |
| --- | --- | --- |
| 运行时·依赖运行 | 全部重写 | Python 特有：`sys.path` 注入、Windows DLL 目录装载（`jz_plugin_host.py` 的 `setup_dep_components`）、`.pyd`/wheel 装载 |
| 核心层·依赖管理 | 大部分失效 | `jz_deps.evaluate` 三态判定建立在 `importlib.import_module` 实测之上（`jz_deps.py` 的 `probe_module`）；venv/wheel 机制（`supervisor/venv_mgr.py`）整条不适用 |
| 核心层·上下文管理 | 思想可保留、代码重写 | 数据根解析、原子写、模板同步均为纯文件操作，可移植 |
| 核心层·进程管理 | **大部分可移植** | `supervisor/supervisor_core.py` 是标准库 + 子进程 + 系统调用，**与语言无关** |
| 能力层·进程运行 | 可移植 | 进程间 JSON 协议与 HTTP 反代都是语言中立的 |
| 能力层·插件调用 | **唯一真正的阻塞点** | 见 §2.2 |

### 2.2 阻塞性问题（决定性）

插件交付物是 **WSGI 应用**，通过 `register(app)` 或 `bp` 暴露。三处同款加载点：

| 加载点 | 形态 |
| --- | --- |
| `jz_worker.py` 的 `run_worker` | 服务端 worker |
| `client/plugin_host.py` 的 `build_app` | 桌面端 worker |
| `jz_host/plugin_loader.py` 的 `_load_plugin_routes` | 进程内注册 |

Node 侧要接住，只有三条路：

1. **复刻 mini-WSGI 派发语义** → 需在 Node 中实现 environ 构造与测试客户端派发的等价物，**等于把 Flask 重写一遍**；
2. **每个 Python 插件旁挂 Python host 进程** → 插件仍是 Python，Node 只多一层代理，**收益归零**；
3. **全量改写插件** → 超出框架层范围，且违背"插件开发模型两端一致"的现有契约。

**次级阻塞**：依赖组件机制深度绑定 CPython。共享槽内是原生扩展 + 其配套 DLL（同装同卸），靠 Windows DLL 目录 API 装载。Node 侧要么改用 N-API 重编（该类库无稳定 N-API 构建），要么整条链保留——**保留即迁移不彻底**。

## 3. 维度二：插件热插拔能力

**结论：不会更好，部分形态略差。**

现状已达三级热插拔：进程内形态用子应用派发（绕开框架级"首请求后不可注册蓝图"限制，天然规避模块缓存问题）、子进程形态支持常驻与空闲收割、混合类升级走能力层秒级重启（会话镜像持久化免重登）。

| 形态 | 现状 | 迁移后 | 对比 |
| --- | --- | --- | --- |
| 前端包装载 | 静态伺服，装新版即生效 | 同 | 持平 |
| 进程内插件 | 子应用派发 = 字典操作 | 模块缓存需手动失效后重新求值 | **略差**：无框架级缓存失效保证 |
| 子进程插件 | 常驻复用 + 空闲收割 + 超时即杀 | 同样可做 | 持平 |
| 混合类升级 | 能力层秒级重启 | 同 | 持平 |

**关键点**：Python 侧热插拔的隐性优势是"重启进程即干净"。迁 Node 后若追求极致热插拔会倾向用线程或模块热替换，而**线程方案与隔离目标冲突**（见 §5）。

## 4. 维度三：整体性能

**结论：启动确定变快；内存恶化；跨语言调用成本新增；业务侧冷启动一分不省。**

| 指标 | 现状 | 迁移后 | 判断 |
| --- | --- | --- | --- |
| 框架启动 | Python + 框架导入（量级见运行架构设计文档"venv 不改善 import 冷启动"条） | Node 冷启通常更快 | **确定性改善**，收益真实 |
| worker 冷启动 | 内嵌解释器 + 插件导入（同一量级） | 若插件仍 Python 则**不变** | **取决于插件语言**，非框架收益 |
| 吞吐量 | 业务在 Python 内 | 混合；转发层更优 | 小幅改善，主要在转发层 |
| 内存占用 | 单运行时 | **双份**（Node 运行时 + 内嵌 Python） | **恶化**；桌面端已有 WebView2 进程，再加一份对低配机不友好 |
| 跨语言调用开销 | 无 | 每次往返增序列化与编解码；若走 FFI 还需处理解释器 GIL 与对象生命周期 | **新增成本**，进程间 JSON 往返为毫秒量级 |

**注意**：启动改善只发生在**框架自身**。插件执行仍在 Python，故用户感知的首屏时间 = 框架启动 + 插件首调，收益被摊薄。

## 5. 维度四：崩溃隔离

**结论：不会更强；特定选型下更弱。**

现状隔离边界（已核实）：

```
supervisor（作业对象，kill-on-close）
├─ 主应用进程
└─ worker 进程 × N     ← 真进程边界：原生崩溃/OOM 不连坐
     └─ 插件代码
```

外加三重纵深：进程边界 → 统一 errorhandler（插件异常 → 该插件降级响应，其余照常，见 `supervisor/mainapp_bridge.py` 的 `install_worker_proxy`）→ supervisor 熔断下线（双计数器，见 `supervisor/supervisor_core.py` 的 `_monitor_loop`）。

| Node 侧隔离机制 | 强度 | 对比现状 |
| --- | --- | --- |
| 子进程 | 与现状同级 | **持平** |
| 工作线程 | **弱**：共享内存，原生崩溃/OOM 污染宿主 | **倒退** |
| VM 上下文 | 弱：非安全沙箱 | 倒退 |
| WASM | 强 | 需重编译全部插件，超出范围 |

**结论**：迁移不提供更强的隔离模型。要保持现有强度就必须继续用子进程，则迁移对隔离的贡献为零。若误以为线程方案可替代进程边界，则是**净倒退**。

## 6. 维度五：多语言插件支持

**结论：现有契约已支持，无需迁移。这是本方案收益与成本倒挂最关键的一点。**

核查发现当前插件协议**已是语言中立**：

- 桌面端：进程间 JSON 行协议（请求含方法/路径/头/体，响应含状态/头/体）；
- 服务端：HTTP 反代 + 公开健康探针路径；
- manifest：`runtime` + `kind` + `entry` 已是**声明式**结构。

即一个非 Python 插件**今天就能接入**，只需三步：

1. manifest 增加 `language` 字段（现有 `kind` 只区分承载方式、不区分语言）；
2. 一层薄适配（对端换成该语言的进程内服务，实现同一协议）；
3. 依赖三态判定对该语言走"外部程序组件"分支（`jz_deps._probe_external` 已有此路径）。

| 维度 | 评估 |
| --- | --- |
| 扩展成本 | **小**（一个适配层 + 一个字段） |
| 接口约定 | 现有 manifest + 进程间协议已够，只需扩字段 |
| 运行时依赖治理 | **不变差**：Python 侧仍走三态声明，新语言走外部组件探测 |

**多语言支持是"加一个字段 + 一层适配"的问题，不是"换运行时"的问题。**

## 7. 维度六：总体收益与代价

| 维度 | 代价 | 收益 | 净判断 |
| --- | --- | --- | --- |
| 工程复杂度 | 框架层重写（依赖管理全部作废）、双运行时分发、两套打包描述 | — | **负** |
| 运维与排障 | **三语言栈**（Node + Python + 前端）；一次故障可能跨两层；日志与审计链需重做；现有各套台架全部失效需重写 | 启动快 | **明显负** |
| 依赖管理 | 现有共享槽 + venv/wheel 机制须保留（插件仍 Python），同时新增 Node 侧包管理 | — | **负** |
| 安全与供应链 | 双运行时扩大攻击面；Node 生态传递依赖数量大；**内网离线环境需额外做镜像与审计** | 可用成熟 npm 生态 | **负**（离线内网场景尤甚） |
| 多语言 | — | 已有协议可达成 | **不必迁移即可获得** |
| 崩溃隔离 | — | 无变化 | **持平或倒退** |
| 启动性能 | — | 快（量级见 §4） | **正，但收益面窄** |

## 8. 结论与推荐路径

### 8.1 结论性判断

**不建议迁移。** 唯一确定性收益是框架启动耗时，而代价是全量框架层重写、双运行时运维、三语言栈排障、依赖治理复杂度翻倍；且主要收益（多语言）可在不迁移的前提下取得。

**重新评估的触发条件**（须同时成立）：① 启动耗时已成为实测瓶颈；② 未来插件以 JS/TS 为主。届时插件契约本身也要改，现在推进会构成二次返工。

### 8.2 若确有多语言诉求（推荐路径，按投入递增）

| 序 | 动作 | 成本 | 解决什么 |
| --- | --- | --- | --- |
| 1 | 补齐已存在的空转架构：建注册表让 A 类真迁 worker | 低（代码与台架就绪） | 隔离能力落地（另见 `eval/分层架构契合度审计.md` S1） |
| 2 | manifest 加 `language` 字段 + 一层薄适配 | 低 | **多语言支持**，不动运行时 |
| 3 | 补桌面端熔断闭环 | 中 | 崩溃自愈（审计 D1） |
| 4 | 依赖版本槽（若触发条件成立） | 中（设计稿已就绪） | 依赖版本共存（审计 D2） |

### 8.3 风险与适用边界

| 项 | 说明 |
| --- | --- |
| 评估范围 | 仅框架层。现有插件作为契约形态样例，未计迁移成本 |
| 唯一可迁移形态 | 以"进程间服务"形态交付的插件。任何依赖 `register(app)` 的插件在迁移后都需重写或旁挂 Python host |
| 结论有效期 | 依赖"插件契约保持 WSGI"这一前提。若未来契约改为语言中立服务形态，本评估需重做——但那时也意味着**迁移的必要性已下降**（协议已中立） |
| 未量化项 | 启动耗时与内存的具体数值需实测；本文只给方向与量级判断，不复述易漂移数值（口径见 `docs/README.md` §3.1） |
