## 一、总体定位

本平台为插件驱动的工具平台，分为桌面端与服务器端。桌面端面向用户，提供插件加载、运行、管理、更新与 UI 承载能力；服务器端面向插件后端包，提供上线、下架、调度、运行、鉴权、配置与可观测性能力。

架构必须满足以下约束：

1. **最小内核稳定**：壳层、IPC、权限、配置、日志、更新、插件注册、环境管理属于最小内核，不可作为普通插件被随意卸载。
2. **除最小内核外，一切皆插件**：主界面、后台管理、插件管理、插件市场等可作为核心插件，但必须随壳层启动，代码受控。
3. **每插件独立进程或服务**：桌面端每插件一个子进程，服务端每插件一个独立服务或容器，防止单插件崩溃影响全局。
4. **依赖隔离优先**：禁止将多版本依赖动态挂载到共享 Python 运行时。默认按依赖指纹复用 venv，共享只读环境，不共享运行时可变的模块状态。
5. **supervisor 职责收敛**：supervisor 只负责进程启停、健康检查、崩溃重启、日志采集和生命周期状态机，不承担上下文存储、鉴权、配置中心等职责。
6. **控制面与数据面分离**：服务端控制面负责注册、调度、配置、鉴权、审计；数据面负责插件后端实例运行。
7. **低内存目标机可运行**：在 8GB 内存目标机上，通过按需启动、空闲回收、并发上限、重依赖服务化等策略，保证平台稳定运行。
8. **插件契约先行**：所有插件必须通过 Manifest 声明元数据、依赖、权限、入口、API 版本、资源需求和健康检查。
9. **平滑演进**：轻量方案（环境池 + 子进程）可平滑迁移到容器/K8s，环境指纹对应 runtime 镜像，子进程对应 Pod。

## 二、桌面端架构

桌面端分为壳层、核心层、能力层、运行时。

### 1. 壳层

壳层是桌面端主体，负责窗口、WebView、系统托盘、文件系统访问、更新器等系统集成。壳层不直接执行插件业务逻辑，只承载核心层与能力层。

### 2. 核心层

核心层是桌面端运行核心，必须拆分为以下模块，而不是全部塞进 supervisor：

- **进程管理器**：负责插件子进程的启动、停止、健康检查、崩溃重启、指数退避、熔断和告警。
- **环境池管理器**：负责依赖指纹计算、venv 创建与复用、引用计数、LRU 回收、只读保护、缓存管理。启动插件时使用对应环境的 Python 解释器，并清理 `PYTHONPATH`。
- **消息总线/IPC**：桌面端建议使用 JSON-RPC over stdio 或本地 Unix Socket；禁止插件直接操作主 GUI 对象。
- **上下文服务**：传递 `request_id`、`user_id`、`tenant_id`、`token`、`config_ref`、`trace_id`。大对象走共享内存或文件，不塞进消息体。
- **鉴权与权限**：核心层统一鉴权，向插件注入受限 token，插件不持有主凭证。
- **配置中心**：管理插件配置 schema、实例配置和热更新。
- **插件注册中心**：管理插件 Manifest、版本、API 兼容范围、前端包和后端包。
- **日志与指标**：结构化日志、指标采集、审计事件，日志必须带 `plugin_id`、`instance_id`、`request_id`。

### 3. 能力层

能力层是插件主要运行区域。主界面、后台管理、插件管理、插件市场、依赖升降级部署等均以插件形式实现，但插件管理、更新器、权限管理等应作为核心插件。普通插件通过核心层提供的 API 访问平台能力，不得越权访问系统资源。

### 4. 运行时

运行时为依赖运行层。默认采用 **环境池 + 子进程** 模式：

- 按依赖指纹创建并复用 venv，多个插件共享同一只读环境。
- 每插件独立子进程，使用对应环境的解释器启动。
- 插件默认不常驻，按需启动，空闲回收。
- 重依赖（torch、CUDA、大型数据栈）服务化，避免每个插件重复加载。
- 提供低内存模式，限制并发插件数，动态降级。

## 三、服务器端架构

服务器端分为核心层/控制面、能力层/数据面、运行时。

### 1. 核心层/控制面

服务端核心层负责插件后端包的上线、下架、调度、配置、鉴权、审计和生命周期管理。生产环境建议：

- **单机开发模式**：systemd 模板单元或 supervisord，配合环境池。
- **生产集群模式**：每个插件后端包打成容器，使用 K8s Deployment/Operator 管理。
- **控制面**：负责注册、版本、路由、配置、权限、灰度、回滚和日志聚合。
- **数据面**：负责插件实例运行，按插件 ID 和版本路由请求。

### 2. 能力层/数据面

能力层为后端插件运行层。插件后端包独立部署，独立数据库 schema 或独立 DB，迁移由插件负责但必须版本化。前端包不部署到后端，走 CDN 或静态资源服务。

### 3. 运行时

运行时为依赖运行层，与桌面端一致。生产环境优先容器化，venv 仅用于开发或单机模式。依赖锁、SBOM、镜像签名必须纳入 CI/CD。

## 四、依赖管理与环境池

### 1. 总体模型

采用“**基础运行时只读 + 环境池按指纹复用 + 插件子进程隔离**”三层结构：

1. **基础运行时层**：系统只装一个 Python，只读，不含插件依赖。
2. **环境池层**：按依赖指纹创建并复用 venv，多个插件共享同一环境。
3. **插件进程层**：每插件一个子进程，使用共享环境的解释器，进程间隔离。

共享的是：

- 同一指纹的 venv 和 site-packages（只读使用）。
- wheel/pip/uv 缓存，硬链接复用。
- 基础 Python 标准库。

不共享的是：

- 运行中的 Python 进程和模块状态。
- 插件私有配置、数据、连接。
- 可写目录。

### 2. 依赖指纹

```text
fingerprint = hash(
  python_version +
  platform +
  abi_tag +
  sorted(requirements.lock) +
  critical_system_libs
)
```

要求：

- 插件必须提交 `requirements.lock`，锁定精确版本。
- 平台解析依赖时，按指纹归组。
- 相同指纹的插件复用同一个 venv。

### 3. 环境池结构

```text
runtime/
  base/                  # 系统 Python，只读
  envs/
    py311-linux-x86_64-abc123/   # 指纹 A 的 venv
    py311-linux-x86_64-def456/   # 指纹 B 的 venv
  cache/
    uv/                  # 硬链接缓存
    wheels/              # 离线 wheel 仓库
  refs/
    abc123.json          # 环境引用计数与插件列表
```

环境状态：

- `active`：至少一个插件在用。
- `idle`：无插件使用，保留以便快速复用。
- `evictable`：超过 LRU 阈值，可删除。

### 4. 创建与复用

- 优先用 `uv venv` + `uv pip install`，安装时硬链接到全局缓存。
- 相同文件在多环境中共享 inode，磁盘不重复。
- 环境创建后设为只读，插件不得写入 site-packages。
- 插件若需写，写入自己的用户数据目录，不写环境。

### 5. 引用计数与回收

- 插件安装时 `refs +1`，卸载时 `refs -1`。
- `refs=0` 进入 LRU，低内存时优先回收。
- 回收只删 venv，不删 wheel 缓存和基础运行时。

### 6. 可共享与不可共享边界

**可共享**：

- wheel 缓存、pip/uv 缓存
- 只读基础镜像层或基础运行时
- 通过硬链接或写时复制共享的依赖文件
- 完全一致、纯 Python、无全局状态、无 C 扩展的只读基础库
- 平台级稳定 API

**不可共享**：

- 可变的 site-packages
- 同一 Python 进程内的第三方模块状态
- 多版本 C 扩展
- 插件私有依赖
- 会被 monkey patch 的库
- 生命周期和插件绑定的依赖

## 五、低内存目标机专项方案（8GB）

8GB 内存下，真正的瓶颈是**同时运行的插件进程数**，而不是 venv 数量。

### 1. 按需启动 + 空闲回收

- 插件默认不常驻。
- 用户打开插件 UI 或调用其 API 时才启动。
- 空闲超过阈值（如 5–10 分钟）自动退出。
- 退出后保留环境，下次启动秒开。

### 2. 限制并发插件数

- 设置 `max_concurrent_plugins`，例如 6–8。
- 超出时排队或拒绝启动，给用户明确提示。
- 后台任务型插件走队列，不与 UI 插件争内存。

### 3. 重依赖服务化

如果多个插件依赖 torch、pandas、CUDA 等重库：

- 不要每个插件进程都导入一份。
- 起一个**共享服务进程**，加载重库，插件通过 IPC/gRPC 调用。
- 服务进程按需启动，空闲回收。
- 插件只装轻量客户端库。

### 4. 延迟导入

- 插件入口只做最小初始化。
- 重库在使用时才 `import`。
- 平台提供 `lazy_import` 工具和规范。

### 5. 内存监控与降级

- 用 psutil 监控总内存和每插件 RSS。
- 超过阈值时按 LRU 回收空闲插件。
- 提供“低内存模式”：只允许轻量插件，禁用重依赖插件。

### 6. 基础只读共享库

- 把纯 Python、无 C 扩展、无全局状态的基础库预装到基础运行时。
- 插件 venv 用 `--system-site-packages` 叠加，减少重复安装。
- C 扩展和易冲突库仍走插件环境，不放进基础层。

### 7. 8GB 预算参考

| 项目               | 估算                        |
| ------------------ | --------------------------- |
| 操作系统           | 1.5–2.5 GB                  |
| 壳层 + 核心层      | 200–400 MB                  |
| supervisor + 监控  | 50–100 MB                   |
| 每个中等插件进程   | 60–150 MB                   |
| 每个重依赖插件进程 | 200 MB–1 GB                 |
| 同时活跃插件建议   | 6–8 个中等，或 2–3 个重依赖 |

策略：活跃插件总数受限；重依赖走共享服务；空闲插件及时回收；低内存模式动态降级。

## 六、插件契约与通信

每个插件必须提供 Manifest，至少包含：`id`、`name`、`version`、`apiVersion`、`entry`、`runtime`、`requirements.lock`、`fingerprint`、权限声明、前端包、后端包、配置 schema、健康检查、资源需求、重启策略、签名、`lazyImports`、`memoryHint`。

核心 API 需版本协商，插件声明兼容范围，不兼容拒绝加载。

通信协议：桌面端用 JSON-RPC over stdio/本地 Socket；服务端用 HTTP/gRPC + 消息队列。上下文传引用不传大对象。

---

## 七、生命周期与治理

插件生命周期：安装 → 校验签名/哈希 → 创建或复用环境 → 注册 → 启动 → 健康检查 → 就绪 → 运行 → 崩溃重启退避 → 熔断 → 下架 → 停止 → 卸载/保留数据。

资源限制：桌面端用 psutil 监控，服务端用 cgroup/K8s resources 限制 CPU、内存、进程数、句柄和网络。

可观测性采用结构化日志、指标、追踪、审计，推荐 OpenTelemetry。

安全：插件签名、哈希校验、SBOM、权限最小化、审计。不可信插件必须容器/WASM/gVisor 隔离。

---

## 八、安全与资源限制

容器不是虚拟机，共享内核，所以不可信插件仍需 gVisor/Kata/Firecracker。基础加固：

- 非 root 用户运行。
- 只读根文件系统，必要时 `tmpfs`。
- 删除所有 capabilities。
- `no-new-privileges`。
- seccomp、AppArmor/SELinux。
- NetworkPolicy 限制出入站。
- Secret 挂载，不写环境变量明文。
- 镜像签名 cosign、SBOM、漏洞扫描。
- 资源 requests/limits、临时存储限制、GPU 配额。

轻量方案下，子进程同样需要：

- 独立用户或低权限账户。
- 工作目录隔离。
- 环境变量清理。
- 文件系统访问白名单。
- IPC 鉴权与超时。

---

## 九、演进路径

1. **轻量单机阶段**：环境池 + 子进程 + 按需启动 + 空闲回收 + 重依赖服务化。
2. **服务端单机阶段**：环境池 + systemd 模板单元。
3. **生产集群阶段**：容器/K8s + Operator，环境指纹对应 runtime 镜像，子进程对应 Pod。
4. **强隔离阶段**：不可信插件使用 gVisor/Kata/WASM。

环境池方案与容器方案不冲突：环境指纹可复用为镜像标签，插件 Manifest 可同时声明 `runtime.type=venv|container`，平台按目标机能力选择。

## 十、给开发者的技术细化清单

开发者需输出：

1. 插件 Manifest JSON Schema，含 `runtime.type`、`requirements.lock`、`fingerprint`、`lazyImports`、`memoryHint`。
2. IPC IDL 与错误码、超时、重试、上下文透传。
3. 权限模型、受限 token、审计事件。
4. 环境指纹算法、环境池管理器、引用计数、LRU 回收、只读保护。
5. uv/硬链接缓存集成，Windows/macOS 兼容方案。
6. 进程/容器生命周期状态机，崩溃重启退避、熔断、健康检查。
7. 按需启动与空闲回收策略，含超时、LRU、并发上限。
8. 重依赖服务化设计：服务发现、IPC、生命周期。
9. 低内存模式：阈值、降级规则、用户提示。
10. 内存监控与告警：总内存、每插件 RSS、回收触发。
11. 基础只读共享库白名单与准入规则。
12. 存储 schema、数据库隔离、迁移、备份、卷生命周期。
13. 安全基线：非 root、只读、cap-drop、seccomp、NetworkPolicy、镜像签名。
14. 可观测性：结构化日志、Prometheus、OpenTelemetry、审计。
15. 测试：多插件共享环境、冲突指纹、低内存压力、回收正确性、崩溃恢复、版本兼容、灰度回滚。
16. CI/CD：镜像构建、签名、SBOM、灰度、回滚、插件契约测试。

## 十一、结论

本平台采用“**最小内核 + 插件化 + 环境池 + 子进程隔离 + 按需启动 + 重依赖服务化**”的总体架构。桌面端默认轻量方案，服务端单机可用环境池 + systemd，生产集群可平滑迁移到容器/K8s。该架构既满足多插件依赖复用，又能在 8GB 内存目标机上稳定运行，同时保留向容器化和强隔离演进的能力。

开发者可基于本文进行接口、存储、部署、安全和测试层面的技术细化。
