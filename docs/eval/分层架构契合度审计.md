## 0. 判定基线

| 端 | 层次（自上而下） | 合法依赖方向 |
| --- | --- | --- |
| 服务端 | 核心层 → 能力层 → 运行时 | 上层可依赖下层；**下层不得反向 import 上层**；同层只经显式接口（provider / 注册表 / 门面）协作；插件只能依赖「稳定契约面」 |
| 桌面端 | 交互层 → 核心层 → 能力层 → 运行时 | 同上；且**交互层不得越过核心层直连能力层/运行时** |

**四档判定**：符合（职责与依赖方向都干净）/ 基本符合（职责对，边界靠约定而非结构）/ 偏差（职责错位或越界依赖）/ 严重偏差（反向依赖、跨层直取运行时内部）。

**两条纪律项**：**N1 静态可验证性**（层级边界能否由目录 + import 规则静态检出，而非注释声明）；**N2 单一真源**（同一职责是否在单一模块实现）。

## 1. 结论速览

**判定：职责分层基本符合，但存在实质越界依赖与巨型汇聚点**（既非"完全符合"，也非纯"基本符合"）。

- **骨架对、实现质量不低**：服务端进程管理（作业对象 + 双计数器熔断 + 同端口回滚）、依赖三态判定与版本门控、worker 零决策进程运行；桌面端子进程隔离执行与交互层边界，都是干净实现。
- **插件侧纪律尤其好**：服务端插件与桌面端本地插件均未反向 import 端内部模块，只依赖 `jz_api`/`jz_deps`/`jz_relay` 契约面。
- **偏差集中在"边界维持手段"**：层级靠注释与模块头纪律声明，而非目录与 import 规则强制 → 出现实质越界（插件→运行时、能力层→运行时内部、门面→核心内部）与一个巨型汇聚点。
- **没有空壳层**：四层职责两端均有真实实现。问题不是"没做"，而是"做在了错误的位置 / 被上层顺手代劳"。
- **最紧迫项不是设计偏差，而是实施进度**：服务端 E 架构代码齐全但从未被真实流量走过（S-10）。

## 2. 两端共同强项（值得保持）

| 强项 | 说明 |
| --- | --- |
| 同源内核双包 | 内核四件套两端共用；客户端 spec 只带内核不带业务插件 |
| 端口分配一次持久化 | 分配即写回注册表；冲突报错不起不换号；占用探测用 connect 而非 bind（避开 TIME_WAIT 误报） |
| 熔断双计数器 | 探针连败 + 快速崩溃连击，任一达阈值即下线——单一计数器对"路由触发型毒插件"永远到不了阈值 |
| 依赖组件免重启 | 暂存 + 启动时应用 + 请求期刷新标记，装完刷新页面即用 |
| 数据根注入对插件零感知 | 两端同款口径（现读即时生效 + worker 启动时显式注入） |
| 失败隔离不拖垮全局 | 单插件加载失败被隔离记录，统一兜底把插件异常转 503、其余照常 |

## 3. 服务端

### 3.1 层 → 模块映射

| 路径 | 归属层级 | 判断依据 |
| --- | --- | --- |
| `app.py` | 装配外壳（设计外，等价宿主入口） | 只做实例装配、CLI 分派、启动编排 |
| `jz_deps.py` | 核心层 · 依赖管理 | 依赖判定唯一入口：三态结论 + 版本门控 + 请求期标记重算 |
| `jz_host/dep_bootstrap.py` | 核心层 · 依赖管理 | 启动期依赖组件三连（应用暂存 → 注入 → 注册重扫回调） |
| `jz_plugin_host.py` | 核心层·依赖管理 **与** 能力层·插件调用（双职责，见 S-6） | 组件注入/状态 vs 后端动态加载 |
| `jztools_data.py` | 核心层 · 上下文管理 | 数据根解析/迁移、原子写、模板同步、待重启标记 |
| `jz_api.py` | 稳定契约门面（设计未单列） | provider 注册表：会话/操作标签/组织架构/用户 LLM/壳密钥 |
| `jz_host/access_log.py` | 核心层 · 上下文管理 | 请求上下文（客户端 IP / 操作标签 / 当前用户）、访问日志、gzip、安全头 |
| `jz_host/shell_gate.py` | 核心层 · 上下文管理 | 壳身份门：接入密钥生命周期（单一写方）+ 请求级准入 |
| `jz_host/plugin_loader.py` | 能力层 · 插件调用 | 注册表/manifest 扫描、版本依赖门控、进程内装配 |
| `jz_host/llm_routes.py` | 能力层 · 插件调用（框架能力路由） | 挂载 `/api/llm/*`，本身不实现推理 |
| `supervisor/supervisor_core.py` | 核心层 · 进程管理 | 受管单元容器：拉起/健康探针/熔断/重启/日志；作业对象孤儿收割 |
| `supervisor/apply_chain.py` | 核心层 · 进程管理（升级编排） | 备份 → 落盘 → 健康检查 → 回滚 |
| `supervisor/control_api.py` | 核心层 · 进程管理（控制面） | 控制接口：apply/rollback/clear-circuit/restart |
| `supervisor/venv_mgr.py` | 运行时 · 依赖运行 | venv 建环境 + wheel 离线闭包安装 + 幂等 marker |
| `supervisor/mainapp_bridge.py` | 能力层 · 插件调用，**却落在 supervisor 包内**（见 S-4） | 主应用侧反代桥（import flask/requests） |
| `jz_worker.py` | 能力层 · 进程运行 | 一插件一进程：Flask 实例 + provider 注入 + `register(app)` + waitress |
| `runtime/pylibs`、`runtime/libreoffice`、`runtime/chrome`、数据根 `venvs/<id>` | 运行时 · 依赖运行 | 共享组件包、外部程序组件（由依赖探测函数判定） |
| `jz_host/tray.py` | 交互层实现，**却落在核心层包内**（见 S-9） | 托盘图标 + 气泡通知 |
| `static/` | 交互层，物理位置在框架目录 | 首页/工具壳页等 UI |
| `plugins/<id>/backend/routes.py` | 业务侧（插件） | 经 `register(app)` 契约被能力层装配 |

### 3.2 逐层剖析

**核心层**

| 职责 | 关键类 / 接口 | 判定 | 问题 |
| --- | --- | --- | --- |
| 进程管理 | `Supervisor`（进程表/熔断表/应用抑制集）、`JobObject.assign()`、`ensure_unit_port()`、`apply_chain.apply_package()`/`rollback_unit()`、`control_api.make_handler()` | **符合** | 主应用自身生命周期不在本层：由外部服务管理器与安装脚本兜底，应用只提供自重启助手——**属刻意设计**（管理进程必须比受管对象更"不倒"） |
| 依赖管理 | `jz_deps.evaluate()`/`evaluate_all()`、`read_version_json()`、`apply_pending_components()`、`register_component_rescanner()` | **符合** | 严守"仅标准库、不 import 插件"纪律；唯一毛刺是 `install_refresher(app, ...)` 接收应用对象（隐式耦合 Web 框架，非 import 依赖） |
| 上下文管理 | `get_data_root()`/`migrate_legacy_app_data()`/`sync_templates()`、`jz_api.register_providers()`/`get_session_user()`、`access_log.parse_operation()`、`shell_gate.install()` | **基本符合** | ① 上下文分散四个模块，无统一入口（S-8）；② 门面反向依赖核心内部（S-3）；③ 数据根模块物理在仓库根，与 `jz_host/` 分裂，归属靠约定识别 |

**能力层**

| 职责 | 关键类 / 接口 | 判定 | 问题 |
| --- | --- | --- | --- |
| 插件调用 | `register_plugin_backends()`、`_register_tool_plugin()`、`_load_plugin_routes()`、`_gate_state_of()`、`install_worker_proxy()`/`_proxy_to_worker()` | **基本符合** | ① 进程内加载与 worker 反代两套并存，切换靠"注册表里有无单元"隐式判定 → **能力层必须读运行时层的注册表**（S-2）；② 失败隔离与三态门控实现完整 |
| 进程运行 | `run_worker()`、回环客户端（取会话/组织树）、`/_worker/health` 探针 | **符合** | worker 不做端口/路径决策（全由 supervisor 经环境变量注入），边界干净；鉴权权威留主应用，回环失败即降级（fail-closed） |

**运行时**

| 职责 | 关键类 / 接口 | 判定 | 问题 |
| --- | --- | --- | --- |
| 依赖运行 | `venv_mgr.ensure_venv()`/`discard_venv()`、外部组件探测 | **基本符合** | ① 无独立运行时目录，按路径约定散在 `runtime/`、数据根 `venvs/`、安装脚本三处；② venv 形态仅源码态可用（冻结态无 site-packages），属已知限制 |

### 3.3 依赖方向

```
app.py（装配外壳）
  ├─→ jz_host.{dep_bootstrap, plugin_loader, access_log, shell_gate, llm_routes, tray}
  ├─→ jz_api / jz_deps / jztools_data / jz_plugin_host
  ├─→ jz_worker（--worker CLI 分派）
  └─→ supervisor.mainapp_bridge（装配期接线）              ★ 方向合法

jz_host.plugin_loader ──→ jz_deps、jz_plugin_host
                       ──→ supervisor.mainapp_bridge        ★ 核心层 → 运行时侧件（S-2）
jz_api ──→ jz_host.shell_gate（懒 import）                  ★ 门面 → 核心内部（S-3）
插件 backend/routes ──→ jz_api / jz_deps / jz_llm / jztools_data（合法）
plugins/admin/backend/store_admin ──→ supervisor.{mainapp_bridge, apply_chain}
                                                              ★ 业务插件 → 进程管理/运行时（S-1，最严重）
supervisor.{supervisor_core, apply_chain, venv_mgr, control_api} ──→ 仅标准库（纪律达标）
supervisor.mainapp_bridge ──→ flask / requests / jztools_data ★ 与同包纪律冲突（S-4）
static/*.html ──→ /plugin/admin/...                          ★ 交互层 → 具体插件（S-5）
```

### 3.4 服务端偏差

| 编号 | 严重度 | 类型 | 证据与说明 |
| --- | --- | --- | --- |
| S-1 | **高** | **越界依赖** | `plugins/admin/backend/store_admin.py` 三处 `from supervisor...`（取控制端点、worker 快照、venv 节点校验、发布即部署）。业务插件硬 import 进程管理层，把部署形态（是否 worker 化、端口/令牌）泄漏进插件；supervisor 缺包时该路径直接失败 |

| `client/plugin_source.py` | 能力层 · 插件调用（源） | 服务器商店源 / 共享盘源抽象 |
| `client/plugin_host.py` | 运行时 · 依赖运行（进程内宿主） | 独立解释器进程加载插件后端，stdio 行协议 |
| `client-plugins/` | 业务侧（本地插件） | 客户端工件 |
| 内核四件套（仓库根） | 共享核心层（两端共用） | 客户端经 `sys.path` 与打包 `kernel/` 两种形态消费（见 D-7） |

### 4.2 逐层剖析

**交互层**

| 职责 | 关键类 / 接口 | 判定 | 问题 |
| --- | --- | --- | --- |
| UI 交互 | `run_shell()`、`ShellBridge`、`GeometryStore`、`_tray_image()` | **基本符合** | 依赖方向干净（UI → `client_config` 核心层），业务逻辑不入本层；问题在框架静态页绑定具体插件（D-4） |

**核心层**

| 职责 | 关键类 / 接口 | 判定 | 问题 |
| --- | --- | --- | --- |
| 进程管理 | `main()`、`handle_stop()`、`await_prev_instance()`、`acquire_or_exit()`；`PluginExecutor._spawn/_roundtrip/_reap_idle` | **偏差** | ① worker 进程管理（执行器）落在能力层 → 能力层直接掌握运行时路径、进程生死与 kill（D-10）；② `PluginExecutor.shutdown()` **全仓无调用点**，退出走 `os._exit(0)`，常驻 worker 靠 OS 回收（D-3）；③ **无健康探针、无崩溃自动拉起、无熔断**（D-9） |
| 依赖管理 | `install_local_zip()`、`install_component_zip()`、`installed_components()`；能力层内的商店 preflight/install/uninstall 端点 | **偏差** | 依赖装卸的**编排逻辑不在核心层**，而在能力层 HTTP 装配文件内（2026-10-15 实测约 700 行量级）；编排直接读写运行时目录布局（D-2） |
| 上下文管理 | `load_client_config()`、`resolve_address()`、`runtime_python_exe()`；`SessionMirror.update_from_set_cookie()`、`secure_store.protect/unprotect`；账号上下文却在能力层内 | **偏差** | "账号/数据根上下文"这一核心职责被写进能力层（约 300 行，2026-10-15 实测），核心层只剩配置与会话镜像两个碎片（D-1） |

**能力层**

| 职责 | 关键类 / 接口 | 判定 | 问题 |
| --- | --- | --- | --- |
| 插件调用 | `create_capability_app()`、`api_tools_merged()`、`forward()`、`local_plugin_api()`、`scan_local_plugins()`、`JzRelay.request()` | **严重偏差（职责体量）** | `capability_app.py` 单文件约 2200 行（2026-10-15 实测），模块头自述"业务逻辑禁入本层"，实际内含账号上下文、插件装卸、客户端重启、商店安装、依赖装卸、运行时文件清理 → 核心层与运行时职责大量泄入能力层 |
| 进程运行 | `plugin_host.build_app/dispatch/emit/main`、`PluginExecutor._spawn` | **基本符合** | 一插件一进程 + 行协议，隔离性达成；与服务端 `jz_worker.py` 是两套并行实现（HTTP vs stdio），无共享抽象 |

**运行时**

| 职责 | 关键类 / 接口 | 判定 | 问题 |
| --- | --- | --- | --- |
| 依赖运行 | `runtime_python_exe()`、`host_script_path()`、`webview2_runtime_dir()` | **基本符合** | 运行时按路径约定外置；但"谁有权知道这些路径"无约束——能力层也在拼同一批路径（D-2） |

### 4.3 依赖方向

```
client_main（组合根）
  ├─→ client_config、single_instance（核心，合法）
  ├─→ plugin_executor（进程管理，但物理在能力层）
  ├─→ capability_app（能力）
  └─→ shell_window（交互；由组合根装配，未反向依赖，OK）

shell_window（交互）──→ client_config（核心）                方向合法
capability_app（能力）──→ client_config、session_mirror（核心） 方向合法
capability_app（能力）──→ pkg_install、plugin_source            合法但职责混淆
capability_app（能力）──→ runtime/pylibs 直接读写               ★ 能力层 → 运行时内部（D-2）
capability_app（能力）──→ 实现账号上下文/插件装卸/自身重启        ★ 能力层吞噬核心层（D-1）
plugin_executor（能力位置）──→ 拉起运行时解释器 + plugin_host    方向合法
plugin_host（运行时）──→ jz_plugin_host（共享核心）             上层无关，OK
本地插件 ──→ jz_api / jz_deps / jz_relay（契约面）             干净，无反向 import
static/index.html ──→ /plugin/admin/...                        ★ 交互层 → 具体插件（D-4）
```

**值得肯定**：本地插件侧纪律良好——只依赖契约面，未发现反向 import 能力层/执行器/配置模块。

### 4.4 桌面端偏差

| 编号 | 严重度 | 类型 | 证据与说明 |
| --- | --- | --- | --- |
| D-1 | **高** | 职责错位 + 汇聚点 | `client/capability_app.py`：账号上下文、插件装卸、依赖编排、商店安装、自身重启等核心层与运行时职责全在该文件内。无物理包边界 → **无法静态检出（N1 不达标）** |
| D-2 | **高** | **越界依赖：能力层 → 运行时内部** | 能力层内直接拼 `runtime/pylibs`、暂存目录、待删目录并改写组件清单登记。正确方向应由核心层依赖服务暴露 install/remove/status，能力层只调接口 |
| D-3 | 中 | 生命周期缺口 | `PluginExecutor.shutdown()`（收割全部常驻 worker）无调用点；退出路径为 `icon.stop()` + `os._exit(0)`。声明的清理契约未接线 |
| D-4 | 中 | 层级间耦合 | 框架静态页引 `/plugin/admin/...`；侧边栏硬编码 `/tool/store` |
| D-5 | 中 | 硬编码插件身份 | 能力层 `_builtin_ids = {"store","admin"}`；更新源抽象直连商店私有端点。与"一切皆插件"声明相悖 |
| D-6 | 中低 | 边界不可静态校验 | 组合根 `sys.path.insert(0, 仓库根)`；能力层 `_sys.modules["jz_relay"] = relay`（把对象伪装成模块注入）。为兼容源码态/打包态绕开包边界 |
| D-7 | 中 | 客户端不自包含 | 客户端 spec 从仓库根复制静态资源与内核四件套 → 桌面端核心层的一半物理上不在 `client/` 内；共享内核无源码目录（`kernel/` 只存在于产物中） |
| D-8 | 中 | 缺失层次 | **桌面端无 supervisor 等价物**：核心层无健康探针、无崩溃自动拉起、无熔断。毒插件可无限崩溃-重启循环，无自愈上限；与服务端（已有 supervisor + 熔断）**不对称** |
| D-9 | 低 | 空壳/占位 | 无真正业务占位（仅 3 处形式性 `pass`，均为有意设计）；但能力层模块头仍写"本地插件 API（本批次占位）"而实现已存在 → **过期注释** |
| D-10 | 中 | 目录归属错位 | `client/plugin_executor.py` 语义属核心层·进程管理，物理在能力层且由能力层直接引用 |
| D-11 | 中 | 职责错位 | 依赖装卸编排（能力层内）+ 运行时目录知识（能力层内）双错位，见 D-2 |
| D-12 | 中 | 能力缺口 | 依赖版本槽（O1）解析模块 `client/dep_slots.py` 不存在 → 依赖版本冲突只能灰显、无法共存。设计稿已就绪（`docs/design/桌面端依赖版本槽-设计文档.md`，自标未实施） |
| D-13 | 中 | 职责错位 | 账号上下文状态机写在能力层路由文件内，直接改数据根环境变量并触发子应用重挂 → 层级耦合 |

> **【2026-10-16 现状旁注 · 修法见 §7 A6】** D-3 经需求方拍板 **补立卡**（不是「明确不做」）：
> 把 `PluginExecutor.shutdown()` 接进退出路径，修法即本文 §7 的 **A6**（托盘退出回调 + 回收常驻 worker）。
> 已登记进 `docs/plan/20261011全仓未完成事项汇总-TODO.md` §1.1（代码级）。
>
> **落地前须知（本次核实现场代码所得）**：① 现有退出路径是 `icon.stop()` + **`os._exit(0)`**，
> `os._exit` 会跳过 `finally`，故 A6 说的「组合根 finally 段兜底」**须先改造退出路径**（改显式清理后再退出），
> 否则 finally 永不执行；② 正常关窗**不漏进程**——常驻 worker 是 stdio 子进程，父进程退出即 stdin EOF、
> worker 自杀；缺口只在两处：**(a)** 在途长任务不即时收割（台架 `tools/e2e/t13-thread-discipline.py` B2 正在演练此场景，生产未接线）；**(b)** `--stop` 的 `taskkill /PID … /F` **无 `/T`**，卡死 worker 会成孤儿。
> ③ 全仓唯一调用者就是该台架 —— 即"台架在替生产演练一个生产没实现的动作"。
>
> 其余 23 条偏差（S-1…S-12 / D-1…D-13 除 D-3、S-10）**暂不裁定，列入下一个版本的工作**（2026-10-16 需求方裁定）；S-10 已立项，见 §3.4 表后旁注。
