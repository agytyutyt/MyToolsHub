## 0. 结论速览

1. **三层拓扑（2026-10-03 拍板）**：**UI 层** = pywebview 窗口（WebView2 渲染，主线程）；**能力层** = 本地服务（后台线程）——项目主界面、插件、request 交互都在这里；**运行时** = 内置 Python（PyInstaller onedir + `runtime/pylibs` 组件包机制）。业务权威（类 A 插件、鉴权、数据）仍在远程服务器。
2. **三类插件模型（2026-10-03 拍板；离线语义 2026-10-04 明确）**：类 A 服务器插件（逻辑在服务器，桌面端只渲染，**离线不可用**）；类 B 本地插件（本地界面+本地逻辑，**离线完全可用**）；**类 C 混合插件**——本意=**部分简单逻辑无需服务器进行，本地化运算，完成后交由服务器端进行复杂操作、敏感操作**（本地界面+基础业务逻辑+服务器数据交互，经会话中继门面，以用户会话取数，权限与浏览器路径一致；**离线降级可用**：本地简单运算照常，服务器复杂/敏感步骤降级）。
3. **能力层与主包同构**（决定迁移成本的关键推论）：能力层 = 宿主内核（托管/中继/注册表，不含业务逻辑）+ 已装本地插件（进程内 `register(app)` 注册，与现有插件开发模型完全一致）；类 C 插件迁移≈一轮机械的挂载前缀适配。
4. **选型推荐**：pywebview + WebView2（UI 层已由需求拍板；实测壳+渲染 202 MB，能力层增量见 §8）。Electron 的 dsh 形态（Node 壳管理本地服务）与三层拓扑同构性上升，但磁盘/工具链代价不变（§4.2）。
5. **内置 Node.js 运行时不引入**：运行时层已拍板为内嵌 Python；Node 四作用的论证保留存档（§3.3）。
6. **需求 6 判定**：窗口级拖放/改大小/改比例由 UI 层 + 弹性 iframe 基本满足；页面级连续缩放不满足（仅 600px 一档断点、无 resize 监听、无面板分栏），需流式布局改造（§5）。
7. **P0 待验证**：PyInstaller×pywebview 打包、WebView2 缺失兜底、OS 文件拖放、会话中继正确性（§9）。

## 1. 需求映射与三类插件模型

### 1.1 需求映射（2026-10-03 三轮需求合并口径）

| # | 需求 | 本方案落点 |
| --- | --- | --- |
| 1 | 支持托盘化 | 托盘挂能力层进程（pystray，复用 `app.py:1204` 口径）；关窗不退出 |
| 2 | 运行占用不太大 | 渲染底噪 126–131 MB 是公共成本；能力层承载框架+已装插件，业务重活在服务器/worker（§8 预算） |
| 3 | 服务端在远程（三轮演进后的口径） | **业务权威在远程**：类 A 插件、鉴权、数据、统一大模型配置；客户端能力层承载本地界面与本地基础逻辑（类 B/C），不持数据权威 |
| 4 | 客户端=前台展示与数据交互 | UI 层渲染；类 A 只渲染、类 B/C 本地逻辑；数据交互分「服务器数据（中继）」与「本地数据（直接）」两路 |
| 5 | 减少插件开发/迁移成本，沿用 HTML 前端 | 能力层与主包插件模型同构（`register(app)` + frontend 直出）；主界面静态资源原样复用 |
| 6 | 可拖放、改变比例、大小 | UI 层最小尺寸 + 几何记忆；页面侧流式改造（§5） |
| 7 | 调用本地封装打包的 Python 功能包 | 类 B worker（stdio-json 子进程）+ 类 C 进程内注册（§6.4） |
| 8 | 参照 DeepSeek-Harness 四层架构 | 三层拓扑为其「壳+WebUI→后端服务→内置运行时」的换型映射；分层模式采纳、内涵替换（§3.2） |

### 1.2 三类插件模型（本方案的中枢概念）

| | 类 A：服务器插件（现状 16 个） | 类 B：本地插件 | 类 C：混合插件（新增） |
| --- | --- | --- | --- |
| UI 来源 | 远程直出（经能力层中继） | 本地直出 | 本地直出 |
| 业务逻辑位置 | 服务器进程内 | 本地（stdio worker 或纯前端） | **本地（能力层进程内注册）** |
| 服务器数据 | 天然（逻辑就在服务器） | 无 | **有**：经 `jz_relay` 门面，附用户会话 |
| 离线可用 | ✗ 不可用 | ✓ 完全可用 | **✓ 降级可用**（本地简单运算照常；交由服务器的复杂/敏感操作离线时降级，恢复后续作） |
| 安装/升级 | 服务器插件包链路（admin/共享盘） | 客户端本地装包（GD7） | 同类 B |
| 典型场景 | trajectory-sketch、file-filter、知识库 | 表格批处理、脱敏/加解密（敏感数据不出机） | 「服务器台账 + 本地报表加工」类工具 |

**类 C 本意（2026-10-04 需求方明确；2026-10-05 需求⑨扩展）**：类 C 存在的理由是**部分简单逻辑无需服务器进行**——本地化运算，完成后**交由服务器端进行复杂操作、敏感操作**（如需密钥/审计/数据权威的步骤）。由此三类的离线语义定为：**类 A 离线不可用、类 B 离线完全可用、类 C 离线降级可用**。落地含义：①`jz_relay` 白名单需支持"操作提交"型 POST 规则——随服务器侧处理端点真实提供时增补（维持"不加新面"口径：有面才加）；②降级 UX=类 C 页面明示"服务器步骤暂不可用，本地部分可继续"。**需求⑨（批次 8 已落地）：类 C 归入 server 类、双包形态**——客户端工件=现行 hybrid 包（前端+本地逻辑，`local-` 前缀），服务器工件=同 id 去 `local-` 前缀的 API 型后端包（承载复杂/敏感操作，发布即部署）；本地部分经 `jz_relay.own(<自身id>)` 调用自身插件的服务器端点（附用户会话；其他插件端点仍禁），契约见商店设计文档 §3.5.1 与 `服务端插件运行架构-设计文档.md`。

**边界铁律（v3）**：① 业务逻辑只存在于**插件包**（进程内注册包或 worker）；**宿主内核**（托管、中继、注册表、配置）不含业务逻辑——解耦设计文档 §3 判据在客户机复用；② **跨类禁调用**：服务器与本地两类互不可达（网络边界天然保证「服务器→本地」方向）；类 C 仅经 `jz_relay` 触达**框架级 API 与数据接口**，不触达其他插件端点（铁律跨端延续）；③ **数据权威在远程**：类 C 以用户会话取数（无越权、与浏览器路径同权限），不持久化服务器业务数据；类 B 不上传用户数据；④ 类 C 需要大模型时经中继调用服务器侧统一大模型，**Key 不落本机**。

## 3. 需求 8 评估：DeepSeek-Harness 四层架构

### 3.1 参照对象是什么（2026-10-03 公开资料核对）

DeepSeek Harness 是 DeepSeek 开源的 harness 架构（cordis「一切皆插件」）。其官方桌面端（`apps/desktop`）：**Electron 壳**承载 dsh Web UI，Electron 与 `@deepseek-ai/dsh` 版本精确锁定；**自带 Node.js 运行时 + Harness 运行时 + 全部依赖**（目标机无 Node/npm 可用）；直接启动官方本地 Web UI、不维护独立前端分支；定位本地优先（上游 dsh 本身就是跑在本机的 Node 服务）。第三方同构样本 `anywhere-labs/dsh-desktop`（Electron 44 + electron-builder 26，主进程自动拉起并管理本地 Harness 服务）。

### 3.2 四层映射：模式采纳，内涵替换

| 参照架构（dsh） | 本方案（三层拓扑） | 判定 |
| --- | --- | --- |
| 壳（Electron 窗口/托盘/更新） | **UI 层**：pywebview 窗口（渲染+窗口管理）；托盘挂能力层进程 | ✅ 模式照用（2026-10-03 已拍板 pywebview） |
| Web UI（由本地后端服务提供页面） | 由**能力层**混合供给：主界面与类 B/C 本地直出，类 A 经中继取自远程 | ⚠ 单源→混合双源 |
| 后端服务（本地业务服务） | **能力层**：宿主内核（托管/中继/注册表）+ 已装类 B/C 插件；业务权威仍在远程 | ⚠ 内核薄、插件承载业务、权威外置 |
| 内置 Node.js 运行时 | **运行时**：内嵌 Python（已拍板）+ pylibs 组件包 | ✅ 换型定案（Node 不引入，§3.3） |

与参照架构的本质差异一句话：**dsh 是「本地优先」（业务服务就在本机），本方案是「权威外置」（业务权威在远程服务器）+「本地承载」（界面与基础逻辑在能力层）**——这正是需求 3「服务端在远程」与类 C「本地逻辑+服务器数据」的合成。

### 3.3 存档：内置 Node.js 运行时为何不引入

内置运行时的本质是「壳自带的、版本受控的第三方代码执行环境」。Node.js 运行时在参照架构中的四个作用逐条对照：① 上游服务运行时——本项目业务权威在远程且是 Python ❌；② 扩展宿主（VS Code Extension Host 式）——本地插件代码是 Python，运行时应为 Python（类 C 进程内注册 / 类 B worker）❌；③ npm/MCP 生态桥——无此需求 ❌；④ 进程编排粘合——pywebview 路线编排由 Python 自带，Electron 路线主进程已覆盖 ❌。性能对照上 Node 赢依赖加载与纯 JS 计算，Python 赢常驻内存/磁盘/数据负载（numpy/pandas/cv2 的 C 扩展赛道），GIL 差异在子进程隔离模型下不构成因素。**翻案条件**：出现 npm/MCP/JS 插件市场真实需求时重评（届时 Electron 顺位上调）。

### 3.4 值得从参照架构吸收的四点

① 固定上游、不改上游（客户端与主包代码同源不分叉，GD8）；② 桌面作为可探测的附加层接入（`window.jzShell` 桥 + `html.jz-shell` 结构类）；③ 生命周期清理与安全恢复单独设计验证（worker 收割、会话失效恢复，RP5/RP7）；④ 页面只有一份、壳不注入页面（只注入桥与结构类）。

## 4. 技术路线对比与评估

### 4.1 三族分类（渲染内核从哪来）

| 族 | 内核来源 | 成员 | 族级特征 |
| --- | --- | --- | --- |
| Ⅰ 复用系统浏览器 | 已装 Chrome/Edge（app 模式） | A | 体积 0；无托盘/几何/本地能力 |
| Ⅱ 复用系统 WebView | WebView2（常青） | B pywebview / E Tauri / F C# 宿主 | 增量几 MB；能力完整；族内选谁只看宿主语言 |
| Ⅲ 自带内核 | 随包 Chromium | C Qt WebEngine / D Electron | 磁盘 +150–368 MB；引擎版本钉死、更新自负 |

### 4.2 六路线评述（对比轴：三层拓扑的挂法）

| 路线 | 优点 | 代价/风险 | 能力层挂法 |
| --- | --- | --- | --- |
| **A. 浏览器 app 模式** | 零体积零工具链，当天可用 | ❌无托盘；❌无本地执行能力=无类 B/C 插件 | **无法满足**；仅作保底与调试入口 |
| **B. pywebview + WebView2（推荐）** | 与现有栈同语言；**UI 层+能力层+运行时同进程**（webview 主线程 + waitress/托盘后台线程，原型已验证此线程模型）；沿用 PyInstaller 流水线 | 常驻较高档（§8）；PyInstaller×pythonnet 打包摩擦需 spike | **最顺**：能力层就是同进程的 waitress 线程组，插件进程内注册 + spawn worker，零跨进程编排 |
| **C. 原生 C# + WebView2** | 内存/磁盘最低档（实测 149 MB / ≈1 MB）；原型已跑通 | C# 第二语言；**能力层必须是独立 Python 进程**（C# 无法承载 Python 插件）→ 双主管问题（拉起/守护/端口/退出清理/双 spec） | 拧巴：C# UI 层 + Python 能力层进程，两套生命周期 |
| **D. Electron + Node** | 生态最全；Node 写本地服务顺手；**与 dsh 桌面端形态同构**（Node 壳管理本地服务），v3 下同构性上升 | 磁盘 368 MB 解包级；Node/npm 第二工具链；Chromium 更新自负；双产物 | 可行：Node 壳 + Python 能力层 sidecar（dsh-desktop 即此形态），仍是双进程双语言 |
| **E. Tauri 2** | 体积最小；内存同 C 档；sidecar 成熟；跨平台后路 | Rust 工具链税（内网需镜像）；能力层仍须独立 Python 进程 | 可行：Rust UI 层 + Python 能力层 sidecar |

### 4.5 选型结论

**UI 层：pywebview + WebView2（已拍板）；能力层：同进程 Python 本地服务；运行时：内嵌 Python。**
决定性权重：三层拓扑下「UI 层 + 能力层 + 运行时」同语言同进程只有 B/F 两条路（C/D/E 的能力层都必须是独立 Python 进程，双主管问题随三层拓扑加重）；B 相对 F 省掉最重档磁盘/内存。B 的硬前提 RP1（打包 spike）通过；失败降序转 C 或 F。Electron 与 dsh 形态同构是真实优点，但 Node 在本方案没有服务对象（§3.3），且磁盘/工具链代价不变。
**体积复核（2026-10-03，应"体积不理想是否改 Electron"之问）**：Electron 44 实测解包 **368MB**（它自带的就是一整个 Chromium，且是 13x 新内核、只会更大）vs 本路线 fixed-100 内核裁语言包+LZX 后实占 **≈180–250MB**——Electron 体积更大不是更小；若为满足"内核不能太新"而钉旧 Electron 18（Chromium 100 代），等于老框架+老 Node+生态断供，全面劣化。加上内核/程序解耦后更新流量仅 40–60MB/次，**体积不构成改用 Electron 的理由，维持否决**。

## 6. 三层拓扑与三类插件契约

### 6.1 拓扑（2026-10-03 拍板口径）

```
远程服务器（业务权威：类 A 插件、admin/鉴权、数据、统一大模型配置）
   ▲ HTTP（能力层会话中继；REST 无 WS）
   │
桌面客户端进程（单进程，内嵌 Python 运行时）
├─ UI 层：pywebview 窗口（WebView2，主线程）→ http://127.0.0.1:<port>（安全上下文）
├─ 能力层（后台线程组，Flask+waitress）：
│   ├─ 本地直出：主界面 static/、类 B/C 插件 frontend/、兜底页、本地配置页
│   ├─ 插件挂载：类 C/B-light 进程内 register(app)（与主包同构）；类 B-heavy spawn worker
│   ├─ 会话中继：类 A 页面/API 转发远程；登录会话镜像；jz_relay 门面供类 C 取服务器数据
│   └─ 清单合并：/api/tools = 远程清单 ⊕ 本地注册表（local- 前缀命名空间）
├─ 托盘（pystray 后台线程，复用 app.py:1204 口径）
└─ 子进程（按需）：类 B-heavy worker（stdio-json，超时即杀）
```

**路由分区表**（能力层唯一的流量裁决规则，业务逻辑禁入此层）：

| 请求 | 处置 |
| --- | --- |
| `/api/local/<id>/*`、`/plugin/local-*/`、主界面 static、`/local-admin/*` | **本地**：直出静态或派发本地插件（进程内/worker） |
| `/api/tools*` | 中继远程后**合并**本地插件条目（id 冲突拒装并提示） |
| 其余 `/api/*`、类 A 的 `/plugin/<id>/*` | **中继远程**（请求/响应头透传；上传流式透传不全量缓冲） |
| 健康探测/兜底 | 远程不可达：类 A 显兜底页；**类 B 照常、类 C 降级可用**（本地简单运算照常，服务器步骤降级——2026-10-04 语义） |

### 6.2 运行时层

内嵌 Python = PyInstaller onedir 产物（复用主包 spec 模式与 `--check-deps` 语义）+ **子进程运行时目录**（embeddable Python，一次性 15–25 MB，供 plugin_host 派生插件子进程，GD4 已拍板保留执行器）+ `runtime/pylibs` 组件包机制**原样复用**（`app.py:51` 注入口径）。**依赖口径与 HTML 版同构（2026-10-03 收口）**：客户端包只随带项目必要依赖；插件依赖（cv2/zfec 类）由桌面端按需安装「依赖组件包」，插件只作 `requires` 声明，三态判定原样复用；多版本共存已评估并**列为后续优化**（§6.6，暂不实施：版本不符按三态判定提示）。运行时层对上层只暴露两个事实：解释器版本（随包固定）与已装组件清单（`installed-deps.json` 同构）。

### 6.3 会话中继与 `jz_relay` 门面（request 交互的中枢）

- **登录**：登录页经中继 POST 远程；成功后远程 Set-Cookie，能力层**镜像会话**（内存持有，供后端中继与类 C 取数用），浏览器侧 Cookie 照常存于 127.0.0.1 jar；会话过期（admin 滑动续期失效/401）→ 中继返回统一信号，前端引导重新登录。
- **类 C 后端取数**：能力层提供 `jz_relay` 门面（与主体 `jz_api` 依赖倒置层同构的门面模式）：`jz_relay.get/post(框架级路径, ...)` 自动附用户会话；仅放行**框架级 API 与数据接口**，其他插件端点不可达（铁律 ②）。**白名单初版口径（2026-10-03 拍板）**：= 当前 HTML 版插件实际调用的框架级 API 面，从现有前端/后端调用关系**机械提取**（grep 调用点即得清单），不加新面、不删现用面——类 C 拿到的服务器数据访问与 HTML 版现状完全一致，不引入新权限模型。
- **大模型**：类 C 经中继调用服务器侧统一大模型接口，Key 不落本机（复用《统一大模型模块》现有契约）。

### 6.4 三类插件托管矩阵与本地插件包契约

| | 类 A | 类 B-light（纯前端） | 类 B-heavy（worker） | 类 C（进程内注册） |
| --- | --- | --- | --- | --- |
| UI | 远程直出 | 本地直出 | 本地直出 | 本地直出 |
| 逻辑 | 服务器 | 无（前端完成） | **源码包 + 共享运行时子进程**（plugin_host + stdio-json；exe 为例外通道，§6.6） | **能力层进程内 `register(app)`**（与主包插件同构） |
| 服务器数据 | 天然 | 无 | 无（保持类 B 纯净） | `jz_relay` 门面 |
| 隔离 | 服务器侧 | — | 进程级（依赖/崩溃全隔离） | 进程内（依赖冲突由 requires+组件包管，与主包现状同构；崩溃影响能力层） |

```jsonc
// 本地插件 manifest.json（示意，类 C）
{
  "id": "local-report-tool",
  "name": "台账报表（本地）",
  "version": "1.0.0",
  "runtime": "local",
  "kind": "hybrid",                 // local（类B）/ hybrid（类C）
  "entry": {
    "frontend": "index.html",
    "backend": "backend/routes.py", // 类 C：进程内注册；类 B-heavy 改 "backend/__main__.py"+protocol（源码子进程，§6.6）；exe=例外通道
    "mount": "/api/local/report-tool" // 端点挂载前缀，安装时校验无冲突
  },
  "server_data": true,              // 类 C 标记：允许 jz_relay
  "requires": { "python_packages": [ /* 与主包插件同格式 */ ] }
}
```

**迁移成本口径（需求 5 的诚实答案）**：类 C 由现有服务器插件改造时，代码结构不变（frontend + backend `register(app)`），需要一轮**机械适配**——端点统一挂 `/api/local/<id>/` 前缀（前后端各一处常量，保证与服务器端点空间零歧义、也是跨类禁调用的技术保障）+ manifest 增补；主界面与 admin 前端**零改动**。类 B-heavy 按模块包形态新写，复用包校验/安装链。

### 6.5 安全边界

类 B/C 是本架构新增攻击面（本地代码执行 + 服务器数据触达本地）：装包哈希校验 + `local-` 前缀命名空间 + `mount` 冲突检查 + 禁 `shell=True`；类 C 经 `jz_relay` 只能以**用户本人会话**取数（无越权）；`server_data: true` 在安装时明示用户（数据出机提示）；跨类禁调用保证被攻陷的远程服务器无法触达本地插件执行体。

### 6.6 依赖解析与版本槽（**已评估，列为后续优化，暂不实施**——2026-10-03）

> **当前交付口径**：只做共享槽（标准「依赖组件包」模式，与 HTML 版同构）；插件声明的版本与共享槽不符 → 三态判定报「版本不符」灰显提示，**不做版本化槽**。下表为后续优化的设计存档，触发条件见 TODO 清单「后续优化方向」O1；**深化设计稿已另立**：`docs/design/桌面端依赖版本槽-设计文档.md`（2026-10-04，槽布局微调为 `pylibs/.slots/` 以保内核零改动，待拍板）。

| 项 | 口径 |
| --- | --- |
| 物理约束 | Python 单进程内一个顶层包只有一个生效版本——**「多版本共存」的物理形式 = 每进程一份**，故版本槽只对子进程形态（类 B）生效 |
| 槽结构 | `runtime/pylibs/`（共享槽）+ `runtime/pylibs/<name>__<version>/`（版本化槽）并存；同版本多插件去重共用一个槽 |
| 解析顺序 | 插件声明 → 共享槽满足即用（零额外安装）→ 不满足查/装版本化槽 → 仍缺 = 三态「缺」，门控提示 |
| 注入 | plugin_host 按本插件解析结果拼 `sys.path`（版本化槽前置），**只影响该插件子进程**；原生 DLL 跨进程各自加载，无冲突 |
| 求解边界 | **不做深层依赖求解器**（与服务器现状对齐）：只做声明级版本匹配，传递依赖冲突由出包/安装期暴露 |
| 硬边界 | 版本槽要求该版本存在客户端运行时 Python 的 wheel（cp314）：如 numpy 1.26 无 cp314 wheel，旧版需求三选一——插件升版适配 / 客户端基线降档（旋钮，默认不，涉及 GD8 同源内核双基线）/ **exe 例外通道（自带运行时，跨运行时共存的终极形态）** |
| 类 C 冲突处置 | 进程内不能双版本：三态判定报「版本不符」→ 灰显提示，或**一键降格为子进程形态执行**（同源码零迁移，执行器 mini-WSGI 派发承载同一份 register(app) 源码） |

### 6.7 热插拔承诺（GD4 拍板时一并定，2026-10-03）

热插拔分三级，按形态分别成立。执行器统一具备：崩溃检测（退出码/超时）→ 错误回传前端（不炸页面）→ 常驻 worker 自动拉起 → 审计日志（插件 id/时刻/退出码）。

| 级别 | 类 B（子进程/exe） | 类 C（进程内） |
| --- | --- | --- |
| L1 装载即时 | ✅ 注册表加条目即可 | ✅ 运行时 `register(app)` |
| L2 停用/卸载即时 | ✅ 注册表删条目，下次调用自然不可达 | ⚠ 受控路由摘除（`url_map` 私有 API 操作，专项验收） |
| L3 升级即时 | ✅ 按需 spawn 天然新版；常驻 worker 由执行器收割替换 | ❌ 模块级 reload 不可靠（**不做**）→ 能力层秒级重启生效（复用主包 `restart_pending`/`--wait-restart` 口径；**镜像会话持久化以免重登**，并入 T14） |

### 6.8 插件商店适配预留（下一步已立项，2026-10-03；批次 4 落地接缝）

定位：插件商店 = 插件**上架 / 分发 / 下载 / 安装更新**的平台化形态，用于升级 GD7 的 C 通道（共享盘索引 → 商店目录）。**本方案不实现商店**，但批次 4 必须为它预留四个接缝，保证商店上线时客户端零改造切换：

| 接缝 | 批次 4 落地口径（T21） | 商店上线时的切换 |
| --- | --- | --- |
| 索引 schema | 本地插件索引 = 版本化 JSON 文档，字段与商店目录**同构**：id / version / api_version / min_app_version / runtime / sha256 / size / download_url / changelog；读取器抽象为「源」 | 商店 = 新增一种源（HTTP 端点），读取端零改动 |
| 更新源配置 | `plugin_source` 配置项：共享盘文件路径（默认）或 HTTP base URL | 改配置即切商店 |
| 安装动作 | 管理页安装收口为**单一服务入口 `install(pkg_source)`**：本地文件 / 共享盘 / HTTP 三来源同一链路（校验→落盘→注册表→热装载） | 商店下载的包走同一入口 |
| 包格式与类别 | 包格式与 `plugin-packages.json` 同构（manifest+sha256+file_hashes）；索引/目录带 `runtime` 类别中立字段（local/server）——商店未来可同时承载两类插件的分发（服务器插件安装仍走 admin 三分法，商店只做分发） | 商店阶段决策 |

边界：商店的**服务端形态**（部署位置、上架审核流程、账号与权限、与 admin 插件的关系）属商店阶段独立设计——**设计稿已另立并按需求方 2026-10-05 六条需求定稿（v2）**：`docs/design/桌面端插件商店-设计文档.md`（商店=主包第二核心插件、admin 管理面、数据契约解耦）；本方案只承诺客户端侧四个接缝。
**已定稿落地（2026-10-05，批次 8 T-O2-0~10）**：形态=v2 主包核心插件（本文初稿的静态目录型两阶段已废弃）；四接缝全部兑现——①Source 抽象（`client/plugin_source.py`，ServerSource 默认/ShareSource 兜底）②`plugin_source` 配置链（客户端配置免重启切换）③`pkg_install.py` 唯一安装链④catalog schema-2 与 index.json 同构扩展；server 条目边界按需求⑧取代（可安装=前端包，安装权威口径见商店文档 §3.5.1）。

## 7. 分层实现要点

### 7.1 UI 层（pywebview）

`webview.start()` 占主线程；`min_size` 720×560、几何记忆（resize/move 防抖落盘，原型已验证）、关窗=隐藏（会话与本地服务不中断）、导航锁定（仅放行 127.0.0.1）、外部链接转系统浏览器、WebView2 用户数据目录指向客户端自有目录、注入 `window.jzShell`（3 项：`version`/`engine`/`openExternal`）与 `html.jz-shell` 结构类。桥缺失（浏览器路径）时页面行为与现状完全一致。

### 7.2 能力层

waitress（`threads=8` 同主包口径）+ Flask 路由分区（§6.1 表）；本地插件注册表（`%LOCALAPPDATA%\<客户端>\local-plugins\`）；单实例互斥（命名 mutex + 第二实例激活已有窗口，补主包现有空白）；客户端配置（本地插件清单、**远程地址——以配置文件为准（2026-10-03 拍板）**：构建配置给默认 → 安装落地到客户端配置文件 → 运行时读文件，无首启向导，兜底页「改地址」=编辑该文件）存客户端自有目录；健康探测用匿名可达探针（**实测 `GET /login` 可达；`/api/session` 在当前版本 404，2026-10-03 修正，勿用需登录的 `/api/tools`**）。

### 7.3 宿主内核与主包的关系（GD8 已拍板，2026-10-03）

**同源内核、双 spec 出包**：一份内核代码，主包 `JZToolsHub.spec` 与客户端 spec 各自组装；内核变更随主包发版节奏演进，客户端可滞后（兼容面=框架级 HTTP API + 插件 API 版本）。内核边界：Flask 装配、静态路由、插件加载/`register(app)`/冲突防护、`jz_deps`、`_setup_dep_components`、`jz_api` 门面、数据根；**业务插件、admin、数据权威、`jz_llm`、共享盘升级链不进客户端包**。

**三档落地方式（批次 1 T06/T07 的执行口径）**：

1. **独立模块直接 import**：`jz_deps.py`、`jz_api.py`、`jztools_data.py` 原样进客户端 spec，零改动；
2. **`app.py` 机制函数行为保持抽取**：插件加载/register/冲突防护（`app.py:758-764` 一带）抽为共享函数，以「主包全量自检 + smoke 双绿」为红线背书（验收红线 4）；
3. **装配层两端各写**：主包 `main()` 与客户端装配各自实现，端侧差异（会话提供者等）一律走 `jz_api.register_providers` 扩展点，**内核不写死端侧分支**。

日常纪律：内核改动过双端回归（红线 4）；客户端外围模块（中继/会话镜像/`jz_relay`/本地插件注册表/托盘/UI 层）不回灌主包。
