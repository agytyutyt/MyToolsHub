## 0. 一页速览

1. **性能问题的性质**：不是单点慢，而是「加载链路（静态无压缩无缓存 + 多页全量加载）+ 运行时（hybrid 进程内 GIL 阻塞 + worker 冷启动/全缓冲协议）+ 请求路径同步副作用（探针/账号刷新/复评）」三层叠加。
2. **收益排序**：静态与前端加载链路 ＞ worker 协议与懒挂载 ＞ 能力层并发模型 ＞ 壳层。前两项不动架构、风险低。
3. **最值得抄的三个范式**：Tauri 的「壳=渲染、业务=sidecar、自定义协议取代 localhost」；Home Assistant 的「manifest + 按需 setup + Coordinator 合并上游」；VS Code 的「激活事件懒加载 + 启动分段计时」。
4. **不建议现在做**：全栈换 Rust/Go；微前端化；ASGI/WebSocket 化（除非先要推送）；动服务端。
5. **落地顺序**：阶段 0 基线 → 阶段 1 静态/加载（1–2 周）→ 阶段 2 插件运行时 → 阶段 3 能力层并发 → 阶段 4 壳与升级体验 → 阶段 5 可选深化。

## 1. 现状架构盘点（2026-10-13）

```
JZClient.exe（单进程，PyInstaller onedir，GUI 子系统）
├─ 壳（主线程）：pywebview 窗口（WebView2，storage_path 持久 profile）+ pystray 托盘（后台线程）
├─ 能力层（后台线程）：Flask + waitress，127.0.0.1 随机端口，threads=8
│    ├─ 路由六区裁决：本地直出 / 前端包直出 / 清单合并 / 本地插件 API / 中继远程 / 自有接口
│    ├─ 会话镜像（DPAPI 落盘）+ 账号上下文（60s TTL）+ jz_relay 白名单门面
│    └─ 类 C hybrid 子应用（进程内 test_client 派发）
├─ 子进程（按需）：类 B-heavy worker（stdio-json-v1；resident 常驻 + idle_ttl 600s 回收）
└─ 远程服务器（业务权威）：A 类插件 / 鉴权 / 数据 / 商店目录
```

### 2.2 分述

**① Tauri（tauri-apps/tauri）**
架构：Rust 核心（tao 窗口 + WRY 统一 WebView，Windows 即 WebView2）+ 任意 Web 前端；**不起 localhost HTTP**，经自定义协议（`tauri://`）与 IPC 命令向 WebView 供内容；`tauri-plugin` 插件体系；sidecar 外部二进制；官方自更新器。性能策略：不捆绑 Chromium（二进制 MB 级）、复用系统 WebView 更新、细粒度 command IPC + 事件总线。**与本项目关系**：同点=都用系统 WebView2、都有托盘/自更新诉求、都需要本地服务承载业务；差异=壳语言（Rust vs Python）与内容供给方式（自定义协议 vs 本地 HTTP 端口）。**可借鉴**：把「壳」收敛为纯渲染+窗口+托盘+更新，能力层降为 sidecar 子进程；自定义协议可消除本地端口安全面（现有壳自证 Cookie 门正是为补这个面而存在）。迁移成本高，属阶段 4 决策点而非默认路线。

**② Home Assistant（home-assistant/core）**
架构：asyncio 事件循环核心；integration 平台（`manifest.json` + config entries + config flow）；前端独立 Web 应用经 WebSocket/HTTP 通信；HACS 社区商店；Supervisor/Add-on 容器承载重服务。性能策略：**DataUpdateCoordinator**（对上游统一 debounce/throttle、多订阅者合并请求）；集成按平台按需 setup；recorder 异步批量落库。**关系**：同点=Python、目录式插件 + manifest、社区商店、移动端配套 APP；差异=asyncio vs Flask 同步栈、IoT 域。**可借鉴**：a)「manifest + 按需 setup」——本项目 hybrid 目前启动即全量 import，应改首次派发激活；b) Coordinator 合并上游——`/api/tools` 的多消费者与 `refresh_account` 可合并为带 TTL 的单一协调者；c) 商店 catalog 的版本区间解析。Apache-2.0 对内部部署与二次开发均友好。

**③ LocalSend（localsend/localsend）**
架构：Flutter 跨平台客户端；mDNS/DNS-SD 发现 + 设备间**直连 HTTP**，无中心服务器；按能力协商传输协议。**关系**：同点=离线/内网传输场景、跨平台客户端；差异=网络通道 vs 本项目二维码光学通道（后者属插件域，本评估不展开）。**可借鉴**：客户端层「多通道传输」组织（二维码 / LAN 直连可并存，由能力层统一派发）；发现与传输分离（零流量发现）。许可证以仓库 LICENSE 为准（GitHub API 2026-10-13 返回 Apache-2.0）。

**④ Syncthing（syncthing/syncthing）**
架构：事件驱动核心（非轮询）、GUI 与服务可分离、模块分层、SQLite 索引 + 块级传输。性能策略：**配置保存防抖**、扫描批处理 + 退避、事件总线解耦。**关系**：同点=长驻桌面客户端、配置/状态频繁写盘；差异=Go vs Python、P2P 同步 vs 工具集。**可借鉴**：a) 写盘防抖推广到 `session_mirror`（当前每次 Set-Cookie 都加密写盘）与账号快照；b) 事件驱动替代请求路径上的同步副作用。注意 MPL-2.0 文件级 copyleft：拷贝其源码文件需保持该文件开源，本项目独立实现无碍。

**⑤ VS Code（microsoft/vscode）**
架构：Electron 多进程（main / renderer / **Extension Host** / GPU / utility），扩展经 RPC 与扩展宿主通信，webview 独立进程。性能策略：**激活事件（activation events）懒激活**、渲染层虚拟滚动、启动分段计时与遥测、扩展宿主崩溃不连坐。**关系**：同点=桌面外壳 + 插件生态 + 多渲染隔离；差异=Electron（重）vs pywebview（轻）。**可借鉴**：a) 懒激活范式（本项目 hybrid/worker 的"用到才加载"）；b) 启动分段计时（阶段 0 基线直接照做）；c) 渲染进程隔离思路（iframe 已是轻量版）。

**⑥ Grafana（grafana/grafana）**
架构：Go 后端 + React 前端；**后端插件=独立进程，经 gRPC 与主进程通信**（grafana-plugin-sdk-go）；数据源代理与缓存；统一 `/apis` 资源模型。**关系**：同点=插件后端进程隔离、页面懒加载、自托管；差异=Go/TS vs Python。**可借鉴**：a) 「进程隔离」从 B-heavy 推广到 C 类重计算端点（file-filter 的 apply 等）；b) 只读中继热点的缓存代理。**许可注意**：AGPL-3.0-only，改写并分发其代码需开源；本项目仅借鉴架构、独立实现，无冲突；未来产品化对外提供服务需法务评估。

**⑦ JupyterLab（jupyterlab/jupyterlab）**
架构：Lumino 微件框架 + **插件系统（token 依赖注入、声明依赖/可选）**；ServiceManager 统一服务访问；扩展懒激活；虚拟渲染。**关系**：同点=Python 生态里最成熟的「可扩展 Web 工作台」，前端插件化组织方式；差异=计算笔记本域。**可借鉴**：前端从「脚本拼接」演进为「模块 + token 式依赖 + 按需加载」的路径；`ui-profiler` 式的 UI 性能剖析工具化。

**⑧ Node-RED / n8n**
架构：Node-RED 运行时与浏览器编辑器分离，**npm 节点插件**（package.json 声明 nodes）；n8n 社区节点 npm 包 + 声明式描述 + 凭证类型系统。**关系**：同点=插件市场化分发、声明式 manifest；差异=低代码流域。**可借鉴**：a) 「manifest 即包描述 + 语义化版本区间」的插件包契约（现 `_ver_lt` 是数字分段比较，可升级）；b) 编辑器/运行时分离（壳只渲染、能力层只执行）。**许可注意**：n8n 为 fair-code（Sustainable Use License，非 OSI 认可），禁止多租户 SaaS 用途——内部自用无碍，产品化需法务；Node-RED Apache-2.0 友好。

## 4. 重构思路与技术选型

### 4.1 总原则

1. **度量驱动**：没有基线不优化；每阶段设可验收红线（阶段 0）。
2. **分级隔离**：轻路由内嵌（hybrid 保留）、重计算外移（worker 化）、壳与业务分离（进程边界清晰化）。隔离粒度与通信成本成正比，不追求一刀切。
3. **加载链路优先**：静态资源与前端加载是用户可感知面积最大的部分，先改这里，风险最低。
4. **协议流式化**：worker 与中继的长响应走流式/文件路径，淘汰全缓冲 + 8MB 硬顶。
5. **请求路径净化**：任何网络 I/O、重文件扫描都不允许出现在用户请求的同步路径上（后台化 + TTL 合并）。
6. **不改对外契约**：路由分区、端口模型、壳门、`/local-api/*` 全部保持，重构对外无感。

### 4.2 选型对比

| 决策点 | 选项 A（推荐） | 选项 B | 选项 C | 建议 |
| --- | --- | --- | --- | --- |
| 壳 | pywebview 延续（优化） | Tauri 壳 + Python sidecar | Electron | A；除非要移动端同壳或极致体积/安全才 B |
| 静态资源 | Flask 复用 `jz_host/access_log` 中间件 + 构建期打包 | Caddy 单二进制反代（gzip/brotli/缓存/HTTP2） | nginx | 先 A；静态成瓶颈再 B（ install.ps1 要改） |
| 能力层服务器 | waitress（threads 调优） | hypercorn/uvicorn（ASGI，支持流式/SSE） | 保持不动 | 先 A；确有推送需求（B9）再评审 B |
| worker 协议 | 长度前缀帧 + 流式响应 | worker 内嵌迷你 HTTP（127.0.0.1 随机端口）能力层代理解析 | 保持 stdio-json | A（改动小、语义清晰）；要 WS/SSE 再 B |
| hybrid 挂载 | 懒挂载（首次派发构建） | 保持启动全量 | — | A，直接消 B2 |
| 推送 | 轮询（保持） | SSE（需 ASGI） | WS | 阶段 5 再决策，先不动 |
| 插件包版本解析 | 语义化版本区间（借 npm/HA 语义） | 保持数字分段比较（`_ver_lt`） | — | A，随商店下轮迭代 |

## 5. 分阶段实施路径

**阶段 0 — 基线度量（先决，零风险）**
动作：client.log 增加启动分段计时（互斥→配置→执行器→能力层装配→waitress→webview 首帧）；e2e 计时探针（冷启动→首屏可交互、首页加载、工具打开、worker 冷/热 RTT、中继 RTT、常驻内存、waitress 线程峰值）；对抗场景（远程挂起、10MB xlsx 处理中）采样的交互延迟。
验收：产出基线报告与目标值（建议：冷启动 ≤1.5s；热 worker 工具打开 ≤800ms；慢远程下本地页可用；重计算期间其它工具交互延迟 ≤100ms）。红线：所有后续阶段以此对比，无基线不合并。

**阶段 1 — 静态资源与加载链路（低风险，收益最大）**
R1.1 能力层复用 `jz_host/access_log.py` 的 gzip + 静态缓存（该模块依赖 `jz_api`/`plugin_loader`，按同源内核纪律抽公共件或裁剪客户端子集）。
R1.2 构建期资源合并最小化（壳 CSS/JS 归并，保留 `?v=` 版本戳；`/plugin/admin/*` 依赖随前端包直出化解）。
R1.3 `/api/tools` 短 TTL + 本地优先渲染（先出本地条目，远程增量合并）；探活全面后台化（启动即后台预热，导航只读缓存）。
R1.4 工具页进入即异步预热该插件 worker（新增 `/local-api/plugins/<id>/warmup`，前端进 `/tool/<id>` 时触发）。
验收：静态传输量 −60% 以上；二次导航零重传（缓存命中）；工具打开不再含 worker 冷启动（已预热时）。

**阶段 2 — 插件运行时（worker 协议与生命周期）**
R2.1 协议升级：stdio-json 全缓冲 → 长度前缀帧 + 流式响应；大结果走「临时文件传路径」常态化（替代 8MB 502）。
R2.2 hybrid 懒挂载：`_refresh_local_states` 不再启动即 import；改首次派发构建子应用并缓存；卸载/停用仍弹字典（热插拔语义不变）。
R2.3 worker 并发：常驻单锁串行 → worker 内线程池或每插件小实例池（manifest 声明并发度，缺省 1 保持现状）。
R2.4 worker 冷启动减重：`plugin_host.py` 启动路径裁剪（重依赖懒加载纪律核查 + 只 import 必需 WSGI 部分）。
R2.5 审计日志异步化（队列 + 批量 flush，复用 access_log 的 QueueListener 模式）。
验收：热请求 RTT −50% 以上；冷启动 −30% 以上；启动时间与插件数量解耦（加插件不涨启动）。

**阶段 3 — 能力层并发与进程模型**
R3.1 CPU 密集 hybrid 端点外移 worker（file-filter `apply`、trajectory-sketch 渲染优先；manifest kind 已有 hybrid 语义，增 hybrid-worker 变体），或至少线程隔离 + 超时。
R3.2 静态资源服务外置评估（Caddy 或裁剪静态处理器）；能力层只留 API/页面后重校 waitress 线程数。
R3.3 会话镜像与账号同步事件化：Set-Cookie 合并写（debounce ~200ms）；`refresh_account` 改定时器后台刷新，退出请求路径。
R3.4 三态复评改事件触发 + TTL（依赖装卸/安装时 force，平时不扫）。
验收：对抗测试——file-filter 处理 10MB xlsx 期间，首页与其它工具交互延迟 ≤100ms；远程挂起 30s 内本地功能全可用。

**阶段 4 — 壳与升级体验**
R4.1 壳选型决策点（pywebview 延续 vs Tauri 化）：以阶段 0–3 后的残留痛点清单驱动，不预设结论。
R4.2 免重启升级收口：hybrid 走 `_rescan` 重挂（机制已在），把「整进程重启」限定到 DLL 依赖变更场景；壳提供重载而非重启。
R4.3 fixed 内核装载收口（真机清单 R3 遗留）+ 渲染基线重截。
验收：装卸/升级/停用插件 UI 无感（不重启、不掉登录）。

**阶段 5 — 可选深化**：SSE 替换安装/下载/任务轮询（需先过 ASGI 评审）；worker 池内存水位管理；启动链并行化（插件扫描/账号恢复/依赖扫描并行）；多通道传输组织（二维码 + LAN 直连，借 LocalSend 的发现/传输分离）。

## 6. 选型取舍因素

1. **栈延续性 vs 性能天花板**：Python 生态（zfec/cv2/openpyxl/PyInstaller 打包链）与团队技能是沉没资产；启动/内存是真实代价。混合架构（轻壳 + Python sidecar）用最小变更拿大部分收益，全栈重写暂不做。**与同日「Go 重构评估」结论一致**：整体换栈不成立（hybrid 进程内注册 + 同源内核 + worker 运行时全钉死 Python），唯一可行是「换壳」，且壳与能力层需同进程才不双主管——故本文只把壳迁移列为阶段 4 决策点，默认路线仍是 pywebview 延续 + 内部优化。
2. **隔离 vs 通信成本**：进程越隔离越健壮，但序列化/传输/冷启动成本线性上升。判据=「会不会长时间占 CPU 或可能崩溃」：会→worker；不会→进程内。
3. **localhost HTTP vs 自定义协议**：现有壳自证 Cookie 门已在补端口安全面；自定义协议更彻底但 pywebview 不支持，等于强制 Tauri 化。先用现有门 + 阶段 4 再评审。
4. **推 vs 拉**：轮询简单、空转占资源；SSE 需 ASGI 化并与「REST 无 WS」既有决策冲突，须正式评审而非顺手改。
5. **静态外置的运维面**：多一个二进制/进程，`install.ps1` 与干净机验收链都要改；先用 Flask 中间件扛，量化确有必要再外置。
6. **许可证**：Apache-2.0/BSD/MIT（Tauri/HA/Node-RED/JupyterLab/LocalSend）友好；MPL-2.0（Syncthing）文件级 copyleft——拷源码文件需保持开源；AGPL-3.0-only（Grafana 核心）改写分发需开源，对外提供服务需法务；fair-code（n8n）禁多租户 SaaS。本项目为独立实现、仅借鉴架构，但产品化路线图应把这条纳入评审。
7. **参考项目的「域差异」**：HA/IoT、Grafana/可观测、VS Code/IDE——抄模式（生命周期、协调者、懒激活、进程隔离），不抄领域模型。
8. **度量优先于直觉**：B5/B6 这类「感觉不慢」的项（无缓存、同步探针）往往是用户可感知延迟的大头；反之 B8 这类「感觉该慢」的项可能无关痛痒。一切以阶段 0 基线排序。

## 7. 明确不做（本轮范围外）

- 不动服务端架构（supervisor/worker/E 架构）与信息传输协议（属插件域，另有活清单）。
- 不做微前端改造（iframe 隔离保留；壳 SPA 化仅在阶段 1 评估壳本身）。
- 不做全栈语言迁移（Rust/Go 重写）。
- 不新增第三方运行时依赖（Caddy/ASGI）除非阶段 3 量化后确有必要。
