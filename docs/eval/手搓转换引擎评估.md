## 摘要

**结论先行：整体替代不划算；唯一性价比尚可的方向是 .xls，.doc 明确不建议做。**

- **.doc → .docx**：估 15k–30k 行代码、4–12 人月起步，保真度上限仅 60–80%，且野文件长尾以年计不收敛。**业界至今无可信的纯 Python 先例**（antiword 只出纯文本；doc2docx 类包全是 Word COM 或 LibreOffice 的壳）。
- **.xls → .xlsx**：可行。xlrd 已解析 BIFF8 大部分记录打底 + openpyxl 有现成写端，估 +3k–6k 行、1–2 人月，效果可达 LibreOffice 通道的 70–85%。
- **现状对比**：LibreOffice 核心组件（164MB 独立组件包，不占 122MB 主包；解压即用、免管理员、目标机隐身）零新增投入即接近满分（内容无损）。

**建议**：维持 LibreOffice 组件方案不动。若目标是"提升无组件机器上的体验"，优先做 .xls 方向——而且更省的中间态是**直接增强 xhr 现有 xlrd 兜底通道的样式渲染**（跳过"归一化成 xlsx"的写端），投入约减半。

## 一、校准基准：本项目自己已经"手搓"过一遍了

知识库插件 vendor 下的 xhr（Excel）+ dhr（Word）双引擎是**本项目实测过的手搓成本样本**，且它们处理的是**文档齐全、XML 明文**的 OOXML 格式（.xlsx/.docx）：

| 项 | 实测值 |
| --- | --- |
| 代码量 | **12,045 行**纯 Python（xhr 51 文件 + dhr 12 文件） |
| 第三方依赖 | 核心链路零依赖（纯标准库），这是刻意选型 |
| 覆盖范围 | 样式解析、条件格式、数字格式化、合并/冻结、分页、IR 中间层、安全白名单 |
| 代价佐证 | vendor 升级后需维护 5 条补丁并递增 `PREVIEW_CACHE_VERSION`；主题色/条件格式优先级等行为需用 LibreOffice 26.8 实测校准 |

**要点：OOXML 是明文 XML、微软有完整文档，尚且花了 12k 行。而替代 LibreOffice 要对付的是二进制老格式（.doc = Word 97 二进制流嵌 OLE2 容器；.xls = BIFF8 记录流），难度比 XML 格式高一个数量级。**

## 二、.doc → .docx：人年级投入，上限七成

### 2.1 工程量估算

| 端 | 内容 | 估算 |
| --- | --- | --- |
| 解析端 | OLE2/CFB 容器（可借 olefile）、FIB、piece table（快速保存碎片）、PAPX/CHPX 二进制属性表、样式表、表格 TTP、列表 LFO/LVL、页眉页脚、域、绘图对象 | 15k–30k 行 |
| 写端 | dhr 只有 docx **读端**，需新写 docx 生成器（或引入 python-docx 但其样式模型覆盖率不足） | 5k–10k 行 |
| 时间 | 熟手 4–12 个月到"干净文件基本正确"；野文件长尾收敛以**年**计 | — |

### 2.2 保真度上限

| 层面 | 可达上限 | 说明 |
| --- | --- | --- |
| 文本/段落结构 | 80–90% | 干净文件可以；快速保存产生的 piece table 碎片是著名难题 |
| 字符/段落样式 | 60–80% | 二进制属性表继承链复杂，压缩增量编码需按位解 |
| 版式（分页/页眉页脚/域） | 更低 | Word 的布局由实现定义，规范只描述"是什么"不保证"怎么排" |
| 损坏/非常规文件 | 直接翻车 | 野文件大量违反 MS-DOC 规范（~500 页），规范与 Word 实际行为并不一致 |

### 2.3 业界先例盘点（为何说"无人做成"）

- **antiword**（C，已停止维护）：只能提取纯文本，不产 docx；
- **doc2docx / 各种 PyPI 包**：本质是 `subprocess` 调 Word COM 或 soffice 的壳，不含解析器；
- **LibreOffice 自己**：写 .doc 导入过滤器用了数百万行 C++，二十余年社区维护；
- **结论**：这不是"没人想到"，是性价比公认的差。

### 2.4 对比：现状 LibreOffice 通道

- 实测 .doc→.docx **内容无损**（见《LibreOffice核心组件一键安装评估.md》§3.4）；
- 60s 超时、唯一临时 profile、并发安全三条铁律已在 `vendor/xhr/normalize/libreoffice.py` 固化。

## 三、.xls → .xlsx：唯一值得考虑的方向

### 3.1 有利条件

- **读端有现成底子**：xlrd（项目已依赖，xhr 兜底通道在用）已解析 BIFF8 绝大部分记录；info-transfer 也用 xlrd，说明依赖已在包内；
- **写端有现成库**：openpyxl 写 .xlsx 成熟稳定（注意本机记忆中的坑：openpyxl read_only 读不到 merged_cells、data_only 对未计算公式返 None——写端不受影响，但模型组装要自管公式缓存值）；
- **BIFF8 比 Word 97 二进制规整**：记录流结构清晰，无 piece table 类碎片难题。

### 3.2 工程量与效果估算

| 方案 | 新增代码 | 投入 | 效果（相对 LO 通道） |
| --- | --- | --- | --- |
| A. 完整归一化：xlrd → 组装模型 → openpyxl 写 .xlsx → 复用 xhr 高保真链路 | +3k–6k 行 | 1–2 人月 | **70–85%**（字体/颜色/边框/合并/列宽行高/数字格式可覆盖；条件格式、图表、透视表仍难） |
| B. 增强兜底：不写转换器，直接给 `vendor/xhr/normalize/fallback.py` 的 xlrd 兜底通道补样式渲染 | +1.5k–3k 行 | 0.5–1 人月 | **60–75%**（省掉写端与中转文件，投入约减半） |

### 3.3 已知局限（两种方案共有）

- 公式：xlrd 1.x 不计算公式（BIFF8 有缓存值可读），复杂函数结果取缓存即可，但无缓存的损坏文件只能显示公式串；
- 图表/透视表/条件格式：BIFF8 中结构复杂或记录不全，建议明确声明"不支持，降级为纯数据"；
- .xls 的拖影：部分非常老的 .xls（BIFF5 以下）xlrd 2.x 已不支持，需保留报错路径。

## 四、决策矩阵

| 方案 | 新增投入 | 效果上限 | 风险 | 判定 |
| --- | --- | --- | --- | --- |
| 维持 LibreOffice 组件（现状） | 0 | ≈100%（内容无损） | 组件包 164MB / 解包 558MB，需随包分发 | ✅ **维持** |
| 手搓 .doc + .xls 全套 | 4–12+ 人月 | .doc 60–80% / .xls 70–85% | 野文件长尾无底洞；业内无先例 | ❌ 不建议 |
| 只手搓 .xls（方案 A） | 1–2 人月 | 70–85% | 边界特性（图表/条件格式）覆盖不全 | ⚠️ 仅当强需求"去 LO 化"时做 |
| 只增强 xlrd 兜底（方案 B） | 0.5–1 人月 | 60–75% | 同上，但无写端中转、改动更小 | ⚠️ 性价比最优的折中 |
| xlrd 兜底（现状） | 0 | ≈40%（内容 100%、样式降级） | 无 | 现状基线 |

## 五、结论与建议

1. **不要为替代而替代**：LibreOffice 组件已经是"零投入接近满分"的形态——独立组件包不撑大主包（v1.9.0 主包 122MB）、裁剪到位（357.5MB→164MB）、免管理员、目标机隐身、无组件机器自动走兜底不影响其他功能。
2. **若动机是"减小分发体积"**：手搓引擎省下的磁盘（≤164MB）换不回等值的保真度与维护成本；主包瘦身空间也不在此处。
3. **若动机是"无 LO 机器上体验更好"**：按 方案 B → 方案 A 的顺序递进。先花 0.5–1 人月增强 xlrd 兜底样式（字体/颜色/边框/合并/列宽），无组件机器的 .xls 预览即可从"样式降级"提到 LO 的六七成；验证有真实需求后再决定是否补归一化写端。
4. **.doc 方向维持现状**：无 LO 时明确报错（现有行为），不建议投入。
