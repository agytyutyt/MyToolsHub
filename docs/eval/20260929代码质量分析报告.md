## 〇、判定框架（v2）

**优先级从高到低**：

| 级别 | 轴 | 判定 |
|---|---|---|
| **P0** | 插件独立性与解耦（D-9/B-7/C-11） | 任何新的插件间耦合都是缺陷；跨插件重复代码**不是**缺陷，是解耦的既定成本 |
| **P1** | 数据安全与正确性 | 竞态丢数据、真 bug、编码口径、互操作契约漂移 |
| **P2** | 宿主与构建层内部质量 | app.py / jz_* / tools 脚本 / 测试的重复与复杂度——**不属插件，去重不受 P0 约束** |
| **P3** | 插件内部质量 | 单插件内部的重复、god file、吞异常——同插件内去重同样不受 P0 约束 |

**本仓库已确立的「合法解耦手段」**（分析以此为基准，不另发明）：

1. **主体模块门面（封闭白名单）**：`FRAMEWORK_MODULES = {'jz_api', 'jz_deps', 'jztools_data', 'jz_llm'}`（tools/build-plugin-package.ps1:315）。插件 import 主体模块是正规出口（B-7），import 其他插件模块被 C-11 构建期拦截。白名单扩张属规范级决策，不是去重的免费手段。
2. **同源副本、各自独立演进**：解耦修补的既定产物。先例：`trajectory-sketch/backend/filter_local.py` 自带一份与 file-filter `core.py` 同源的过滤实现（filter_bridge.py:11-12 文档串明示「同源副本、各自独立演进」）。
3. **依赖倒置提升主体**：插件间调用改为插件→主体门面。先例：notice-board 原直调 admin 的 `/api/admin/org-tree`，修补后经主体 `/api/org/tree`（notice-board/frontend/app.js:69 注释、jz_api.py:17-18）。
4. **零跨插件调用验收口径**：后端 import / HTTP / 前端请求三处均为零（设计文档 AC-22），C-11 负责拦截回归。

**推论**：独立 ≠ 忽视副本。跨插件副本需要的是**台账 + 契约成文 + 漂移监测**，而不是合并；插件间互操作（如二维码编解码）唯一合法的共享物是**协议契约**，不是代码。

## 一、总体结论（修订）

- **独立性现状总体达标**：仓库内零跨插件 import / HTTP / 前端调用，C-11 构建期拦截在位，requires 三类依赖明确不含插件依赖（设计文档 :325）。两处遗留协作已按「副本」与「提升主体」两种模式修补完毕，且留下可复用的先例。
- **P0 层面仍有四个真实问题**：admin 插件每次启动改写其他插件的数据文件（C1）；解耦修补后的死垫片误导维护者（C2）；二维码互操作协议依赖三处人肉同步的帧头常量、契约未成文（C3）；同源副本无台账、漂移无监测（C4）。
- **P1 层面两处无锁读-改-写竞态可静默丢数据**（admin.json、tools.json），一个一行可修的真 bug（`plugin_names(None)`），一处 BOM 可致整站空注册表的编码口径分叉。
- **P2/P3 沿用 v1 结论**：宿主与构建层重复密度高（构建脚本双实现、依赖知识四处手工同步）；若干 god file（admin routes.py 2365 行、app.py 1385 行、file-filter register() 585 行）；约 50 处吞异常。这些不受 P0 约束，仍是待还的债。

## 二、P0：插件独立性与解耦

### 2.1 达标盘点（不需处理，作为后续判定基准）

- **零跨插件调用**：设计文档 §5.4 记录两处遗留协作已修补——① notice-board 改调主体 `/api/org/tree`（提升主体模式）；② trajectory-sketch 自带 `filter_local.py` 同源过滤实现（副本模式，与 file-filter `core.py` 各自独立演进）。
- **构建期拦截在位**：C-11 扫描 `backend/**/*.py`，import `jztools_<其他 id>` 拒绝出包（build-plugin-package.ps1:367-369、:486）；`FRAMEWORK_MODULES` 白名单放行四个主体模块（:315）。
- **依赖声明不含插件**：requires 三类依赖（python_packages / vendored / external），「不含『依赖的插件』——插件间保持独立」（设计文档 :325）。
- **加密与密钥收口**：LLM Key 一律交 `jz_llm`（SEC-2 例外条款），插件不得自持；admin 的历史明文 Key 清理（见 C1）正是该原则的执行动作。

### 2.2 发现

#### C1.【提级】admin 插件每次启动改写其他插件的数据文件

- 证据：`plugins/admin/backend/routes.py:308` `migrate_plugin_legacy_llm`，启动时调用（:959）；遍历数据根下全部插件目录，把各插件 `config.json` 的明文 `llm` 段收编进 `jz_llm` 后删除（:368-377 原子写）。
- 性质辨析：动机正当（清除明文 Key 泄漏面，属 SEC-2 落地）、实现幂等、admin 随主体分发。但 `<数据根>/plugins/<id>/config.json` 是各插件的法定存储（F-4/SEC-2），由**一个插件**常驻改写**其他插件**的数据文件，是一次不声明、不退场的插件间数据耦合——它是数据面的 `filter_bridge` 旧模式，只是方向从「读对方」变成「写对方」。
- 建议（按解耦优先级排序）：
  1. **归属上移**：迁到主体启动流程（app.py `init_data_root` 一侧），作为主体对插件数据根的一次性清理——主体管理插件生命周期是 sanctioned 方向（admin 管理插件清单同理，见 B-6 职责划分）。
  2. 至少**加退场标记**：收编完成后写 `<数据根>/config/llm_migrated.flag`，有标记即跳过扫描，让这次协作像一次性迁移而不是常驻权限。
  3. 迁移完成、目标版本全覆盖后**整段删除**（迁移代码不该永驻）。

#### C2.【提级】filter_bridge.py 解耦残留误导维护者

- 证据：`plugins/trajectory-sketch/backend/filter_bridge.py:44-52` `filter_enabled`/`filter_route_available` 恒返回 True（文档串自述「不再依赖其他插件」）；`:85-97` `apply_filter` 的 `app/cookie/host_url` 形参声明废弃但全链路仍传（routes.py:157-159、:377-380）；死配置键 `use_filter_plugin_rules` 仍在默认配置（config_store.py:38）、仍被规整（:130）与写入（routes.py:274-275），而 routes.py:149 注释已说明该分支不存在；另有孤儿 `_probe_fix.cpython-314.pyc`。
- 性质：解耦修补（第二处）的收尾没做完。恒真函数与死形参让后来者以为仍存在跨插件协作点，与 D-9 的「零耦合」口径相悖；死配置键则是旧协作在配置面的残迹。
- 建议：删除恒真函数与废弃形参（同步修调用方）、删除死键的三处读写、清孤儿 pyc。这是**完成解耦**，不是单纯卫生清理。

#### C3.【新增】二维码互操作契约未成文，帧头常量三处人肉同步

- 背景：trajectory-convert、info-transfer、map-marker（开发脚本）是编码端，qr-video-decode、info-transfer 是解码端——这些插件通过二维码视频**交换数据**，属于合法的互操作。独立原则下唯一该共享的是**协议契约**，但目前契约没有独立落点。
- 证据：帧头常量 `SIZE_INDEX/SIZE_PREFIX/SIZE_DATASIZE/BYTE_ORDER` 三份拷贝（trajectory-convert:48-51 ↔ info-transfer:175-178 ↔ qr-video-decode:38-40），各文件注释靠「与 qrtransfer.py 保持一致」人肉对齐；编码实现四份（trajectory-convert:481 起 ↔ info-transfer:1433 起 ↔ map-marker/frontend/generate_qr_stream.py ↔ 解码侧 qr-video-decode:145-189）。
- 已发生的分叉及其定性：info-transfer 的 `_chunk_data` 多了 `PAYLOAD_SAFETY=0.9` 安全系数（:1463-1481）。**解码端从帧头读取 seg_n/k/m，编码端更保守的分块不影响解码**——这是编码端本地调参，不是互操作 bug；但它未被声明为「有意的分叉」，下一个改动者无从分辨。
- 真正的互操作风险：帧头布局或 FEC 参数若只改一端，静默坏，且四个插件独立出包、独立升级，坏的时候很难定位到是哪端漂了。
- 建议（不引入任何代码共享）：
  1. 写一份**协议契约文档**（docs/design/：帧头字节布局、FEC 参数、版本字段、分块规则；声明 PAYLOAD_SAFETY 属编码端本地调参空间）。
  2. 在 `testdata/protocol/` 放**跨实现测试向量**（同一输入的标准编码帧 + 期望解码结果），由根目录测试文件分别驱动四个插件的实现做一致性断言——测试在宿主侧，不构成插件间依赖，C-11 不涉及。
  3. 各插件保留自己的实现，不合并。

#### C4.【新增】同源副本无台账、漂移无监测

跨插件副本是解耦的既定成本，但目前**哪些副本存在、哪些是有意分叉**没有登记处，漂移只能靠偶然发现：

| 副本对 | 状态 | 证据 |
|---|---|---|
| filter_local.py ↔ file-filter core.py（过滤实现） | ✅ 已声明「各自独立演进」 | filter_bridge.py:11-12 |
| bg_image.py ×2（442 行，md5 相同，xlsx/xls 背景图解析） | ❌ 未声明 | file-filter/backend/bg_image.py ≡ trajectory-sketch/backend/bg_image.py |
| QR-transfer 编解码 ×4 | ❌ 未声明，且已有未声明分叉（PAYLOAD_SAFETY） | 见 C3 |
| jsqr.min.js ×2（256,890 字节 vendor） | ❌ 未登记 | map-marker/frontend ≡ qr-video-decode/frontend |
| llm_client 适配层样板 ×4 | ✅ 规范既定模式（§9.4 防幻觉约束属插件） | file-filter:19-31、case-report:14-21 等 |
| `_viewer()` 等任务样板 ×6-10 | ❌ 未登记（见 §6） | 各插件 routes.py |

- 建议：
  1. 在《插件设计规范》或 docs/design 增设**同源副本台账**一节：登记副本对、同源日期、演进策略（同步修 / 各自演进）、漂移时以谁为准。
  2. 构建期加**漂移提示**（warning，不阻断）：对已登记副本对比 md5，不一致时提示「副本已分叉，请确认是否为有意演进并更新台账」——与 C-11 同一脚本宿主（build-plugin-package.ps1），机制一致、方向相反（C-11 拦耦合，这项管副本）。
  3. bg_image.py 修 bug 时两份同步，直到任一方声明分叉。

## 三、P1：数据安全与正确性

#### D1.【高】admin.json 无锁读-改-写竞态

- 证据：`plugins/admin/backend/routes.py:134-146`（load/save 无锁）；`batch_io.py:273/284` 同样。对比：knowledge-base 有 `_LOCK`（routes.py:122）、trajectory-sketch 有 `LOCK`（report_store.py:35）。
- 后果：waitress 8 线程下并发写（改角色 × 改密码、批量导入 × 单人编辑）后写者整份覆盖，**账号/权限更新静默丢失**。
- 建议：模块级 `threading.RLock` 包住 load→mutate→save 全程。

#### D2.【高】tools.json 并发写竞态 + 固定 tmp 文件名

- 证据：`app.py:525-530` tmp 固定为 `CONFIG_PATH + ".tmp"`；`api_tools_reorder`（:1073-1116）与 `api_tools_visibility_save`（:1148-1184）无锁读改写。
- 后果：并发时 `os.replace` 可能 rename 走对方写了一半的内容；`load_registry` 失败按空注册表继续（:518-522），**整站工具清单清空**。
- 建议：加模块级锁；tmp 改 `tempfile.mkstemp(dir=os.path.dirname(CONFIG_PATH))`。

#### D3.【中】`plugin_names(None)` 恒返回空 dict（真 bug，一行修）

- 证据：`plugins/admin/backend/plugin_admin.py:1365` 传 `None`，函数（:883-892）对非 dict 恒返回 `{}`。
- 后果：已安装插件扫描永远拿不到 tools.json 中文展示名。

#### D4.【中】JSON 读取编码口径不一致（BOM → 整站空注册表）

- utf-8-sig：`jz_deps.py:125,156,211,236,292,334`、`app.py:122`、`jz_llm.py:811`；普通 utf-8：`app.py:515`（**读 tools.json**）、`:548`、`jztools_data.py:112,307`、`jz_llm.py:301`。
- 后果：记事本编辑 tools.json 带 BOM → `load_registry` 失败 → 按空注册表继续，整站卡片消失；同一文件走 jz_deps 读法却正常，极难排查。
- 建议：外部可手工编辑的 JSON 统一 utf-8-sig。

#### D5.【中】任务归属校验两端口径相反（安全语义分叉）

- `trajectory-convert:192-205`、`file-filter:225-236`：无归属旧任务**仅超管可见**（收紧版）；`character-graph:157-169`、`qr-video-decode:106-118`、`info-transfer:367-376`：**所有人可见**（放行版）。六份拷贝复制时各自改动所致。
- v2 处理方式（**不沉淀公共模块**）：拍板正确口径（建议从严——旧任务结果含用户数据，放行默认不安全），三个放行版插件**各自本地**改为收紧口径。副本各自改，恰恰是解耦原则下的正常修法。

#### D6.【中】轨迹速写 v2/v3 报告口径漂移（单插件内）

- v2 保证「无有效数据的号码也出『无。』条目」（`v2/report.py:222-231`）；v3 只遍历有窗口数据的用户（`v3/__init__.py:145`）。核对产品预期后在插件内统一。

#### D7.【中】工具 ID 口径可能分叉

- 聚合接口用 manifest.id（`app.py:687`），visibility 接口用 registry.id（`:1142`），目前靠「目录名=注册 id=manifest.id」惯例兜底无校验。建议 `register_plugin_backends` 加载时校验一致，不一致记入 `_manifest_errors`。

#### D8.【中】前端 401 处理不一致（行为 bug，各插件本地修）

- case-report（app.js:43-61，:50 跳顶层登录）与 shared-docs（:47-70）处理会话过期；notice-board（:35-40）、file-filter（:1683-1697）、knowledge-base、trajectory-sketch 的 fetch 封装**静默失败**。
- v2 处理方式：这是行为缺陷不是重复问题，**各插件本地**补 401 跳转即可，不需要公共 JS 模块（见 §6.3 对 jz-ui.js 的降级）。

## 六、跨插件重复逻辑的重新定级（v2 核心改写）

### 6.1 定性

跨插件重复**不再计为待消除缺陷**。它是 D-9 解耦的既定成本，且仓库已有成功先例（filter_local.py 同源副本运行良好）。副本的正确管理方式是 §2.2 C4 的「台账 + 契约 + 漂移提示」，不是合并。v1 统计的样板量（任务三件套 6 份约 500 行、`_viewer` 10 份、toast/fetch/copy 前端样板各 4-6 份）作为**成本记录**保留在台账里，不作为整改项。

### 6.2 仍必须处理的三类（因为它们是缺陷，不是重复）

1. **行为不一致即 bug**：401 处理（D8）——各插件本地补齐；`_task_owned_by` 口径相反（D5）——拍板后各插件本地统一。
2. **互操作契约漂移**：QR-transfer 帧头常量（C3）——契约成文 + 测试向量，代码不合并。
3. **未声明副本**：bg_image.py 等进台账（C4）——修 bug 时同步，分叉须声明。

### 6.3 v1 建议的撤回与降级清单

| v1 建议 | v2 处置 | 理由 |
