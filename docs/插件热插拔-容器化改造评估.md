## 摘要（先看结论）

**1. 用户的目标是合理的，但"Docker 式容器"这个提法在当前目标机上做不到。**
Docker Desktop 要求 Windows 10 **Enterprise/Pro/Education 22H2（build ≥19045）** + WSL2 + BIOS 虚拟化 + 8GB RAM + `LanmanServer` 自动启动，且 `wsl --install` 需提权；大型企业（>250 人或 >1000 万美元营收）商用需付费订阅。而本项目的部署画像是：内网、常无外网、部分机器为家庭版/精简 Ghost 系统、**追求免管理员安装**（LibreOffice 组件"对目标机隐身"就是这条原则的产物）。容器路线与这条原则正面冲突。

**2. 但"类容器式"的内核——"每个插件一个独立运行时，宿主永不为其重启"——是完全可行的，答案是把容器降级为进程。**
业界成熟做法是 **`host + subprocess sidecar`**：HashiCorp `go-plugin`（Terraform/Vault/Nomad）、Grafana 后端插件（直接构建在 go-plugin 上）、Telegraf `execd` + shim、Steampipe FDW（每插件一个 gRPC 子进程）、Dapr pluggable components（进程或容器二选一，用 Unix socket 互通）、以及 Python 生态自带的 LSP/`pygls`（宿主 + 语言服务器子进程，JSON-RPC over stdio）。**这些模型的容器化与否只是部署变体，协议与生命周期契约是同一套。**

**3. 同进程热插拔在 Python 中没有干净解，这不是懒政，是语言约束。**
Flask 官方文档明写：*"you cannot unregister a blueprint once an application was created without having to destroy the whole application object"*。Python 侧不支持模块洁净卸载（C 扩展全局状态、线程/线程池、`atexit`、旧类对象被排队请求持有）。行业基线同样如此：Home Assistant 的 custom component 明确要求 "**After adding a custom component, Home Assistant must be restarted**"。APISIX/Kong 能热加载，是因为 Lua 可以 `package.loaded[...] = nil` 干净丢弃模块且无 C 扩展包袱——**Python 没有等价机制**。

**4. 真正需要修的其实比你以为的窄。**
现行架构里，**纯前端插件（5 个）已经是即插即用的**（`tools.json` 每请求读、`/plugin/<id>/<path>` 实时读盘）。必须重启的只有 11 个带后端的插件的 **Python 代码变更**。评估不是"推翻重来"，而是给这 11 个插件换一条装载通道。

**5. 工作量：约 24~33 人日（4~6 人周，单人全责），且可长期"新旧并存"地渐进推进。**
最大的隐藏成本不在网关，而在**依赖怎么跟着 sidecar 走**（打包态 Windows 没有独立 venv）和**异步任务表的归属**（工序不能随进程被杀而丢）。这两件事必须在写代码前先定方案，否则会返工。

> **2026-09-14 追加：D1（依赖/打包）已实测验证通过，不再是风险。**
> 见 [附录 A · W0 探测报告](#附录a-w0-探测报告pyinstaller-双入口实测)：同一个 `COLLECT` 里放两个

> 且为一次性成本）**；sidecar 冷启动 431 ms；`CREATE_NO_WINDOW` 下握手行可读；Token 校验生效。

## 二、为什么同进程热插拔在 Python 里做不干净

### 2.1 Flask / Werkzeug 侧

- `app.url_map` 在首次请求后被 `_check_setup_finished()` 冻结；
- Flask 官方（pallets/flask `docs/blueprints.rst`）明确：Blueprint **无法反注册**，除非销毁整个 app 对象；
- 因此"即拔即停"在进程内没有官方路径，只能靠 hack `app.url_map._rules`（私有 API，且已注册 view_func 与闭包、蓝图 setup state 仍泄漏）。

### 2.2 Python 侧

即使强行 `del sys.modules[...]`：

1. 第三方 C 扩展持有进程级全局状态（`openpyxl`/`pillow`/`cryptography`(abi3)/`opencv-python`(abi3)/`zfec`(cp314) 全是 C 扩展），子进程/子解释器都救不了同一个解释器；
2. 已启动的 `ThreadPoolExecutor`、后台线程、`atexit` 钩子无法回收；
3. 旧版本的类对象可能被排队中的请求、正在轮询的任务持有（本项目 6 个插件使用 `ThreadPoolExecutor(2)` + TTL 30min 任务表，正是这条命中的场景）；
4. `dataclass`/`NamedTuple`/异常类跨版本重载会产生"同名不同类"的身份陷阱。

**行业佐证**：Home Assistant 的 custom integration 文档与社区实践都是"放文件 → 重启 HA"；只有部分集成支持 UI "Reload"，且官方注明"改了依赖或 manifest.json 仍需完整重启"。这是 Python 大项目的通行做法，不是本项目的缺陷。

### 2.3 唯一例外：Lua / Erlang / Java 能做到，Python 不行

| 系统 | 热加载机制 | 为何可行 |
| --- | --- | --- |
| Apache APISIX / Kong | Admin API `PUT /apisix/admin/plugins/reload` 热加载，**明确不需要重启** | Lua 模块可 `package.loaded[name] = nil` 干净丢弃；无成熟 C 扩展包袱 |
| Erlang/OTP | 代码热替换（保留两个版本） | VM 原生语义 |
| OSGi (Java) | BundleActivator + 独立 ClassLoader | 类加载器的遮蔽/卸载语义 |

这一对照说明：**能不能热插拔，取决于运行时是否提供"模块卸载"语义**，而不是"决心够不够"。

### 2.4 唯一的理论出路：PEP 554 / PEP 684 Sub-interpreter（**不建议**）

- Python 3.12 起支持 Per-Interpreter GIL（PEP 684），`_xxsubinterpreters` / 3.13 的 `_interpreters` 提供 Python 层接口；社区封装见 `jsbueno/extrainterpreters`（LGPL-3.0，状态 beta）。
- 但：① CPython issue #98627 明确指出，未实现 PEP 489 多阶段初始化的 C 扩展在子解释器中应直接 `ImportError`；② 本项目所有插件依赖都含 C 扩展；③ PEP 554 至今仍是 **Draft**，`interpreters` 模块尚未进 stdlib 稳定态；④ 现有 11 个插件的 `register(app)` + `from jztools_admin.routes import get_session_user` 写法与解释器隔离模型完全不兼容，等于重写全部插件。

> 一句话：**这条路的投入等于换一门语言，收益等于人家早就用子进程做到的同一件事。**

## 三、四条候选路线对照

| 路线 | 核心做法 | 可行性（本项目） | 主要参考实现 | 结论 |
| --- | --- | --- | --- | --- |
| **R1 · 容器编排**（v1.0 二/三阶段） | 主框架容器化 + 每插件一个容器 | ❌ 不可行 | Home Assistant Supervisor Add-on、Dapr pluggable components (K8s 模式) | 目标机装不上 Docker；仅可作为 Linux 生产可选形态保留 |
| **R2 · 进程 sidecar** | 每插件一个本地子进程，宿主反向代理 | ✅ **推荐** | `hashicorp/go-plugin`、Grafana backend plugin、Telegraf `execd`+shim、Steampipe FDW、Dapr pluggable components (standalone)、LSP/`pygls` | **唯一能在 Windows 10 桌面上兑现"挂载即用"的路线** |
| **R3 · 同进程热注册/热卸载** | 动态 import/lazy dispatch/`del sys.modules` | ⚠️ 半可行 | `dumpmemory/flask-plugin`（支持 start/stop/reload，但 Flask 3 不支持）、APISIX（反例对照，Lua） | 能"热更新"，**做不到干净卸载**；内存单调增长、故障隐蔽 |
| **R4 · Sub-interpreter 隔离** | 每插件一个子解释器 | ❌ 现阶段不可行 | `jsbueno/extrainterpreters`、CPython PEP 554/684 | C 扩展不兼容、API 未定，等于重写全部插件 |

### 3.1 关键参考：Go 生态已经把这道题做完了，且**它们的容器化只是部署变体**

**HashiCorp `go-plugin`**（Terraform / Vault / Nomad / Boundary / Waypoint 生产验证）

- 握手协议：子进程把一行 `核心协议版本|应用协议版本|网络类型|网络地址|协议` 打到 stdout，宿主据此建连；
- `MagicCookieKey/Value`：**不是安全机制，但能防止插件被当作普通程序双击执行，给出友好提示** —— 这个 UX 细节本项目应照抄；
- `VersionedPlugins map[int]PluginSet` 做协议版本协商；
- 崩溃隔离：*"Plugins can't crash your host process: a panic in a plugin doesn't panic the host"*；
- stdout/stderr 自动同步回宿主日志、TTY 保留、支持 `ReattachConfig`（宿主升级而插件不中断）、可选 mTLS。

**Grafana 后端插件**（直接构建在 go-plugin 之上，官文档 `plugin-lifecycle.md`）

生命周期七步：安装/卸载 → 发现（扫 `plugin.json`）→ 校验（签名）→ 注册到**内存注册表** → 启动后端二进制子进程 → 版本协商 → 前端懒加载。要点三条：

- **注册表是内存的、每请求/每安装刷新** —— 这正是本项目缺的"扫描"环节；
- **宿主负责守活**：*"Grafana will make sure to restart the backend plugin in case it crashes"*；宿主关闭时统一终止；
- **关键区分**：用 CLI 装插件**仍需重启 Grafana**，只有在 UI 里从 catalog 安装才能免重启 —— 说明"入口统一"比"机制先进"更决定体验。本项目已有管理后台插件页，这是**现成的正确入口**。

**Telegraf `execd` + shim**（最贴近"任意语言 + 任意依赖"）

- 外部程序以长驻 daemon 方式运行，通过 stdin/stdout 交换指标；`restart_delay = "10s"` 控制异常退出后的重启；
- 提供 **Go shim**，让原本写在同一进程里的插件，几乎不改代码就能变成独立二进制 —— **这就是本项目的 `jz_plugin_sdk` 需要扮演的角色**；
- 明确列出动机：任意语言、非 Go 的库、闭源许可软件、大依赖不膨胀主程序、不必等官方发布。**每一条都与本项目高度契合。**

**Steampipe FDW / Dapr pluggable components**

- Steampipe：Postgres FDW 不直连外部系统，**只通过 gRPC 调插件**，"Postgres 特有逻辑封装在 FDW，API 特有代码只在插件里" —— 与本项目"框架只做代理，业务逻辑在插件"同构；
- Dapr：组件工商编著级「放在归档运行时外、自托管 exe 或容器、任意支持 gRPC 的语言、写好 gRPC 服务丢个二进制进文件系统就能插入」，Unix domain socket 寻址。它的 proposal 同时坦陈**代价**：延迟上升、需要额外的打包分发体系、组件与运行时的兼容性各自演进难以保证。**这三条同样会在本项目出现，必须提前认账。**

## 四、推荐方案：进程式「挂载运行时」（Sidecar Runtime）

### 4.1 形态

```
浏览器 ── /api/<pid>/… ──▶ Flask 主进程（常驻，PID 不变）
                              │
                              ├─ mode=in-process：老样子，启动时 import（保留）
                              ├─ mode=sidecar   ：按需 Popen 子进程，127.0.0.1:<随机端口>，健康检查后反代
                              └─ mode=remote    ：直连外部服务（未来 Linux 容器 / 内网服务）

Sidecar 契约（建议命名 jz-runtime-2，沿用并扩展规范 8.7 的 jz-runtime-1）
  ├─ 握手：随机端口 + 一次性 Token（环境变量注入），非本地-or-无 Token 一律拒绝
  ├─ 健康检查：GET /healthz
  ├─ 身份：宿主剥离 Cookie，注入 X-JZ-User / X-JZ-Unit-Id / X-JZ-Super-Admin
  ├─ 数据：JZ_PLUGIN_DATA / JZ_PLUGIN_CONFIG_FILE 指到数据根目录对应位置（与现在一致）
  └─ 生命周期：懒启动 → 空闲 N 分钟回收 → 崩溃 atexit/monitor 自动拉起 + 5 分钟内 3 次则熔断
```

### 4.2 三个必须先定、否则必返工的决策

| # | 决策点 | 选项 | 建议 |
| --- | --- | --- | --- |
| **D1** | sidecar 的 Python 依赖从哪来？ | ① 独立 venv（体积 + 每台机器要 pip，内网不可行）<br>② **复用 PyInstaller 冻结环境**：主 exe 之外再产一个 `jz-sidecar.exe`，与主程序共享 `_internal`<br>③ sidecar 只允许用"已冻结依赖白名单" | ✅ **已定案：② + ③，且 ② 已实测通过**（见附录 A）。结论：不必额外装 Python，包体只一次性 +3 MB，sidecar 冷启动 431 ms |
| **D2** | 长任务怎么办？ | 插件内的任务表随进程回收而丢（现在是 `ThreadPoolExecutor` + 30min TTL） | 任务表外置到磁盘（`jztools_data` 下 `<root>/plugins/<id>/tasks.sqlite` 或 jsonl），否则"Idle 回收"和"停止插件"都会静默丢用户正在跑的任务。**这是硬前置条件** |
| **D3** | 信任边界怎么划？ | 回环端口意味着本机任意进程都能访问 sidecar 并伪造 `X-JZ-*` 头 | **必须用一次性握手 Token**（等价 go-plugin 的 MagicCookie 思想，但本项目要把它升级为真实凭据：随机值经环境变量注入，每次请求由宿主校验）。这一点在 v1.0 设计稿里是缺失的，属于本评估新增的必做项 |

### 5.2 兑现不了或要付代价的（**必须提前认账**）

| 项 | 代价 | 缓解 |

## 七、需要你拍板的三个问题

1. **要不要现在就立项？** 如果近半年内没有"频繁新增带后端插件 / 插件之间依赖冲突"的实际痛点，建议先只做 W0（1~2 人日）把最大不确定性打掉，其余排队。
2. **依赖策略选哪条？**（D1）如果接受"sidecar 只能用已冻结依赖白名单"，落地成本最低但要牺牲一点灵活性；如果要 sidecar 能自由 pip，就必须接受目标机上多一套 Python 与离线 whl 分发。
3. **首批试点选谁？** 本报告建议 `qr-video-decode`（最小 + 重依赖，能验证收益上限）+ `knowledge-base`（体量大 + vendor 纯标准库，能验证迁移成本下限）。若你有其它优先级（比如某个正在出问题/正要重写的插件），可以在这儿替换。

## 附录A：W0 探测报告（PyInstaller 双入口实测）

> 实施日期：2026-09-14 · 目的：验证 §4.2 的 **D1**——"sidecar 以独立 EXE 形式存在，且与主程序共享
> 同一份 `_internal`"是否成立。这是整条 sidecar 路线能否低成本落地的唯一技术前提。
> 实验代码在 `C:\Users\yfjz\AppData\Local\Temp\jz-w0-probe\`（临时目录，未入库）；
> **决定立项后可直接把 `probe.spec` 的双入口写法搬进 `JZToolsHub.spec`**。

### A.1 实验设计

| 角色 | 文件 | 职责 |
| --- | --- | --- |
| 共享模块 | `probe_common.py` | 模拟未来的 `jz_plugin_sdk`：确定性 crypto 指纹、运行时布局探测 |
| 宿主 | `probe_host.py` | `CREATE_NO_WINDOW` 拉起 sidecar → 读握手行 → 带 Token 请求 → 逐项断言 → 优雅停止 |
| sidecar | `probe_sidecar.py` | 选随机端口起 HTTP 服务 → stdout 打 `JZRT|1|<port>` → 校验 `X-JZ-Token` |
| 打包配置 | `probe.spec` | **两个 `Analysis` → 两个 `EXE` → 同一个 `COLLECT`**（刻意对齐 `JZToolsHub.spec` 写法） |
| 对照组 | `probe_single.spec` | 只打宿主一个入口，用于测量"多一个入口"的增量 |

### A.4 可直接复用的 spec 写法

```python
# 关键：两个 Analysis 喂同一批 collect_all 结果，两个 EXE 塞进同一个 COLLECT
from PyInstaller.utils.hooks import collect_all
_d, _b, _h = collect_all("cryptography")   # 真实项目换成 JZToolsHub.spec 的 PACKAGES 全集

a_host = Analysis(["app.py"],     binaries=_b, datas=_d, hiddenimports=_h, noarchive=False)
a_side = Analysis(["sidecar.py"], binaries=_b, datas=_d, hiddenimports=_h, noarchive=False)

exe_host = EXE(PYZ(a_host.pure), a_host.scripts, [], exclude_binaries=True,
               name="JZToolsHub", console=False)          # 打包运行无控制台
exe_side = EXE(PYZ(a_side.pure), a_side.scripts, [], exclude_binaries=True,
               name="jz-sidecar", console=False)

coll = COLLECT(exe_host, exe_side,
               a_host.binaries, a_side.binaries,
               a_host.datas,    a_side.datas,
               strip=False, upx=False, name="JZToolsHub")
```

**已确认不需要改 `build-deploy.ps1`**：第 132 行 `Copy-Item -Recurse -Force (Join-Path $Dist "JZToolsHub\*") $AppDir`
是整目录搬运，新增的 `jz-sidecar.exe` 会被自动带上（这把 W6 的一部分工作量直接归零）。

### A.5 三条从实测中提炼的推论

1. **包体成本是一次性的，不是按插件线性增长的。** 因为做一个"通用 sidecar 入口"（由 `runtime.json`
   决定加载哪个插件）而非每插件一个 exe，11 个插件也只要这一个入口。这条修正了 §5.2 早先含糊的表述。
2. **握手走 stdout + 随机端口是可行的，且 `CREATE_NO_WINDOW` 不影响读管道。** 组合
   `stdout=subprocess.PIPE` + `creationflags=0x08000000` 实测有效——这是 Windows 上最容易翻车的
   一处（很多人误以为隐藏窗口就拿不到输出）。
3. **回环端口必须配一次性 Token。** D1（无 Token → 401）证明校验链有效，但也提醒：sidecar 监听
   `127.0.0.1` 是本机任意进程可达的，Token 是唯一的信任边界（= 评估 §4.2 的 D3，必须落地）。

### A.6 局限（诚实标注）

- 本实验 sidecar 只依赖 stdlib + cryptography。**真实 sidecar 需 import Flask 与插件依赖**，
  PYZ 会更大 → 入口增量粗估 5~8 MB（非 3 MB），冷启动也会从 431 ms 涨到 0.6~2 s。实施时复测。
- 未验证：Windows Job Object 关联（防 `kill -9` 后孤儿进程）、优雅停止协议（本实验用
  `terminate` 强杀，真实实现应让 sidecar 支持"stdin 关闭即退出"）、日志轮转。这三项属于 W2 范围。
- 未验证：sidecar 崩溃自动拉起与熔断——需要 W2 的生命周期管理器。
